# 界面精修设计指南

用于在已认可的风格、布局和功能范围内，把页面做得完整、协调、自然。面向设计、实现与体验审查，提供可重复使用的判断方法；具体页面的问题与整改记录留在相应任务中。

整体风格与成熟页面保持稳定；尚未建立清楚使用方式的局部工作区，应先重新组织体验，再精修控件。保留基线不意味着保留已经妨碍用户的结构。

遵循[项目哲学](../philosophy.md)：由系统承担复杂度，让用户轻松识别内容、理解状态、完成操作。具体功能和交互边界仍以产品与模块设计为准。本指南不另立配色、字号、间距或组件库，实施时沿用现有设计语言和令牌。

## 1. 精修的判断标准

精致感来自每个元素都有恰当的分量、位置与行为。用户无需研究界面，就能感到这里有秩序、操作有把握。

| 目标 | 设计时的判断 | 验收时看什么 |
| --- | --- | --- |
| 方向清楚 | 第一眼应看到什么，随后看什么，下一步在哪里 | 眯眼看整体仍能辨认主次；正常阅读时行动与对象紧密相连 |
| 关系明确 | 哪些属于一组，哪些是不同层级 | 靠位置、距离和排版即可分组，边框与底色只作必要辅助 |
| 形态稳定 | 同一种角色是否有一致的尺寸、对齐和状态 | 换页、换内容、悬停、加载前后没有无理由的漂移 |
| 密度合适 | 当前内容值得占多大空间 | 空时有明确落点，少量内容自然，内容增多后仍易扫读 |
| 操作从容 | 用户是否看得见入口、点得准、知道结果 | 键盘、鼠标和触摸都能操作，过程与结果在相关位置可见 |
| 表达克制 | 这段文字或装饰是否帮助理解、选择或确认 | 去掉无价值信息后仍然完整；必要说明容易读到 |

美感判断要回到这些关系。只有“高级一点”“加些留白”“按钮统一一下”的要求，还不足以指导实现。

## 2. 先定注意力顺序，再改局部样式

开始前写下四件事，每项一句即可：

1. **当前任务**：用户来到这里最想完成什么。
2. **阅读顺序**：定位当前页面 → 看到相关内容或状态 → 找到下一步。
3. **操作归属**：页面级动作、区域级动作、对象级动作分别作用于什么。
4. **保留基线**：已获认可的风格、布局、导航、成熟页面，以及不能破坏的交互。

据此检查视觉重心：

- 页面标题负责定位；内容负责吸引阅读；主操作负责引导行动。三者的强度随任务调整，不能每件都最醒目。
- 全页动作跟随页头，局部动作靠近所属区域，对象动作靠近对象。先明确归属，再决定左右位置。
- 同一视野中的同一个动作以一个主要入口为主。重复入口只有在减少明显的滚动或查找成本时才保留，并拉开主次。
- 次要导航保持可发现，但不与主要创作、确认或恢复动作竞争。
- 删除不能帮助判断的标题、计数和重复说明。保留承担定位或状态意义的信息，不能为整齐而隐藏必要事实。

**技巧：先画一张只有文字和区域边界的草图。** 如果注意力顺序仍然混乱，先调整归属和层级；配色、圆角和动效解决不了这个问题。精修通常只需调整局部关系，无需改变成熟页面的整体构造。

## 3. 用少量对齐基准组织空间

### 3.1 区分四种边界

对齐前先分清：容器边界、控件外框、文字行框、字形或图标的可见轮廓。它们经常不重合。

- **同类按钮并排**：优先统一外框高度和内容中心。
- **标题与文本动作并排**：选择文字基线或整体视觉中心，按字阶关系判断；不要同时强求二者。
- **上下区域的动作列**：先建立共同的右侧或左侧轨道，再核对文字与背景的视觉重量。
- **文本链接与实心按钮混排**：即使外框对齐，可见文字也可能错位。明确该组是按外框还是按文字组织，必要时用共同的操作槽位承接不同形态。

### 3.2 明确父容器的责任

每个区域都应能说明：内容起点在哪里、宽度受什么限制、动作贴近谁、空间不足时如何换行。

正文宽度按阅读需要限制，操作位置按作用范围决定。宽屏多出来的空间不必全部分配给元素之间的距离；无约束地把两端推开，会让相关内容失去联系。

父容器负责区域布局，组件负责内部排版。发现多个按钮都向同一侧偏时，先检查共同容器与组件变体，不逐个增加偏移。

### 3.3 几何对齐之后检查光学对齐

几何中心是起点，可见图形的重心才决定看起来是否居中。字体的上下留白、图标画布的空边、箭头方向都会影响重心。

先排除错误的尺寸、行高、内边距和图标画布，再作必要的光学微调。微调应属于同一图标或控件的稳定规则，并在不同字号、缩放与状态下复核；不能用页面里的临时位移掩盖结构问题。

### 3.4 先分配可用空间，再确定谁负责滚动

滚动归属是页面结构的一部分，应在画草图时确定。先标出工作区边界、需要常驻的区域、允许滚动的区域，再放入内容和提示；不能等内容溢出后，给某个父层加滚动条了事。

| 页面形态 | 空间与滚动的安排 |
| --- | --- |
| 连续内容页 | 正文随主内容区域自然增长，保留一条主要阅读路径；不要在正文中再套一个矮滚动框 |
| 目录与正文并列的工作区 | 外框占据分配到的可用空间；目录列表与正文各自滚动，互不带走对方，也不把整个工作区向下推 |
| 画布与检视区 | 画布在自己的边界内平移、缩放；长详情在检视区内阅读，不让页面滚动代替画布操作 |

**同一块空间只分配一次。** 父层统筹常驻导航、动态区域和主体，主体取得剩余空间，内部各栏再分配自己的工具区与内容区。上方增加一行提示时，下方应自然获得新的可用高度；不能让主体仍占满整个视口，再把提示高度叠在它上面。

实现应让这些区域共享同一条尺寸约束链。例如由父层的自动高度轨道承接提示，由剩余空间轨道承接主体；内部可收缩，溢出交给指定的滚动区域。Grid／Flex 子项的最小尺寸也要纳入检查，不能让内容的默认最小高度撑破外框。不要为每种提示、断点分别猜一个高度，再累加 `100vh - 固定像素` 的补丁。

窄屏、低窗口或放大字号时，若独立区域已无法保有可用空间，应明确切换为单栏、分步或连续阅读的结构。滚动方式可以随设计改变，但不能由意外溢出决定；也不能靠全局禁止滚动、裁掉底部或吞掉滚轮事件掩盖空间不足。

### 3.5 动态元素进入已有布局，不另造一套页面结构

接续入口、待处理提示、进度与错误说明都应在初始设计中有归属。先判断用户是否需要持续看见、是否必须操作，以及它作用于全局、当前区域还是单个对象，再选择承载方式。

| 使用需要 | 合适的安排 |
| --- | --- |
| 持续可用的接续或状态入口 | 优先放入已有的对应工具区；确需独立一栏时，由父布局分配实际占用空间 |
| 与某个对象有关的校验、进度或失败 | 放在该对象的上下文内，由所属区域消化高度，不扩成全页横条 |
| 短暂且不需要阻断的结果反馈 | 可以使用不参与主体排版的提示，但避开正文、输入点、导航与重要动作；必要信息仍有可找回的去处 |

常见状态可以预留一个紧凑位置，以减少跳动；偶发状态不应长期占着大片空白。动态区域出现后的**合理收缩**与布局失控不同：前者保留滚动归属、关键内容和操作，后者制造额外外层滚动、遮挡或截断。绝对定位和悬浮只能改变占位方式，不能自动解决这个问题。

同时出现多项状态时，先按重要性与归属合并、排序，避免多条全宽提示层层堆叠。长文案允许正常换行；空间不足时收起次要细节并提供完整查看方式，不用省略关键后果或缩小字体换取一行显示。每个需要吸顶的区域还要考虑前面的常驻区域，不能都占据同一个顶部位置。

出现、更新和消失都应保留用户正在看的对象、编辑选区及合理的阅读位置。不要因状态变化重建列表、重置到开头或自动抢焦点；移除当前焦点所在的入口时，将焦点交回合理位置。动效解释变化，不让按钮在用户准备点击时滑走。

验收要从**已滚到中段的真实工作状态**触发变化：无提示 → 单条 → 换行或多条 → 消失，再跨页面接续。检查外框是否仍在可用空间内、原定滚动区域是否仍各自工作、首末内容是否可达、当前对象与焦点是否保留；同时覆盖窄屏、低窗口和放大字号。只看初始页面或提示出现后的静态截图不足以验收。

## 4. 让间距表达关系，让留白有归属

间距表达的是亲疏和层级。先确定角色，再从既有标尺中选值。

| 间距角色 | 处理方式 |
| --- | --- |
| 图标与文字、标签与对应值 | 紧密，形成一个可识别的整体 |
| 标题与说明、说明与相关操作 | 近于相邻独立区域的距离，保留明确归属 |
| 同级列表项、同级设置项 | 按同一节奏重复，内容换行时自然增高 |
| 独立区域之间 | 有清楚停顿，但不把用户的视线切断 |
| 页面边缘与内容 | 留出稳定的安全边距，弹层与悬停背景也不能贴边 |

“组内近、组间远”是关系原则，不是全页套一个倍数。记录中的段落间距、工具栏的操作间距和阅读栏的外侧留白承担不同职责。

留白要围绕内容形成可读的区域。不要用固定大高度替代版式设计，也不要为了填满屏幕而拉宽按钮、稀释文字或添加无用卡片。已有列表为空时，重新判断该区域的高度，而不是原样保留几十行内容的空壳。

**检查方法**：先看整页，再沿纵向阅读。若某个标题与其内容像被拆成两处，或多个无关元素像挤在一组，优先检查距离关系。缩略图能检查重心，实际尺寸才能检查舒适度。

边框、底色与阴影也有角色：分隔内容、标明可交互范围、区分浮层。相同角色沿用一致的线宽、圆角和明暗关系；不要同时用厚边框、底色和大间距重复分组。深色主题尤其要实看悬停底色与边线，既不能糊成一片，也不能突然成为最亮的区域。

### 4.1 局部滚动列表：把边界、阅读留白与行密度分开设计

目录、二级导航与侧栏列表首先服务于快速扫读和定位。它们的整体应当像一条连续的内容带，而不是在窄栏里再塞一叠宽边距卡片。设计时分别画出四条边界：**所属面板、滚动视口、列表项背景与命中区、文字内容列**，不要把它们当作同一个矩形。

| 层次 | 负责的空间 |
| --- | --- |
| 面板 | 确定栏宽及与相邻区域的分隔，不重复给内部每一层施加整页留白 |
| 标题与工具区 | 按操作需要保留内边距；需要常用的搜索、筛选等位于列表滚动区之外 |
| 滚动视口 | 使用该栏剩余空间，滚动条靠近所属栏的边界，避免缩在宽内边距后的内容中间 |
| 列表项 | 让行背景与命中区充分利用可用宽度；文字、状态和行内动作各有空间，阅读留白主要在这一层分配 |

**对齐文字的阅读起点，不必让每个外框同宽。** 标题、搜索与条目文字可以共享对齐基准，列表的选中背景则可以比文字列更宽，滚动边界也可以更靠外。这样既有呼吸空间，又不必用“面板内边距 + 列表内边距 + 条目内边距”反复吃掉标题宽度。需要内嵌列表时同样保留清楚的所属边界，不把所有滚动条一律推到屏幕最外侧。

栏宽应先用有代表性的标题、摘要和状态试排，再决定留白与密度。若常见标题只剩几个字、每行却占很大高度，应检查空间分配与信息取舍，而不是继续截断或缩字。标题优先获得可辨认的长度；摘要与来源只保留有助于区分条目的信息。行高来自这些信息的排版与必要触达尺寸，不套固定的大卡片高度，也不为追求紧凑压缩到难以点选。

滚动条与文字之间留出清楚的通道。为会占宽度的系统滚动条选择合适的稳定占位，让滚动条出现前后内容不突然变窄；覆盖式滚动条也不能压住行内动作。沿用平台可操作的滚动能力，不靠隐藏滚动条、极细且难以抓取的自绘滑块或只支持鼠标悬停的提示来换取整洁。选中背景、焦点提示与首末条目在裁切边界处仍须完整可辨。

列表滚动时，工具区和相邻正文保持各自的位置；滚到底不应把本来固定的工作区一起带走。键盘定位、触摸及加载更多都属于同一设计：当前条目进入可见范围，增量加载不重置阅读位置，也不临时制造第二层滚动框。分页、空态和加载提示由同一个列表区域承接。

验收对照无滚动、刚好溢出和长列表，观察常见／长标题、选中／未选中、滚动顶部／中段／底部；检查文字实际可用宽度、每屏可辨认的条目数量、行高与信息量是否相称，以及滚动条和行内动作是否挤在一起。再单独滚动每一栏，并让上方动态区域出现和消失。好的结果是易扫读、易定位且结构稳定，不是单纯把边距变小。

### 4.2 滚动条：低干扰、可发现、容易操作

滚动条是内容的辅助刻度：让人知道还有多少内容、目前在哪里，并能直接拖到目标位置。它应融入所属区域的边缘，平时安静、需要时清楚；不能像一根额外的侧栏，也不能淡到只有熟悉页面的人才知道可以滚动。

**先确认是否真的需要滚动，再设计滚动条。** 内容能够完整放下时不产生滚动条；只有内容超过实际可用空间时才滚动。测量必须统一内容盒与边框盒，计入边框、内边距和小数像素；每次展开重新量测自然尺寸，不能继承上次受限的高度。短菜单优先完整展示，空间不足时调整展开方向或限制高度；不能用隐藏滚动条掩盖测量错误。

| 设计层次 | 处理方式 |
| --- | --- |
| 轨道 | 贴合所属滚动区边界，与该区底色相融；避免高对比槽框、立体凹槽和无意义的装饰 |
| 滑块 | 使用主题内的中性色，与底色保持足够辨识度；明暗主题分别取值，不直接把分隔线颜色当作可操作控件颜色 |
| 粗细与触达 | 按主阅读区、紧凑侧栏等少量角色共享规则；视觉轻巧仍须可抓取，不把所有区域统一压成极细线，也不在悬停时改变内容宽度 |
| 操作状态 | 悬停、拖动、键盘进入时仍清楚可辨；反馈由平台和共享样式协同完成，不新增跳动、闪烁或持续动画 |
| 留位 | 根据会占宽度的传统滚动条或覆盖式滚动条安排边缘空间；稳定占位服务于防止内容跳动，不给短菜单无条件预留一条空槽 |

**实施路线：保留浏览器原生滚动，以共享 CSS 统一外观。** 主内容区、目录、正文、图谱检视、弹层与长选项列表使用同一组滚动条颜色和密度令牌，具体区域只决定滚动归属与是否预留宽度。优先使用标准 `scrollbar-color`、`scrollbar-width`；`scrollbar-gutter` 管理占位，不负责美化。不要为了外观接管滚轮、模拟滚动位置或另造拖动滑块。[CSS 滚动条规范](https://www.w3.org/TR/css-scrollbars-1/)、[滚动槽占位说明](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/scrollbar-gutter)

跨系统一致性应落实为同一视觉层级、主题色系、边缘关系和操作规则。原生滑块的精确圆角、箭头、自动显隐和实际宽度受浏览器、系统及用户偏好影响，标准 CSS 不能承诺逐像素一致。保留这些平台行为，让触控板惯性、触摸、拖动、键盘和辅助技术继续正常工作；不为消除细小外观差异而重新实现整套滚动机制。

兼容性通过特性检测和明确的降级规则处理，不按操作系统名称分叉。确需兼容不支持标准属性的旧内核时，才在共享层使用有界的 `::-webkit-scrollbar` 回退；它是非标准接口，不是唯一实现，也不能与标准样式叠加争抢。高对比度、强制颜色及用户加宽滚动条的偏好优先；不支持装饰时仍保留完整原生操作。[兼容与无障碍注意事项](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/::-webkit-scrollbar)

**验收同时看外观和行为**：对主页面与局部列表分别覆盖无溢出、刚好放下、少量溢出、长内容；检查滑块的顶部／中段／底部、默认／悬停／拖动、键盘及触摸路径。覆盖明暗主题、窗口缩放、系统缩放、常显与覆盖式滚动条、强制颜色；确认内容不跳宽、不被遮住，首末项和末行始终可达。共享规则变更后逐类检查消费者，不能只看一个菜单。当前可用环境先实测，其余平台保留明确待验证项，不把模拟尺寸当作跨系统验证。

## 5. 排版与图标：检查实际字形

- **角色稳定**：页面标题、区域标题、正文、说明、元信息、操作文字各有稳定字阶。同级内容不会因为来自不同组件就出现不同字号或字重。
- **主次适量**：大小、字重、颜色、间距共同形成层级，一次只强化必要的因素。小字号加浅色不能成为所有辅助信息的默认处理。
- **系统字体实看**：用实际中文、英文、数字和标点验证。字体回退后仍需检查行高、截断、按钮居中；不能只凭字体名称判断效果。
- **长短皆成立**：标题从短词到两行，说明从一句到一段，都有自然的宽度和节奏。省略优先作用于可补充查看的摘要，不截断关键动作或操作后果。
- **换行有秩序**：文字增长时容器自然增高，动作不覆盖正文；不靠手工空格、强制换行或只对样例有效的宽度凑齐。
- **图标成套**：保持画布、笔画粗细、端点和可见尺寸的协调。视觉尺寸与点击尺寸分别设计；图形小不代表命中区也小。
- **符号有度量**：简单符号也应检查字形边界。若需要稳定的图标几何，使用既有图标体系或明确尺寸的矢量图形，避免依赖某个字体字符恰好居中。

文案同样属于排版材料。动作名称表达用户将做的事，状态说明表达当前事实，帮助文字只补充必要的后果或下一步。同一含义保持同一用词，避免内部术语、口号、责备语气和重复自证。先删去无价值信息，再调整行宽与间距；不能靠缩小字号容纳本来就不该出现的长说明。

对比度是可读性的底线，不是层级设计的替代。普通文本通常需达到 4.5:1，大文本可按标准定义采用 3:1；淡色说明也属于需要阅读的文本。具体条件与例外见 [WCAG 文字对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。明暗主题应分别核对实际前景、背景组合。

## 6. 控件工艺：外部位置与内部居中分开验收

### 6.1 按使用语境选择控件形态

| 语境 | 内部排版 | 外部安排 |
| --- | --- | --- |
| 独立文字按钮 | 文字或图文整体在按钮内居中 | 按页面、区域或对象的作用范围定位 |
| 图标按钮 | 可见图形光学居中，命中区完整 | 与同组控件共用尺寸和中心线 |
| 工具栏按钮 | 密度紧凑，图文间距一致 | 形成动作组，避免散落在整行两端 |
| 可点击列表项 | 标题、摘要等内容按阅读方向对齐 | 保持整行可识别的命中范围 |
| 文本链接 | 随上下文文字组织 | 邻近其解释的对象，悬停范围合理 |

文字按钮、可点击列表和导航不能共享一条不分语境的居中规则。组件应显式表达用途，避免依赖页面选择器反复覆盖。

### 6.2 从外到内检查一个控件

1. **位置**：属于哪个对象，与相邻控件按什么基准对齐。
2. **外框**：高度、宽度、圆角和边框是否符合角色，文字变长后是否仍成立。
3. **命中区**：点击范围与视觉归属一致，没有重叠或挤压邻居。
4. **内容组**：图标和文字作为一个整体排布；纯文字按钮保持合理的两侧余量。
5. **光学中心**：观察实际笔画，不只检查计算样式里的 `center`。
6. **状态**：依次看默认、悬停、键盘焦点、按下、进行中、不可用。

悬停背景是检查内部偏移的有效工具：背景出现后，左右和上下余量应仍然协调。默认态看不出的问题，不能留到用户把鼠标移上去才暴露。

状态切换通常只改变颜色、描边或细微反馈，不改变外框尺寸。加边框、改字重、替换为进度文字时，要避免按钮跳动或推挤同组动作。不可用状态有必要时应说明原因，不能只让用户面对一个点不动的控件。

键盘焦点须清楚，触达大小不能只照顾鼠标精度。WCAG 2.2 的目标尺寸最低条件为 24 × 24 CSS px，并有间距等例外；这只是底线。沿用项目既有的更舒适控件尺寸，尤其照顾高频和触摸操作。见 [WCAG 目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。

### 6.3 输入、选择与弹层是同一套工艺

输入框、筛选器和相邻按钮共用高度与基线；提示文字不代替必要标签。下拉箭头有独立空间，长选项不压住它。展开内容与触发器位置有关联，选中、悬停和焦点各自清楚，键盘进入、移动和退出连贯。

弹层宽度由内容决定，边缘留有空间；打开后焦点进入，关闭后回到合理位置。点击热区、浮层边界和文字排版一并设计。控件实现方式沿既有技术方案，精修不自动要求引入新组件库。

弹层还要识别所属滚动区的可见边界，而不只检查浏览器边缘。下方不足时向上展开，两侧都有限时让选项在弹层内部滚动；键盘定位只移动选项列表，不拖动背后的正文或整个工作区。父层滚动或窗口变化后，应重新定位或收起弹层，不能让它悬在已经离开的触发器旁。

### 6.4 聚焦沿用控件的视觉结构

焦点告诉用户“接下来输入或操作的是这里”。它必须可辨认，也必须属于控件本身；给所有元素套同一个外扩矩形，不能算完成设计。先明确由输入区、完整控件还是图形对象承接提示，再选择形态。

| 控件语境 | 聚焦的处理方式 | 重点排除 |
| --- | --- | --- |
| 下划线输入、搜索组合 | 强化已有底线；输入光标明确落点，相邻提交按钮有自己的键盘提示 | 底线外再叠矩形、双层描边、误把按钮焦点表现成输入焦点 |
| 独立按钮、有框选择器、文件选择按钮 | 贴合可操作部分轮廓的清晰描边，颜色沿用主题中的语义令牌 | 外扩挤占间距、方框与圆角冲突、将旁边的文件名也框住、弱到看不见 |
| 文字动作、折叠标题、紧凑筛选 | 强化文字下划线或已有底边，范围贴合实际操作 | 给长空白行描框、选中与焦点无法区分 |
| 可点击目录与列表项 | 使用行内提示，当前选中项与键盘所在项仍可分别辨认 | 外描边被滚动容器裁掉、覆盖相邻行 |
| 长篇编辑区 | 让插入点、选区与当前编辑位置清楚可辨，必要提示贴近正在操作的内容 | 用整页亮边或大矩形代替输入定位；键盘进入后无法定位编辑处 |
| 图谱节点和连线 | 沿用节点外沿、连线等与对象一致的提示 | 整块画布套框、专用提示与全局样式叠加 |

普通按钮按键盘焦点显示提示；文字输入即使由鼠标进入，也应清楚表示正在编辑。不要为了减少鼠标点击后的边框，连同键盘提示一起去掉。移除浏览器默认描边时，必须在对应状态提供可见替代；选中、悬停、错误状态不能冒充焦点。

描边粗细、间距与颜色采用共同令牌，例外按控件家族组织，避免逐页补丁。状态变化不改外框尺寸、不挤动文字；焦点一到便可辨认，不依赖等待动画。明暗主题分别检查，对使用阴影作为提示的控件补充高对比模式下仍可见的边界。

验收必须把**默认态与聚焦态并排看**：同尺寸截图，分别用鼠标进入、Tab 进入、移到相邻控件；检查视觉重量、轮廓归属、双重边框、滚动边缘裁切与布局跳动。再核对主题、窄屏、展开弹层及焦点返回。仅证明 `:focus-visible` 生效或“有边框”，不能证明体验合格。

### 6.5 状态颜色成对设计，控件角色互不串用

悬停、按下和执行中仍须一眼读出动作。每个状态一起确定**文字／图标、底色、边界**，不能只换背景而沿用原来的反色文字。通用悬停规则不能盖掉主操作、危险操作等填色按钮的角色；同一套按钮规则要覆盖常驻、悬浮和弹窗中的实例。

- **填色按钮**：各状态保留清楚的底色与文字对比，变化服务于反馈，不让按钮悬停后消失、像被禁用或突然变成另一个角色。
- **轻量文字动作**：适度改变底色、下划线或文字强度，文字与图标仍清楚可读；背景透明时按实际承载面计算。
- **执行中**：保留动作的可读性，由既有状态、进度或忙碌提示说明正在处理；不靠降低整颗按钮的透明度表现忙碌。
- **不可用**：与可操作状态有区别，文字仍能辨认。使用专门的前景与底色，不以整体淡出代替设计；鼠标经过也不应恢复可点击的反馈。
- **错误提示**：与危险按钮可以共享语义颜色，但不能复用按钮的反色文字规则。浅底／深底提示应分别拥有完整的可读组合。

实现按控件角色组织样式，约束选择器的作用域与优先级；避免“危险”“选中”等通用类名同时改写按钮和说明文字。颜色令牌的名称正确，不代表组合正确：半透明底色、整体透明度及叠加承载面都要计入最终呈现。

验收按控件家族取实际实例，依次比较默认、悬停、聚焦、按下、忙碌、禁用，并在明暗主题复核。既看同尺寸截图，也检查浏览器最终计算的前景与背景；正常态通过不能替代状态组合通过。发现共因时查齐使用同一规则的控件，以及同名类的非控件用途，修复后复验这些路径。

## 7. 空状态是一种完整的页面构图

### 7.1 先识别原因，再设计呈现

空白区域不一定表示“没有资料”。先确认数据状态，再选择表达。

| 情况 | 用户需要知道什么 | 合适的下一步 |
| --- | --- | --- |
| 首次使用，确实没有内容 | 这里能承接什么，如何开始 | 一个最相关的开始动作；必要时一句简短说明 |
| 用户处理完或清空了内容 | 当前状态已成立，资料是否受影响 | 安静确认；有实际需求才提供动作 |
| 当前筛选或搜索无结果 | 没有符合本次条件的内容 | 保留查询条件，提供调整或清除条件的入口 |
| 列表已有内容，但尚未选择 | 当前区域等待选择 | 轻量选择提示，避免误导为内容不存在 |
| 页面中只有一个区域为空 | 该区域当前没有内容 | 局部、低强度提示，让已有内容保持主导 |
| 仍在加载、整理或恢复 | 结果尚未确定 | 诚实的过程状态，不能提前显示零内容 |
| 读取失败或无权查看 | 当前无法取得结果 | 就地解释可采取的行动，不能声称数据不存在 |

“当前列表为空”与“整个资料库为空”也要区分。分页、筛选和访问范围限制了判断能力，文案必须落在实际已知的范围内。

### 7.2 选择匹配区域的空状态尺度

- **整页为空**：形成一个明确的视觉落点。保留页面定位和重要入口，将有用的说明与下一步组织为紧凑内容组。位置服从原有阅读起点和页面重心，居中是选择之一，不能成为默认模板。
- **局部区域为空**：贴近该区域标题或内容起点，缩减高度和视觉强度。不要让一个空区块比旁边真实内容更抢眼。
- **目录与正文双区**：让两侧承担不同职责。目录说明列表状态，正文区域提供必要的下一步或选择引导；避免两侧重复相同的空提示和主按钮。
- **多个区域同时为空**：保留用户仍需理解的结构，合并重复解释与动作。没有独立意义的空分组可以收起；稳定导航与关键入口不能随之消失。

空态可以由“状态标题、必要说明、相关动作”组成，但不强制三件齐全。若标题已足够清楚，就不补一句同义解释；若没有合理动作，就不造按钮。

### 7.3 控制空态的分量

空态的标题应明显但不压过页面标题，说明宽度应适于阅读，动作紧随说明而不是飘在远端。正文为空时，沿用正常页面的间距层级，允许局部收紧；不要把无内容误解为无限留白。

插图只有在解释对象、过程或下一步时才加入。口号、巨大图标、装饰卡片和虚构样例不能填补真实任务的缺席。安静的页面仍然需要精确的排版和落点。

### 7.4 同时设计空与非空之间的变化

至少并排比较 **0 条、1 条、少量、较多内容**。第一条内容出现后，页头、导航和主要入口应保持可预期；不能突然更换整套布局。最后一条消失后，空态自然接回同一区域，焦点有合理去处。

搜索与筛选无结果时，保留用户的输入与条件；新内容出现时不无故抢焦点。空态、加载态、失败态分别验证，不能用一个“空组件”承担全部情况。

## 8. 写作与阅读：设计连续的文稿空间

### 8.1 先确定内容形态与工作过程

编辑界面的定位由用户怎样思考和修改内容决定。连续文字以阅读顺序、插入点和段落组织；空间画布以对象位置与连接组织；表单以字段、校验和提交组织。先选定主形态，再设计控件，不能把一个大输入框放进页面就视为完成编辑体验。

**本项目采用连续文稿：进入就能写，写的过程可以读，离开后能接着写。** 风格沿用现有阅读界面，主体由文字形成；页头、状态与辅助操作围绕文稿安排。依照[模块产品设计中的文稿承诺](../tasks/owner-window.md)，内容仍为纯文字；草稿自动保存、整体确认生效、来源保留与并发保护均不改变。以下是体验设计方法，不表示这些视觉调整已经实现，也不新增富文本、画布或窗口内智能。

先用五个阶段检查完整性：**开始 → 持续输入 → 回看与修订 → 核对结果 → 离开与接续**。每个阶段明确用户注意什么、下一步在哪、哪些内容必须保留。空白页只是起点，不能独自代表编辑器。

### 8.2 正文先成立，工具围绕正文组织

先放好第一行文字，再安排页头与工具。正文有稳定的阅读起点、适宜行宽和纵向节奏；空白时，光标与一句起笔提示落在实际输入处。提示不成为正文，不用示例文章、装饰框或居中欢迎语占据写作位置。用户明确新建或进入编辑时可直接起笔；只来查看内容时，不自动进入输入态。

| 区域 | 承担的职责 | 设计要点 |
| --- | --- | --- |
| 文稿页头 | 知道正在处理什么、如何返回、下一步是什么 | 返回与文稿识别在一侧，保存状态与当前阶段的主动作在另一侧；长标题截断不推挤操作 |
| 正文列 | 阅读、输入、选择与修改 | 文字是最强的视觉主体，保留舒适边距；底色服务于阅读，不以固定大矩形暗示可拖拽画板 |
| 辅助操作 | 低频显示选项、协助与文稿管理 | 收在明确的次级入口，菜单项写清用途；删除放在管理区并与日常写作动作分隔 |
| 核对状态 | 看清改动、后果与最终确认 | 延续文稿的排版与对象身份，给全文和对照足够空间；恢复编辑的入口明确 |

共同的页面边距组织页头，较窄的正文列保证阅读舒适，两者不必强行同宽。正文底部不堆放一排无关命令；重要动作也不应迫使用户滚到文章末尾才能找到。隐藏侧栏只是空间安排，不能抢占每次写作的主操作位置。收起工具后仍须保留可发现的返回与操作入口，不能只靠悬停或记住快捷键。

**先画这条注意力顺序：文稿身份 → 第一行／上次位置 → 正文 → 当前需要的动作。** 保存状态在余光中可确认，异常才提高强度；不让状态、导航开关与删除按钮获得同等分量。

### 8.3 用排版建立文档感

- **行宽按文字度量。** 从现有正文字阶出发，用真实中文、中英混排和长句试读；中文约 30—40 个全角字的行宽可作初始样本，再按字体和窗口校正。这个范围是设计起点，不是标准或硬限制；宽屏增加外侧留白，窄屏保留最低阅读边距。
- **字号、行距与段落一起判断。** 先让一段普通正文读起来舒适，再处理标题层级。编辑与查看共用文字排版基准；编辑状态不能像小字号表单，查看状态也不应突然变成另一套模板。
- **内容结构必须真实。** 标题、段落、换行按已有内容规则呈现。没有独立标题字段时，不为了视觉层级强行要求用户先填标题，也不静默拆分、重写正文；未命名提示属于界面，不随保存混入文字。
- **外观与文本分开。** 排版留白由界面承担，不往正文补空格、空行或标记。复制、粘贴和保存仍得到用户写下的内容；空行是否保留、标题如何显示必须在读写之间保持可解释的一致性。
- **看文稿而非控件外壳。** 日常编辑不依赖厚边框、固定纸张比例、深色大底板或缩放把手建立范围。有限的纸面层次可以服务阅读，但不能让人误认为要先调整画布才能开始写。

纯文字是内容约束，不决定界面粗糙程度。底层采用何种输入控件，应服从排版、输入可靠性与可访问性，不把浏览器控件的默认外形当作产品形态。

### 8.4 连续输入的手感是设计的一部分

普通写作保留一条主要纵向阅读路径。正文增长由系统处理，不要求用户拖大编辑框；避免页面滚动与一个矮输入框内部滚动互相争夺。同屏对照确需两个阅读区域时，滚动归属必须清楚，不能强制同步到错误段落。

正在输入或移动光标时，活动插入点、相关文本与输入法候选应在可视范围内。页头、通知和软键盘不得遮住它们；末行下方留有继续写作的空间。默认只在光标即将越出可视范围时适度跟随，不在每次输入时把当前行拉回屏幕中心。用户主动回看上文时，后台保存与更新不能夺回滚动位置。

中文输入、连续删除、跨段选择、粘贴、撤销与重做应当连贯。换主题、显示状态或渲染装饰不能重建输入区、打断输入法组合、清空撤销记录。聚焦反馈围绕当前操作建立，不能把整篇文稿的一条长亮边当作持续编辑的唯一提示。

### 8.5 查看、编辑与核对保持同一篇文稿的连续感

查看用于理解内容，编辑用于改字，核对用于确认结果与后果。三者职责清楚，入口只在需要时出现；编辑中的文字本身就应当好读，不能把“先去预览”当作补救排版的方法。

切换时保留对象、文本、阅读位置及可恢复的编辑选区；正文起点和宽度尽量稳定。因标题排版或对照需要发生重排时，围绕同一段内容接续，不强求相同滚动像素。返回编辑应回到刚才工作的地方。

长篇阅读和核对使用足够的正文空间，可以采用同一工作区的独立状态或完整阅读面；不要挤进小确认框，再在框内塞多层滚动。宽屏按内容需要并排展示“现在／将成为”，窄屏清楚切换两者；改动提示辅助定位，全文仍可核对。取消核对不丢输入，进入核对不表示同意保存。

普通显示切换不改变资料。需要整体生效的工作流继续保留显式确认，并绑定用户实际核对的那份内容；期间发生更新，界面须回到可核对状态，不沿用失效的确认。来源与原件说明只在影响理解或决定的位置出现。

### 8.6 让保存带来确定感

区分“输入已经保留”和“结果已经生效”。既有产品存在草稿与资料两个阶段时，界面必须说清保存的是哪一个；不能用含糊的“已保存”让用户误以为原资料已更新，也不能为减少一步操作而取消必要确认。

| 状态 | 合适的呈现 |
| --- | --- |
| 正常编辑与自动保存 | 固定位置的轻量状态，宽度稳定；不在每个按键后闪烁，不重复堆放自动保存说明 |
| 草稿已保留，尚未生效 | 清楚标明草稿，最终动作表达实际结果，如加入资料或保存修改；具体名称服从产品语义 |
| 保存失败、结果待核对 | 在编辑上下文内提高提示强度，说明已保留什么及下一步；不能只改变颜色或声称成功 |
| 另一处有修改 | 保留双方文字与明确选择，不以自动覆盖制造顺滑体验 |
| 返回、关窗、重新打开 | 依照已核实状态接续；正常保存不反复确认，确有未保留内容时才呈现必要保护 |

辅助状态要能在长文中找到，不能只留在已经滚出屏幕的页尾。操作失败后仍能继续看见自己的文字；提示不盖住正文，也不偷偷替换编辑现场。

### 8.7 用真实写作过程验收

先比较空白、一句话、数段文字和长文的构图，再完成下列动作。共用控件按 §6 验证，写作体验还需单独过关：

1. **开始**：新建后立即知道在哪里写；不用先命名、调大小或理解模式；第一行到来时布局自然接续。
2. **持续**：中文输入、粘贴多段、跨段选择、撤销重做；光标不被遮住，文字不丢失，状态变化不挤动正文。
3. **回看**：滚到长文中段，修改一句，再查看或核对并返回；内容位置可接续，用户不需要重新寻找刚才那段。
4. **安心离开**：分别经历草稿保存、确认生效、失败和结果未知；用户能辨认文字是否保留、资料是否改变及如何继续。
5. **空间变化**：同一内容在明暗主题、窄窗口、浏览器放大与软键盘条件下仍可读、可操作；当前环境无法实测的明确记录。

至少保存一组**同一内容、同一尺寸的编辑与查看对照**，另核对一次真实长文操作。验收既看排版，也看手感；只有空白截图、输入成功或保存接口通过，均不足以证明文稿体验完成。

| --- | --- | --- |

## 9. 关系图：把联系组织成可以探索的空间

关系图应帮助用户从一份内容出发，发现相邻内容，看清联系，再回到阅读。它的价值不由节点数量、画面复杂度或是否三维决定。设计先回答：第一眼能发现什么，选择之后能理解什么，读完之后能否接着探索。

### 9.1 区分空间感、坐标维度和绘制技术

这三个问题需要分别判断：

| 层面 | 实际含义 | 不应混淆的事 |
| --- | --- | --- |
| 空间感 | 疏密、聚散、主次、前景与背景，以及移动时的连续感 | 二维图也能有丰富的空间层次；加阴影、渐变或透视不自动带来清楚的关系 |
| 坐标与相机 | 二维的 x/y、平移与缩放；三维增加 z、投影和绕场景旋转 | 三维网络最终也投影到屏幕；旋转能分开某些遮挡，也增加找回节点和阅读的成本 |
| 绘制技术 | SVG、Canvas、WebGL 等把位置与样式画出来 | WebGL 可以绘制二维图，SVG 也可以做自然布局与连续交互；渲染器不决定构图品质 |

**Obsidian 内置 Graph view 与 Local Graph 是二维关系图。** 官方示例中，节点围绕联系自然散布，焦点及邻接线突出，外围内容退成背景；这种层次可以产生用户感受到的纵深，但不等于节点具有三维坐标。Local Graph 的 depth 表示沿链接展开多少跳，不是空间的 z 轴。可旋转的三维图另有社区插件，不能用插件效果描述内置能力。依据：[官方说明](https://github.com/obsidianmd/obsidian-help/blob/master/en/Plugins/Graph%20view.md)、[官方示例图](https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Attachments/obsidian-graph-view.png)、[Three D Graph View 插件](https://community.obsidian.md/plugins/three-d-graph-view)。

因此，面对“像在纸上排点连线”的问题，先检查节点是否表达真实聚散、文字是否有主次、选择是否建立前景、视图是否随探索接续；不能把它简化成“需要换成三维”，也不能用“它本来就是二维”否定视觉问题。

### 9.2 从不同产品提炼方法

以下为 2026-10-01 调研。Obsidian 核对了官方说明与官方静态示例，未运行其桌面程序；示例图不作为当前版本全部细节的证明。Sigma 与 3D-force-graph 打开了真实浏览器示例并检查交互，其余依据官方技术与产品文档。表中体验取舍是设计分析，不是统一条件下的性能排名。

| 产品／技术 | 已核实的路线与表现 | 可借鉴的体验及代价 |
| --- | --- | --- |
| [Obsidian](https://github.com/obsidianmd/obsidian-help/blob/master/en/Plugins/Graph%20view.md) | 二维力导向关系图；提供斥力、连接力、距离、聚拢等控制，以及标签渐隐、邻接高亮和局部图 | 自然聚散与焦点层次让关系有空间感；局部图把注意力带回正在读的笔记。不能推定其当前内部渲染库，也不必把全部力学参数交给普通用户 |
| [Neo4j Bloom](https://neo4j.com/docs/bloom-user-guide/current/bloom-visual-tour/bloom-scene-interactions/) | 从查询或局部片段进入场景，逐步展开邻居并检视详情；支持力导向、层次、坐标与圆形布局 | 先限定问题，再选择布局，复杂网络才可读。企业分析面板与布局切换不是所有资料产品都需要的功能 |
| [Gephi Lite](https://github.com/gephi/gephi-lite)／[Sigma](https://www.sigmajs.org/docs/advanced/layers/) | Graphology 管图数据与算法，Sigma 分层绘制 WebGL 节点／边和 Canvas 文字；[二维示例](https://www.sigmajs.org/demo/index.html)呈现不规则团簇和有选择的标签 | 大图概览与局部阅读采用不同密度；GPU 绘制、布局计算和文字管理各负其责。大量点画得出，不代表大量标题读得清 |
| [Cytoscape.js](https://blog.js.cytoscape.org/2020/05/11/layouts/) | 布局算法与绘制分离，支持离散与持续布局；传统 Canvas 路线，另有[2025 年 WebGL 预览方案](https://blog.js.cytoscape.org/2025/01/13/webgl-preview/) | 先取有意义的子图，再排列；算法应服从关系结构。预览方案显示加速与样式能力存在取舍，不能用该历史文章断言当前版本能力 |
| [Cosmograph](https://next.cosmograph.app/docs-app/)／[技术说明](https://next.cosmograph.app/library/) | 当前路线包含 GPU 布局与 WebGL 绘制，支持二维、三维及预计算坐标，结合查找与筛选探索网络 | 适合观察大范围分布，再缩小范围；全局纹理与逐条阅读是不同任务。厂商规模宣称不作为本项目性能承诺 |
| [3D-force-graph](https://github.com/vasturiano/3d-force-graph) | Three.js／WebGL 绘制，配合 d3-force-3d 或 ngraph；[示例](https://vasturiano.github.io/3d-force-graph/example/basic/)可旋转、平移和缩放真实三维场景 | 透视和旋转确有纵深；同时要处理前后遮挡、标题朝向、选取和迷失方向。是否采用取决于任务收益，不能仅凭截图震撼程度决定 |

共同方法是：让数据决定联系，让布局组织空间，让视觉控制注意力，让交互逐步揭示细节。具体库与力学公式是实现选择，不能替代这四项设计。

### 9.3 按职责拆开整条呈现链

| 层 | 负责什么 | 最先检查什么 |
| --- | --- | --- |
| 关系数据 | 节点身份、关系方向与类型、来源依据、版本及可见范围 | 关系是否真实、重复记录是否被误画成多个事实、失效内容是否退出 |
| 场景取数 | 本次显示哪些内容，哪些尚未展开，怎样继续 | 当前画面是不是有意义的范围，是否把局部结果冒充完整网络 |
| 布局 | 位置、聚散、碰撞、断开部分的摆放及更新 | 邻接结构能否看出，是否重叠，新增关系能否改变不合适的位置 |
| 相机 | 平移、缩放、适配画面与返回现场 | 目标是否保持在视线内，侧栏打开后是否挤丢内容 |
| 绘制 | 节点、边、文字、命中区域和更新成本 | 绘制是否清楚、可选、及时，是否每次悬停都重做昂贵工作 |
| 视觉与交互 | 当前重点、相关背景、详情、阅读接续与操作反馈 | 用户能否看懂并完成下一步，是否需要先学图算法 |

布局只处理已知关系的几何组织。连通分量表示当前边能否互相到达；算法社区表示某种结构聚集；主题分类表示内容含义，三者不能互相冒充。前端不能因为两点靠近就新增联系或给一组内容命名。力学参数、位置和缩放属于视图状态，不成为新的业务权威。

### 9.4 先决定展示范围，避免把全量数据变成线团

概览用于寻找聚集处、连接处和独立内容；局部查看用于回答“这份内容与谁有关、为什么”。两者应能连续切换，不能要求用户先在全量线团里准确点中一个小点，才能开始使用。

- 为当前任务选择有界子图；资料查找、相关列表和图相互接续。数量限制是系统预算，用户看到的是还能如何继续。
- 清楚区分真正没有关联、尚未展开、加载失败和部分内容不可见；没有画出的边不等于不存在。
- 独立内容也有价值，不能为让画面整齐而悄悄丢弃。没有内容时提供明确起点；只有一个节点时保持正常可读尺寸，不放大成巨球。
- 同一关系的多份依据可以共用布局上的连接，呈现时须保留逐份核对能力；不同方向与不同含义不能静默合并。既有契约要求独立可选的内容仍须可选。
- 位置距离通常只服务布局，不能让用户误以为距离就是相似度、可信度或重要性。若确有数值编码，须有明确来源和解释。

### 9.5 布局要表达结构，并照顾文字和真实画布

先根据问题选布局：一般关联适合力导向；围绕一个对象检查邻居可采用局部放射组织；明确的先后或上下级适合层次布局；地理或其他有真实坐标的数据保留其坐标。表格与网格适合按顺序比较条目，通常不能表达自由关联的疏密。不能为追求“不规则”而随机撒点，也不能用一套圆周模板排列所有网络。

力导向需要一起设计吸引、排斥、碰撞、聚拢与收敛：

1. **连接组织局部**：有联系的节点形成可跟随的邻接结构；过长的桥接线和高连接节点不应把整个网络挤成团。
2. **排斥保留呼吸**：节点不重叠，局部有足够空间展开文字；只把斥力调大可能让画面稀散，并不能消除所有交叉。
3. **碰撞考虑尺寸**：节点半径与实际显示的标题有占用面积，不能只检查点与点的距离。文字最终还需在屏幕坐标里避让，避免缩放反复牵动全图。
4. **分区按实际边界摆放**：互不连通的部分保有间距，组内紧密、组间舒展；以实际包围范围安排位置，避免用固定格子容纳大小悬殊的组。
5. **收敛后稳定**：相同输入与初始条件可复现；结合位移／能量阈值与计算预算结束计算，不能把“永远缓缓漂动”当作生命力。极端输入也须按预算给出可用结果。

成熟算法可以复用，但要验证适用条件。[ForceAtlas2](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0098679)及其[Graphology 实现](https://graphology.github.io/standard-library/layout-forceatlas2.html)提供力学、节点尺寸、近似计算和工作线程等选择；它们不自动解决中文标签、视口构图与探索接续。小图未必需要复杂近似，大图也不能只靠增加迭代次数。

适配画面应按实际可用区域、必要标签和安全留白计算。侧栏、工具条与窄屏抽屉都是空间约束。不能让离群点把主要内容缩成画布中央的小岛，也不能裁去它来制造好看截图；可用整体概览与局部聚焦分别承担两种阅读尺度。

### 9.6 位置记忆用于接续，不能把旧构图永久锁死

第一次进入、关系陆续到达、展开邻居、刷新与从阅读返回，是同一空间的不同阶段。仅检查一次静态布局，会漏掉最影响体验的更新问题。

- 首次得到足够关系后形成可读构图；分批取数时，后到的边必须能参与后续布局。
- 旧位置作为继续计算的起点或适度约束；新增节点优先从相关节点附近展开，已有区域尽量少移动。只有明确需要固定的位置才硬锁定。
- 拓扑改变时允许必要调整，保住当前节点和主要空间关系；没有拓扑变化时不因悬停、颜色或选中状态重新洗牌。
- 从阅读返回，恢复选择、相机与相容的位置；关系已变化时做局部调整，不能在计算结束后无条件覆盖回所有旧坐标。
- 展开邻居不自动反复缩放到全图。优先保住当前目标的屏幕位置；确需移动视图时解释变化，另保留明确的整体适配入口。
- 布局、取数与页面切换有清楚的版本归属；过期结果不覆盖新选择，离开页面后停止不再需要的计算。

这里需要平衡的是“关系变化能够看出来”与“用户不会丢失方向”。完全冻结和每次重排都会破坏其中一项；通过延续计算、限制不必要的位移与保留焦点，同时满足两者。

### 9.7 用疏密、层次与线的秩序建立空间感

**节点**首先是可识别、可选择的内容。默认大小克制，选择和键盘焦点清楚；可见圆点与可点击区域分开设计，小点也要容易点中。若用大小编码连接数量或其他量，限定变化幅度并说明含义，不能让枢纽无限膨胀，也不能随意用尺寸暗示内容价值。

**连线**帮助视线从一个节点走向另一个。普通边退后，当前相关边突出，但退后不等于几乎不可见。曲线用于区分真实重叠路径，方向在需要判断时可读；为每份依据叠一条近似线容易制造噪声，应先检查是否是同一联系的重复呈现。拥挤时优先缩小范围和局部展开，不依靠把所有边淡到看不见。

**标题**承担识别，不能全部以同样强度压在点线上。按当前选择、悬停／焦点、邻居、其余内容分配显示优先级；缩放时逐步增加细节，避免轻微移动便反复闪现。使用实际字体度量与碰撞检测，当前目标标题保持可读；短标题在图上识别，完整名称在相邻检视区可得，不能只靠鼠标悬停才能看到。

**层次**由前景明确、背景安静、局部聚集与组间留白共同形成。选中时相关区域成为视觉主体，其余空间仍提供方向参照。不要照搬某张参考图的透明度：主题、显示器与内容密度改变后，过淡的节点和线可能完全丢失。

**分组底色**仅在有真实可解释分组且能帮助阅读时使用。优先让位置自身形成聚散；底色边界不能包住无关节点、与邻组大片重叠，或把算法连通区域暗示成确定的主题。发光、雾化、投影和视差都不能补偿没有结构的布局。

### 9.8 探索过程要像读内容一样自然

理想路径是：找到一份内容 → 看见邻接关系 → 选择联系查看依据 → 阅读原文 → 回到刚才的位置继续。每一步都要有明确对象和返回点，图不能成为与资料阅读脱节的展示页。

- 悬停做短暂提示，选中形成持续上下文，键盘焦点表明下一步操作对象；三种状态不能互相抢走选择。
- 平移、缩放、点选和拖动有清楚边界；缩放围绕操作位置，点选不被误判成拖动。用户准备点击时，目标不应仍在自动漂移。
- 详情与图并存，避免小点承担长篇解释。边也能进入可读的关系与依据详情，而不是只有视觉高亮。
- 浮动详情出现后，以剩余可见画布确定相机边界，让当前目标留在面板之外；只检查节点是否位于 SVG 内部，仍可能把它藏在浮层下面。
- 触摸场景不依赖悬停；键盘和辅助技术可通过具有名称的节点、邻接列表或详情路径完成等价探索。换渲染器不能取消这些入口。
- 布局过渡表达位置变化，镜头过渡解释探索方向；减少动效时直接落到稳定终态，仍保持定位。没有必要持续播放、自动旋转或让整个网络随鼠标漂浮。

### 9.9 根据瓶颈选择技术，不按“高级程度”排序

| 路线 | 合适条件 | 必须承担的成本 |
| --- | --- | --- |
| SVG | 有界场景、需要细致的节点／连线交互，DOM 结构有助于检查与无障碍接线 | 控制元素数量与更新范围；文字、命中和布局仍要设计，DOM 不自动保证无障碍 |
| Canvas 2D | 绘制对象较多，愿意用统一绘制循环管理场景 | 自行处理命中、文字测量、像素比及等价的可访问界面 |
| WebGL 二维 | 实测瓶颈在大量图元绘制，GPU 能带来有意义收益 | 文字层、选取、显存与上下文生命周期、样式限制；仍需单独解决布局耗时 |
| 三维场景 | 用户确实需要观察三维坐标，或旋转检查网络能带来经过验证的探索收益 | 相机方向、遮挡、标签、点选、性能和返回现场；不能把学习操作作为默认代价转给用户 |

节点数不是唯一选型阈值，边密度、标题数量、样式、交互频率和设备同样重要。分别观测取数、布局、文字处理、绘制和交互响应，再决定优化哪一层；不能将“换 WebGL”当作布局提速方案。[Sigma 的分层](https://www.sigmajs.org/docs/advanced/layers/)与[坐标系统](https://www.sigmajs.org/docs/advanced/coordinate-systems/)说明这些职责可以独立处理。

计算达到稳定状态后应停止无用帧；页面隐藏、被替换或关闭时释放监听和计算资源。只有实际布局阻塞交互时才引入分帧或工作线程，并防止旧结果回写。库的选择还应检查许可证、离线运行、包体、维护和现有交付约束，不把一套分析平台搬进只需浏览关联的产品。

### 9.10 用拓扑变化和完整探索验收

用代表性结构揭示机制问题，不能只用一种漂亮的样本网络：

| 样本／过程 | 要确认的体验 |
| --- | --- |
| 无资料、单点、互不相连的少量内容 | 有起点、有正常尺度，不虚构联系，不留下无意义操作 |
| 链、环、星形、多个团簇及中间桥接 | 结构可辨认，枢纽不吞没邻居，交叉和密度可管理 |
| 稠密局部、长中文标题、中英混排、重复依据 | 当前目标文字不遮挡，线可选择，原有关系含义与依据均可核对 |
| 先有节点后有边、展开邻居、更新或移除内容 | 后到关系能影响构图，视线不丢目标，旧结果不回写，已移除内容不残留 |
| 看图 → 看依据 → 读原文 → 返回 | 选择和位置可接续，用户不用重新寻找起点 |
| 缩放、侧栏变化、窄屏、明暗主题、键盘与减少动效 | 实际可用区域内仍可读可选，输入方式不改变能力，移动不过量 |

至少保留同一数据、尺寸与主题下的概览、选中邻接、展开后及阅读返回四种状态；与原基线并排看构图和注意力，再实际完成探索。既量测当前标题碰撞、命中范围、更新位移与响应，也观察空间是否自然、关系是否好跟随。计时分开记录首次可用、布局收敛和交互响应，稳定后检查是否仍有无用计算。

通过标准是用户能识别起点、沿联系到达内容、核对依据并继续探索，且动态更新与有界范围诚实可见。截图有纵深、动画流畅、接口成功或节点全部画出，任何一项都不足以单独证明关系图做好了。

## 10. 状态与动效：让变化可理解

每个动作都要设计点击之前、进行之中和完成之后，而不只设计静态按钮。

分页和后台更新共存时，分别保存**当前集合、浏览位置、最新请求**。筛选先于分页；“下一页”和待办数只计算符合条件的记录。后台刷新重读当前位置，保留已展开范围、滚动和焦点，不把第一页覆盖到用户正在看的后续页；迟到响应不得覆盖新导航。撤销或决定完成后，更新发生操作的列表，而不只刷新其背后的页面。身份变化、内容删除导致原位置不可用时，清理旧视图并提供清楚的返回路径。验收覆盖恰好满页、全部已处理、第二页遇后台写入、响应倒序和原位操作后的结果。

- 点击后立即产生可见反馈；较慢操作说明正在做什么，重复提交受到控制。
- 成功反馈靠近发生变化的对象，用户能看见结果落在哪里；失败提示靠近可修复的位置，并保留已输入内容。
- 不用新弹窗承接每个小动作，也不用页面顶部通知替代屏幕下方操作的反馈。
- 加载时保留已知结构和可用内容；骨架只预测真实内容形态，不制造空卡片墙。
- 动效帮助解释出现、消失、位置与状态变化。延迟不能妨碍下一步，装饰性移动不能改变点击目标的位置。
- 减少动效时直接到达清楚的终态，状态信息仍然完整。交互触发动画的可关闭原则参见 [WCAG 动画说明](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)；本文将尊重减少动效偏好作为设计方法，不据此宣称完整合规。

优先复用既有动效令牌。是否顺手要在真实操作中判断：等待过长、切换闪烁、视线被拉走，即使每段动画单独看都好看，也应调整。

## 11. 内容、尺寸与主题变化都属于设计输入

不要把某一张大屏截图当作页面本身。精修时至少覆盖以下变化：

| 维度 | 代表样本 | 关注点 |
| --- | --- | --- |
| 内容量 | 空、1 条、少量、需要滚动 | 重心、密度、动作位置与滚动边界 |
| 内容形状 | 短标题、两行标题、长说明、中英混排 | 基线、换行、截断、图文间距 |
| 可用宽度 | 常用桌面、较窄窗口、窄屏 | 布局何时换行，是否遮挡，触达是否方便 |
| 缩放与字体 | 常用系统缩放、浏览器放大、实际字体回退 | 光学中心、清晰度、控件是否裁字 |
| 主题 | 浅色、深色 | 层级、边界、可读性和悬停分量 |
| 交互 | 鼠标、键盘、触摸条件下的布局 | 焦点、目标尺寸、无悬停时的操作可发现性 |

窄屏重排依据内容需要发生，优先让相关元素一起移动；不把桌面上的远距离排列简单压缩。固定导航、浮层和页面底部动作要互相避让。保持用户的阅读位置和当前选择，避免尺寸变化造成上下文丢失。

矩阵用于选有区分力的样本，无需机械穷举所有组合。当前环境能验证的亲自验证，其余明确记录覆盖边界。

## 12. 从根因修复，避免补丁堆积

按这个顺序定位问题：

1. **信息关系**：动作放错区域、重复入口、说明与对象脱离。
2. **容器布局**：宽度、轨道、内外边距、换行策略不合理。
3. **组件规则**：同一控件缺少明确变体，继承或覆盖造成分叉。
4. **字形与图标**：字体度量、行框、图标空边造成视觉偏差。
5. **状态与时序**：悬停、加载、失败或内容变化后才出现异常。

先定位在哪一层，再决定改动范围。共因问题修共同规则并检查所有使用处；真实例外保留明确的语境。禁止用一串更强选择器、临时负边距或页面编号规则，把错误藏到另一种状态里。

令牌负责一致的尺度，组件负责内部工艺，页面负责布局，业务状态负责呈现条件。边界清楚，精修才容易稳定保持。只整理实际存在的模式，不为此次精修预建大而全的设计系统。

## 13. 一轮精修的工作方法

### 开始前：建立可比较的基线

保存相同数据、窗口尺寸、主题和缩放下的页面截图；记录已经认可的区域。先使用隔离样本构造空、少量和正常内容，不以修改用户真实资料制造测试状态。

先完整巡看受影响页面，再按共同机制归组。排序优先考虑：误导或阻断操作 → 高频且跨页的问题 → 页面节奏与细节。不要发现一个控件就立即局部试色，最后再拼成整页。

### 设计时：写清每项调整的理由

每类改动只需说明四项：用户要完成什么、当前关系为何妨碍它、准备统一哪条规则、哪些页面和状态必须同时复验。先解决主次、归属与构图，再细调字号、间距和光学偏移，最后处理动效。

### 实现后：分三遍验收

1. **整页看**：在真实尺寸下确认重心、阅读顺序、空态构图和疏密；与基线并排比较。
2. **逐组看**：检查同级标题、操作列、列表节奏与控件家族；依次触发悬停、焦点、按下、忙碌和失败状态。焦点按 §6.4 逐类对照默认态，不能用一个控件或“可见”断言代替全类视觉检查。
3. **实际走**：用鼠标与键盘完成主要动作，经历空到有、有到空、筛选无结果和恢复，再确认页面仍然协调。

测量用于证明几何、边界、溢出和对比；真实截图与操作用于判断视觉重量、阅读舒适度与反馈。两者共同构成证据。自动化通过不能代替视觉验收，单张好看的截图也不能代替完整状态。

### 结束条件

- 已认可的整体风格、布局和成熟页面得到保留。
- 受影响区域的主次、归属、对齐和密度有一致依据，已知同类问题全部核对。
- 空、少量、正常内容与关键交互状态均有真实验证，按钮内部与外部对齐分别通过。
- 涉及动态区域或局部滚动时，按 §3.4—3.5 与 §4.1 核对空间分配、滚动归属及列表密度，不能只验默认无提示状态。
- 涉及文稿时，另按 §8.7 完成从起笔到离开接续的真实写作验收，不能只验空白编辑页。
- 涉及关系图时，另按 §9.10 验证代表性拓扑、动态更新及阅读返回，不能只验初次出图。
- 页面在已验证的宽度、缩放、字体和主题下可读、可操作，无明显跳动、裁切和遮挡。
- 每项保留的调整都能说明实际收益；没有收益或引入新摩擦的变化撤回，保留更好的基线。

达成后结束本轮。优秀的精修让页面更自然、更可靠，同时保留用户已经熟悉和认可的部分。
