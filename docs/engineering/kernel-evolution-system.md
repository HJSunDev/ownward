# 内核持续演进体系

本文档负责维护Ownward 内核长期产生、验证和晋升更优实现，是内核持续优化的统一工作方法。

## 决定信息内核效果的核心因素

Ownward 要优化的对象是**信息组织与检索内核**。它的效果来自从信息进入体系到证据交给外部智能体的完整技术链路，不由某一种索引、模型、编程语言或搜索算法单独决定。检索质量要求相关信息能够被完整召回、正确排序、按当前时间与场景适用并作为充分证据交付；检索效率同时包括可检索时延、查询时延、组织与索引维护成本、重建成本及资源占用。

| 技术方向                     | 优化方向                                                                                                                                                 | 影响                                                                                                                           | 优化优先级                   |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| **信息表示与组织结构** | 优化信息单元颗粒度、稳定身份、来源、时间、版本、冲突、场景及关系模型，使跨时间、跨会话和多跳事实既不割裂也不错误合并。                                   | 直接决定内核实际拥有怎样的可检索知识，能够同时提高召回、关系推理、更新正确性并减少索引噪音，是质量上限的基础。                 | **最高：核心优化层**   |
| **检索架构与算法**     | 优化查询约束表达、多路候选召回、路径选择、过滤、关系扩展、分数校准、融合、重排、去重、多样性及证据交付，使正确证据既能进入候选集又能稳定排到前面。       | 直接决定“能否找全、选对并交付”，通常对端到端质量影响最大；更好的路径选择还能减少无效召回和读取，同时提高效率。               | **最高：核心优化层**   |

| **数据结构与存储架构** | 优化倒排、向量、关系、时间和场景索引，数据布局、增量更新、缓存及冷热分层，使更多有效检索能力能够在真实长期资产规模下成立。                               | 主要抬高延迟、吞吐和规模上限，也会通过允许更广召回、更及时更新和更复杂融合间接提高质量。                                       | **中高：规模与效率层** |
| **执行架构与状态维护** | 优化在线与离线边界、并发、批处理、增量计算、数据复制、序列化、派生世代构建、原子切换及故障恢复，消除链路中的重复工作和等待。                             | 主要提升端到端效率、资源和新鲜度；只有测量证明执行链已经限制检索策略或组织质量时，才上升为核心优先级。                         | **中：证据驱动层**     |
| **实现技术与计算基础** | 在现有实现中优化热点路径、内存布局、分配与回收、编译、系统调用、本地推理和硬件利用；只有不可消除的运行时瓶颈得到证明时，才评估编程语言或基础运行时替换。 | 编程语言和硬件能够抬高性能下限，但很少单独改变检索质量上限。当前 Go 已提供高效、可维护的基础，第一版不以语言迁移作为优化方向。 | **低：基础保障层**     |

## 目标

每个大版本必须使信息组织质量、检索质量和端到端效率相对当前基线形成整体跃升。上升型核心指标优先争取至少翻倍，下降型错误、时延或资源优先争取至少减半；处于高基线时使剩余错误超大幅收敛。改善没有上限，小幅变化不构成大版本完成。

## 基线与边界

体系始终只维护一个当前有效内核基线。新方案先作为候选与它使用相同资产、输入、环境和评价边界竞争；未经验证不得覆盖基线或成为后续工作的隐含前提。

- 长期信息资产、稳定身份、明确语义和统一能力契约不因内核迭代而改变。
- 组织状态、关系、索引和检索表示属于可重建的派生状态；候选失败不得损坏资产或当前有效世代。
- 外部智能体继续负责主动检索方向、累计证据判断和结果组织；内核负责提供可组合的高质量检索能力，不内置替代外部智能体的检索智能。
- 不针对验收题目、答案、题型或表面形式增加规则，不以降低质量、缩小信息范围、隐藏成本或改变评分口径制造提升。
- 质量、时效和资源分别评价，不能相互补偿；架构复杂度必须由可验证收益证明。
- 基线与候选必须冻结相同的评测工具、模型、提示词、评分器、配置和环境；重复测量误差单独记录，超出误差的差异才能归因于候选。
- 候选与证据身份只绑定内核内容及其真实直接依赖，不绑定 Git 提交或全仓状态；无关变更不得使有效内核证据失效。
- 当前大版本不更换 Go 或基础运行时；只有证据证明基础设施阻断上层优化时，才单独立项处理。

## 智能化与代码固化边界

只有永久安全边界，或确定能被后续多个版本、多个候选直接复用的能力，才固化为代码；其余临时生成、判断和归因由智能直接完成。

通用代码只负责参数化执行、候选与评测条件冻结、角色和数据隔离、检查点恢复、失败关闭、版本级盲测封存与退役、聚合结果、组件级身份与精确证据失效，以及真实通用缺陷的回归保护。智能负责临时随机生成高质量数据、独立质量准入、覆盖选择、一次性探针、首个通用根因分析和下一优化路线；除版本级封存盲测外，临时内容在本次用途结束后只保留不可逆摘要和可泛化结论。

禁止为单个关卡、版本、题目或事故新增专用控制器、Schema 或执行路径；禁止把盲测题目、答案、Case ID、表面形式或诊断逻辑写入代码或普通仓库文档；禁止重复资格化直接依赖未变的模型、提示词和裁判；禁止用 Git 提交或全仓状态扩大证据失效；禁止因评测流程变化重跑未受影响的产品证据。为完成当前一次运行而产生的需求不得直接转化为代码，除非先证明它是长期不变量或可复用的通用能力，并以参数化实现替代场景特例。

## 大版本范围

每轮先依据端到端失败、性能剖析和当前基线证据审视全部方向，只把存在可证瓶颈和有效提升空间的方向纳入实施；已经足够优秀或没有限制整体结果的方向只承担保护，不为覆盖清单强行修改。跨层问题归入首个可证根因，同一根因只实施一次。

开始前冻结整体跃升目标、资源边界和不可退化能力。方向指标只用于定位和判断局部实现，不能代替最终证据片段、回答正确性和端到端性能。

## 证据分层

以下是内核演进方法内部的证据职责，不增加 Acceptance Suite 的正式证据层级：

| 证据             | 职责                                                                                 | 使用规则                                                               |
| ---------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 问题池           | 汇总正式测试、内部测试和真实运行暴露的失败，定位通用根因                             | 可以持续积累和复用；只能指导优化，不能证明泛化                         |
| 开发集           | 从问题池按根因选取最小代表集，以结构真实的端到端案例快速复现当前问题                 | 可以反复运行；只用于分钟级开发反馈，不承担晋升证明                     |
| 回归集           | 分层覆盖当前基线已经正确的任务类型、复杂度、关键结构和历史通用缺陷                   | 固定复用；不得挑选容易保护的样本，候选不得以修复新问题换取既有能力退化 |
| 版本级反拟合盲测 | 检查候选是否只适配已知样本或狭窄代理                                                 | 每个大版本按 5、15、25、50 题逐关生成并封存一套；下一大版本全部换新    |
| 正式验收         | 形成可复核的内部结果和社区基准结果                                                   | 只对已经通过前述证据的最终候选运行                                     |

开发集和回归集必须直接评价完整链路：所需事实是否被精确、完整、按正确时间和冲突状态交付，以及最终回答是否正确；资产 ID、局部召回或阶段代理只能用于诊断，不能作为关闭依据。社区失败只能抽象为通用缺陷，再独立构造与原事实、答案和表达不重合的内部案例。现有 V1 合成快速视图只保留诊断与局部保护价值，不能再承担方向关闭、整体跃升或泛化证明。

## 版本级反拟合盲测

盲测采用**统一生命周期、版本批次隔离、内容与运行解耦**的架构。跨版本只维护一套参数化的“生成—准入—冻结—运行—诊断—归档”能力；每个大版本建立独立评测批次，下一版本只创建新批次，不复制控制器、Schema 或执行路径。

- **评测策略**冻结题量、覆盖、质量、模型、门槛和成本，不承载具体题目。
- **盲测套件**保存四级内容、真值、覆盖清单和完整性身份，只绑定大版本与生成、准入策略；同一版本的候选变化不得使套件失效。
- **候选运行**绑定盲测套件、候选和评测条件，保存可恢复的执行与裁决证据；运行失败或候选变化只失效对应结果，不得改写套件。
- **诊断反馈**只输出可泛化根因与下一验证点，原始题目、真值、Case ID 和逐题输出始终由隔离评测侧持有。

套件准备是一次原子生命周期：一次生成全部四级内容，准入阶段只替换不合格题并复审完整集合，随后整体封存。封存后内容不可变；中断从检查点恢复，泄漏、内容变化或完整性损坏必须使整个批次失败关闭。大版本结束后批次归档并退出活动评测，不得带入下一版本。

独立流程为每个大版本依次准备 5、15、25、50 题四级闸门，每一级只生成一次并封存至该大版本结束；下一大版本必须生成全新套题。各级标准在生成前冻结，必须同时约束完整答案的绝对质量、证据充分性、时间与冲突正确性、性能边界及相对基线无实质退化，只在基线确有提升空间的指标上判断相对跃升。生成过程不得读取候选实现、候选输出、开发集、回归集或正式测试题，只能依据产品能力边界、公开任务定义和已经冻结的抽象缺陷类别；具体人物、事实、表达、顺序、时间、关系和干扰信息随机变化，四级累计必须广泛覆盖长会话、多事实、更新冲突、时间关系、多跳关联及无答案边界。

每级数据必须在接触候选输出前通过独立质量准入：任务结构、难度和干扰强度能够代表真实使用，事实、关系、时间线、答案与证据可机械校验且语义一致，并以已知正确与错误对照证明评分能够识别缺证、错证、过时证据和错误答案。准入只替换不合格题并对完整集合复审；整级通过后立即冻结，版本内不得增删、改题或依据候选结果重新生成。

每一级先运行候选；候选未达到绝对质量或性能门槛时直接失败，不再运行不能改变结论的基线。候选通过后，当前基线再运行完全相同的数据，用于判断相对跃升和既有能力退化。执行中一旦剩余题目即使全部通过也无法改变冻结门槛的判定，立即停止该级。单级只负责尽早拦截坏候选；整体跃升由四级累计结果判断，不能用单级小样本宣称泛化。

性能异常必须先区分内核退化与环境噪声。触发已冻结的单次硬超时或错误边界时直接失败；未触发硬边界的单个离群值不得单独否决候选、修改内核或展开长期调查。已有同身份充分样本证明整体达标时直接复用并停止；证据不足时只允许一次有界的充分样本复核。只有异常复现、整体分布越界或触发硬边界，才进入性能归因与优化。

任一级失败后，独立评价过程只向优化侧提供判定、首个通用根因、负责方向、受影响证据和下一验证点，不得泄露题面、真值、答案、Case ID 或逐题输出。通用根因进入问题池，并由独立路径构造与盲测事实、答案和表达均不重合的新开发或回归案例；禁止照题修改。候选退回完整迭代闭环并重新冻结后，使用本大版本已经封存的同一套关卡从 5 题级重新开始；下一大版本才更换整套数据。

封存数据只能由隔离评测入口读取，优化者和执行者始终不可见。同一候选、数据、标准和环境下中断时，从尚未完成的题目恢复；候选身份变化时只使旧执行结果失效，不使本大版本盲测数据失效。不得用选择性替换、重复运行取最好值或改变标准影响结论；四级全部通过后才允许进入最终测试，大版本结束后原始数据退出活动评测并不得带入下一版本。

## 迭代闭环

1. **归因**：沿完整链路定位首个可证根因，区分现象、根因和下游损失。
2. **选向**：按优先级、影响规模和提升空间确定本轮方向；没有真实瓶颈的方向不实施。
3. **定标**：冻结基线、端到端跃升目标、回归边界、成本上限和淘汰条件。
4. **设计与实现**：从第一性原理消除根因，建立不污染当前基线的独立候选，不以最小改动或既有投入限制方案。
5. **快速迭代**：使用开发集和受影响回归集取得分钟级反馈，只重跑失效部分；失败路线直接淘汰，不向主架构叠加补丁。
6. **整体验证**：所有实施方向对同一候选有效后，运行完整回归与内部端到端验证；只有整体大幅提升且无实质退化，才冻结候选。
7. **盲测**：对冻结候选运行版本级封存盲测；失败只输出通用反馈并返回完整闭环，禁止接触题目或照题调优。

单次开发集与受影响回归反馈以五至七分钟为目标、最多十分钟；超过边界先修复验证路径，不以缩小质量范围换取速度。

## 落地与成本边界

开发、回归和盲测必须复用 Acceptance Suite 的候选身份、直接依赖、原子检查点、局部失效和恢复能力，不建立平行验收体系。版本级盲测只是非正式候选闸门，不写正式 state，也不构成候选冻结后动态生成正式验收数据。执行入口未能机械证明数据职责隔离、基线可比、版本级封存、原始证据完整和失败后精确失效前，不得开始下一轮内核优化。

各级预算、并发和重复测量误差边界必须在版本套题生成前用非候选材料完成最小校准并冻结；直接依赖变化后只重校受影响部分。生成与准入成本只在本版本首次建立各级数据时发生，候选重验直接复用封存数据；相互独立的生成、准入和单侧题目执行使用经校准的有界并发，候选与基线不得因资源竞争破坏可比性。不能在成本上限内完成时先优化执行路径，不得放宽质量。

正常开发只运行十分钟内的失效部分；完整内部验证只对已有明显跃升的候选运行，版本级盲测只对内部验证通过的冻结候选运行，数小时社区基准只对四级闸门全部通过的同一候选运行。盲测失败路径在当前级立即停止；重新迭代后复用封存数据，但所有关卡结果从 5 题级重新产生。

## 持续调度接口

协调者负责整体进度、方向选择、候选裁决和工作包连续性，执行者负责工作包内的设计、实现和验证。每轮建立唯一任务文档，只维护基线、候选及其直接依赖身份、方向判断、目标、证据、当前根因、盲测级别和下一验证点；机器证据仍由 Acceptance Suite 保存，任务文档只引用。

每个工作包只处理当前价值最高的一条完整问题链，写清根因、方向、基线、跃升目标、保护边界、验证成本、完成证据和排除项。协调者独立复核结果；未通过盲测和整体验证不得关闭大版本。

## 大版本与最终验证

内部整体验证按验收体系运行当前候选所需的完整 frontier、固定内核和 Ownward 专项层，并复用仍然有效的证据。完整回归与端到端结果必须先证明质量和性能大幅提升、全部保护成立，才能冻结候选并进入版本级盲测；此时不得晋升当前基线。四级累计结果还必须一致支持泛化；固定开发集满分、局部指标翻倍或单级随机测试通过均不构成完成。

四级全部通过后保持候选不变，达到可运行社区基准的条件时，持续调度停止并向用户报告。完整 LongMemEval-S 只对该候选运行一次，其结果承担社区可比性，不能单独替代泛化证据；同一候选的内部、盲测和最终证据共同满足完成条件后，才由 Acceptance state 晋升当前基线。失败必须进入下一轮问题池，不以反复运行全量基准代替定位和修复。

验收体系中的基线身份和证据是晋升事实的唯一权威。每轮大版本状态由任务文档承载，关键决策进入[关键工作留痕](../records/README.md)，已晋升实现进入[检索体系演进](../modules/retrieval/README.md)；本文不记录实验过程和临时进度。
