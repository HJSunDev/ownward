# 提交规范

## 授权与提交时机

暂存、提交和本地历史整理须有用户明确授权，推送须单独授权。定时审视、阶段结束或准备冻结候选都不产生Git授权；任务中的既有明确授权按其范围执行。

在工作达到可独立交付的状态后审视实际变更，按[分支管理](../../.agents/skills/branch-management/SKILL.md)确定集成位置，避免成熟成果无故积压。没有可形成完整提交的内容时保留工作区，不靠提交次数表示进展。

## 提交拆分

先识别架构不变量，提交边界不能切开不变量。每个提交须可独立理解、构建、测试和回滚，不能依赖后续提交修复中间债务。在此约束内优先按功能边界拆分；同一合同的代码、测试及必要说明一起提交。用户明确要求合为一次提交时，仍须保证整体完整。

## 验证与候选

提交前核对暂存范围，排除无关、临时、运行态及敏感内容；验证必须覆盖实际提交成果，不能依靠提交外的改动通过。

候选须绑定可追溯的源码、构建输入、制品及验证依据。源码、配置或前提改变后，按[版本与证据规则](../workbench/cross-session-collaboration.md#52-独立复核)确定失效部分并补验；未变内容的有效证据复用。仅重整本地提交顺序且终态内容不变时，核对并更新身份绑定，不一律作废全部证据；对包含提交标识的制品另核实际影响。正式发布仍按产品交付合同重新确认身份一致性。
