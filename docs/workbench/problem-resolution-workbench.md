## 一、问题描述

Acceptance Suite 没有为“首个有效内核基线”阶段准确区分变更影响、执行资格、直接消费事实、候选制品、可比环境、结果聚合和单次执行选择。`targeted`、`core`、`frontier`、`qualification` 与 `promote` 所经过的计划、预检、配置、绑定、模块加载、检查点复用、失效和晋升分别硬编码了不一致关系，造成无关依赖阻塞当前步骤、有效证据被无效重跑，以及过期证据可能被复用。

该问题已经真实阻塞当前任务：内部 `preflight` 在没有配置 `community`、本阶段也明确禁止 LongMemEval‑V2 时，仍会访问其远程仓库。修复不能只删除这一条检查，否则当前阶段的后续步骤仍可能在相同根因下再次失败。

本问题只负责使首个内核基线阶段正确、高效地完成。LongMemEval‑V2 在本问题中只代表当前阶段不得读取、下载、校验、绑定或加载的后续能力；不得修改它自身的领域执行、数据、适配器、结果复用、官方提交或评分逻辑，也不得运行完整专项集、LongMemEval‑V2 和最终汇总。

## 二、问题定位

根因不是某一项检查本身无价值，而是当前内部阶段没有用一份带关系类型的权威定义分别回答“为什么运行、开始前需要什么资格、实际消费什么、什么变化会使结果失效、结果被谁聚合”。经逐条核对当前任务的完整执行链，问题范围如下：

1. **内部预检混入社区前置条件**
   - `benchmarks/acceptance/suite/preflight.py` 无条件读取社区适配器与固定版本，并通过 `git ls-remote` 访问 LongMemEval‑V2 官方仓库；返回结果还固定包含社区仓库可用性和版本。
   - 同一入口把来源于社区长任务的二十 GiB 空间门槛和四至八小时成本说明带入内部预检，即使当前阶段明确不执行社区层。
2. **预检与配置不是层级感知的**
   - `preflight` 不接收执行配置或目标层级，因而不能区分只使用冻结材料的前沿观察、无需外部智能的固定内核、需要外部智能体的专项集和最终社区基准。
   - 单独执行低层级验证时仍被迫准备后续层级的 Codex、模型或社区条件。
3. **候选绑定强制创建全部内部 scope**
   - `binding.py` 固定要求 `frontier`、`core`、`product` 同时存在，并在创建任何内部绑定前统一要求发布包、生产规模存储报告、Codex、候选二进制、向量能力包和前沿观察器。
   - 这与固定内核可以独立执行、普通开发只运行最低充分层级的体系原则冲突。
4. **公共候选身份与分层制品身份混为一体**
   - 候选提交和发布二进制被放在同一个全局绑定中；任一二进制变化都会使包括前沿观察在内的所有检查点失效。
   - 前沿观察实际消费的是与候选提交一致的观察器和冻结输入，不消费发布二进制；固定内核、专项集和社区基准才真实消费发布二进制。
   - 当前配置还把 core 实际需要的候选二进制与向量能力、product 才需要的发布包、生产规模报告和 Codex 混在同一个 `product` 区段，无法形成最低充分配置。
5. **环境依赖归属错误**
   - 前沿观察器只使用冻结向量和冻结语义，不消费真实 Embedding Bundle；当前环境清单却对全部 scope 都校验和绑定真实模型与运行时，使模型缺失或变化错误地阻塞、失效前沿观察。
   - 固定内核、专项集和社区基准真实使用候选向量能力，其对应绑定仍然必要。
6. **输入与工具清单存在过度绑定和漏绑**
   - 每个 scope 都直接绑定包含全部层级内容的 `contract.json`、`adapters.json` 以及混合了各层分支的共享执行文件；社区专属逻辑变化会使内部 scope 摘要变化，破坏局部失效。
   - 固定内核适配器实际导入 `benchmarks/support/ownward_mcp.py`，但 core 工具清单没有绑定该文件。
7. **入口提前加载所有层级实现**
   - `run.py` 在启动时无条件导入 `frontier`、`execution` 与 `preflight`，`execution.py` 又无条件导入 `community` 与 `product`。即使执行 core 或 frontier，后续层代码仍会被读取和解释。
   - 当前工具清单既没有完整绑定这些实际提前加载的模块，也无法阻止后续层代码的局部错误阻塞内部低层执行；仅修改清单不能消除这一运行时耦合。
8. **变更影响计划把日常反馈、候选晋升和最终验收混为一次计划**
   - `retrieval` 当前同时计划 `targeted` 和完整 `frontier`，而普通检索迭代按定稿体系只需受影响阶段的定向观察。
   - `organization` 当前直接计划 `targeted`、`core`、完整 `frontier` 和 `qualification`，把只有准备晋升基线时才发生的高成本步骤下沉到每次修改。
   - `asset` 只计划 core，却同时返回不会被执行的前沿阶段列表，计划结果自相矛盾。
   - “准备晋升内核基线”“候选稳定”和“最终候选”属于阶段触发，不应由普通代码影响类型自动推导，否则会重现无价值的完整验收和社区长任务。
9. **执行资格关系本身存在错误**
   - `contract.json` 要求完整 `frontier` 必须已有 `targeted` 检查点，但定向观察只是开发反馈，不是完整前沿观察成立所需的证据；首次建立基线或定向结果失效时，完整观察仍应能够独立运行。
   - qualification 在开始和基线晋升时必须确认当前 core 与 frontier 资格，但资格检查不等于把前置报告内容写入 qualification 的直接证据身份。
10. **定向执行选择没有进入检查点身份**
   - `frontier.targeted_stages` 不属于稳定材料和基线身份是正确的，但当前检查点也没有记录本次阶段选择。
   - `execute` 在进入观察器前先复用同 scope 的旧 `targeted` 检查点，可能把针对另一组阶段的结果当作本次定向验证；已计算的 `_config_sha256` 也没有参与判定。
11. **失效语义互相矛盾且原方案把资格门槛误当成内容依赖**
   - `invalidate` 按执行顺序向全部后续模式传播，`rebind` 主要只删除同 scope 结果，Suite README 又写成“某层变化只失效该层和最终汇总”，三处语义不一致。
   - qualification 不读取 frontier 或 core 报告内容；它们是开始资格与晋升资格。只要同一候选下 qualification 的直接输入、环境、工具和逐场景证据未变，重新取得当前资格后不应重复八场景执行。
12. **基线晋升没有完整保存并验证当前 core 证据**
   - `promote_baseline` 只检查 frontier 与 qualification；在重新绑定失效传播不完整时，即使当前 core 检查点已经不存在，旧 qualification 仍可能参与晋升。
   - 晋升记录只保存 frontier 与 qualification 报告，没有保存 core 报告摘要与可复核快照；现有测试也把这一缺口固化为预期。
13. **直接说明与机器契约已经漂移**
   - Suite README 声称候选二进制属于全部层共享身份，并声称某层绑定变化只使同层与汇总失效；这与实际消费边界、机器失效规则和定稿体系的“只重跑受影响证据”均不完全一致。
   - 修复实现而不同时修正直接说明，会使后续执行者再次按错误流程恢复全局准备或无效重跑。
14. **前沿观察器制品身份与可比环境身份混为一体**
   - `binding.py` 把随候选提交重新构建的前沿观察器摘要写入 frontier 环境清单，而 `frontier.compare` 要求候选与基线的环境完全一致；正常的新候选观察器因此可能被误判为环境变化，阻止跨候选比较。
   - 观察报告已经分别提供 `tool_sha256` 和 `environment`，说明观察器制品与硬件、操作系统、运行时和测量配置本应是两个身份维度：前者必须与当前候选绑定并允许随候选变化，后者才用于判断候选与基线是否处于可比环境。
15. **专项资源中间证据复用身份不完整**
   - qualification 会先取得产品资源准入报告；已有报告目前只核对候选提交、发布二进制和自身原始文件完整性，没有核对当前 product scope 的环境、输入与工具身份。
   - 报告虽记录阈值和生产规模报告摘要，复用时却没有与当前文件及发布包重新对应；同一候选下外部制品、阈值、资源工具或生产规模证据变化后，旧资源结论仍可能被带入八场景资格集。

上一次问题复查只沿“运行时条款确认”这一具体链路检查，随后对 `f176a09` 的复查又只证明内部绑定没有生成 `community` scope，没有以“依赖只能约束真实消费它的阶段”审查预检、清单和生命周期全链路。预检测试反而模拟并接受了远程 Git 校验，因此局部测试通过掩盖了体系边界错误。

以下内容不属于本问题的修改范围，必须保持原状：

- Ownward 的本地模型进程只在首次向量请求时启动；模型不可用会形成可见的降级状态，不阻断长期资产和稳定身份读取。
- Ownward 专项资格集真实消费 Codex、正式向量能力、发布制品和资源证据；这些依赖必须在 qualification 被严格验证。
- 完整专项集、LongMemEval‑V2 与最终汇总的固定材料、配置、适配器、执行、缓存、评分、提交和正式校验逻辑均不属于当前修复；只确保它们不会在本阶段被访问或触发。
- 社区阶段对本地官方仓库固定提交、清洁状态、数据、协议和提交产物的校验仍属正式社区证据边界，不得删除或放宽。
- 固定内核、专项集与社区基准确实必须绑定同一候选提交及它们实际运行的同一发布二进制；修复只把不消费该二进制的前沿观察从二进制身份中分离。
- 前沿观察器仍必须由对应候选提交构建、记录摘要并在执行时验证；修复只禁止把该候选制品摘要冒充跨候选可比环境，不会放松观察器完整性或环境校准要求。

当前尚未执行该远程检查，也未启动正式验收。第二轮候选 `ea5a8c7` 的独立仓库、二进制和 Embedding Bundle v3 已准备完成，但阶段状态已在预检前标记为阻塞。

## 三、对抗式复盘问题价值（站在对立面思考问题是否成立）

最强反方观点有五项：

1. 一次准备全部内部和社区依赖可以更早暴露未来问题，减少入口数量；
2. 将完整契约、共享执行代码和全部运行环境绑定到每个 scope 更保守，似乎能避免漏绑；
3. qualification 执行前已经检查过 core，因此晋升时不必再次确认，scope 变化也可以依靠人工判断是否重跑。
4. 按执行顺序向后全部失效最稳妥，宁可重跑也不应冒险复用旧证据。
5. 把观察器摘要放进环境身份更严格，可以确保执行文件变化时不复用旧结果。

这些观点不能支持当前实现：

- 提前发现未来条件不等于把未来条件设为当前层的成立门槛。社区网络、发布制品或外部智能状态不会改变冻结前沿观察与固定内核证据的真实性。
- 过度绑定会把无关变化变成失效和重跑，漏绑则使证据无法复核；两者都不是保守，而是依赖身份不准确。
- 已有检查只有在其候选、输入、环境、工具和全部前置证据仍然有效时才成立。依靠历史执行顺序或人工记忆无法保证中断恢复与长期复核。
- 最终社区阶段已有自己的正式校验；当前阶段提前访问社区既不能形成社区证据，也违反本任务边界。
- “曾经满足开始资格”与“结果实际由该前置报告计算而来”不是同一关系。高成本结果仍绑定同一候选和全部直接事实时，重新确认当前资格即可继续使用；无差别向后删除既不增加真实性，也会破坏高效复用。
- 严格绑定不等于混淆身份：观察器摘要必须作为当前候选的执行制品独立校验，但跨候选比较只应要求真实测量环境一致。把必然随候选变化的制品摘要纳入环境相等条件，会让任何正常迭代都无法比较，既不增加真实性，也破坏基线用途。

因此问题真实成立。最优修复不是重构整套最终验收，而是完整修正当前内部基线链路的关系与证据身份，同时以隔离测试证明后续层不会被触碰；既不能只修眼前一行，也不能借机修改未来社区验收。

## 四、问题解决预期

- 当前阶段涉及的变更影响计划、模式对应 scope、执行资格、直接输入、候选制品、可比环境、工具、单次执行选择和基线聚合关系由一套带类型的权威定义驱动；预检、绑定、复用、失效和晋升不得再把不同关系混为顺序链。
- 每次预检和绑定只处理本次明确启用的内部层级及其真实依赖：
  - frontier 只依赖冻结材料、观察器及其真实执行环境；
  - core 只依赖候选产品路径、正式向量能力、固定内核材料及其实际执行工具，不依赖 Codex 或社区材料；
  - product 在 core 与 frontier 有效后才依赖 Codex、专项材料、正式向量能力、发布与资源证据；
- 未启用的层级不得被读取、探测、下载、校验、绑定或写入当前阶段报告；其缺失和变化不得阻塞当前层或使当前层证据失效。
- 每个 scope 的输入、环境和工具清单必须既不遗漏实际消费的事实，也不包含无关事实；更改任一直接依赖时，只失效该层及实际聚合其结果的产物。
- frontier 必须分别维护候选观察器制品身份与跨候选可比环境身份：观察器摘要绑定并验证当前候选，允许随候选变化；只有硬件、操作系统、运行时和测量配置等真实环境事实参与候选与基线的环境一致性判断及重新校准。
- qualification 复用的资源报告必须绑定并重新核对当前 product scope、发布包、阈值、生产规模报告及资源测量工具，任何直接事实变化都不得复用旧报告。
- 执行资格只控制一个模式能否开始或关键结论能否形成，不自动污染当前证据身份；已完成结果仍与候选和全部直接事实一致时，不得仅因后来重新取得资格而重跑。
- 定向阶段选择必须成为该次定向检查点的一部分，但不得进入固定材料、完整 frontier 结果或有效基线身份。
- 日常变更只计划最低充分反馈；完整 frontier 与 qualification 只由本次“建立内核基线”阶段触发，完整专项、LongMemEval‑V2 和最终汇总不得由当前任务触发。
- 基线晋升必须重新验证同一当前候选的 core、frontier 和 qualification 检查点、绑定及原始证据全部有效，并把三项报告纳入可复核晋升记录，不能依赖“曾经按顺序运行过”的隐含事实。
- 内部阶段能够完全脱离 LongMemEval‑V2 成立；修复不得改变社区层自身的任何行为。
- 修复只作用于当前内部基线链路的验收实现、直接说明和本阶段失效状态，不改变验收材料、真值、评分、成本标准、产品代码、内核行为、整体架构、模块职责、完整专项或社区验收，也不得提前运行任何正式证据层。确需修改被后续模式共用的基础函数时，既有合法最终验收配置在相同输入下的可观察行为必须保持不变；只允许因证据身份校验更完整而拒绝原本不应复用的过期中间产物。

## 五、问题解决方案

1. **建立当前阶段唯一、带类型的执行关系定义**
   - 对 `targeted`、`core`、`frontier`、`qualification` 与 `promote` 分别定义影响类型到最低反馈、阶段触发、模式到 scope、执行资格、scope 直接事实、单次选择和基线聚合；不同关系不得共用无类型“前置图”。
   - 当前阶段的计划、预检、配置验证、绑定、检查点身份、当前性验证、失效和晋升统一读取该定义；完整专项、community、LongMemEval‑V2 与最终汇总保持现状，不进入本次行为修改。共享入口和生命周期函数只增加当前内部模式所需的分层分派，不得改写其他模式的既有关系。
   - 三层标准、固定材料、真值、评分、成本值和最终执行次序保持不变。
2. **修正最低充分计划与阶段触发**
   - `local` 不启动 Suite；`asset` 运行 core；`retrieval` 与 `organization` 只返回各自受影响阶段的 targeted。一次修改同时影响多个方面时合并显式影响类型，不暗中追加更高阶段。
   - 完整 frontier 与 qualification 只由“准备晋升内核基线”阶段触发；当前任务不得计划或执行完整 product、community、LongMemEval‑V2 与 summarize。
   - 完整 frontier 可独立运行，不再要求已有 targeted；高成本阶段开始前仍严格验证其当前资格。
3. **使预检按本次执行配置工作**
   - `preflight` 接收并验证当前执行配置，只检查本次启用 scope 的真实依赖和对应资源预算。
   - 内部配置不得读取社区适配器、访问远程 Git、要求 LongMemEval‑V2 文件、返回社区字段，或使用社区长任务推导的二十 GiB 与四至八小时说明。
   - 本次不重写社区预检；只保证内部配置不会导入或调用它。未来社区阶段原有正式校验保持不变。
4. **使配置与绑定按实际启用 scope 增量建立**
   - 配置显式声明本次模式或 scope，并把候选提交、候选运行制品、product 专属资源与 community 专属资源分开；低层配置不再被迫填写后续层字段。
   - 候选提交是全部层共享身份；发布二进制只进入真实执行它的 core、product 与 community scope，frontier 以同提交构建的观察器作为自身制品身份。观察器摘要不得并入跨候选必须相等的环境身份。
   - 只为当前配置启用的 scope 生成绑定，不再强制 `frontier`、`core`、`product` 同时存在。
   - 缺少未启用 scope 只在执行真正消费它的模式时拒绝，不得阻塞当前内部模式。
5. **隔离实际模块加载与执行入口**
   - 唯一 CLI 入口保留，但按所选命令和模式延迟导入对应实现；core、frontier 或内部 preflight 不得读取或解释 community 模块，frontier 不得加载 product 模块。
   - 执行模块按层拆分或延迟加载，确保运行时实际 import 闭包与该 scope 工具清单一致；后续层代码缺失或损坏不得阻塞不消费它的低层。
6. **校正每个 scope 的清单边界**
   - frontier 不再校验或绑定真实 Embedding Bundle；分别绑定冻结输入、当前候选观察器制品和真实测量环境。观察器摘要通过工具/制品身份校验，真实环境身份只包含硬件、操作系统、运行时和测量配置；候选与基线比较只要求后者一致，环境变化仍按校准规则处理。
   - core 绑定候选二进制、相邻正式向量能力、固定内核材料、core 适配器、进程控制及实际使用的 `benchmarks/support/ownward_mcp.py`，不绑定 Codex、产品专项或社区材料。
   - product 继续绑定 Codex、专项固定材料、正式向量能力、实际资源与发布证据及其全部执行工具。
   - 对包含多层内容的 `contract.json`、`adapters.json` 和共享执行代码采用与当前内部 scope 对应的规范化投影，或拆分真正独立的内部实现，使后续层专属变化不会改动当前 scope 摘要；不得修改后续层实际消费的材料或工具清单。
7. **补齐单次执行身份**
   - targeted 检查点除 frontier scope 绑定外，还记录规范化的 `targeted_stages`；复用、恢复和报告校验必须与本次选择完全一致。
   - 该选择只决定当前定向结果，不写入固定材料、完整 frontier 绑定或有效基线；删除无实际用途的全配置摘要，避免以全配置变化制造无关失效。
8. **封存专项资源中间证据**
   - 资源报告写入当前 product scope 的环境、输入和工具摘要，并绑定发布包、阈值、生产规模报告及资源测量适配器的实际摘要。
   - qualification 复用资源报告前逐项与当前绑定和文件核对；不一致时只使资源报告及消费它的当前 qualification 结果失效，不得把旧报告重新包装成当前证据。
9. **按真实消费关系统一当前阶段失效、资格复核和晋升**
   - `rebind` 只删除当前内部 scope 直接变化的模式、实际嵌入该结果的内部聚合产物和包含受影响报告的有效基线；不得仅因执行顺序靠后而删除直接事实未变的 qualification。
   - `invalidate` 必须声明当前内部层级的失效原因，区分直接事实、开始资格和基线聚合；不能沿执行先后无差别传播。
   - 高成本模式开始前重新验证当前资格；恢复和关键结论形成时也复核必要资格。资格重新成立且结果全部直接事实未变时，旧高成本证据继续复用。
   - `promote_baseline` 明确要求当前绑定下的 core、frontier 和 qualification 全部存在、通过且原始证据仍有效；晋升记录保存三项报告摘要与可复核快照，缺失、过期或跨候选结果必须拒绝。
10. **以当前阶段关系矩阵测试封死同类回归**
   - 为每个 scope 增加正反两类测试：删除任一真实依赖必须在消费它之前失败；删除、修改或禁止访问无关依赖不得影响当前层。
   - 测试内部预检不存在网络、Git 远程和社区文件访问；frontier 不需要模型；core 不需要 Codex、发布包或社区；qualification 不需要社区。测试同时断言社区执行文件、配置和材料没有被本次修复改写。
   - 对每个 scope 的输入、环境、工具和 import 清单做消费闭包测试，防止漏绑实际使用文件、绑定未消费文件或提前加载后续层。
   - 验证 frontier 观察器摘要变化会使当前候选观察证据失效，但不会被报告为环境变化；同一真实环境中的不同候选能够比较，真实环境变化仍会拒绝比较并触发既定重新校准路径。
   - 验证资源报告的任一直接身份变化都会拒绝复用，全部身份不变时 qualification 可以复用该报告。
   - 验证影响计划只产生最低充分步骤，阶段触发只产生对应正式步骤；验证不同 targeted 阶段不可互相复用。
   - 分别验证当前阶段的资格门槛、直接事实和基线聚合关系：资格缺失阻止新的 qualification 执行或晋升，但不删除直接事实未变的 qualification 证据；直接事实变化精确失效相应内部模式。
   - 验证缺少当前 core、frontier 或 qualification 时无法晋升，晋升记录同时包含三项有效报告。
11. **统一当前阶段说明并以最小验证收口**
   - 只同步修正 Suite README 中直接涉及内部执行的说明、内部执行示例和本阶段任务说明；不得改写完整专项、LongMemEval‑V2 与最终汇总说明，不得修改定稿验收体系、产品交付边界或模块架构。
   - 只运行 Suite 静态检查、相关单元测试和按 scope 隔离的非正式预检，证明关系隔离、完整绑定、精确失效和晋升防线真实可执行；不得运行固定内核、完整前沿、资格集、完整专项集、LongMemEval‑V2 或最终汇总。
