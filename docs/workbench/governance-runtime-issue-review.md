# 自主治理运行时问题核查

> 临时文档：只保存本轮事实核查与判断；不属于权威依据，不修改治理体系或产品实现。

## 核查基准

自主治理闭环必须同时做到：主 Agent 是唯一实现者；Governor 从宏观视角独立判断当前路径是否必要、高效且最优；确定性运行时跨上下文保存工作包、证据与阻塞事实，并让合法的人类输入能够回到闭环。除真实产品决策或无法自行取得的外部输入外，任务应自主持续推进。

## 已解决问题

### 1. 合法用户输入无法确定性地解除暂停

**发生场景**

持续开发遇到真正需要用户决定的产品问题，或者缺少无法自行取得的外部条件。Governor 暂停主任务并提出最小问题，用户随后给出明确答复。

**预期流程**

```text
Governor 请求用户输入
→ 系统保存暂停原因
→ 用户回答
→ 回答与原问题绑定
→ Governor 根据新事实复核
→ 生成获批工作包
→ 主 Agent 继续开发
```

即使中途发生上下文压缩，系统也应知道用户回答了哪个问题，并从正确位置继续。

**实际流程**

```text
Governor 请求用户输入
→ 系统进入暂停状态并清空当前工作包
→ 用户回答
→ 主 Agent 能收到并理解答复
→ 治理状态仍停留在原暂停状态
→ 用户答复没有与原暂停事项绑定，也没有进入新的复核请求
→ Governor 没有可跨上下文核对的新事实
→ 产品修改仍被 Hook 阻止
```

这不是 Codex 收不到用户消息，也不是绝对无法继续：在当前对话尚完整时，主 Agent 可以依赖对话记忆手工重新请求 Governor 复核。但该做法没有正式状态转换，压缩或恢复后不能可靠重建，因此不属于确定性、可审计的治理闭环。

**原因映射**

- Governor 返回 `product_decision_required` 或 `external_input_required` 后，`apply-review` 会清空当前工作包，把状态置为对应暂停状态，并把所需输入写入 `next_action`。
- 后续 `UserPromptSubmit` 只返回当前状态说明，不保存用户答复、不创建包含答复的复核请求，也不执行恢复转换。
- `SessionStart` 虽能再次创建固定复核，但复核请求 Schema 没有承载本次用户答复的字段；CLI 也没有消费答复并恢复任务的操作。
- 非读取工具在暂停状态下继续被 Hook 阻止。

这些底层缺口最终形成的业务问题是：**治理体系能够把问题交给用户，却没有把用户答复持久化并经过复核后恢复主任务的正式入口。**

从主 Agent 视角，它看到了答复却无法正式恢复；从 Governor 视角，它没有收到能够核对的新事实；从体系整体视角，唯一合法的人类介入场景只有暂停出口，没有恢复入口。

**目标状态**

用户提供所需输入后，系统应将安全、必要的答复事实绑定到原暂停事项并重新交给 Governor 判断；Governor 确认后恢复获批工作包，主 Agent 自动继续。不得依赖单次对话记忆，也不得把凭证等敏感内容本身写入治理状态。

**解决方案**

只补齐现有单一治理状态机的暂停恢复链路，不新增任务管理体系，也不修改产品架构：

1. Governor 返回 `product_decision_required` 或 `external_input_required` 时，在 `state.json` 中原子建立唯一 `pending_intervention`，绑定原 `review_id`、输入类型、最小问题和处理状态；保留当前工作包及其连续性事实，由暂停状态统一禁止产品修改，不再清空工作包。
2. `UserPromptSubmit` 在存在待处理事项时只向主 Agent 注入事项身份和处理规则，不自行判断每条用户消息都是答案，也不自动保存原始消息。用户只是追问时维持暂停；用户真正给出答案时，由主 Agent 调用唯一的 `resolve-intervention` 操作。
3. 新增唯一的 `resolve-intervention` 治理操作，并把它作为暂停期间可执行的精确治理命令纳入 Hook 放行范围；其他产品写操作继续被拒绝。该操作必须校验当前 `intervention_id`，只保存准确保留用户决策语义的安全摘要、来源 `turn_id` 和必要证据引用，并原子生成包含该解决事实的新 Governor 复核请求。密码、令牌、密钥及其他凭证原文不得写入状态、事件或复核材料；此类事项只记录“已由用户在外部配置并经指定方式验证”的事实与证据。
4. Governor 重新判断解决事实：信息不足时继续保持暂停并给出新的最小输入；信息充分时返回 `continue` 或 `replan`。只有有效结论通过现有身份、Schema 和哈希校验后，`apply-review` 才清除待处理事项并恢复运行；`continue` 恢复原工作包并只更新批准令牌，`replan` 才建立新工作包。
5. 将待处理事项、解决摘要和复核身份纳入状态与复核请求 Schema，使用户答复后立即压缩、关闭或恢复会话时，`SessionStart` 仍能从同一事实继续，不能依赖聊天历史猜测。
6. 用隔离自检覆盖完整业务链：追问不解除暂停、有效答复触发复核并恢复、答复后压缩仍可恢复、过期或错误事项身份被拒绝、复核前产品修改仍被阻止、原工作包连续性不丢失、任何治理产物都不含敏感原文。

这是唯一推荐路径：Hook 只负责确定性提示和拦截，主 Agent 负责理解用户是否已经回答，Governor 负责判断输入是否足够，运行时只负责绑定、持久化和状态转换，职责没有交叉。

**修复状态：已完成并验证。** 运行时现在保留被暂停工作包、持久化唯一待处理事项，通过 `resolve-intervention` 绑定安全答复并生成新复核；隔离自检已证明追问不落盘、错误事项身份被拒绝、答复可跨恢复复核并恢复原工作包。

**最强反方与结论**

反方可以认为主 Agent 在当前对话中重新执行 `request-review`，并把用户答复交给 Governor 即可继续。这条临时路径确实可能成功，所以本问题不是绝对死锁；但它没有把答复与原暂停事项形成持久、可校验的正式状态转换，压缩后不可恢复，也无法拒绝过期答复。因此问题作为跨上下文治理契约缺口真实成立。

方案可以在现有 Hook、CLI、状态 Schema 和 Governor 复核链内完整实现，不依赖 Codex 平台新增能力。它不会自动采信用户消息，不会保存敏感原文，也不会绕过 Governor；修改范围只涉及治理运行时及其直接契约和自检，不改变 Ownward 产品定位、产品代码、模块职责或正式能力。问题成立，方案有效、范围最小且可长期恢复。

### 2. `continue` 会错误重建工作包并丢失连续性事实

**发生场景**

主 Agent 正在执行一个已经批准的工作包。发生任务恢复、上下文压缩或其他固定复核后，Governor 判断当前路径仍然必要、高效且最优，因此返回 `continue`。

**预期流程**

```text
原工作包持续执行
→ 触发固定复核
→ Governor 判断继续
→ 只更新批准令牌
→ 保留开始时间、已有证据、检查点和失败历史
→ 主 Agent 从原位置继续
```

`continue` 应当意味着工作没有换目标、没有换路径，也没有重新开始。

**实际流程**

```text
原工作包持续执行
→ Governor 返回 continue
→ 运行时重新创建工作包
→ 开始时间被刷新
→ 最近证据、检查点和失败记录被清空
→ 主 Agent 得到一个看起来刚刚开始的任务
```

独立证据仍然保存在 `reusable_results`，但当前工作已经进行到哪里、最近何时取得进展、同类失败是否重复等连续性事实丢失了。

**原因映射**

- `apply-review` 把 `continue`、`replan` 和 `stage_complete` 合并处理，三者都会调用 `packetFromProposal` 新建工作包。
- 新建过程会重置 `started_at`，并使 `last_evidence_at`、当前检查点和失败签名回到空值。
- 固定复核会在启动、恢复和上下文压缩后反复发生，因此正常的继续决定会反复刷新这些事实。

这些底层状态重置最终形成的业务问题是：**Governor 明明批准继续原任务，系统却把它记录成重新开始，使监督体系逐渐失去判断重复失败、停滞和无价值投入所需的连续事实。**

从主 Agent 视角，恢复后的任务看似刚开始，容易重复工作；从 Governor 视角，下一次复核无法区分真正的新工作与旧路径的延续；从体系整体视角，防止主 Agent 长期钻牛角尖的核心能力因此被削弱。

**目标状态**

`continue` 必须保留原工作包的开始时间、最近证据、检查点、失败历史和其他连续性事实，只替换本次复核产生的批准令牌。只有真正换路的 `replan`，或者进入下一阶段的 `stage_complete`，才能建立新工作包。

**解决方案**

将当前合并处理的三种决定拆成语义唯一的状态转换，不新增状态权威，也不改变主 Agent 与 Governor 的职责：

1. 收紧复核结果 Schema 和校验规则：首次建立工作包使用独立的 `start`；`continue` 不得携带 `next_work_packet`，必须通过当前复核快照绑定现有工作包的 `packet_id` 与 `plan_hash`；`replan` 和 `stage_complete` 仍必须提供符合契约的新工作包。
2. `apply-review` 收到 `continue` 时，先确认当前工作包存在、身份与计划未改变、复核快照仍有效；随后只替换 `approval`，并将状态恢复为 `running`。原工作包的 `started_at`、`last_evidence_at`、当前检查点、检查点到达状态、失败签名及其他执行事实必须原样保留。
3. `replan` 只在 Governor 明确换路时使用：保留仍有效的独立结果，按新提案建立新工作包。`stage_complete` 只在当前条件证据充分时关闭当前阶段、登记完成证据并建立下一工作包。两者不得再与 `continue` 共享重建分支。
4. 同步更新 Governor 契约和直接说明，使 Governor 在路径不变时只能返回 `continue`，不能通过重新提交相同提案伪装继续；目标、范围、路径或检查点发生变化时必须明确返回 `replan`。
5. 增加隔离自检：首次复核只能通过 `start` 建立工作包；预置已经运行一段时间且包含证据、检查点和失败历史的工作包，多次执行固定复核与 `continue` 后，除批准令牌和复核状态外全部连续性事实保持不变；`replan` 与 `stage_complete` 分别只产生各自允许的转换；旧快照、错误工作包身份和变更后的计划继续失败关闭。

该方案直接修复错误的状态转换，不依赖恢复算法补猜历史，也不触碰 Ownward 产品实现。它与第一个问题的恢复链路兼容：用户输入经复核后返回 `continue` 时，同样恢复原工作包而不是把任务伪装成重新开始。

**修复状态：已完成并验证。** 首次工作包改由 `start` 建立；`continue` 不再接受替换工作包，只刷新批准令牌。隔离自检已证明开始时间、最近证据、检查点和失败历史在固定复核及用户介入恢复后保持不变。

**最强反方与结论**

反方可以认为每次复核都会产生一次新批准，因此新建工作包是合理的。但批准代次与工作包身份不是一回事：路径改变应使用 `replan`，阶段改变应使用 `stage_complete`；`continue` 的语义就是保留原工作包。问题真实成立。

## 已裁决问题

### 3. Governor 没有被确定性地隔离于主 Agent 的历史上下文

**裁决：误判，问题不成立，不实施修复。** 以下内容保留为判断轨迹，避免后续再次把“独立判断”错误等同于“隔离全部历史背景”。

**发生场景**

主 Agent 启动或恢复持续开发，或者在执行中完成一次上下文压缩。治理 Hook 要求暂停产品工作并启动 Governor，从宏观视角复核当前路径是否必要、高效且最优。

**原假设中的预期流程**

```text
主 Agent 当前思路与执行历史
→ Hook 生成只含稳定事实索引的复核请求
→ 以不继承主线程历史的独立上下文启动 Governor
→ Governor 从产品依据、完成条件、仓库和原始证据重建判断
→ 最后才读取主 Agent 状态并比较
→ 返回继续、换路或完成结论
```

Governor 必须能够真正跳出主 Agent 的局部视角。主 Agent 的对话历史只能通过已经持久化并可复核的状态、证据和用户决策进入判断，不能预先成为 Governor 的背景叙事。

**原假设中的实际流程**

当前 Hook 指令只要求主 Agent 启动名为 `governor` 的子 Agent、传入复核请求路径并等待结果；父子交互规范也没有固定子 Agent 的上下文继承方式。在当前 Agent 接口未显式指定时，子 Agent 默认继承主线程上下文。

```text
主 Agent 已经形成局部判断
→ 启动 Governor
→ Governor 在读取复核请求前已经接触主线程历史
→ 再按指令尝试独立重建事实
```

因此它是独立线程，却不一定拥有独立的认知起点。主 Agent 若已经钻入错误或低效路径，Governor 可能受到同一套问题框架和中间结论的锚定，削弱体系用外部宏观视角纠偏的核心能力。

**原误判依据**

- `reviewInstruction` 只规定启动、等待和结果落盘，没有规定以空白父线程历史启动 Governor。
- 父子交互规范把“独立子会话”当成“独立判断”，但没有把不继承主线程历史落实为调用参数和可验证契约。
- Governor 配置虽然要求先读权威依据、最后读状态，但无法撤销启动时已经进入上下文的主线程叙事。

这些底层缺口形成的顶层问题是：**体系建立了第二个判断者，却没有完全建立第二个独立观察点。**

**原拟议目标**

Governor 每次复核都从空白的父线程历史启动，只接收复核请求路径和自身固定职责；所需事实全部从权威文档、仓库、状态与原始证据读取。它完成独立判断后再与主 Agent 工作包比较，使纠偏结论不依赖主 Agent 当前叙事，同时不丢失任何已经正确持久化的用户决策和执行证据。

**原拟议方案（不执行）**

1. 主 Agent 启动 Governor 时必须显式使用不继承父线程历史的调用方式，只把复核请求路径作为任务输入；不得依赖 Agent 接口的默认上下文行为。
2. 将这一调用约束同步写入 Hook 注入指令、父子交互规范、Governor 宏观复核规范和可复用模板，确保首次启动、固定复核、事件复核及用户介入后的复核采用同一入口。
3. 保留现有原生返回、等待、Schema、身份、快照哈希和落盘链路；本问题不改变状态机、工作包或产品实现。
4. 增加一次最小真实链路校验：在父线程放置不进入复核请求的唯一标记，确认 Governor 无法读取该标记，同时仍能从请求路径完成复核并经原生通道返回有效结果。文字约束和模拟单元测试不能代替这项上下文隔离证据。

**处置状态：无需修复，禁止据此引入强制空白上下文。**

**最终裁决与依据**

问题不成立。此前把两件不同的事混为一谈：Governor 需要独立形成判断，但不需要隔绝主任务已经拥有的事实背景。用户所经历的真实失效并不是主 Agent 无法识别错误，而是它沉浸在局部执行时缺少一次固定触发的宏观复核；一旦被提醒，它能够依据同一背景立即识别低效路径。治理闭环真正要补的是视角切换与复核触发，而不是制造一个缺少背景的观察者。

当前 Governor 契约已经要求它先从产品目标、权威依据、仓库与原始证据重建事实，把主 Agent 的状态和结论只当作待验证声明，独立判断当前路径是否必要、高效且最优，并在存在更优路径时明确纠偏。这已经建立了独立判断所需的职责、证据优先级和审查顺序。

强制以空白父线程历史启动反而会丢失用户已经说明但尚未完全结构化沉淀的背景，增加重复读取、误解语境和无效成本；它不能证明判断更独立，只能证明信息更少。因此不得实施上述原拟议方案。以后只有出现可复现证据，证明 Governor 因继承主 Agent 的结论而忽略权威事实或无法纠正低效路径时，才能重新登记为新问题；不能仅凭“继承上下文可能产生锚定”再次启动改造。

## 未登记为问题的事项

- **单主线任务没有额外会话绑定**：当前体系只服务一个持续主线，状态已经以唯一 `run_id` 和主线入口激活；在未引入并行主线前，这不是现实阻塞。
- **部分事件复核需要主 Agent 主动申报**：路径价值变化、代表性探测完成等包含开放语义，不能强行交给 Hook 猜测。运行时已提供 `request-review`，固定复核又提供周期性兜底；在没有实际漏触发证据前，不把“不是全部自动判断”视为独立缺陷。

## 最终判断

治理机制的总体设计成立，主 Agent、Governor 与确定性运行时的职责没有冲突。前两个真实闭环缺口已经统一修复；“Governor 必须隔离主线程历史”已经裁决为误判，不构成待修复事项。现有机制应保留共享事实背景，同时依靠独立职责、证据优先级和固定审查顺序保证独立判断，不再为追求形式上的空白上下文增加复杂度。
