# 开发工作台

## 一、用户提示词

### 审查工作留痕体系

```text
以乔布斯式产品直觉和极致删减标准，重新审查这套工作留痕体系。

颗粒度是审查核心：体系不是工作日志，不得记录日常操作、实现细节和可由代码或结果还原的过程，只保留真正影响后续工作的关键进展、关键决策与选择、关键问题及解决方案。任何不能帮助后续智能体接续工作、作出判断或避免重大重复错误的内容，都不应进入体系。

检查现有设计是否会造成过度记录、内容重复、无限膨胀或额外维护负担，并提出最小、直接的优化方案。所有规则与记录必须凝练、简洁、清晰，禁止长篇论述、重复解释和低价值信息。

先给出审查结论及需要优化的内容，不要直接修改。
```

### 持续收敛架构总纲

```text
目标：持续审查并收敛 `overview.md`，直到它准确承载产品需求，并成为当前范围内最简单、完整、能够经受长期变化且足以支撑预期效果的架构总纲。

`goal.md` 已封版；`requirements.md` 是产品权威；`mragent-paper-research.md` 只提供研究依据，不构成必须照搬的实现方案。只允许修改架构总纲，不得修改其他文档。现有内容能够成立的应当保留，不以大改为目标。

每次开始、续跑或上下文压缩后，重新完整读取上述文档的最新版本，不依赖旧结论。

持续执行以下循环：

1. 先从目标与产品需求独立推导架构必须回答的问题，再审查现有架构总纲是否准确承载。
2. 以“首席产品官 + 乔布斯式产品直觉 + 顶级架构师”的标准判断：
   - 是否抓住产品不可替代的本质与边界；
   - 是否形成职责清晰、依赖稳定、逻辑闭合的整体架构；
   - 是否以最少的结构完整承载需求，没有多余能力、重复职责和低价值复杂度；
   - 当模型、存储、检索技术、协议和智能个体形态变化后，核心架构是否仍然成立；
   - 是否不存在阻碍检索时效、检索质量、信息组织质量以及轻量运行目标的结构性瓶颈。
3. 严格控制颗粒度。架构总纲只保留整体结构、核心职责、能力边界、依赖方向、关键不变量及质量目标的架构响应；不得进入模块拆分、接口定义、数据结构、算法流程、技术选型、参数指标、实施步骤和交付计划。
4. 每项架构判断必须能够直接反绑产品需求，或属于满足明确需求不可缺少的架构推论。不得以最佳实践、未来可能、技术先进性或“更加完整”为理由扩张范围。
5. 完整审查一轮后统一归并问题并集中修复根因，随后复审受影响范围。最优架构不是抽象最多或预建最远，而是锁定范围内最简单、完整、清晰、可演进且没有已知结构债务的方案。
6. 准备结束时，对同一份未修改的最新文档分别执行产品本质、整体架构、长期稳定性与性能支撑、需求反绑与范围控制四次独立冷启动审查，不得复用此前结论。任何一次发现问题，都应继续修复并重新执行全部审查。

只有产品依据本身存在冲突或缺失，且不同选择会改变产品定位或需求范围时才暂停询问；其余架构判断自主收敛。

完成条件：

- 所有必须由架构承载的需求均有准确落点；
- 产品边界、核心职责、依赖关系和关键不变量清晰一致；
- 架构能够支撑既定质量与性能预期，不存在已知结构性阻碍；
- 内容始终停留在架构总纲层级，没有设计细节和实现细节；
- 不依赖当前具体技术，也没有为未来预建产品能力；
- 不存在需求之外的复杂度和已知结构债务；
- 同一份未修改文档通过全部冷启动审查。

满足后回复“架构总纲收敛完成”，简要说明最终判断和实际修改，立即停止，不再追加视角、继续润色或扩大范围。
```

### 持续收敛第一版完成条件

```text
目标：持续审查并收敛 `first-version-delivery-definition.md`，直到它成为第一版必要、充分且可执行的完成边界：全部条件通过就能确认产品真正完成，任何一项未通过都不能结束开发。

`goal.md` 已封版；`requirements.md` 是产品权威；`overview.md` 规定架构方向；`development-collaboration-guidelines.md` 规定代码质量。只允许修改第一版交付定义，不得修改其他文档。

每次开始、续跑或上下文压缩后，重新完整读取上述文档的最新版本，不依赖旧结论。

持续执行以下循环：

1. 先从目标、需求、架构和开发规范独立推导第一版必须交付的最小完整产品及其质量要求，再审查现有完成条件是否准确覆盖。
2. 以“首席产品官 + 乔布斯式产品直觉 + 顶级架构师 + 顶级性能工程师”的标准判断：
   - 所有条件通过后，产品本质、完整使用闭环和架构不变量是否真的成立；
   - 每项条件是否具有明确对象、固定前提、可观察结果和通过标准，使独立第三方无需猜测即可判定；
   - 是否存在条件全部通过但产品实际上没有完成的假通过，或产品已经满足需求却被需求之外条件阻断的假失败；
   - 是否能够防止通过模拟实现、人工补偿、旁路能力、特制数据、缩小范围、挑选结果或临时调参取巧达标；
   - 产品、代码和项目整体是否达到顶级质量，不存在边界内已知缺陷、架构偏离或结构债务；
   - 检索时效、检索质量、信息组织质量，以及程序体积、CPU、内存、存储占用和写入、持久化、组织、索引、检索效率，是否在等价条件下达到需求规定的同类前沿，且没有以牺牲其他目标换取单项达标。
3. 严格控制颗粒度。本文只规定第一版交付边界、验收基线、完成条件、明确排除和最终判定；不得进入实现方案、模块设计、技术选型、接口细节、任务拆解和具体执行命令。
4. 每项条件必须能够反绑目标、产品需求、架构约束、开发规范，或属于证明产品完成不可缺少的验收推论。无法证明必要性的内容删除，不得以最佳实践、未来可能或“更加完整”扩大第一版。
5. 完整审查一轮后统一归并问题并集中修复。修复后复审受影响范围，确保所有条件共同覆盖同一份产品，而不是各自证明互不相干的局部能力。
6. 准备结束时，对同一份未修改文档执行四次独立冷启动审查：
   - 产品完成性：全部通过后是否已经形成可实际使用的最小完整产品；
   - 判定清晰性：独立验收者能否无歧义地判断通过或失败；
   - 质量与性能：能否以可复现证据证明顶级质量和全部性能目标；
   - 范围控制：是否遗漏必要条件，或混入需求之外的能力与实现细节。
   任何一次发现问题，都应继续修复并重新执行全部审查。

只有产品依据本身存在冲突或缺失，且不同选择会改变第一版产品范围时才暂停询问；其余验收设计自主收敛。

完成条件：

- 第一版边界最小但完整，全部产品本质和使用闭环均可真实验收；
- 每项条件必要、可观察、可复现并能明确判定；
- 不存在假通过、假失败、取巧路径、主观措辞或待定标准；
- 所有质量与性能目标都有不可规避的验收落点；
- 完成判定绑定同一份未修改产品、固定基线和完整原始证据；
- 不包含需求之外的能力、未来预建或实现细节；
- 同一份未修改文档通过全部冷启动审查。

满足后回复“第一版完成条件收敛完成”，简要说明最终判断和实际修改，立即停止，不再追加视角、继续润色或扩大范围。
```

### 持续完成第一版开发

```text
目标：持续完成 Ownward 第一版开发，直到 `first-version-delivery-definition.md` 的全部交付边界与完成条件在同一最终版本上真实通过。无论首次启动还是中断后恢复，均依据仓库当前事实确定进度，从最近的有效检查点继续。

以下文档共同构成工作依据：

- `docs/delivery/goal.md` 已封版，直接说明要构建什么；内容不足以确定产品判断时，以 `docs/product/requirements.md` 为产品权威。
- `docs/architecture/overview.md` 规定整体架构方向与长期不变量。
- `docs/engineering/development-collaboration-guidelines.md` 规定代码设计、实现质量和验证方式。
- `docs/delivery/first-version-delivery-definition.md` 是第一版范围、验收与结束条件的唯一依据。
- `docs/engineering/commit-guidelines.md` 规定提交审视、拆分、确认和提交信息。
- `docs/records/README.md` 规定关键工作留痕的准入、格式和不可变规则。

目标、产品需求、架构总纲、开发规范、提交规范、关键工作留痕规则和第一版交付定义均不得在开发过程中自行修改。只有这些依据存在真实冲突或缺失，且不同选择会改变产品定位、架构方向、第一版范围或完成判定时，才暂停并询问用户。其余实现方案、技术选型、代码设计、项目结构、依赖和验证方法自主决定，以当前范围内最简单、完整、可靠且能达到质量与性能目标的方案为准。

任务首次启动、暂停后恢复、重新创建或上下文压缩后，先恢复工作状态：

1. 重新完整读取上述文档的最新版本，不依赖旧上下文中的转述或结论。
2. 按 `docs/records/README.md` 读取分卷索引、当前分卷及当前工作直接引用的历史记录，不无差别加载全部历史。
3. 检查 Git 状态与历史、仓库结构、现有代码、测试、构建和验收材料，区分已经验证的结果、正在进行的变更和尚未开始的内容。
4. 依据事实重建当前阶段、已满足与未满足的完成条件、最近一个有效检查点和下一项工作；保留并理解既有变更，不覆盖、不丢弃，也不因上下文中断重复已经成立的工作。

进度反馈：完成状态恢复后报告一次整体进度；此后只在完成实质阶段时以百分比报告距离第一版全部完成条件的整体进度，并用一句话说明已完成、当前和剩余。不得以单轮、单项或测试命令的进度冒充整体进度，不得为汇报中断工作或重复检查。

恢复后持续执行以下循环：

1. 从尚未满足的第一版完成条件反推当前最关键的前置问题，选择能够形成真实进展的下一完整工作阶段；不得扩张第一版范围，也不得以局部原型冒充产品闭环。
2. 对影响架构质量、性能上限或长期资产稳定性的选择，基于当前可靠资料、同类前沿和必要实验判断，不因熟悉程度或个人偏好沿用旧方案。
3. 按架构总纲和开发规范完成设计与实现。优先解决根因，保持代码、测试、文档和工程入口一致，不留下已知中间债务等待后续修复。
4. 开发与修复期间执行覆盖当前变更的最小充分验证；失败时先定位根因，只重跑受影响范围。只有实现稳定、定向验证全部通过并准备完成判定时，才对同一候选版本执行完整验证与验收。
5. 仅当事项符合关键工作留痕准入条件时，向当前分卷末尾追加一条记录；不得记录日常操作、普通实现过程或可由代码和结果还原的内容，不得修改既有记录。
6. 按提交规范执行低频提交审视、终态拆分、实际内容验证和提交。允许在本任务范围内执行暂存与 `git commit`；不得把未完成、无关或无法独立验证的变更带入提交，不执行 `git push`。
7. 每个工作阶段完成后重新核对受影响的交付条件和证据，随后直接进入下一项尚未满足的条件，持续工作直至全部完成。

只有缺少无法自行取得的权限、凭证或外部状态，或权威依据存在会改变产品范围的真实问题时才暂停；暂停前保留可恢复的工作状态，并明确报告唯一阻塞点。

完成前必须对同一份未修改的最终候选版本执行完整验收，逐项取得第一版交付定义要求的可复现证据，并确认：

- 全部交付边界和完成条件真实通过，没有跳过、豁免、模拟达标或范围外替代；
- 实现符合产品需求、架构总纲、开发规范和提交规范，不存在边界内已知缺陷、架构偏离或结构债务；
- 最终代码、测试、文档、验收材料和关键留痕一致，所有应提交变更已经形成合格提交，工作区不存在本任务遗留变更；
- 同一最终版本在不复用旧结论的情况下再次核对，仍能明确判定第一版完成。

全部满足后回复“第一版持续开发完成”，简要说明最终产品、验收证据、关键技术判断和提交结果，立即停止；任何一项未满足都继续开发，不得以“基本完成”“主体可用”或后续补齐结束任务。
```
