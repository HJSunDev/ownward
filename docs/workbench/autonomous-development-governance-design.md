# 自主开发治理体系方案草案

> 临时文档：用于保存当前判断与核心方案，尚未纳入正式 Skill。

## 判断

目标可行，能够建立一套既保持高度自主、又能跨上下文持续工作并主动避免低效失控的开发体系。关键不是继续增加规则、缩小任务或依赖人类监督，而是让自主执行同时具备持久状态、成本约束和独立的全局复核能力。

现有“明确起点—受约束执行—可判定终点”闭环方向成立，但还缺少两项基础能力：不依赖模型上下文的实时工作状态，以及能够主动跳出局部执行、重新判断全局价值的治理闭环。

## 核心目标

- 人类定义产品意图、长期边界和充分且可判定的完成条件，不逐步指挥实现。
- 智能体自主选择路径、实现、验证、修复和换路，并持续推进至完成。
- 系统保证跨上下文连续性，监督行动价值与资源成本，在浪费扩大前自动触发复核。

## 核心方案

### 1. 权威层

以用户需求原话、产品需求、架构总纲、开发规范、完成定义和关键工作留痕保存稳定方向，回答为什么做、做什么、什么不能变以及何时完成。

### 2. 持久状态层

另设可更新的执行状态，不把实时进度塞入关键留痕。状态至少保存当前未满足的完成条件、当前动作及其价值、预期证据、预计与实际成本、最近有效检查点、可复用结果和唯一下一动作。上下文压缩、重启或更换执行者后，依据权威层和该状态恢复工作。

### 3. 自主执行层

智能体自主选择最能推进未满足完成条件的工作。高成本或成本未知的动作必须先以最小代表性样本证明路径有效、估算完整成本，并确认不存在更小的等价证据；通过后才扩大投入。有效结果即时形成检查点，后续只补失败或缺失部分。

### 4. 独立治理层

治理复核与局部执行分离，以尽可能冷启动的视角只读取目标、完成条件、当前状态、证据和成本，判断：

- 当前动作是否直接推进未满足的完成条件；
- 已产生什么不可替代的价值；
- 实际成本是否仍符合预期；
- 当前方法是否仍是最小有效路径；
- 是否正在重复失败、扩大范围或把手段当成目标。

上下文恢复、成本显著偏离、长期没有新增有效证据或重复失败时自动触发复核。复核只能决定继续、保留结果并换路、确认阶段完成，或在确属产品决策时请求用户介入；不能等待人类主动发现失控。

### 5. 分层验证

将高频开发验证与最终证明分开：快速诊断用于持续定位和迭代，稳定资格验证只对成熟候选运行，完整验收只对冻结的最终候选执行。验证材料保持稳定，产品变化只使受影响证据局部失效；新问题进入固定回归，不整批重建或重跑无关证据。

## 成立标准

- 上下文压缩或中断后无需人类重新解释即可从有效检查点继续；
- 任何高成本动作都不能在缺少价值证明、成本估算和自动复核的情况下无限延伸；
- 每项正在进行的工作都能对应未满足的完成条件和预期证据；
- 失败只使受影响状态和证据局部失效；
- 除产品决策外，技术问题、路径失效和效率异常均由体系自主识别、处理并继续；
- 全部完成条件真实成立后立即停止。

## Codex 可执行落地方案

### 运行形态

不运行两个常驻 Codex。主任务只有一个持续开发者；确定性看门狗持续检查状态，在需要全局判断时短暂启动一个独立、只读的 Governor 子智能体：

```text
Codex Goal 主任务
    ├─ 开发者：唯一产品修改者
    ├─ 状态：跨上下文保存当前事实
    ├─ Hooks / 超时包装器：发现并阻止失控
    └─ Governor：按事件冷启动，只负责全局复核
```

该方案使用 Codex 已有的 Goal、项目级自定义 Agent、子智能体和 Hooks，不引入 API Key、常驻模型服务或项目内置智能体。

### 项目资产

```text
.codex/
├─ agents/
│  └─ governor.toml
├─ hooks.json
└─ governance/
   ├─ state.schema.json
   ├─ review.schema.json
   ├─ governance-cli.*
   ├─ governed-run.*
   └─ runtime/                 — 不提交
      ├─ state.json
      ├─ events.jsonl
      ├─ review-request.json
      └─ reviews/
```

- `state.json` 是当前执行状态的唯一权威。
- `events.jsonl` 只追加实际时间、工具结果、失败和有效证据事件。
- `review-request.json` 表示当前存在尚未完成的治理复核。
- `reviews/` 保存与状态哈希绑定的监督结论。
- `runtime/` 加入 `.gitignore`；其余配置、Schema 和脚本随项目维护。

### 状态契约

`state.json` 至少包含：

```json
{
  "run_id": "...",
  "authority_hash": "...",
  "completion_conditions": [],
  "current_action": {
    "condition_id": "...",
    "action": "...",
    "value": "...",
    "expected_evidence": "...",
    "started_at": "...",
    "estimated_seconds": 0,
    "hard_deadline": "...",
    "last_progress_at": "...",
    "checkpoint": "..."
  },
  "reusable_results": [],
  "next_action": "...",
  "review": {
    "required": false,
    "request_id": null,
    "state_hash": null,
    "decision_path": null
  }
}
```

状态通过 `governance-cli` 原子更新，不由多个文档重复维护。关键工作留痕只保存长期关键结论，不保存这里的实时状态。

### 触发机制

Hooks 只做可确定判断，不冒充智能监督员：

1. `SessionStart` 在启动、恢复和上下文压缩后注入当前状态及唯一下一动作。
2. `PreToolUse` 在高成本或成本未知动作前检查是否已登记价值、预期证据、成本和有效监督结论；缺失时阻止动作并创建复核请求。
3. `PostToolUse` 追加实际耗时、结果和失败事件；预算偏离、长期没有新增证据或同类失败重复时创建复核请求。
4. `Stop` 在完成条件尚未满足且不存在产品决策时，要求先复核而不是结束任务。
5. 预计超过短时执行窗口的命令必须经 `governed-run` 启动；包装器在硬截止时间终止进程、保存输出和检查点，并创建复核请求。

高成本动作的预算优先来自历史实测；没有历史数据时，先运行最多 5 分钟的最小代表性探测，再据实测吞吐确定完整预算。预算只累计实际执行时间，不计用户中断、关机、休眠或其他离线等待。监督触发后，除读取状态、启动 Governor 和接收结论外，相关高成本动作保持阻止状态。

### Governor 的启动与信息交换

Hook 不能直接启动智能体。它发现触发条件后执行以下链路：

```text
Hook 创建复核请求并阻止原动作
        ↓
主 Codex 收到机器可识别的复核原因并启动 Governor
        ↓
主 Codex 进入等待，不再执行原任务
        ↓
Governor 在独立上下文中读取固定输入
        ↓
Governor 通过 Codex 原生父子通道返回结构化 JSON
        ↓
主 Codex 收到结果并交给 governance-cli
        ↓
governance-cli 校验并原子写入监督结论文件
        ↓
Hook 验证结论与当前状态匹配后允许继续
```

Codex 原生父子通道负责实时交互，文件不承担“通知完成”的职责。对应的执行关系是：

```text
父线程：spawn_agent(governor, 复核请求)
父线程：wait_agent(governor)
子线程：完成判断并 final(结构化 JSON)
父线程：直接收到该 JSON
父线程：governance-cli accept-review(复核请求, JSON)
```

`spawn_agent` 启动独立子线程，`wait_agent` 使主线程等待其完成；子线程的最终结果会由 Codex 自动返回主线程。Skill 必须规定：复核触发后立即启动并等待 Governor，在结论成功落盘前不得恢复原动作。Hook 同时保持原动作被阻止，因此主线程不能绕过等待继续投入。

复核请求必须包含 `review_id`、触发原因、当前 `state_hash`、完成条件、当前动作、价值、预期证据、预计与实际成本、检查点和证据路径。

Governor 配置为只读，不实现功能、不修改产品，只读取权威依据、复核请求、当前差异、证据和必要事件。它只能返回：

- `continue`：限定动作、证据和预算后继续；
- `replan`：保留有效结果并换路；
- `stage_complete`：当前阶段证据已经充分；
- `product_decision_required`：存在真正需要用户决定的产品问题。

监督结论必须带回相同的 `review_id` 和 `state_hash`。任何目标、动作、代码、证据或完成状态变化都会产生新哈希，使旧结论自动失效。

“确定性程序校验并落盘”是指主线程收到 Governor 的 JSON 后，调用普通本地程序 `governance-cli accept-review`：程序只检查 JSON 是否符合 Schema、`review_id` 和 `state_hash` 是否匹配、`decision` 是否属于允许值；全部通过后原样、原子写入 `reviews/`，任一检查失败则拒绝保存。它不重新判断内容，也不是另一个智能体。主线程直接收到的结果用于当次继续，落盘文件用于跨上下文恢复和 Hook 的后续机械验证。

### 主任务执行规则

1. 开始或恢复时读取权威依据与 `state.json`，核对状态哈希和唯一下一动作。
2. 选择最能推进某项未满足完成条件的动作，并登记价值、预期证据和预算。
3. 普通低成本动作直接执行；需要复核的动作先完成 Governor 闭环。
4. 每次取得独立有效结果即更新检查点，后续只补失败或缺失部分。
5. 路径失效由 Governor 促成自主换路；只有 `product_decision_required` 才暂停找用户。
6. 全部完成条件在同一最终成果上成立后立即停止。

### 最小实施顺序与自检

1. 实现状态与复核 Schema，以及 `governance-cli` 的初始化、动作登记、进展登记、复核请求、结论接收和完成命令。
2. 建立只读 `governor.toml`，固定输入范围和四种输出。
3. 接入 `SessionStart`、`PreToolUse`、`PostToolUse` 和 `Stop` Hooks。
4. 实现带硬截止时间和检查点保留的 `governed-run`。
5. 使用最小隔离夹具证明：压缩后能恢复；未授权高成本动作会被阻止；Governor 结论能够放行；旧哈希不能复用；超时会停止并保留结果；普通低成本开发不受干扰。

以上自检全部成立后，治理体系才算真正落地；不能只以 Skill 文字或 Hook 配置存在作为完成证明。
