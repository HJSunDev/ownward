# 跨会话智能体协作体系

> **权威**：本文件是本体系的**设计权威**；落地时的 SKILL.md 等执行文件是本文档的派生摘要，只做打包，冲突时以本文件为准。
> **状态**：设计已收敛；剧本流程与文件机制已实战验证。
> **用途**：任何环境只要具备 3.1 节前提，即可按第七、八节直接迁移复用，不依赖本项目其他文档。

## 一、目标与第一原则

**协作的目标不是快速达成一致。** 为求快而一致、为一致而妥协或降低已证判断，是 1+1<1，不如单干。正确目标是：**各角色各自发挥最强能力、各自尽力做出自己的最优解，再以需求与证据为准绳收敛，把事做出最好效果——1+1>2；扩展到三个角色时，1+1+1>3，扩展角色绝不成为拖累。**

由第一原则导出的可执行条款：

1. **分歧是资产**：分歧必须显式化为可裁决的问题，不得抹平或回避。
2. **不盲从**：任何"接受"必须附理由与证据；无理由接受视为未回复。
3. **不为一致而折中**：允许改立场，但必须写明因何种证据改变。
4. **delta 审计**：收敛或关闭前必须有 delta 段——其他角色贡献了什么、我因何改变、残余分歧为何不推翻当前版本。全部角色都给不出 delta 时，线程不得以"成功协作"关闭，只能以 `redundant` 关闭（见 3.5），并说明该产物为何仍必要。
5. **异议保留**：`dissent` 永久保留；不得删除或改写对方异议。
6. **重开有界**：新证据可重开结论；每方对同一论点限一次，无新证据不得二次重开。
7. **用户只判定最终产物**：协作双方负责收敛出唯一版本；用户判定其是否过关，不给用户出选择题。
8. **扩展角色价值审计**：任何扩展角色（第三个角色）必须通过价值门（见 5.1），并在终版以 `unique_contributions` 审计实际贡献；无独特贡献标 `redundant`，不计入 1+1+1。

## 二、总体结构

```text
L0    协作第一原则（本文第一节，一切规则的准绳）
L0.5  宿主规则：宿主项目常驻规则（如 AGENTS.md）优先于本协议；
      宿主要求的输出格式（如首行横幅）保持，信封置于其后；
      线程与登记文件不得存放密钥、凭据。
L1    通用协作底层：任何场景都适用的身份、信封、文件、通知、状态、
      Token 纪律、回复义务、超时死信、严重度、单写者（第三节）
L1.5  资源协调层：跨场景、与线程解耦的声明式租约与资源槽（第四节）
L2    场景剧本：可插拔的相位编排（第五节）；新场景=新剧本，不改底层
L3    线程实例：threads/ 下的消息与产物（第六节）
```

## 三、通用协作底层（L1）

### 3.1 前提

运行环境须提供三个接口（本项目实现为 OpenCode 环境内置工具，其他环境等价实现即可）：

| 接口 | 语义 |
| --- | --- |
| 会话列表 | 列出全部会话的 ID、名称、busy 状态、工作目录；能识别"当前会话" |
| 会话读取 | 读取目标会话最近的消息与所用工具名称 |
| 会话发送 | 向目标会话投递消息；`wake=true` 触发对方立即处理（fire-and-forget，尽力唤醒），`wake=false` 静默投递由对方下回合读取 |

如实声明的限制：`wake` 不是送达保证——目标 busy 时消息排队，环境无调度器，唤醒丢失只能靠"文件为准"与回合制核对恢复。**本体系提供的是零轮询，不是零等待。**

技能系统（如 skills 目录）是**可选打包方式**，不是前提；规则可用纯文本交付（见 7.1）。

### 3.2 身份与登记

- 命名规约：`<项目>-<角色名>`，例如 `ownward-Ken Thompson`。
- 登记文件 `collab/roles/<role-slug>.md`，**一角色一文件**：逻辑角色是耐久身份，会话 ID 与名称只是本地映射，迁移或重启只更新映射，不丢身份。
- 每个角色文件维护自己的 `open_threads` 清单（未闭环线程及"轮到谁做什么"）；**每回合只核对自己名下的线程，禁止全 threads/ 扫描**——检查成本不随全局线程数增长。
- `open_threads` 在状态变化时同步更新：进入 `waiting` 时登记"等谁"，`closed`/`dead-letter` 时移除。
- 发起人：**用户所在会话即发起人**，固定写在线程首消息，不因用户移动而改变；无用户参与时，启动线程的会话即发起人。发起人负责启动、推进相位、发布终版；辩论期间无否决权，仅持有僵局裁决权（见 5.1）。

### 3.3 消息信封（聊天通道）

任何协作消息使用统一信封；无信息增量的字段省略。传输模式与期望分离，避免二义：

```text
【协作信封】
发件：<角色名>｜<会话ID>
收件：<角色名>｜<会话ID>
传输：串行 ｜ 并行
期望：reply ｜ draft ｜ review ｜ none
场景：<剧本名>（thread: <线程ID>，phase: <相位>）
事项：<一句话>
────────────────────────────
<正文>
────────────────────────────
回复约定：完成后用会话发送回 <发件角色名>（<会话ID>），wake=true；
内容=结论+证据+遗留分歧；无法承担回"拒绝+原因"，不得静默。
```

- `传输：串行` = 对方回复前本会话结束回合等待；`并行` = 发送后继续本职。
- `期望：none` 时免回复；`draft`/`review`/`reply` 均为需回复的期望，按对应剧本执行。
- **回复三步硬清单**（`期望≠none` 时）：①先落盘（线程消息或工作产物"决策"段）；②`session_send` 发起人（wake=true）；③更新自己角色文件 `open_threads`。无线程的一次性请求也须在角色文件登记一行（来源、期望、状态），完成移除；发起人下一自然回合核对到达。
- **降级模式下**（见 8.5），消息体必须显式携带 `state/phase/reply_to/expectation/artifacts` 字段。

### 3.4 消息文件与通知（文件通道）

- **文件是协议，消息只是中断。** 全部状态落文件；聊天消息丢失、上下文压缩都不影响恢复。
- 线程目录 `collab/threads/<thread-id>/`；**首消息固定命名 `request.md`**，其余消息 `YYYYMMDDTHHMMSSfff-<sender-slug>-<phase>.md`（毫秒命名防同秒覆盖；一消息一文件消除多写者的整文件读写竞争）。
- **消息文件格式**（YAML front matter + 正文）：

```yaml
---
thread: <thread-id>
msg: <本消息文件名>
from: <角色slug>
to: <角色slug>
state: open|waiting|closed|dead-letter
close_reason: -          # 终态必填：completed|redundant|timeout|rejected-blocker|user-decision-needed
sedimentation: -         # 终态必填：<records-id|文档路径|none>（沉淀落点）
phase: <剧本相位>
scenario: <剧本名>
reply_to: <被回复消息文件名>   # 无则 "-"
expectation: reply|draft|review|none
artifacts: [<相对线程目录的产物路径>]
summary: <一句话>
---
<正文>
```

必填：`thread/msg/from/to/state/phase/scenario/reply_to/summary`；`expectation/artifacts` 按需；**`expectation` 省略时默认 `reply`（防静默丢失），知会类消息必须显式 `none`**；终态消息必填 `close_reason` 与 `sedimentation`。`request.md` 即线程首消息文件，额外含 `initiator/participants/roles/success-criteria`。产物路径一律相对线程目录。
- **通知格式**（经会话发送，只含）：thread-id、phase、消息文件路径、一句话摘要、reply_to、expectation。
- **先落盘、后通知**：先写完消息文件，再发送通知。

### 3.5 状态与推进

线程状态：`open | waiting | closed | dead-letter`；`closed` 与 `dead-letter` 为终态（可凭新证据重开）。`state` 语义：`waiting` 表示线程至少存在一个未完成义务（等某角色回复或交付）；全部义务清空才置 `open`。迁移规则：

| 迁移 | 触发 | 置位方 |
| --- | --- | --- |
| open → waiting | 发出需回复或需交付的消息 | 发送方 |
| waiting → open | 该线程全部未完成义务清空（最终回复收到、应交付产物均已落盘）；临时 ack（排队）不迁移 | 接收方 |
| open/waiting → closed | 关闭条件满足（各剧本定义） | 发起人（或经发起人确认方） |
| open/waiting → dead-letter | 超时未闭环升级用户、blocker 被拒且用户未决等 | 发起人（或经发起人确认方） |
| closed/dead-letter → open | 携带新证据重开（见 1.6） | 重开方 |

`closed` 必须带 `close_reason: completed | redundant`；`dead-letter` 必须带 `close_reason: timeout | rejected-blocker | user-decision-needed`。重复状态消息幂等，以最新为准。
**推进有效性**：phase 推进以前置产物**已落盘并被引用**为条件（推进消息的 `artifacts` 字段列出前置产物，接收方校验存在性）；提前推进无效，线程停留原相位；重复推进幂等，以发起人下回合确认为准。

### 3.6 Token 纪律

- **串行**：发送（wake=true）→ 立即结束自己的回合，向用户报告一句"已交发，回复到达时我会被唤醒" → 严禁 sleep、轮询、反复读取对方会话 → 对方完成 → 回发通知（wake=true）→ 发件方被唤醒继续。
- **并行**：发送后继续本职工作；对方完成时回发通知，或发件方在自然检查点读取一次。
- **每回合只读最新状态消息与被引用产物，不读全历史。**

### 3.7 回复义务与超时死信

- 闭环只认三类最终回复：**结果、拒绝（附原因）、dead-letter**。"排队"是临时 ack（线程保持 `waiting`，结果另行发送），不构成闭环，也不触发 `waiting→open`。
- 超时检查是**回合制**的（智能体无定时器，只能在下次被唤醒或用户催问时检查）：**超时=发件方下一次自然回合时仍未闭环**→发一次提醒；用户催问后仍未闭环→追加 `dead-letter` 状态消息、停止等待、升级用户。
- **决策咨询的默认处置**：咨询消息必须预写"未回复时的默认处置"且仅限可逆步骤；不可逆/阻断项不得因超时转单干，按 D3 升级路径处理（单一推荐+异议记录，不给用户出选择题）。

### 3.8 用户中途输入

用户在其所在会话的输入，由该会话写成 `user-input` 消息并通知相关线程；**用户指令优先于线程既有约定**。

### 3.9 严重度定义

| 级别 | 定义 | 关闭要求 |
| --- | --- | --- |
| `blocker` | 安全、数据完整性、权限问题，或导致结果不可用的缺陷 | 未关闭则线程不得 `closed`；关闭路径按剧本映射：独立复核为 5.2 的三条路径；多角度分析为——全体相关角色书面确认解决，或用户明确接受并记录；否则升级用户，未决 `dead-letter` |
| `major` | 显著影响正确性或可用性 | 必须处置（accept/reject/defer 均需理由与证据） |
| `minor` | 改进项 | 可 defer，关闭摘要中列出 |

### 3.10 单写者条款

- **每个工作区任何时刻只有一个写者**：代码、配置、权威文档的写者=发起人（实现方）；扩展角色（第二、第三角色）对产品文件一律**只读**，只可写线程目录内自己的分析产物（草案/批判/发现等）。
- 扩展角色可在资源租约下执行验证（测试/构建），但不得修改源码；生成物放临时或构建目录，不得成为权威。
- 需要修改时：扩展角色只提方案与证据；发起人落笔；扩展角色复验。
- 多线程各有发起人时，写权由全局 `workspace-write` 租约串行化（见 4.4）。
- **资源协调元数据不在产品单写者范围内**：槽与租约声明属于协调元数据，每个角色只写自己的声明；过期回收是显式例外（任何角色可回收已过期且持有者空闲的槽）。
- 违反单写者=blocker：记录、恢复被改产物、按严重度流程处置。

### 3.11 决策门与协作模式

**定义。** 决策=在多个可行选项间选择并改变产物、行为或承诺；执行=沿已定路径落地（写文件、跑命令、搬数据）。执行单干，执行中不得改变已定方案；需要改变方案即为新决策。本条适用边界：高杠杆、无先例、不可逆或证据冲突的决策，必须先取得独立第二视角；执行与低代价可逆选择单干并留痕；单点拍板、单点负责——判据以下方分级段为准。

**义务主体（与角色绑定，不与会话绑定）。** 对本条承担发起义务的是**对该决策所属产物持写权的登记角色**（当前为 `donald-knuth`）——与 3.2 的"线程发起人"（用户所在会话）是两个概念；义务随角色迁移、不随会话迁移。本体系的固定登记角色为 `donald-knuth`（发起人/实现方）、`ken-thompson`（伙伴/审查）、`linus-torvalds`（按需第三）；其他历史或外部登记（无活跃会话映射）不承担响应义务。其他登记角色承担**响应义务**（回合内响应咨询、审计决策日志）；**未登记角色与外部智能体不受本条约束**，但登记角色"采纳/合并其方案或产出"仍属该角色自身的 D2 决策。义务主体 inactive/unmapped 或长时间不可达时，按超时/D3 停下或升级用户，由用户决定角色重排。

**分级（按性质判定，不按体量）。**
- D1（执行内选择）：项目已有先例/约定可依，且选错可逆，且代价有界（命名、格式、读哪个文件、既定顺序、预案内重试）→ 单干，留痕。
- D2（路径决策）：满足任一即 D2——影响他人依赖的接口/契约/布局；存在多个可辩护选项且选错代价显著（返工、不可逆、外部成本、安全/数据风险）；本类首次或无先例；与既有证据/假设冲突；需要新机制设计 → 先协作后动。
- D3（重大/不可逆）：架构、范围、对外承诺、真实成本、安全与数据处置、候选/发布冻结变更 → 协作 + 按需升级用户；不得超时单干。
- 判据不足：可逆部分继续，不可逆部分停下按 D2 咨询。对方可将 D1 升为 D2（附一句话理由）；义务主体坚持 D1 须给证据；未决按不可逆部分 D2 处理。

**协作模式（按决策类型路由，可升不可降）。**
- 快速咨询：单一决策、选项与推荐明确 → 一问一答；同类批量合并（一次 ≤5 条、逐项回复，超出拆线程或升级共设计）。
- 独立成稿共设计：开放设计空间、无先例 → 双方各自成稿再交叉（复用多角度分析盲起草）。
- 独立复核：产物已成形 → 审查方独立检查（复用独立复核）。

**咨询内容必含：** 决策点；选项；我的推荐与最强反对理由；请对方攻击的具体不确定性；紧迫度（needed-by：now 阻塞型／可等待）；未回复时的默认处置（仅限可逆步骤）。

**时延纪律（两段式回复）。** 阻塞型（needed-by=now）咨询，受询方被唤醒后的第一个回合内先给快速表态（同意／有异议／需深查＋预计深度），表态优先于其自身深度工作；完整分析随后回合补全。快速表态只解锁可逆推进，不可逆步骤必须等完整分析；表态为"需深查"必须给出补全条件或时点，无补全按未回复处理并计入响应义务审计。受询方忙或未开始处理时，发件方按默认处置推进（仅可逆步骤）并记账——"第一个回合"自对方开始处理起算。非紧急批量咨询允许一次完整回复。快速表态可只经会话消息送达，由义务主体记入决策日志；完整分析走回复三步硬清单。决策日志记录两个指标：发出→表态回合数、发出→完整分析回合数（供反拖累与降级评估）。

**必议与单点负责。** 双方各自独立表态 + 以证据收敛；义务主体合成后**单独拍板、对结果负责**并记录；异议保留（1.5）。不得把决策原样丢给对方（"你定"无效）；无理由同意视为未回复（1.2）。

**决策日志。** 落点：交付类工作产物（代码/脚本/方案/测试等）带"决策"段；跨产物或文档/规则类决策写线程消息或 records——判据：该结论会被后续复核、复现或他人依赖引用→必须落盘。D1 一行一条；D2 记决策点、对方输入、结论、证据链接；降级/未协作项单列。**D2 无日志=未完成协作。** 对方在下一自然回合审计；发现应协作未协作→记录并重开（1.6），blocker 走 5.2 三条路径。

**轮次与成本。** 同一决策咨询一轮为限；未收敛由义务主体裁决并记录（blocker 或涉用户成功标准时升级用户，按 5.1 僵局禁区）。等待期间推进可逆步骤；咨询回复限一次定向回复。

**反拖累。** 同一决策类连续 ≥3 次咨询、对方回复无任何具体改动/新证据/新选项（按 1.4 delta 判据）、义务主体书面提案（列出该类咨询与 delta=0 证据）、对方一次否决权（须给具体反例）、降级自动到期（下一个线程关闭或用户重置）、D3/安全/数据/合同/对外承诺类永不降级；任一具体反例可即时恢复。先穷尽批量咨询、异步追审、D1 判据澄清等减负手段；降级是最后手段。

**审查独立性保护。** 审查方的 findings 与独立判断不受决策门约束（5.2 先落盘后讨论优先）；其义务仅限咨询响应与日志审计。决策门不管辖回答/解释类陈述——那属于断言与归因的证据纪律，由宿主常驻规则（如 AGENTS.md）约定。

### 3.12 任务书保真（中继失真防护）

**问题。** 并行协作的价值来自对同一真相的独立视角；用户原话经发起人中继转述时若发生抽象损耗或误解污染，独立性只会放大错误——共享被污染的任务书时，N 个视角只是 N 次同误。失真卡点唯一：用户原话→中继转写→方向性结论；本条只修这个卡点，不建通用保真协议（无哈希链、回执链、逐任务确认往返；智能体间互述仍可转写＋线程引用）。

**适用分级。** 需求梳理、产品设计、用户意图解释类任务（语义词密度高）强制适用；纯执行类任务（跑测试、查文件、机械搬运）可豁免——任务书自标类型，并行者发现语义密度高于标记时，可要求升级适用，争议按 §3.11"判据不足"处理。

**规则。**

1. **原话区制度**：适用任务的任务书必须含两区——【用户原话】全文机械复制（不得改写、摘要、凭记忆转写；凡用户消息以文本到达发起人，一律复制落盘为原件）＋【发起人理解】（显式标注为理解、可质疑）。两区分离，不得混写。
2. **冲突规则**：原话＞理解。接收方发现原话与理解冲突必须标记、不得静默沿读；质疑义务只针对**方向性理解**（"由此推出／据此排除"类结论），不扩张为事事质疑。
3. **推断标记**：任务书中由原话或权威引证推出的方向性结论（尤其排除／不做某事项）必须显式标【推断】并附依据链；原话区没有的内容不得直接作为排除依据。
4. **引证排除核验**：以权威引证排除事项时，任务书须注明引证的适用范围；接收方核验的是**解释在语境中成立**，不是引文存在。
5. **转述降级**：用户原话确无法全文照录（口头／跨场景）时，任务书标【转述·保真降级】，接收方据此提高核验权重。
6. **复用断言核验**：凡"复用／既有能力／零改动"类声明被作为依据引用（含任务书内），按 §3.13"依赖断言证伪式举证"执行。

**任务书两区模板**（载体为消息正文或 `request.md`）：

```text
【用户原话】（机械复制，不得改写）
<原文>
【发起人理解】（可质疑；与原话冲突处以原话为准并标记）
<理解／背景／任务与产出契约；方向性结论逐条标【推断】＋依据链>
```

### 3.13 终审质量门（唯一门禁清单）

**触发。** D3 级（按 §3.11 分级判据）产物门槛判定前必过；已过门产物的修改，diff 触及承诺句、机制句、验收句或语义句即过门，纯措辞调整豁免——句类由执笔方标注、门裁判按实际 diff 复核，争议或可疑降级一律按过门处理（代码产物：触及状态机、生命周期、权限或并发语义的 diff 视同机制句）。D1/D2 不适用为意图设计。触发与宣判（含过门版本哈希，作后续 diff 基线）记入线程。

**角色与顺序。** 执笔方举证（锚点＝可核对工件引用：文件:行、消息、哈希）；非执笔方任门裁判，执行三法后开冷读、依冷读结果终判；冷读者做内容对抗审（subagent、外部智能体或任一新会话，零讨论史即合格）。任何人不给自己的产物判门；门内 blocker 按 5.2 三条路径关闭；裁判不可达沿用既有超时与升级纪律。

**审查三法（缺组不合格）。**

1. **符合性**：锚点核实、承诺与权威文档一致（适用任务含任务书两区在案）。
2. **闭合性**：承诺×承诺×呈现面矩阵（面＝产物的用户可见部分），张力必须解决或收窄承诺范围；**排除性原则必须写明负担落点**（"不做X"须回答 X 的需求由谁、以何契约承接）。含持久状态与生命周期（批准、拒绝、撤销、中断、过期任一）的代码实现，另按**终局六问**走查（通用方法，对一切此类实现适用，非问题限定规则；与场景电池分工——六问穷举状态收尾，电池走故事）：①动作收尾后留下什么残余状态？②从残余／失败／拒绝态能否再次到达目标？③收尾是否依赖届时可能缺席的一方？④失效／撤销后的事项能否回流并再次可达？⑤被拒绝／中断是否阻挡后续同类操作？⑥自造探针：构造既有套件未覆盖的失败情境并运行（跑既有套件不算），探针与结果证据在案。①–⑤答"否"时：刻意设计（吊销、一次性令牌等）写明理由即闭合，无理由即开放发现。**走查答案与探针证据写入当次审查记录，供门裁判复核。**
3. **场景走查**：故事电池逐条走查，每步指认支撑条款，无支撑的步＝blocker。通用电池：首开验证／工作中断（断网、崩溃、关窗、冲突）／第二实体接续／位置迁移／长期规模／重建进行中；加模块特有故事；触及运行时表面必含故障故事。

**代码门（代码类 D3 产物的门槛判定＝可提交判定，提交前唯一时点）。** 代码类＝含可执行实现逻辑的产物（代码、schema、配置、脚本）。判定三件套：**冷执行**＝零讨论史执行者只读产品契约与公开接口文档（不看实现与既有套件），自行构造场景、对冻结版本（哈希在案，产物变更即失效重跑）跑真实接口；**既有套件**全绿（全新产物无套件时自动满足）；**定向读审**（含终局六问①-⑤走查收尾状态）。**过＝冷执行零未处置发现＋套件全绿＋读审零开放发现，由门裁判宣判**；探针清单与证据在案是必要条件，读审零发现不单独构成可提交。判定范围＝整个产物面，不区分首版与修复。冷执行者与冷读者可为同一会话（零讨论史即合格），不可达沿用超时与升级纪律。文档类产物不变（冷读为最后一步）。

**冷读。** 定稿与过门修订的最后一步＝无讨论史的新会话只读产物＋固定 grounding（产物与产品权威文档，由裁判指定）做对抗审查，冷读未过则门禁无效。**修复纪律**：修复对照产物自身的不变量（其排除性原则与"零X"承诺）审计，不得只修被指出的点；与审查者建议冲突时以不变量为准。

**依赖断言证伪式举证。** "复用／既有能力／零改动"类声明是集成声明：凡被作为依据引用（含任务书内）的，必须附 file:line 工件并以证伪为目的核验。

**回归用例（门的有效性验收）**——外审发现与规则映射，每次冷读后复盘，任一规则抓不住对应漏点即本门失效：

| 外审发现 | 由哪条抓住 |
| --- | --- |
| 直接编辑语义边界（触发器即推断） | 闭合性（零智能×语义判断）＋冷读 |
| 更正判断责任未闭合（第一轮） | 闭合性（谁执行×承诺） |
| 内核独立矛盾（第一轮） | 闭合性（承诺×呈现面矩阵） |
| 草稿"只写不可读"断接续 | 场景走查（第二实体接续） |
| 断网关窗丢用户输入 | 场景走查（工作中断＋故障故事） |
| 浏览器入口"复用既有"失实 | 依赖断言证伪式举证 |
| 验收／场景表未同步修订 | 机械触发（diff 触及语义句）＋符合性 |
| 双轨表单版本错位／已决决定不可见（时序与投影类） | 代码门：冷执行（自造场景实跑真实接口） |
| 迁移拒绝后交接残留阻挡下次迁移 | 终局六问③⑤（缺席方收尾／拒绝后阻挡） |
| 物主恢复后批准悬空不可再达 | 终局六问④⑥（回流可达／自造探针） |
| 撤销后旧授权凭据被复用（既有教训） | 终局六问④ |

## 四、资源协调层（L1.5）

所有会话运行在用户的同一台机器上，内存、CPU、磁盘、外部调用额度共享且有限。本层**跨场景、与线程解耦**：任何线程的任何角色执行资源动作前都受本层约束。**协调范围**：资源协调覆盖共享同一 `collab/` 工作区根的协作方；跨工作区会话不在协调范围内——如需机器级协调，由用户将资源根配置到共享位置或使用系统级工具。

### 4.1 动作类别与豁免

| 类别 | 定义 | 协调要求 |
| --- | --- | --- |
| `light` | 读文件、小查询、轻量整理（<1 核且 <500MB 且 <10s） | 免租约 |
| `heavy` | 构建、测试套件、批量验证、大文件处理、本地模型推理等（≥1 核 或 ≥500MB 或 ≥10s） | 必须持有资源槽 |
| `external` | 外部付费/远程 API 调用 | 单列并发与成本额度，记录用量 |

阈值与额度在 `collab/resources/config.md` 配置（默认：本地重动作总量=1，本地模型推理占用同一额度；`external` 并发=1 并有成本预算）。

### 4.2 资源槽与声明式租约（原子互斥）

- 槽位目录 `collab/resources/slots/<class>/`，容量 N 即 N 个槽目录（默认 heavy 类 1 个）。**获取槽=对槽目录执行原子独占创建（如 mkdir）**——成功即持有；失败即被占用：写 pending 声明（`claims/pending/`），在自己的下一自然回合复查并重试，**禁止 sleep/轮询**。原子创建是互斥原语，消除"先写文件再通知"的并发窗口。
- 持有后写租约声明文件 `collab/resources/claims/<lease_id>.md` 作审计，字段：`lease_id/role/action/class/estimate/preemptible/safe_point/granted_at/expires_at/heartbeat/status`；完成时把声明移入 `claims/done/` 并释放槽（删除槽目录）。
- **租约时长与过期回收**：`expires_at` 必须覆盖动作的最大预期运行时间（含余量，上限在 `config.md` 配置）；长任务在检查点续期，尽量拆为可检查点子任务。回收前必须核对持有者状态：持有者 busy（可能在运行）时不回收，等下一回合或升级；仅当持有者空闲且租约已过期，才可将槽移入 `claims/expired/` 并记录（用原子重命名，失败即他人已回收）。禁止删除或回收未过期槽。
- 声明全局有效，与线程归属无关；线程关闭不清除未过期租约（由持有者释放或过期回收）。

### 4.3 优先级与抢占

- 用户在场等待的任务（前台）优先于一切后台/分析任务。
- 租约声明 `preemptible: true|false` 与 `safe_point`（安全点描述）。
- 前台任务可抢占 `preemptible` 租约：无需持有者同意，但必须记录理由并通知持有者；持有者应在下一安全点释放。**抢占是协作式的，移槽不释放持有者进程占用的资源**：抢占者只在确认持有者空闲（或持有者已释放）后才接管；持有者仍在运行时不接管、记录违规并升级用户。重动作应尽量在可终止的子进程中运行并声明安全点。
- 非 `preemptible` 租约、或非用户任务之间的抢占：需双方书面确认；不能确认则升级用户。**无安全点声明时禁止抢占。**

### 4.4 workspace-write 租约与验证互斥

- 全局 `workspace-write` 槽（容量 1）串行化工作区写权；仅发起人（实现方）可持有，扩展角色永不持有。
- 验证（测试/构建）必须针对**冻结快照**（副本或提交）执行，并记录：目标快照哈希、命令与参数、环境、结果摘要。
- **验证租约有效期间不得授予工作区写租约**；验证目标只读（包括发起人）。快照变化即验证失效（与 5.2 冻结失效联动）。发起人若要修改，须先撤销验证并声明验证失效。

### 4.5 失败处理

- OOM、超时、崩溃：释放槽、在声明中记录实际用量与失败原因、保留部分结果、有界重试；**禁止静默重试**。
- 外部成本额度超支：须事先向用户申请；超支即停止相关动作并升级用户。
- 失败不得伪装为成功；重试次数与预算在 `config.md` 配置。

### 4.6 降级模式

无共享文件系统时，资源协调退回**消息声明**（动作、估算、开始/结束），弱保证；至少保证同一时刻只有一个 `heavy`/本地模型动作。降级标志写入线程首消息。

## 五、场景剧本（L2）

### 5.0 场景选择指引

> 所有场景位于决策门（3.11）之后：先按 3.11 分级，再按决策类型路由——快速咨询走"一般协作"，开放设计走"多角度分析"，产物检查走"独立复核"。场景由决策类型选择，不再由"事情大小"选择。

| 场景 | 何时使用 | 角色数 |
| --- | --- | --- |
| **多角度分析** | 开放问题需要根因、方案、风险的多视角独立分析（可含测试验证） | 2-3（默认 2；通过价值门才 3） |
| **独立复核** | 已完成的工作（代码/文档/方案）需要另一角色独立检查 | 固定 2 |
| **一般协作** | 传递信息、简单问答、一次性交换 | 固定 2 |

用户不选择场景；发起人按决策门（3.11）路由选择并写入 `request.md`，用一句话告知用户。

### 5.1 多角度分析（2-3 角色，星型）

适用：共同思考问题根因、共同设计最优方案等开放问题。发起人=用户所在会话。

**拓扑：星型协调 + 共享产物面。** 消息与协调走星型——扩展角色只与发起人通信；产物走共享面——线程目录内文件各角色可读，但只在反锚定相位结束后打开可见性。不做网状（消息 O(n²)、锚定级联、用户入口失控）；网状列为未来候选，需证据支持。

**角色与镜头**：每个扩展角色分配不同镜头（如正确性/风险、简洁/可维护、体验/运维、安全/隐私、性能/成本），不得重复。角色数默认 2；**价值门**：发起人必须在 `request.md` 写出第三镜头的独立价值与成功标准，才可启用第三角色。

**相位**：

| 相位 | 动作与约束 | 产物 |
| --- | --- | --- |
| request | 发起人写清问题、约束、成功标准、已有材料、明确不在范围的内容、角色与镜头、价值门（若 3 角色）、资源预算引用 | `request.md`（即首消息；`expectation: draft`） |
| blind-draft | **全体**（含发起人）各自独立成稿；己方落盘前不读他人草案（反锚定）；草案文件一次写定，exchange 相位开始前不得修改（文件时间戳可审计）；每份草案含：方案、依据、已知风险、反对自己的最强理由、自评预期独特价值 | `drafts/<role>.md` |
| cross-critique | 全部草案落盘后，各角色读其他草案，写批判：每份的对方最强处、最弱处、可合并处；**禁止只附和** | `critiques/<role>.md` |
| debate | 星型：各角色只与发起人辩论，每角色每轮一次回应；两轮为限（一轮=各角色各回应一次）；发起人汇总并定向提问 | 辩论消息 |
| converge | 发起人**唯一合成** `final.md`：含 delta、`unique_contributions` 审计、dissent；各角色标 `agree \| residual-dissent` | `final.md` |

**防拖累机制（1+1+1>3）**：价值门（加人前）→独立性（盲起草）→结构化交叉（cross-critique）→单点合成（连贯性）→`unique_contributions` 审计（加人后）。审计=各角色自报 + 发起人归因两部分组成，差异记为 dissent；审计只认"相对发起人初始草案的具体改动或决策"，不接受笼统"有影响"；无具体归因即标 `redundant`，不计入 1+1+1、不进入终版。

**僵局协议**：两轮辩论未收敛 → 发起人书面裁决（争议点、各角色立场、各自证据、选择理由、何种新证据可推翻），写入 `decision.md`，`final.md` 引用；被否方案与异议完整保留。
**僵局裁决禁区**：未关闭项属于 blocker，或异议主张终版不满足用户成功标准时，发起人不得单方关闭——呈用户"单一推荐版本 + 异议记录"，不得给用户出选择题。
**用户可见性**：只有发起人与用户对话；发起人负责汇总，禁止把各角色原文直接倾倒给用户。

### 5.2 独立复核（固定 2 角色，串行）

适用：开发完成后由另一方独立审查。发起人=被审方（用户所在会话优先）。

| 相位 | 动作与约束 | 产物 |
| --- | --- | --- |
| request | 被审方写目标、范围、变更内容/文件、验收标准、已知风险、审查重点；**被审版本冻结并落盘**；`request.md` 记录冻结身份（快照文件哈希；未跟踪文件以文件哈希+冻结副本为准），变更机械可检测 | `request.md` + 冻结快照（`expectation: review`） |
| independent-review | 审查方独立读材料、跑验证；**findings 落盘前不得与被审方讨论审查内容**；默认只读，不改被审产物；每条发现含：严重度、证据、影响、建议、置信度；运行测试/构建须持有资源租约（4.1） | `findings/<reviewer>.md` |
| disposition | 被审方逐条 `accept\|reject\|defer` + 理由 + 证据；**禁止无理由全盘接受——盲收即失守独立视角** | `disposition.md` |
| fix | 修复 accepted 项；写明改了什么、没改什么、为什么 | `changes.md` |
| verify | 审查方独立验证修复，可 reopen；**不能只看被审方摘要**；验证绑定冻结快照与命令（4.4） | `verification.md` |
| close | 全部发现有处置且**全部 blocker 已关闭**方可 `closed`；关闭摘要**顶部**列出全部未关闭 major/minor 与残余分歧；被审方对最终结果负责，审查方保留独立意见 | 关闭状态消息 |

**blocker 关闭路径（仅三条）**：①修复并经审查方 verify；②审查方书面接受降级并附证据；③用户明确接受并记录。**被 reject 的 blocker 不得视为关闭**——线程不得 `closed`，必须升级用户；用户未决时 `dead-letter`（`close_reason: rejected-blocker` 或 `user-decision-needed`）。
**冻结失效**：被审版本身份一旦变化，`independent-review` 与 `verify` 立即失效，必须重审。冻结哈希与被审工作区文件一致；提交时须核对提交内容哈希与冻结哈希一致，不一致即失效并重审。角色文件的 `状态`/`open_threads` 属运行状态：其变更不触发冻结失效，仅职责边界等内容变化触发。
**无否决权**：审查方无 veto；被审方拥有最终决定权，但异议必须保留、高严重度分歧不得埋没。

### 5.3 一般协作（固定 2 角色）

未定义剧本的场景，使用 L1 基础行为：信封 + 串行/并行 + 回复义务 + 文件为准。blocker 关闭路径默认按多角度分析映射（相关角色书面确认或用户明确接受），否则升级用户。新场景需要新剧本时，新增一个剧本文件，不改底层。

**决策咨询（决策门路由下的默认形态）**：一次消息携带 ≤5 条决策（编号、选项、推荐、要攻击的不确定性、未回复默认处置），逐项回复；结论落入工作产物"决策"段，模板见 `templates/decision-log.md`。

**紧急排障的事件级批量咨询**：用户催办的排障事件中，决策呈流式产生、逐条咨询会打断执行。用法：事件开始**先发后动**（不得事后补发）一条事件咨询，声明事件边界、将要执行的**有界可逆步骤类**与排除项（D3/安全/数据/合同/不可逆永不入类）、事件级默认处置（对方第一回合无异议才执行该类步骤；不可逆仍逐决策等待）；事件结束的下一自然回合**批量追审并留完整日志**，对方可否决或重开，**日志缺失即违规**。紧急执行窗口机制暂缓启用，激活判据：任一未协作的不可逆步骤（立即激活，不等计数）；或一次事件内追审确认未被事件咨询覆盖的应协作可逆决策 ≥2 次，或连续两次事件各 ≥1 次；连续两次紧急事件以此模式干净通过（日志完整、零违规）则该机制结案为不需要。

## 六、线程实例与产物（L3）

- 线程 ID：`<YYYYMMDD>-<topic-slug>-<shortid>`；`shortid` 为 4 位随机十六进制。
- `request.md` 即线程首消息文件（含 `initiator/participants/roles/success-criteria`）；`roles` 含每角色的镜头与写权限（`{slug, lens, write}`，扩展角色 `write: false`）。
- 目录内含消息文件与剧本要求的产物；产物路径相对线程目录；产物存在性可机械校验。

## 七、落地设计

### 7.1 落地物

技能打包为**可选**；最小落地=规则文本（本文件）+ 目录约定：

```text
.agents/skills/session-collab/     — 可选打包（SKILL.md 为本文档的派生摘要）
├─ SKILL.md
├─ scenarios/                      — 多角度分析/独立复核/一般协作 摘要
└─ templates/                      — 信封、roles、租约、产物模板（见第九节）

collab/
├─ roles/<role-slug>.md            — 一角色一文件（身份、职责、映射、open_threads）
├─ resources/
│  ├─ config.md                    — 资源额度配置与保留期
│  ├─ slots/<class>/               — 资源槽（原子创建即持有）
│  └─ claims/                      — 租约声明（审计）；pending/、done/、expired/、preempted/ 子目录
├─ archive/                        — 终态线程归档（<YYYYMMDD>-<thread-id>/）与 tombstones/
└─ threads/<thread-id>/            — 线程消息与产物
```

### 7.2 落地步骤

1. 确认 `.gitignore` 已忽略 `/collab/`（运行态不入库，见 7.3）。
2. 放置规则文本（与可选 skill 打包）。
3. 建 `collab/roles/`、`collab/resources/`、`collab/threads/`、`collab/archive/tombstones/`，为当前全部活跃会话登记角色文件并写 `config.md`。
4. 向既有会话发送协议引导（信封样例 + 回复约定），确认其能按信尾回复。
5. 用一次真实串行协作做首次闭环验证（保存全部产物）。

### 7.3 运行态与生命周期

**定位**：`collab/` 是本地运行态（角色映射、资源锁与审计、线程过程产物），**不入版本库**（`.gitignore /collab/`）；设计权威文档与 skill 属工具内容，入库；有持久价值的结论按 `docs/records/` 准入蒸馏，不复制线程。证据线程确需随交付保留时，只把必要产物复制到模块文档或 records，不提交整个线程目录。

**蒸馏（close 把关）**：终态消息必填 `sedimentation: <records-id|文档路径|none>`，缺失不得关闭；由发起人在 close 时（上下文新鲜）完成判断与写入。

**保留与清理**（自然回合触发，幂等，任何角色可执行；无定时器、无共享账本）：

- **永不清理**：`open`/`waiting` 线程、未关闭 blocker、`user-decision-needed`、未 promote 的证据、未释放或未过期的租约。
- **清扫前核对**：目标线程不被任何角色的 `open_threads` 引用（读 roles 即可）。
- **线程**：终态 + `terminal_retention_days=30` → 移入 `collab/archive/<YYYYMMDD>-<thread-id>/`（命名即时间戳）；归档 + `archive_retention_days=60` → 删除，并生成 tombstone `collab/archive/tombstones/<YYYYMMDD>-<thread-id>.md`（`deleted_by/at/reason/close_reason/sedimentation`）。
- **claims**：`done/expired/preempted` 保留 `claim_retention_days=7` 后删除；`hold: true`（记录 `hold_set_by`/`hold_reason`）跳过清扫，由设置者释放，用户可清除任何 hold。
- **roles**：耐久身份，**不自动清理**；会话消失可标 `inactive/unmapped`；仅用户可删除。
- **slots**：由既有过期回收机制处理（4.2）。

**删除不需要用户逐次确认**：归档层即 undo 窗口（总保留约 90 天），蒸馏已在 close 由双方把关；超过保留期后的删除属可接受的残余风险。

## 八、迁移到其他环境

1. **核对前提**：3.1 三接口；协作方共享同一工作区路径（同机共享文件系统）。
2. 确认 `.gitignore` 已忽略 `/collab/`；放置规则文本（可选拷贝 skill 打包）；`collab/` 在目标工作区新建。
3. 按目标项目的常驻规则调整 L0.5（横幅、命名等），其余条款不变。
4. 为目标环境的会话登记角色文件、配置资源额度，完成一次引导与一次闭环验证。
5. **降级模式（无共享文件系统时）**：消息自包含——消息体携带 `state/phase/reply_to/expectation/artifacts`，产物以消息正文或引用交付；线程首消息必须标注"降级"。降级下明确弱保证：无文件为准、无机械状态推导、`open_threads` 不可持久（恢复依赖用户催问与消息历史）、资源协调退化为消息声明；回复义务、超时死信与 blocker 关闭路径仍然有效。

## 九、模板（随文交付）

**角色文件**：

```markdown
# <角色名>
- 角色 slug：<role-slug>
- 当前会话：<名称>（<会话ID>）
- 职责边界：<该角色负责什么、不负责什么>
- 状态：idle|working|waiting
- open_threads：
  - <thread-id>：<phase>，等 <角色>
```

**线程首消息（request.md）**：front matter（见 3.4）另加：

```yaml
initiator: <角色slug>
participants: [<角色slug>, ...]
roles: [{slug: <角色slug>, lens: <镜头>, write: true|false}, ...]
success-criteria: <一句话>
```

**findings 条目**：

```markdown
- [<blocker|major|minor>] <标题>
  - 位置：<文件:行 或 缺失点>
  - 证据：<为什么是问题>
  - 影响：<后果>
  - 建议：<修复方向>
  - 置信度：高|中|低
```

**disposition 条目**：`- <finding编号>：accept|reject|defer — <理由与证据>`

**tombstone（archive/tombstones/<YYYYMMDD>-<thread-id>.md）**：

```yaml
deleted_by: <角色slug>；at: <时间>；reason: <原因>
close_reason: <completed|redundant|timeout|rejected-blocker|user-decision-needed>
sedimentation: <records-id|文档路径|none>
```

**资源租约声明（claims/<lease_id>.md）**：

```yaml
lease_id: <id>；role: <角色slug>；action: <动作>；class: heavy|external|workspace-write
estimate: <内存/CPU/时长/费用估算>；preemptible: true|false；safe_point: <描述>
granted_at: <时间>；expires_at: <时间>；heartbeat: <时间>
status: running|released|expired|preempted
actual: <实际用量>；result: <结果摘要>
```

**决策日志（工作产物"决策"段；完整模板见 `templates/decision-log.md`）**：

```markdown
## 决策
- D1：<选择> — 依据：<先例/约定>（一行一条）
- D2：<决策点>｜对方输入：<消息文件+摘要>｜结论：<选定>｜证据：<链接>｜异议：<保留原文引用；无则填 "-">
- 未协作/降级：<决策点> — <原因>｜追审：<待审/已追认/被重开>
```

**降级信封（无共享文件系统）**：在回复约定之前追加以下行：

```text
state: <open|waiting|closed|dead-letter>
phase: <相位>；reply_to: <文件名或消息摘要>；expectation: <reply|draft|review|none>
artifacts: <产物正文或引用>
```
