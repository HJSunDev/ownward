# 消除信息取用额外等待：探索记录

任务目标、耗时事实与验收题集以[单任务耗时任务](../tasks/single-task-latency.md)为准；本文集中维护探索方法、实验结论和接续状态，运行现场放入独立实验目录，不回填任务文档。

## 启动与续接提示词

```text
启动或继续“保持质量，消除取用信息额外等待”的探索任务。先阅读：
1. docs/tasks/single-task-latency.md：问题事实、任务目标与验收标准。
2. docs/research/low-latency-exploration.md：探索方法、实验材料、已有结论与接续状态。

以文档最新要求为依据，核对实际运行状态与已有产物，从有效进展继续，避免重复启动、重复试错或覆盖证据；若任务已完成，报告已有结论。

从问题根因出发，以架构、智能体工程和用户体验视角探索全流程的可行机制，不预设方案、顺序或调研路线的优先级。按文档固定控制条件，先做最小对照；保留已有改善并深入定位局部失败，以新证据决定继续、调整或转向。自行完成必要实现与验证，理解和判断始终由外部智能完成。

质量优先于效率，效率全程评估。全部通过而耗时略高的版本优先保留为保底候选，继续质量验收；若需提速，另阶段在不退化的前提下优化，不能因稍慢丢弃成果，也不能接受明显不可承受的等待与总成本。

完成并停止的条件，必须同时满足：
1. 最终方案先完整通过固定14题（6＋8），再完整通过固定24题，保住已有质量与内核能力。
2. 完整等待符合任务文档的时效边界：消除原组件额外约500秒的不可接受成本，固定14题平均完整等待约108秒及其附近范围可接受；不再要求小于等于无组件基线。按同题、同等执行条件比较，并满足易用性与总成本约束。
3. 最简有效实现、验证证据和完成结论已经保存。

全部满足后立即停止并报告，不再为额外提速、更多方案或进一步完善追加工作，不自动续跑500题。某个方案失败或候选验证完毕不等于任务完成；若出现经核实且无法自行排除的阻碍，保存进展并报告阻碍，不冒充完成。

持续将核心结论、证据位置及接续状态更新到探索文档，详细现场保存在实验目录，不污染问题分析文档。收到暂停要求时停止相关运行、保留结果并记录未完成工作，供下次使用本提示词接续。
```

## 如何探索

所有方向遵循[质量优先、效率全程评估的核心约束](../tasks/single-task-latency.md#当前任务保持质量消除取用信息的额外等待)：构思、筛选和验证均评估体验与成本，但不要求每轮同时改善质量和速度；全部通过且仅略慢的候选优先保留，提速以不退化为前提。

**探索由当前耗时问题的根因与证据驱动，面向全流程与所有可行机制。** 调研过某种思想不赋予它额外权重、优先级或必经地位；方案选择取决于它与当前问题的具体联系，任务完成以质量、体验和耗时达标为准。

1. **先解释浪费，再提出机制。** 同时查看成功交付与错误现场，定位哪些计算重复、哪些工作可提前完成、哪些信息交接改变了判断；从存入、整理、获取到使用的全流程寻找方案，不预设必须保留组件形态。
2. **用最小对照区分假设。** 每个方案先写清改变的机制、预期质量收益、用户操作负担及完整等待的变化与依据。固定模型、角色档位、原始资料和判分；规则、信息组织或处理流程可以作为明确的实验变量，其他条件保持一致。理解与判断始终由外部智能完成。
3. **保留收益，定位失效。** 先用第一批6题中最能区分假设的题验证；有实质收益则补齐6题，再跑第二批8题。已有改善的方向遇到局部失败时，先查交接和适用条件；没有新证据的重复措辞调整、收益不足的额外调用不继续。
4. **先保住质量成果，再按需要提速。** 14题通过后即进入固定24题验证，不因耗时略高而搁置已有成果；全部通过的版本优先保留，必要提速单独进行且不得退化。完整路径须使用自然清晰、等待及成本符合任务文档边界；不得将内部调度转嫁给用户，达标后不再为额外提速继续探索。

复用[既有探索方法](../engineering/information-use-exploration.md)中的归因、局部复用和中断恢复要求；避免重试已否定的机制，先查[历史探索记录](information-use-exploration.md)。存入阶段不得获知未来问题、标答或答案来源标签，后台工作引起的读取等待也须计入用户等待。

## 调研参考与使用边界

LLM Wiki 的跨资料理解复用、Ontology 的概念与关系明确表达具有项目层面的参考价值，详见 [LLM Wiki 调研](llm-wiki-research.md#对-ownward-整体方向的判断)与 [Ontology 调研](ontology-research.md#对-ownward-整体方向的判断)。**它们与当前耗时问题的联系尚未建立，不因已调研就列为优先方案，也不要求先验证单独或组合方案；当前任务可以完全不采用它们，项目后续仍可独立评估其价值。**

只有具体机制能解释当前浪费及其改善途径时，才与其他方案按相同标准考虑。若开展相关实验，收益与缺陷须同时检验；Wiki 风险见[缺陷分析](llm-wiki-research.md#缺陷用户会遇到什么根因是什么)，明确语义的表达与计算代价见[Ontology 调研](ontology-research.md#耗时与效率)：

| 检验范围 | 必须识别的代价与失效 |
| --- | --- |
| 语义质量 | 整理是否丢失细节、例外与限定，错误关联是否被反复沿用，冲突是否被无依据地消解；含义是否被过早固定，未知是否被误当作否定；输入解析错误是否进入派生理解。 |
| 持续维护 | 新信息、纠正与定义变化能否使相关旧理解更新或失效；资料增长后是否漏选、漏更新，或只完成部分整理却被当作全部完成。 |
| 实际成本 | 两者共有前置理解、组织、存储、持续更新与纠错成本；计入模型调用、计算资源、查询及实现维护负担。检查新信息立即取用时的等待，不假设无限复用，也不把前台等待简单转成后台积压。 |

**实验拆分：** 评估这两类思想时，区分 LLM Wiki 单独使用、Ontology 单独使用及两者组合，分别与同一基线对照、独立记录结论；不规定探索顺序。单独失败不代表组合无效，组合失败也不否定单独方案，一种实现失败不能直接否定整个方向。

**验证与取舍：** 同一批资料、相同使用与更新次数下，比较候选和基线的质量、完整等待及总成本，共享工作只计一次，不重复计算共同收益。涉及存入或检索变化时从原始资料走完整路径；沿用14→24题验收，并针对最可能出现的缺陷做必要验证。有收益但局部失效时先定位可修正原因；最终质量与体验必须同时达标，实际收益不足以覆盖新增成本则不采用，即使答对率提高也不能免除成本要求。

## 已备好的实验材料

工作区实验目录为 `.tmp/latency-exploration/`，不进入产品实现或正式评测结果；不含凭据副本。核心用途如下：

| 材料 | 用途 |
| --- | --- |
| `cases.json` 与 `cases/` | 索引固定14题的原始资料、实际已获信息、历史失败与成功答案、判分和证据；保留6＋8批次。标答与历史答案隔离于 Reader 输入。 |
| `baseline/` 与 `controls.json` | 封存当前组件、规则、执行条件和文件摘要；Reader 与裁判均使用既定千问模型的 xhigh 档，6题并发。 |
| `run.py` | 复用现有轻量运行时、中断恢复和官方裁判；支持已获信息的局部对照，以及现有公共运行器的完整14题分批验证与24题回归。各方案独立目录保存，默认能力不受影响。 |

局部实验入口接收“用户任务＋已获材料”，适合判断信息使用机制；存入或检索发生变化时走完整运行路径，不继续复用旧材料来宣称效果。入口不限定探索方向，涉及上游改变时使用隔离候选制品与对应执行配置，复用公共运行器即可，不另造一套运行器。

在仓库根目录执行；以下检查、计划命令不调用模型：

```text
python .tmp/latency-exploration/run.py --check
python .tmp/latency-exploration/run.py --plan --mode probe --batch 1 --numbers 82 --variant direct
python .tmp/latency-exploration/run.py --plan --mode full --batch 1 --variant direct
python .tmp/latency-exploration/run.py --plan --mode full --batch 24 --variant component
```

实测时去掉 `--plan`；`--batch 1`、`--batch 2`分别选择6题、8题，24题只走完整路径。`--mode probe`只测已获信息的处理；`--variant direct`为不启用组件的对照，`component`为封存原方案，也可传入隔离候选文件。候选按当前接入契约交接，代码只控制流程，模型执行判断。

最小实验用 `--numbers` 选择当前批次内的题，结果只代表这些题，不代替整批验收。上游候选通过 `--mode full --execution <候选执行配置>` 指定；模型和角色档位保持不变，独立制品、语义表示及协议由公共运行器验证。

## 如何读结果

- **质量：** 每题保存答案、判分、错误或未完成原因；以实际任务是否满足和官方判分为准，不额外追求无关的表达完善。失败按已有四方向归因，不凭耗时或单次标签猜测。
- **耗时：** 分开记录后台准备、用户请求至可用结果、独立评分；失败调用、等待与恢复均计入对应阶段。比较同题、同配置和相同缓存条件下的首次有效结果，并保留此前失败成本，不能挑最快或答对的一次。
- **证据：** 历史14题用于证明应保住哪些能力；部分成功来自局部复用或恢复，不能把这些记录的局部秒数当作完整等待时间。相同条件下的无组件等待基线随首轮对照采集，准备阶段不为补表额外调用模型。

实验耗时和判分保留原始记录，是否达标按任务文档的现行边界判断；高于无组件基线本身不构成失败。

## 实验结论

每个方向最多三句话，记录“机制与变量；质量和耗时收益及失效条件；保留、继续或淘汰依据”，附实验目录；接续状态随工作覆盖更新，完整请求和逐次日志只留实验目录。

- **单次交付带条件的结果（保留局部进展）：** 把有依据的不同结果及适用条件纳入一次交付，避免先强行定案再多轮补救；无新增用户操作、预处理或调用。首三题标签2／3→3／3、平均处理223.41→189.34秒，但116两份答案实质接近，不能把单次标签差异当作确定的语义改善；补齐后为5／6，361错误绑定两段购牛经历且耗时344秒，原版本不采用，继续修正决定结果的关联校验。[首三题直接组](../../.tmp/latency-exploration/runs/20260909-142443-117500/summary.json)、[候选组](../../.tmp/latency-exploration/runs/20260909-142518-466900/summary.json)、[其余三题](../../.tmp/latency-exploration/runs/20260909-142929-219200/summary.json)。
