# 向量模型方案

## 最终方案

Ownward 第一版采用 Google `EmbeddingGemma 300M`，以 `Q8 GGUF + llama.cpp` 作为本地运行方案：

| 项目 | 采用配置 |
| --- | --- |
| 模型 | `ggml-org/embeddinggemma-300m-qat-q8_0-GGUF` |
| 模型文件 | `embeddinggemma-300m-qat-Q8_0.gguf`，SHA-256：`6fa0c02a9c302be6f977521d399b4de3a46310a4f2621ee0063747881b673f67` |
| 运行时 | llama.cpp `b10488` 官方 Windows x64 CPU 运行时，SHA-256：`6c938f6d79aac96cb90fda673aade20cff9b1b6c1e97de04f4d5d60bca107082` |
| 运行配置 | CPU-only，2 个推理线程 |
| 向量生成 | 使用官方查询与文档提示、Mean Pooling 和 L2 归一化；768 维输出截取为 512 维后重新归一化 |
| 向量规格 | 512 维 float32，单条 2048 字节 |

## 职责边界

本方案只承担本地语义表示、候选召回和相似度排序，决定基础语义信号的质量与运行成本；它不负责信息关系、场景适用性、证据融合和主动检索，也不代表 Ownward 的最终检索效果。Ownward 内核负责将向量信号与词法、关系、场景及累计证据组合为完整检索能力，并对最终效果负责。

## 选择依据

EmbeddingGemma 在三款候选的两组 Ownward 质量实测中均排名第一。Q8 GGUF 方案相对质量无损的直接 ONNX 方案，将完整周期峰值内存降低 `85.9%`、模型与运行时体积降低约 `20.7%`，代价是热查询 P95 上升 `6.6%`，整体与中文排序质量小幅下降，英文同语言质量未观察到变化，中英文交叉检索下降较为明显。

按照质量 60%、资源 40%，且中文同语言高于英文同语言、二者均高于跨语言的产品权重计算，Q8 GGUF 方案综合得分 `98.47`，直接 ONNX 方案为 `78.32`，原 Transformers.js 方案为 `73.12`。Q8 GGUF 在保持主要使用场景质量的同时，将本地运行代价降到了普通笔记本可以自然承担的范围，因此作为第一版方案。
