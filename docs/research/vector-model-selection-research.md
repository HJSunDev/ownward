# 向量模型选型研究

## 需求

所选向量模型必须首先达到同类前沿的检索质量，并能在普通用户的普通笔记本上以不高于普通应用、不影响其他应用正常运行的资源占用满足性能要求；任何一项无法满足，便不采用本地向量模型方案。

## 社区调研

以真实采用量、社区衍生与运行时支持判断是否经过广泛实践，以 MTEB、C-MTEB 等公开评测和可复现研究判断效果是否获得认可。Hugging Face 月下载量只是采用代理指标，不等于独立用户数；最终是否满足 Ownward 需求仍必须实测。以下数据截至 2026-08-19。

## 评测契约

本任务只选择承担语义候选召回与排序的本地向量模型，不评价完整 Ownward、关系与时间推理或外部智能体的主动检索能力。三款候选只比较最终可交付的本地配置；不得修改或接入 Ownward 主线实现。

### 证据边界

- 公开 MTEB、C-MTEB 等可复现结果用于判断模型的通用质量与前沿位置，记录来源、模型版本、配置和可比限制，不在本机重复运行已有公共评测。
- Ownward 专项实测只回答最终量化配置能否处理产品必需的中英文个人信息语义召回与排序，不用自建数据重复证明通用能力。
- 资源实测只回答模型能否作为普通笔记本上的普通应用运行；输出维度及单条向量字节数作为长期存储成本报告，不预设信息规模，也不评价 Ownward 索引实现。
- 已有临时语料只作为专项样本来源；不得继续扩充、逐条修补或围绕它建设通用评测体系。

### 质量准入与选择

公开证据必须表明候选在可比的中英文检索评测中属于当前主流前沿；公开结果不能替代最终交付配置的本地专项实测，也不得把不同数据、维度或精度的分数直接混为同一口径。

Ownward 专项轨道固定使用最终量化配置，以 `Recall@10` 和 `nDCG@10` 为指标；整体及每个必测类别的两项指标均不得低于 `0.95`。三款候选使用同一查询、语料、预处理边界和真值；模型各自使用官方要求的查询与文档前缀，不得针对结果调参。

通过质量与资源全部硬门槛的候选中，先比较最终量化配置的 Ownward 专项质量；专项存在可信差异时选择更高者。两款候选的专项整体指标差异不超过一个百分点，且配对 bootstrap 的 95% 置信区间不能证明其中一款更优时，视为专项质量实质等价，继续比较同一任务、数据、指标和可比配置下的公开质量证据；公开证据能够可靠区分时选择更高者。只有专项与公开质量均无法可靠区分时，才选择资源占用更低者。不得把不可直接比较的公开分数强行排序，也不追加没有明确决策价值的扩大测试。没有候选同时通过时，如实判定当前候选无可用方案。

### Ownward 专项数据

- 从现有冻结语料中按查询标识排序，每个必测类别取 64 条，共 512 条查询；类别包括中文、英文、中英交叉、同义改写、长短表达、噪声、困难负例和词面相似但语义无关。64 条使每类召回结果以 1.56 个百分点为最小变化单位，足以判断 0.95 门槛；通用质量由公开大规模基准补充证明。
- 每条查询保留真值文档，并在同一隐藏语义世界中按与候选输出无关的字符三元组相似度选取两个最难负例，形成 1536 条文档的共享检索语料；比较前统一执行 Unicode NFKC、大小写折叠并移除空白和标点，同分时按文档标识排序。查询、文档和真值清单在任何候选运行前写入哈希并冻结。
- 冷启动抽样复核只排除真值不唯一、查询无法理解或相关文档不能回答查询的无效样本；不得润色表达、增加类别或为了提高难度反复重生。排除后仍须保持每类 64 条，否则从同类后续查询按固定顺序补足。
- 三款候选在同一查询上配对比较，保留逐查询排名与分数；置信区间使用冻结的配对 bootstrap。专项数据达到上述最低充分条件后立即实测，不再继续完善测试集。

### 资源硬门槛

基准设备为 Intel i7-10710U、16GB 内存、Windows、仅使用 CPU，最多使用 4 个逻辑处理器。最终可交付配置必须同时满足：

- 模型与最小必要运行时的安装体积合计不超过 1GiB；
- 预热后的模型进程峰值常驻内存不超过 1GiB，按测试机全部逻辑处理器总容量折算的空闲 CPU 不超过 0.1%；
- 代表性查询的端到端向量生成 `P95` 不超过 500ms，冷启动不超过 3s；
- 无需管理员权限、付费服务或外部常驻服务，许可与发布方式允许普通用户本地安装使用。

资源验证按成本从低到高执行：

1. 从空目录构建并端到端验证同一份 Windows x64 最小交付运行时，再测量它与各候选必要模型文件的实际体积；交付运行时只包含本平台文本向量生成真实需要的引擎与依赖，不得把评测环境、包缓存、其他平台二进制、开发文件或无关功能依赖计入，也不得用未经运行验证的理论裁剪结果。按 `实际维度 × 4` 计算每条 float32 向量的字节数；向量成本只作模型间比较和未来容量计算，不构造固定规模数据。
2. 每款候选独立执行 3 次冷启动；预热后使用同一组 100 条代表性查询轮换执行 2 轮，记录 `P50/P95/P99`、峰值进程树内存和 60 秒空闲 CPU。只有结果距离对应硬门槛不足 10% 时，才追加 2 次冷启动或 1 轮查询；测试顺序轮换，模型之间不共享进程。

任何资源硬门槛已经明确失败的候选立即失去入选资格，但仍须完成同口径 Ownward 专项质量测试，以形成三款候选真实、完整的效果与资源对照；不得因资源结论省略质量证据。

每款候选只在首次专项质量测试前运行 20 条同配置输入预检吞吐，并直接将其作为预热，不在其他阶段重复；据此更新该候选预计完成时间。发生以下任一情况立即停止当前进程、保留检查点并在本文“执行状态”中记录，不得继续等待或反复重跑：

- 预检推算超过表中对应阶段上限；
- 实际耗时超过预检推算的 1.5 倍；
- 连续 10 分钟没有检查点推进且进程不能证明仍在有效计算；
- 测试进程峰值内存超过 4GiB、系统可用内存低于 2GiB，或明显影响正常使用；
- 发现测试内容写入隔离目录之外、口径漂移、结果文件损坏或候选条件不一致。

时间只在阶段开始、完成、异常停止或恢复时维护一次，不得为了计时频繁轮询、重复检查或打断计算。

## 测试计划

1. 冻结公开证据来源、512 条查询、1536 条共享文档、真值、模型版本、最终量化配置、官方预处理和资源运行配置；现有旧口径配置和局部结果全部失效，不得进入结论。
2. 先完成静态资源核算和实际运行资源测试，明确淘汰越过硬门槛的候选。
3. 对三款候选全部执行同一份 Ownward 专项质量测试，形成完整效果对照；通用质量使用已冻结的公开证据，不在本机重复计算。
4. 对三款候选执行已经冻结的高区分度质量补测，联合原专项广度结果和补测难例结果判断 Ownward 契合度。
5. 只在全部质量与资源硬门槛通过的候选中选择：先比较最终量化配置的 Ownward 专项质量，专项无法可靠区分时比较可直接比较的公开质量证据，两者均无法可靠区分时再选择资源占用更低者；没有候选通过时明确返回无可用方案，不扩大候选或降低门槛。
6. 生成 `docs/research/vector-model-evaluation-report.md`，将最小复现脚本和机器可读原始结果保存在 `benchmarks/vector-model-evaluation/`。报告必须包含模型与版本、证据边界、公开成绩来源、两份专项数据与真值、逐类质量、安装与运行资源、单条向量成本、硬门槛矩阵、异常与限制、淘汰理由、最终结论和复现方式。
7. 冷启动复核报告后停止相关进程，保留隔离目录中的模型、数据、运行时、虚拟环境、脚本、缓存和原始结果，确保后续可以继续复核或补测。清理前须验证全部待删除内容严格位于隔离目录；只有用户明确要求清理时才执行删除，测试完成本身不触发清理。

### 预选模型运行时优化验证

验证目标是在保持 EmbeddingGemma 模型能力、官方预处理和 512 维输出语义不变的前提下，同时降低当前交付配置的实际运行内存与热查询延迟；这一步只收敛最终本地运行方式，不接入 Ownward 主线。

社区与官方资料已经证明该方向具有现实可行性：[Google](https://ai.google.dev/gemma/docs/embeddinggemma) 将 EmbeddingGemma 明确设计为普通手机和笔记本上的端侧模型，并给出量化运行低于 200MB 内存的目标；ONNX Runtime 官方提供[线程与空转](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)和[内存分配](https://onnxruntime.ai/docs/performance/tune-performance/memory.html)策略的运行时调节能力；[llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/examples/embedding/README.md) 已提供 Windows 文本向量运行入口，[ggml-org](https://huggingface.co/ggml-org/embeddinggemma-300m-qat-q8_0-GGUF/blob/main/embeddinggemma-300m-qat-Q8_0.gguf) 发布了 329MB 的 EmbeddingGemma Q8 GGUF，正确包含 Dense 投影的[社区转换](https://huggingface.co/cstr/embeddinggemma-300m-GGUF)与 Hugging Face 参考输出达到 `0.9998` 余弦一致度。以上证据只证明存在明显优化空间，不能替代本机资源和 Ownward 质量复测。

只验证以下两条已有依据的路线，按顺序执行：

1. 保持当前 ONNX INT8 权重、分词、提示格式、池化、归一化和 512 维输出不变，使用最小 ONNX Runtime 调用路径，并在最多 4 个具有明确差异的线程、空转和内存分配配置中寻找资源最优解。预计 20～30 分钟；若没有配置同时改善内存与热查询延迟，立即结束该路线。
2. 第一条路线没有有效结果，或虽有改善但实际资源占用仍明显不符合产品预期时，验证正确包含 Dense 投影的 Q8 GGUF 与 llama.cpp 原生 Windows 向量运行时，完整复现官方提示、Mean Pooling、L2 归一化和 512 维输出。预计 35～60 分钟，另计约 329MB 模型下载时间；先排除调用配置错误，正确配置仍不能通过向量一致性检查时立即淘汰，不自行修补模型转换。

两条路线合计最多投入 90 分钟，不含网络下载等待。任何阶段超过预计上限、连续 10 分钟没有有效进展，或出现需要修改模型、扩大测试范围、自行编译大型运行时才能继续的情况，立即停止并登记事实，不继续消耗时间。

最终候选必须在同机、同输入下与当前配置交错复测两轮，其内存与热查询延迟改善均须超过重复测量波动；随后重新执行已经冻结的 512 查询专项测试和 24 查询高区分度补测。两套质量结果不得出现实质下降，否则该路线无论资源改善多少都不采用。验证完成后保留最优配置、原始结果和复现方式；若两条路线均失败，维持当前预选配置并如实保留资源限制。
