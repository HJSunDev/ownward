# 信息使用能力探索记录

记录日期：2026-09-06。本文保留探索依据与实验结论；产品职责以[核心需求](../product/requirements.md#信息使用能力)为准。

## 一、背景

V2 最终测试最初取得 110 道有效结果：单对话题 68／68 正确，跨对话题仅 35／42 正确（83.33%），7 个错误全部集中在跨对话汇总。修复信息获取短板后，后续九道失败的复核仍发现：多题关键事实已经交付，Reader 却自行增加限制、错误合并事件，或未能合理处理时间与事实冲突。

已有能力核验支持继续使用 Qwen3.8 Flash，但模型具备能力、内核提供信息，并不自动保证任务完成质量。由此产生独立需求：工程上不仅要帮助智能体取得信息，还要帮助它有效使用已经取得的信息，不能把这部分失败一概归为模型问题而停止改进。

## 二、核心思路

**将“信息使用”作为与“信息获取”同等重要的独立产品能力，通过设计外部智能体处理信息的工作过程，提高它在真实、不完美的信息环境中完成用户目标的质量。**

外部智能体始终是主角，提供理解、推理与取舍；Ownward 提供必要的协作支撑，不内置模型，不用确定性代码代替语义判断，也不把增加提示词或处理步骤当成效果。实现路径保持开放，以实际收益选择方案，不预设必须采用工作区、固定流程或多个角色。

方向判断已写入核心需求：产品方向成立且具备工程可行性，具体方案暂时失败不等于方向错误。信息存在冲突不构成放弃任务的理由，只要预期结果合理可行，就应努力完成；无法由事实合理支持的标答，则与系统能力缺陷分别判断。

下一轮优先验证第 82、114、116 题背后的信息使用错误，问题、原因与验效重点统一见[优先三题登记](../tasks/kernel-v2-final-test-failure-analysis.md#信息使用工程优先解决的三题)；第 90、112 题作为伴随口径歧义的辅助案例。

### 多角色头脑风暴与对抗审查（2026-09-06，设计阶段）

两个子智能体分别从产品设计、智能体工程与反方审查出发独立提案；主任务从架构边界、产品价值和乔布斯式简化取舍角度审查，再进行交叉反驳与第二轮复辩。讨论依据上述实验及原脚本，不以多角色共识替代实测。

| 候选 | 关键质疑与辩论结果 | 取舍 |
| --- | --- | --- |
| 先定任务口径再看材料 | 原型已有 `interpret-task → review-task → plan`，前两步尚未接触业务材料。 | 撤回“新方向”判断，不重复投入。 |
| 固定拆成逐项判断再汇总 | 旧工作区已有局部原文核验；新提案仍未解决首轮漏项、关联不全以及最后重判或锁死错误的矛盾。 | 撤回完整方案，不为它重建工作区。 |
| 重排独立来源，检查判断是否变化 | 可用于发现顺序影响，但稳定错误仍会稳定，分歧也不直接给出正确结果。 | 仅保留为必要时的根因诊断，不作为提质产品方案。 |

| 原任务直接交接，减少上游改写造成的干扰 | 114 的上游把任务改成检查是否出现“替换”动词，下游据此排除事实；删除这段改写、让下游直接处理原始任务，是当时尚未单独验证的变量。 | 两题小试后继续完成九题筛查，判定无效并淘汰；不意味着所有委派都应取消。 |

**最有证据的突破口：任务在交接时被增加了条件。** 在[第 114 题的委派文本](../../.tmp/information-use-product/agent-flows-20260906-193337/gpt4_ab202e7f/challenge/challenge.json)中，上游要求核查原文是否使用“replace 或等价主动动词”；[下游判断](../../.tmp/information-use-product/agent-flows-20260906-193337/gpt4_ab202e7f/challenge/consult-0.json)进而以“upgrade 是名词”等理由排除咖啡机，而原始需求只要求统计更换或修理的厨房用品。这里已观察到错误条件被传递并采用，尚未证明它是全部失败的共同根因，也未证明删除后必然改善。

**当时确定的最小对照：** 完整取第 82、114 题这轮已有委派，包括正常的烤面包机去重委派，不只挑错误子问题；两臂均使用原始任务、同一已选原文、同一模型与档位、格式、预算及最终汇合方式，仅改变是否附带上游改写的子问题。两臂统一使用“依据给定材料处理原始任务”的中性职责，避免删除子问题后留下残缺指令，并重新取得两臂首次结果，不把历史答案当作严格配对。

验证同时看新增限制是否减少、正常分工是否受损、最终结果是否改善；局部改对但汇合又改错仍算流程失败，不能靠锁死判断掩盖。若有收益，再复验完整失败集合及固定能力集；若无收益或副作用抵消收益，停止该实现。先在现有接入侧辨别机制，只有验证暴露出现有产品能力无法支持的必要操作时才补产品实现，不先建框架。
