# 图对 Ownward 的收益与成本

调研日期：2026-09-10。依据为原始研究、官方实现说明与 Ownward 产品需求；公开实验数字不冒充本项目实测。

研究顺序：**先确认图对产品场景的收益，再比较不同表示与实现的收益成本，最后设计和验证选中的方案。** 现有代码只属于后续复用审查材料，不作为图价值、类型选择、实现上限或成本下限的判断依据。

## 核心判断

**图对 Ownward 有实质产品价值：把信息之间有依据的关系显式组织并持久化，供不同任务、时期和智能体复用，提升证据覆盖、间接关联发现及依赖追踪能力。** 这一价值来自长期积累、共同使用的产品场景，不依赖项目曾经实现过哪种图；资料图、实体图、事件图及其组合均应按收益和成本比较。

**收益方向有充分研究与机制依据；具体哪种设计的净收益最高，不能由历史实现或竞品名气决定。** 有低成本的关系复用路径，不意味着任意建图方案都划算。无需用“原来答错、加图答对”证明价值，也不能以关系存在、字段非空或竞品总分代替价值。

## 客观判断标准

比较的是**相同资源能提供多少可靠信息，以及同等质量需要付出多少成本**，并覆盖存入、长期复用、增长、更正和遗忘；既看相关场景的增益，也看普通查找是否受损。

| 维度 | 能识别真实增益的依据 |
| --- | --- |
| 质量 | 同阅读预算下必要证据覆盖率、完整依据链比例、关系的对象/方向/条件准确性，以及无关、过时材料占比。 |
| 效率 | 同等覆盖和交付质量需要的搜索轮数、阅读tokens、模型调用及完整等待；关系复用是否实际减少重复工作。 |
| 长期能力 | 资料增长、需求改写及信息变化后的覆盖稳定性，依赖漏处理、误处理和陈旧信息暴露情况。 |
| 成本 | 关系生成、检索、存储、更新纠错、失败重试与恢复的总增量；写入返回、关系可用、用户得到结果分别计时，并关注尾部等待。 |

**有可靠收益且成本可接受，就是正向增幅；允许为更高能力支付合理成本，不要求每项成本都下降。** 若声称省钱，须扣除建库与持续维护成本；若声称质量更高，须确认不是单纯多给材料或增加模型工作。公开的方案比较支持机制可行性，只有控制其他差异的对照才能进一步分离图结构本身的贡献。

| [Hindsight检索机制](https://hindsight.vectorize.io/developer/retrieval)、[Graphiti机制](https://help.getzep.com/graphiti/getting-started/overview) | 前者通过关系补找语义或关键词不相近的材料；后者保存关系的有效时间及历史，并支持混合检索。 | 间接发现和持续变化管理是实际产品能力；它们的整体成绩不能拆算成图本身的增益。 |

## 如何在 Ownward 的实际场景中起作用

以下是根据产品需求与上述研究作出的机制判断，收益幅度尚未在 Ownward 实测。

| 产品场景 | 图的增益如何传递到用户 | 成立条件与代价 |
| --- | --- | --- |
| 长期积累经验、方法及适用条件 | 找到一个方法后，沿有依据的关系取得支持材料、适用场景和反例，帮助智能体少遗漏条件、少误用经验；原来能答对也可以取得更充分依据。 | 关系必须忠实且被交付。宽泛或错误关联会增加噪音；遍历到冲突不等于已判断哪方成立。 |
| 不同时期和不同智能体使用同一信息体系 | 关联不随某个智能体的上下文结束而消失；后来的智能体复用已有连接点，减少重新搜索和关联原文的工作。 | 节省的是找关联的工作，不是省去理解用户需求。频繁复用、相对稳定的信息更有利；首次整理与校验仍计成本。 |
| 用户更正信息、经历变化或遗忘资料 | 从来源反查已知依赖，定位需要失效或重审的组织结果，减少继续使用旧依据或无差别重算。 | 依赖不完整会漏审，错误依赖会扩大重算。现有版本、更正和遗忘能力不能重复算作新增图收益。 |
| 跨领域资料增长、需求没有直接关键词 | 借助中间资料连接语义不相近的内容，增加发现间接联系的机会，扩展有限上下文下可处理的任务范围。 | 找不到入口、缺桥接关系或存在高连接度噪音节点时收益下降；完整全局总结还需额外组织机制，不能算作任意图的固有能力。 |

这些场景来自[信息组织、主动检索及共同使用需求](../product/requirements.md)。软件智能体或具身智能体通过相同接口获得上述收益；图本身不负责联网、设备接入或用户所有权，也不需要把内部结构暴露给用户。关系表和邻接索引都能实现这种关系组织，无须专门的图数据库或可视化界面。

## 不同图如何取舍

以下比较表示方式，不是互斥产品。时间、来源及有效条件可以附着于不同图；增量或批量维护、索引算法和存储引擎需要分别选择，不能把某个实现的成本等同于整类图的成本。

| 表示方向 | 对产品最直接的收益 | 主要代价与不足 |
| --- | --- | --- |
| 资料、事实与证据之间的关系图 | 关联经验、方法、支持材料与依赖，便于原文核对和影响追踪。 | 节点过粗时仍需读很多原文才能分清具体对象与事件；粗粒度不保证总成本低。 |
| 实体与资料连接的图 | 跨来源聚合同一个人、项目、地点或概念的材料，减少反复找别名和相关记录。 | 需要实体识别、消歧和去重；共同提及不等于存在确定的业务关系。 |
| 带明确关系的事实、事件图 | 表达谁在什么条件下做了什么、对象之间如何关联，更适合跨事件关联和精确约束；补充时间语义可支持变化与历史查询。 | 需要保存事件边界、角色、条件和来源，错误合并或遗漏限定会传播；抽取与持续纠错成本更高。 |
| 层级、社区及摘要组织 | 面向整个资料库发现主题、形成概览，减少每次逐份阅读。 | 聚合与摘要有额外生成、更新和信息损失成本；并非精确事实取证的通用替代。 |

实体连接与有类型的事实关系并不相同：[Mem0当前图](https://docs.mem0.ai/platform/features/graph-memory)采用实体与记忆连接，不标注实体间的业务关系；[Graphiti](https://help.getzep.com/graphiti/getting-started/overview)则维护带时间的实体关系。[GraphRAG](https://microsoft.github.io/graphrag/index/methods/)还增加社区摘要；这些不同机制分别承担不同收益，不能统称“上图”后直接比较总分。

**对 Ownward 的取舍：** 来源可追溯、关系能修正、能被多次使用，是各候选必须支持的能力；资料、实体、事实或事件的粒度应按覆盖质量与总使用成本选择，允许组合。仅以“资料图更轻”选资料图，或以“事件图更丰富”选事件图，都缺少依据。社区摘要只有在全局整理收益覆盖持续成本时才值得加入。现有证据不足以宣布某个具体组合已是本项目的最优设计。

### 设计选型

依据产品场景选择**证据单元＋对象线索＋有据关系**的组合，作为实现与验证的目标。它把资料图的来源追踪、对象图的跨记录发现及事件表达的条件边界结合起来；这是有依据的架构选择，实际增益与成本仍须实现验证，不能称为已经实测的最优方案。

| 比较项 | 选择及原因 |
| --- | --- |
| 只连整项资料 | 保留为短信息的自然粒度；长资料中的多个事项需原文定位，否则找到关联后仍需反复阅读、重新区分事件。 |
| 实体中心或共现连接 | 采用对象提及与名称索引找候选；不把共现当作关系，也不依赖全局实体合并，减少错误身份传播与维护成本。 |
| 全量事实、事件三元组 | 保留忠实陈述及有价值关系，不把全部内容强制转换为三元组；事件、条件和不确定性跟随原文单元，避免为了表达丰富而扩张抽取与推理体系。 |
| 社区、层级摘要与全局图推理 | 不纳入本工作包；当前增益可通过局部关系复用取得，尚无必须支付全局生成和持续重算成本的范围内需求。原文中明确的层级关系照常保留。 |
| 运行方式 | 在已有语义协作中增量组织，通过现有检索与导航提供材料；选择可重建记录与邻接索引，不增加图数据库、独立智能体或固定在线模型链。 |

关键取舍是**表示细到足以减少误读，构建和取用仍以有限材料为单位**。同名、跨事件、多条件、更正和遗忘的设计走查确认了必须保留的身份与来源边界；抽取质量、实际阅读节省及高连接度开销属于实现验证项，不以设计推演冒充实测。选择依据及约束已足以进入实现，无需先重启一轮泛化调研。

| 审查对象 | 事实与处理决定 |

| [语义结果结构与归一化](../../internal/semantics/provider.go) | 已有摘要、线索及资产关系；关系仅指向候选资产，证据为文本，去重只考虑方向与目标。保留通用语义协作边界；扩展单元与定位，区分对象身份和陈述等价，替换会吞掉不同关系或条件的去重规则。 |

| [检索融合](../../internal/core/service.go) | 关系扩展已存在，但新增邻居主要依赖折减后的种子得分，紧凑结果没有完整连接依据。保留直接读取与混合召回；补齐关系候选的入选、依据交付和继续取证，不能以内部已查图等同于用户得到收益。 |
| [派生存储](../../internal/derived/store.go)与[信息控制](../modules/information-control/README.md) | 已有资产版本、实际输入引用、世代、回收与删除屏障边界。沿这些端口扩展记录，验证新增单元、名称和关系全部受控；不因旧能力存在就假定新结构已经安全。 |

旧代码审查仅确定复用与修改落点，不承担新设计的质量或性能证明。产品行为见[关联信息的可靠取用](../product/related-information.md)，表示及运行契约见[关系组织架构](../modules/semantics/graph-organization.md)。

## 成本是否可能被收益覆盖

**可以，但关键是表示粒度、关系准确性、复用频率与更新牵连范围。** 预先组织可减少在线探索，增量维护可减少重复整理；细粒度表达可能增加建库成本，却减少后续阅读，必须比较完整使用周期。

| 成本项 | 设计选择怎样改变成本 |
| --- | --- |
| 存入与关系可用 | 共现连接、有类型的关系抽取、事件组织及社区摘要需要不同工作量；可合并语义处理，但新增判断、消歧及输出不免费。整理转到后台仍须计成本和信息可用延迟。 |
| 取用等待与阅读 | 预建关系的索引遍历可以由程序执行；另加在线模型探索则增加等待。应比较找到完整依据的总过程，避免检索便宜却让智能体读更多无关材料。 |
| 更新与纠错 | 来源依赖、局部失效及增量更新可以缩小重审范围；复杂关联、身份误合并及聚合摘要会增加传播和修正成本。时间语义能帮助区分历史与当前，也增加维护义务。 |
| 存储与恢复 | 随节点、边、向量、证据、摘要和历史副本增长。使用来源引用、避免无收益的重复表示可以减负；关系表、邻接索引或图数据库按实际规模与查询需求选择，不能先锁定引擎。 |
| 用户与质量 | 用户不应人工分类、修图或选择模式；证据不足时保留未知、允许无关系，以原文为依据。错误连接会跨任务重复传播，纠错成本必须计入。 |

若只计算费用，增量为：**建图＋更新纠错＋存储恢复＋关系查询开销－重复取用节省**。这个差额可以为正：只要额外取得的可靠能力值得支付且用户等待、资源可接受，仍然是好方案；但频繁变化、极少复用的临时资料不宜承担重度预整理。

## 对项目的最终判断

**图的产品价值成立，目标设计采用证据单元、对象线索与有据关系的组合。** 选择来自产品场景及各类表示的收益成本比较；高通过率不抵消能力上限提升，历史投入也不构成保留某种方案的理由。

研究与设计支持进入实现，实际净收益由工作包验收确认。旧实现审查只决定复用与替换的落点，不反向限定设计；所有语义理解和判断仍由外部智能承担，用户无需维护图结构。

## 工作包：图能力设计、实现与验收

目标：从产品场景出发，交付能提高信息质量、使用效率或能力上限，且用户等待与持续成本可接受的图能力。按以下顺序推进：

1. [x] **产品设计。** 已明确用户增益、自然使用方式、范围及质量、等待和持续成本要求，见[产品设计](../product/related-information.md)。
2. [x] **架构设计。** 已完成图类型与组合取舍、表示和全流程设计，以及目标确定后的旧实现审查，见[选型与审查](#设计选型)和[架构设计](../modules/semantics/graph-organization.md)。实现验收负责验证实际收益与成本。
3. [ ] **实现与验收。** 完成选定范围的最简有效实现，按本文客观标准验证真实增益、完整成本及受影响的原有能力，保存设计、实现和验证依据。

关闭条件：明确的产品增益得到验证，原有质量、安全与易用性不退化，等待和持续成本符合设计约定，必要交付及证据保存完整；达成后停止，不为理论极限继续扩展，也不自动续跑500题。
