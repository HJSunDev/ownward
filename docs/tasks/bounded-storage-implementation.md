## 前置验证

### 价值与边界

前置验证用于以最小成本发现会迫使架构更换关键机制或技术路线的问题，避免完成整体实现后才返工。它只回答：**尚未证实的关键机制，在既定质量、资源与体验约束下是否具备实施可行性？**

它不回答完整产品是否已经实现、所有功能与故障场景是否通过、是否可以发布；不提前实现一整套产品，也不以小样代替正式验收。正式运行时集成及完整接入测试归单元一，并发控制与恢复归单元三，迁移及整体交付归单元四。

前置验证不计入执行单元。复用已有材料与有效证据，不重做语义准备或整套题集；证据足以决定实施或修改机制即停止，不追加穷尽验证。已验证内容仅在直接依赖变化或出现反证时重验。

### 已取得的证据

- [x] **内存超限根因与隔离修复。** 相同编译器和输入下，仅修正无用缓冲分配，进程树峰值由664.78 MiB降至204.97 MiB；6组输入、39个向量逐字节一致。测量含连接器和5 MiB工作区，仅证明隔离修复成立；正式运行时集成结果见单元一。[验证证据](../../benchmarks/acceptance/suite/adapters/product_resource/bounded-assembly-recovery-20260916.json)。
- [x] **数据库基础行为。** 同一隔离小样通过原文保真、回滚、读快照、检查点及完整性校验；不代表完整并发调度和故障恢复已经通过。[验证证据](../../benchmarks/acceptance/suite/adapters/product_resource/bounded-assembly-recovery-20260916.json)。
- [x] **向量筛选离线初检。** 复用4,734条真实向量，13个探针的Top-10均与实验参照一致；采用双精度计分及理想页面布局，尚不能证明正式计分与实际落盘成本。[初检证据](../../benchmarks/acceptance/suite/adapters/product_resource/bounded-filter-design-evidence.json)。

### 其余两项机制验证结论

- [x] **落盘向量检索具备实施价值。** 复用4,734条真实向量，13个查询的候选、排序和分数均与正式 `derived.Index.Search` 完全一致。采用有界批读后，相比落盘精确扫描，平均SQLite读取量由11.67 MB降至3.59 MB，查询由25.78毫秒降至19.14毫秒；查询专用进程峰值18.10 MiB。原全驻内存查询约0.69毫秒，落盘仍增加本地读取成本，不能将筛选收益表述为比原内存实现更快。
- [x] **现有SDK支持有界流式接入机制。** 贯通stdio协议、HTTP及结构化／文本双份响应；约4 KiB、1 MiB、16 MiB的JSON传输负载均保持原文字节及相邻字段一致。最大负载对应约8.44 MiB原文，流式处理峰值15.93 MiB、耗时2.65秒，普通SDK对照为337.03 MiB、3.72秒；小负载增加约1.8毫秒。大负载无需整包进入SDK内存。

两项均取得支持实施的证据，可以进入单元一。[测量、边界及复现材料](../../benchmarks/acceptance/suite/adapters/product_resource/bounded-remaining-preflight-20260916.json)。向量读量包含真实SQLite页面开销，操作系统缓存未清空；流式验证是同进程管道与本机HTTP的隔离机制切片，未包含本地模型。以上不代替完整产品内存、冻结负载耗时及功能验收，相关检查随既定执行单元完成，不另开前置验证轮次。

按相同资料密度与筛选效果估算，累计原文500 MB、1 GB、10 GB时，向量查询约为0.19、0.38、3.84秒；这些是温缓存条件推算，冷读还受磁盘带宽及随机访问影响，不是已验证的性能保证。详细读量和假设见证据，不准备大规模新材料。

本节只维护验证结论与证据；依赖变化或出现反证时更新对应结论和顶部状态，已经完成的内容不得继续列为待办。

## 单元一：有界存取底座

目标：贯通有界的保存、按ID读取与更新。对应架构第2～4节及第5.1节的权威发布部分。

- [x] 将已验证的内存修复机制接入正式构建，生成相互兼容的运行时制品并重算清单与空间身份；落实共享预算和固定连接池。
- [x] 实现SQLite权威资产、控制状态、分块正文、定向读取端口、原子发布及操作回执。
- [x] 贯通连接器、HTTP和工具的流式输入输出，保持权限、修订、取消和接续语义。
- [x] **验证并关闭。** 核对正式调用路径和修复范围；保持模型、精度及计算配置不变，与修复前正式运行时逐字节比较短／长查询、中英文资料及批量的向量输出，保存源补丁、构建配置与制品身份。原文逐字节一致，重复请求不重复执行，大小输入不整包加载，完整进程树峰值保留规定余量。此单元不承担自然语言检索交付。

运行时仅采纳EmbeddingGemma嵌入模式的无用词预测缓冲修复，以及保留管道和生命周期管理的Windows无控制台启动。实验用C接口简化服务和模型类型裁剪不进入正式版，实验制品身份及内存成绩不代替正式构建的验证。

验收：完整运行时的6组、39个向量与修复前逐字节一致；新格式的创建、批量、读取和更新通过真实stdio→连接器→HTTP→工具→SQLite链路。最大输入原文约10.24 MiB，结构化及文本结果均保真，重复操作不重复创建；4线程条件下服务、模型及连接器合计峰值217.46 MiB，距270 MiB上限留有52.54 MiB。未设置额外Go内存上限。全仓Go测试通过，并验证原有依据身份、权限撤销、过期版本、取消回收与协议引用隔离。[证据与复现入口](../../benchmarks/acceptance/suite/adapters/product_resource/bounded-unit-one-20260916.json)。

独立复审（2026-09-16）发现并修复RPC编号转义后无法匹配回执的问题：统一按SDK逻辑身份匹配，HTTP、stdio、客户端及重复编号隔离测试通过。修复后受影响接入测试、静态检查与清单校验通过，随后对固定版本重新完成整轮独立审查，期间源码未变；发现的特殊字符规范编码、批量回执逐项恢复两项缺陷已集中修复并通过自验；修复后的固定版本完整复审通过，无剩余阻塞项，单元一关闭。测量、审查与修复版本身份分别保留在上述证据中。

新格式入口为 `core.StreamingAssets` 与 `mcpserver.NewStreamingStorage`；连接器仅在服务声明对应能力后启用流式路径。单元一验收覆盖已实现的四项存取工具，完整检索、语义组织、维护、控制界面与旧资料切换仍按后续单元完成，不将此成绩表述为完整产品迁移验收。

## 执行边界

每个单元实现并验证通过后再进入下一单元；授权、版本、原子可见与停止使用检查随各条路径落实。四个单元不是独立发布版本，迁移交付前不切换现有用户资料，不开放尚未完成的能力。

各单元改变正式代码行为时，同次更新上述数据说明文档的受影响部分；单元四关闭前完成全篇一致性核对，未实现的设计不得提前写成现状。

复用有效验证成果，正式接入核对实际调用路径；各单元优先进行受影响路径的确定性验证，最终回归集中在单元四，不重复语义准备或逐单元全量跑题。完成后停止，不自动续跑500题。
