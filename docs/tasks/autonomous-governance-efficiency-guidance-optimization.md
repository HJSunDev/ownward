# 自主治理效率引导优化

> **状态**：已完成；实现、无损迁移、事故回放、真实 Codex 冷启动与对抗式复审均已通过。
> **职责**：定义一次自主治理支线的效率引导能力修复任务，使支线能够及时获得主线的真实事实、识别低价值路径并给出有依据的改进建议。本文不规定 Ownward 主线应采用的开发、调试或验收流程，不修改产品需求与验收标准，也不替代自主治理核心 Skill 及其运行时规范。
> **项目根目录**：本任务唯一作用于 `E:\Dev\ownward`；所有相对路径、Git 读取、构建与验证均以此为基准，承载 Codex 对话的其他项目目录不属于本任务范围。

## 一、两个真实低效率场景

### 场景一：首个内核基线工作持续约四小时仍未跨过正式完成点

**问题表象**

- 2026-08-24 的主要连续执行轮次从 02:29 持续到约 06:35，单轮约 4 小时 5 分；连同紧邻的恢复工作，用户实际观察约 4 小时 20 分。
- 开始时，候选的 core/frontier 与资格预检已经有效，qualification 已保存 20/42 个语义单元。期间形成了有价值的时延归因、语义终态恢复、查询工具边界修复、定向探测、测试和多个适配器提交；但被打断时，最新适配器仍未完成最终重绑、预检和正式 qualification，首个有效内核基线没有建立。
- 执行反复经历“正式资格暴露问题 → 修一个局部问题 → 提交并重绑 → 再做预检或资格 → 暴露下一个问题”。先后处理了冷查询与热查询混测、重复冷启动、语义工作完成但未提交、错误信息 ID、查询工具越界，以及后来才确认没有权威依据的“最多八次调用且零失败”门槛。每次修改都使旧 product 绑定和正式证据失效，局部产出不断增加，阶段完成度却没有同步跨越。

**根本原因**

1. 验收执行层同时存在多项尚未验证的假设：时延测量口径、外部智能体提交行为、信息 ID 使用、工具暴露范围和自加调用门槛没有在进入正式 qualification 前形成稳定合同，正式验收因而被反复用作诊断工具。
2. 主 Agent 按每次新暴露的局部现象串行修补，没有先汇总同一执行层的全部失败证据并收敛为一个修复批次；提交、重绑和正式证据失效由此循环发生。
3. 治理支线没有持续获得足以纠偏的真实宏观输入：当前 Codex 的 `exec` 失败未进入事件链，执行焦点和证据身份落后，Governor 还把未经权威证明的“八次调用”当成硬合同。Governor 曾及时阻止一次已经必败的补跑，但整体上无法稳定识别“局部仍有进展、正式完成条件却没有前进”的低效路径。

这不是四小时完全没有技术产出，也不是 Ownward 内核已经被证明失败；问题是有效局部工作相对于阶段目标的转化率过低，而治理体系没有稳定把主线拉回最短完成路径。

### 场景二：一份短文档耗时 20 分 51 秒

**问题表象**

- 该轮从 06:59:51 持续到 07:20:43，共 20 分 51 秒；目标只是确定文档职责与位置并形成一份治理优化任务文档。
- 文档在约 07:08 已经写入，前置阅读和起草约耗时 8 分钟；此后约 12 分钟没有形成等量文档价值，主要用于处理 Governor 反馈。
- 该轮共发起 30 次顶层 `exec` 编排、产生 44 个命令子进程；反馈接收两次因请求后的仓库快照变化被拒绝，主 Agent 又创建了新的主动复核，并多次自行编写 Base64 传输逻辑、查询 CLI 参数和核对暂存状态。

**根本原因**

1. 普通旁支文档任务错误地消费并等待了主目标的当前 Review，随后又用可自由改名的请求标识为同一文档事实创建新复核；主目标治理状态没有与同一对话中的其他工作隔离。
2. Review 接收把整个仓库工作树快照作为有效性门槛，文档任务自身的正常写入就能使已经返回的反馈失效，形成“工作产生变化 → 反馈作废 → 再复核”的自我失效循环。
3. Governor 被放进主线串行关键路径，反馈 JSON 的编码、传输和校验劳动又转嫁给主 Agent；治理本应提供宏观建议，却在文档完成后继续制造协议工作。

这不是文档内容本身复杂，也不是 Ownward 产品问题；主要额外耗时来自治理运行时违反普通工作隔离、旁路顾问和幂等复核原则。

## 三、已确认的体系缺陷

### 1. 真实失败未进入治理状态

当前 Codex Desktop 的统一命令工具在 Hook 事件中使用 `exec`，项目 `PostToolUse` 仍主要匹配旧入口 `exec_command`。结果是实际失败没有进入失败分类、修复状态和事件复核；成功命令与失败命令的治理观测链路也未经过真实客户端验证。

这是客户端集成实现缺陷，不是自主治理方案无法成立，也不是主线产品代码问题。

### 2. 复核输入缺少新鲜差异

生命周期复核能够触发，但当前焦点仍可能描述旧工具绑定、旧检查点和旧证据身份；从上次复核到本次复核之间新增、失效或改变的事实没有被明确交给 Governor。复核次数存在，不等于复核输入有效。

### 3. 判断没有严格绑定权威

Governor 将活动焦点中未经权威来源证明的“最多八次调用”视为硬合同，并据此反对后续修复。治理意见没有区分：

- 权威文件明确规定的约束；
- 当前执行方案的临时目标；
- 尚待验证的假设。

这会把支线从“帮助主线判断价值”变成“用无依据约束干扰主线”。

### 4. 复核频繁但引导价值不足

本次低效率不是因为缺少按时间触发的复核，而是因为失败事实缺失、状态陈旧和判断依据不可靠。继续增加定时复核只会重复处理同一份低质量输入。

### 5. 主动复核缺少事实资格与语义去重

短任务没有产生固定边界或真实治理事件，主 Agent 仍以不同请求标识连续发起主动复核。运行时能够去重相同标识，却不能阻止调用方给同一事实换名后重复请求，因而把普通、短小、可逆的工作错误升级成治理事件。

### 6. 复核被串行化，结果接收把协议劳动转嫁给主线

当前交互说明要求主 Agent 原地等待 Governor；反馈又绑定整个仓库工作树，等待期间的正常修改会使结果失效并诱发重审。当前 Review 在途时也没有收敛后续合法事件的明确语义，继续工作可能替换请求或使返回结果无法接收。Hook 只提示使用 Base64 接收反馈，主 Agent 因而自行研究 CLI、手工编码和处理失败。宏观顾问由此变成主线的串行手续，而不是低成本旁路。

### 7. 工具失败缺少主目标执行身份

治理激活后，`PostToolUse` 主要按会话所有权接收失败，没有证明该工具调用属于当前主目标和执行焦点。同一对话中的旁支任务虽然不会被普通消息 Hook 激活，其失败仍可能进入主目标状态并在后续误触发复核。这会破坏核心 Skill 规定的其他工作隔离。

### 8. 成功工具热路径承担了不必要的进程开销

`PostToolUse` 为观察失败必然在匹配工具结束后进入一次确定性处理，但当前 Windows 配置每次都先启动 PowerShell 包装脚本。隔离实测中，成功事件直接调用现有治理二进制的热态耗时约 24 毫秒，经 PowerShell 包装平均约 1.2 秒；成功调用没有治理价值，却持续支付了约五十倍的启动成本。这不是 20 分 50 秒事故的主要根因，但会随日常工具调用稳定累积，违反核心 Skill 对正确路径不受额外流程干扰的要求。

现有治理二进制位于被 Git 忽略的 `.codex/governance/bin/`，不能假设干净检出后天然存在；当前包装脚本同时承担缺失或源码变化后的构建职责。因此，单纯把 Hook 改成直接调用本机已有二进制并不可交付，必须把安装、升级与运行期调用分开设计。构建也不能转移到 `SessionStart`，因为它会让没有开启治理的普通 Codex 任务承担部署成本。

### 9. 局部产出没有稳定映射为完成条件的净进展

当前状态能够列出修复、提交、测试和检查点，却没有明确表达最关键未满足条件是否改变、哪些证据新增或失效、候选或绑定变化付出了什么证据代价。场景一中局部产出持续增加，但首个有效基线始终没有建立；Governor 因而容易把“仍在做事”误认为“正在有效接近终点”，无法及时识别证据反复失效和正式资格反复承担诊断工作的低转化路径。

这不是要求 Governor 规定主线流程，也不是按时间或产出数量评分；它缺少的是从既有完成条件和证据中直接得出的阶段净变化。

## 四、优化目标

治理支线应形成以下闭环：

> 主线产生真实执行事实 → 运行时准确记录新增与失效信息 → 自然边界或真实事件触发复核 → Governor 按权威和价值判断路线 → 主 Agent 明确回应并自主决定后续执行。

优化完成后，支线必须做到：

1. 对能够机械证明属于当前主目标的命令和治理事件可靠观测成败，不漏报、不误报、不阻塞主线；无法证明归属的普通工具事实保持隔离，不冒充全面观测。
2. 只有已经绑定当前主目标与执行焦点的工具事实能够进入治理状态；同一对话中的旁支任务及其失败保持隔离。
3. 每次有效复核都能看到相对上次复核的新鲜变化，而不是只读一份可能过期的当前焦点。
4. 每次有效复核都能直接看见最关键未满足条件的净变化，区分可复用证据增长、证据失效和只增加局部产出的原地循环。
5. 只在相关依赖真实变化时使结论失效，避免任意提交导致全量证据重做。
6. Governor 的硬性判断可追溯到权威文件及具体位置；无权威依据的判断明确标为假设。
7. 普通、短小、可逆的工作不因治理已激活而产生复核；主动复核必须绑定可验证的治理事件，不能用自由命名制造重复请求。
8. 合法复核与主线并行，反馈在下一个相关自然边界进入主 Agent 的决策过程；Governor 慢、失败或不可用都不能延迟当前工作。
9. 一次事件只形成一个请求、一次 Governor 返回、一次确定性接收和一次主 Agent 回应，不要求主 Agent研究或手工实现序列化协议。
10. 能在不接管主线、不固化主线工作流程的前提下，识别“继续重复高成本路径已无新增价值”，并提出与当时事实匹配的更优验证方向。
11. 运行期 Hook 只承担不可避免的固定判别，不得因普通任务启动、普通消息或正常工具成功而启动重量级脚本宿主、构建运行时、扫描仓库、写状态或调用 Governor。
12. 运行时升级能够无损保留当前主任务、执行焦点、完成条件、有效证据、Review 和主 Agent 回应；Hook 配置只有语义真实变化时才改变内容并进入 Codex 的正式重新信任与新任务加载流程。

## 五、必须完成的体系优化

### A. 提高宏观判断质量

- [x] **统一真实工具入口**：先以真实 `PostToolUse` 载荷固定当前 Codex Desktop 的工具名称和响应形态，再由运行时归一为命令工具类别；项目 Hook、可复用模板、运行时识别和测试同时覆盖当前 `exec`、可能的命名空间形式与兼容入口 `exec_command`，Governor 自身的复核链路排除规则同步一致，不根据界面文案猜测工具名。
- [x] **绑定可证明的主目标执行身份**：先用真实 Hook 载荷验证首次激活、目标提示重放、恢复、上下文压缩和旁支任务各自可用的会话、轮次与来源身份。运行时只能在已经成立的主目标边界或受治理执行入口中产生有界执行身份；普通消息既不创建、清除或更新该身份，也不写治理状态。`PostToolUse` 只有在真实载荷身份与当前主目标执行身份精确匹配时才可记录失败；缺少、过期或不匹配时忽略该工具事实并失败开放。若真实 Codex 载荷不能提供足够身份，则停用通用 `PostToolUse` 失败复核，并在能够触发核心 Skill 事件复核的既有执行入口——证据检查点、代表性探测准备扩大投入及其他资源密集动作——由治理运行时的薄执行封装或已有执行器一次性附加身份并直接登记结构化结果；薄封装必须保持原命令的输入、输出、退出码和生命周期，不增加超时、心跳或流程控制。只有本来就需要外部进程存活检测的动作才复用 `governed-run`，普通执行不得为取得身份被迫经过它。身份绑定由入口自动完成，不要求主 Agent 为内部每次工具调用逐项申报。除此之外只接收主 Agent 在既有执行快照中登记的事实，不得语义猜测任务归属，也不得把无法归属的失败计入主目标。
- [x] **验证失败事件闭环**：以真实 Codex 冷启动证明成功命令不登记失败、失败命令准确入库、同类重复失败能形成一次幂等事件复核、已验证修复后可重新计数，且任一 Hook 故障都失败开放。
- [x] **提供复核增量事实**：`state.json` 在当前 Review 状态中保存上一份已回应反馈的有限基线身份，并在当前执行焦点内维护按类别聚合的失败、证据变化和已由执行快照、验收器、`governed-run` 或真实事件取得的资源事实；首次复核建立完整基线，恢复、压缩和真实事件复核只生成自上次有效复核以来的差异。生成复核前，运行时机械核对权威、仓库、执行焦点和已登记证据的身份；无法证明仍为当前事实的焦点明确标为过期或未知，不得原样交给 Governor。该过程不增加事件流水、不依赖模型记忆，也不要求主 Agent 另写进展报告。不得为了统计尝试次数而记录每次正常工具成功，普通成功调用必须保持无状态写入的快速返回路径。
- [x] **表达完成条件的净变化**：运行时在合法复核边界从既有执行快照、完成条件和已登记证据自动生成一个有界的阶段差异，至少说明当前最关键未满足条件、预期检查点、新增有效证据、复用证据、失效证据、适用的执行身份变化、最近一次对应检查点或高成本尝试结果和准备扩大的下一投入；没有变化时必须明确为零净进展。主 Agent 只维护核心 Skill 原本要求的执行状态和证据，不计算、转录或序列化第二份治理报表。Governor 必须据此判断成本是否转化为可复用证据、下一次正式或高成本扩展是否已有代表性证据支持，并在不成立时提出更小的直接判别路径。不得新增过程日志、人工评分、工时门槛、项目专用字段或固定主线流程。
- [x] **约束 Governor 的证据表达**：扩展反馈 Schema，把硬合同声明与假设分开；每项硬合同必须带权威路径、稳定位置和来源身份，影响建议类型或路线否定时只能引用已经校验的声明。缺少来源的内容只能进入假设，不得判定失败或改变完成条件。

### B. 消除治理自身的执行税
