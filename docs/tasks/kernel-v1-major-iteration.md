## 当前业务问题

- 场景：公开搜索已经返回多个可能来源；一个高排名来源可能同时包含多段必要事实，其他来源也可能各自提供必要证据，外部智能体需在固定 8 次读取和 24,000 字符内取得足够原文。
- 预期：来源排序与源内证据排序保持稳定，在来源广度和高排名来源深度之间有界公平；单条候选不适配剩余预算时继续检查其他可交付证据。
- 实际：V0 正式消费严格读取来源前缀；第一版修复转为“每源首条优先”后，在 24 个返回来源时又会把 8 个名额全部用于 depth=0，最高排名来源的第二、第三段确定性遗漏。
- 原因链：候选已被搜索返回 → 来源前缀贪心导致低位目标不读 → 纯来源广度修复又压制高排名来源必要深度 → 以来源是否出现计分掩盖同源多证据缺失。
- 已达状态：按 `source_rank + evidence_depth` 逐层遍历，同层优先较浅深度；8 个名额的确定顺序同时覆盖前四个来源，并保留最高排名来源的前三段。单项超预算只跳过该项，读满后不再探测低位来源；固定搜索排序、源内排序、24,000 字符和公开工具合同均不变。

## 最终架构与影响

- 产品权威资产、排序、派生状态和公开 MCP 合同不变；本根因属于外部智能体消费公开候选时的预算调度，因此修复落在正式 LongMemEval‑S 消费器，不向产品内核增加第二套选择 API。
- `ownward_search` 先冻结来源顺序；对各来源用公开 `ownward_evidence_search` 冻结源内证据顺序。装载阶段按 `source_rank + evidence_depth` 从小到大逐层遍历，同层按证据深度从浅到深；无需比较跨通道分数，同时避免“读尽同源”和“只读每源首条”两个极端。
- 所有正文仍只由公开 `ownward_evidence_read` 或无细粒度证据时的 `ownward_read` 取得；候选实际字符数纳入同一 24,000 字符累计预算，读取总数仍为 8。
- 不适配剩余预算、无法读取或无证据的单项被明确留痕并继续下一候选，不再把一个局部失败升级成全局终止；没有使用问题答案、Gold、题型或正式表面特征。
- 选择策略身份 `rank-depth-diagonal-budget-fit/v1` 已进入活动机器协议、检索阶段身份和直接说明；相关变化只局部失效检索及后续检查点，相同身份可精确恢复。
