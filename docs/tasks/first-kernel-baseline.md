# 首个有效内核基线建立

## 一、目标

在不进入第一版完整验收的前提下，使同一份干净、冻结的 Ownward 候选依次通过固定内核基线、完整前沿观察和 Ownward 专项资格集，并正式晋升为首个可复用的有效内核基线。

本阶段允许修复阻碍上述条件成立的真实内核问题，但不追求完成整个项目，不运行完整专项集、LongMemEval‑V2 或最终汇总，也不新增、修改或重新验证已经冻结的验收数据。

本阶段的执行配置只保留 `frontier` 与 `product`，候选绑定只包含 `frontier`、`core` 与 `product`；不得配置 `community`，不得下载、读取、校验或绑定 LongMemEval‑V2 仓库与数据。社区层只在全部内部验证通过、进入最终候选验收时另行加入。

本任务不执行暂存、提交、历史改写或推送。修复产生新候选变更时，完成修复和最小充分验证后停止，由用户另行处理提交；提交完成后再从已有状态继续。

候选的干净与冻结只约束验收工作区中的独立候选副本。源项目工作区已有的暂存或未暂存变更不属于该候选时，必须原样保留，不得要求用户先处理，也不得因此停止任务。

## 二、验收工作区

项目仓库保存验收契约、固定材料、评分器和执行代码；候选绑定、运行状态、检查点与原始证据保存在当前候选使用的验收工作区，避免运行状态污染或反复使冻结候选失效。

验收工作区由正式执行配置确定，首次执行时创建，不另建 `baseline-stage` 目录：

```text
<acceptance-workspace>/
├─ execution.json
├─ state.json
├─ stage-status.json
├─ repository/
├─ binding/
├─ evidence/
└─ reports/
```

`state.json` 是 Acceptance Suite 检查点、证据复用、局部失效和基线晋升的唯一权威；`stage-status.json` 只记录本阶段的时间、轮次、当前步骤和下一动作，不复制验收结论。

## 三、用户提示词

### 建立首个有效内核基线

```text
目标：建立 Ownward 首个有效、可复用的内核基线。完成本阶段所需的内核验证与必要修复，直到同一份干净、冻结的候选通过固定内核基线、完整前沿观察和 Ownward 专项资格集，并由 Acceptance Suite 正式晋升为有效基线。

本阶段包括为解决真实失败而进行的内核迭代，但只修复阻碍固定产品不变量、受保护能力或资格集成立的根因；不追求完成整个项目，不证明公开前沿，不新增或修改验收数据，不运行完整专项集、LongMemEval‑V2 或最终汇总。

本阶段的执行配置只保留 `frontier` 与 `product`，候选绑定只包含 `frontier`、`core` 与 `product`；不得配置 `community`，不得下载、读取、校验或绑定 LongMemEval‑V2 仓库与数据。社区层只在全部内部验证通过、进入最终候选验收时另行加入。

`docs/delivery/acceptance-system.md` 与 `benchmarks/acceptance/suite/` 中的契约、固定材料和执行规则是本阶段依据，不得修改。每次开始、恢复或上下文压缩后，重新读取其最新版本，并依据仓库、当前验收工作区、Suite `state.json` 和证据恢复事实，不依赖旧上下文转述。

当前验收工作区由正式执行配置确定。Suite `state.json` 是检查点、证据复用、局部失效和基线晋升的唯一权威；阶段进度写入同一工作区的 `stage-status.json`，不得另建平行状态体系。首次开始时原子创建该文件，此后在每个阶段开始前和结束后原子更新。至少记录：

- `status`：`running`、`awaiting_user_commit`、`blocked` 或 `complete`；
- `cycle`：当前正式候选轮次，只能为 `1` 或 `2`；
- `phase`：`preflight`、`targeted`、`core`、`frontier`、`qualification`、`repair`、`handoff` 或 `promote`；
- 候选提交、Suite `state.json` 路径和验收工作区；
- 阶段开始时间、当前步骤开始时间、最近有效进展时间和累计主动执行时间；
- 已完成事项、证据路径、失效事项与唯一下一动作。

主动执行时间只累计实际检查、执行、验证和修复时间，不计用户中断、关机或其他离线等待。只在首次开始、恢复和阶段边界核对时间，不为计时反复执行检查。

本任务不得执行 `git add`、`git commit`、`git amend`、`git reset`、`git rebase`、`git push` 或其他改变暂存区、提交历史和远程仓库的操作。Git 只用于读取状态、差异和历史。正式验收只能绑定任务开始前已经存在或后来由用户完成提交的干净候选，不得把未提交变更伪装成正式候选。

候选的干净与冻结只约束验收工作区内的独立候选副本，不要求源项目工作区为空。任务开始前已经存在的提交可以复制为独立、干净的候选并直接验证；源项目中不属于该提交的暂存或未暂存变更必须保持原样，不得成为暂停、清理、提交或重建候选的理由。只有本任务修复产品后必须形成新候选时，才进入等待用户提交状态。

按以下顺序持续执行：

1. 恢复事实并执行最低成本预检，区分源项目工作区与独立候选副本，确认候选、二进制、运行时、内部固定材料、专项所需外部智能能力和验收工作区可用；不准备社区层，也不运行正式证据层。源项目已有变更不属于候选时只记录其存在，不处理也不阻塞。
2. 在验收工作区创建或复用已经存在提交的独立、干净候选副本，按 Acceptance Suite 计划依次执行受影响的定向观察、固定内核基线、完整前沿观察和八场景资格集。已绑定且仍有效的检查点直接复用，只补失效或缺失部分。
3. 首轮全部通过后立即晋升基线，不再修改候选或继续优化。
4. 首轮失败时，先完整汇总失败证据并定位共同根因，形成一个修复批次；不得边发现边零碎修改、反复冻结候选或重复资格集。修复期间只运行相关单元测试和受影响的定向观察。
5. 修复稳定且最小充分验证通过后，不执行任何提交操作，也不继续绑定未提交候选。将 `stage-status.json` 标为 `awaiting_user_commit`、`phase` 标为 `handoff`，记录已经完成的修复、验证证据和提交后唯一下一动作，回复“候选修复完成，等待用户提交”并立即停止。
6. 用户另行完成提交后，再次使用本提示词恢复状态；确认新提交准确包含修复且工作区满足候选绑定要求后，将其作为第二轮候选重新绑定，只运行因候选变化而失效的必要层级。第二轮通过后立即晋升基线。

每个正式候选周期必须遵守 Acceptance Suite 的分项成本和总墙钟边界，单轮不得超过 48 分钟。本阶段最多允许两个正式候选周期，累计主动执行时间最多 2 小时；等待用户提交的时间不计入主动执行时间。任何步骤超过契约预算、第二轮仍未通过或累计主动执行时间达到 2 小时时，立即终止相关进程，保留全部有效检查点，将 `stage-status.json` 标为 `blocked`，说明唯一根因和下一项最小动作后停止；不得降低标准、扩大数据、继续追加轮次或以等待掩盖异常。

完成条件：

- 同一份干净、冻结的候选真实通过固定内核基线、完整前沿观察和 Ownward 专项资格集；
- Acceptance Suite 已将该候选正式晋升为首个有效内核基线；
- 状态、报告、原始证据与候选绑定完整，能够中断恢复和复核；
- 没有新增或修改验收数据，没有运行完整专项集、LongMemEval‑V2 或最终汇总；
- 执行配置和候选绑定均未包含 `community`，没有获取或访问 LongMemEval‑V2 仓库与数据；
- 本任务没有执行任何暂存、提交、历史改写或推送操作；
- `stage-status.json` 已标为 `complete`。

满足后回复“首个有效内核基线建立完成”，简要说明候选、通过证据、基线晋升结果和实际主动耗时，立即停止。任何一项未满足都不得宣称完成。
```
