# 首个有效内核基线建立

## 一、目标

在不进入第一版完整验收的前提下，使同一份干净、冻结的 Ownward 候选依次通过固定内核基线、完整前沿观察和 Ownward 专项资格集，并正式晋升为首个可复用的有效内核基线。

本阶段必须自行确认、定位并修复阻碍上述条件成立的真实内核问题和验收执行实现问题，但不追求完成整个项目，不运行完整专项集、LongMemEval‑V2 或最终汇总，也不新增、修改或重新验证已经冻结的验收数据。验收体系的静态标准、固定材料、真值、评分口径、预算和完成边界不得改变；预检、执行入口、适配器、状态与证据生命周期、候选绑定及其直接说明属于可修复实现，不得因实现文件位于 Acceptance Suite 中而将其误判为不可修改的依据。

本阶段的执行配置只保留 `frontier` 与 `product`，候选绑定只包含 `frontier`、`core` 与 `product`；不得配置 `community`，不得下载、读取、校验或绑定 LongMemEval‑V2 仓库与数据。社区层只在全部内部验证通过、进入最终候选验收时另行加入。

本任务不执行暂存、提交、历史改写或推送。只有产品实现修复改变候选内容、必须形成新候选提交时，完成修复和最小充分验证后才进入既定交接点，由用户另行处理提交；提交完成后再从已有状态继续。验收执行实现由独立工具摘要绑定，其变化只精确失效依赖该工具的检查点并重新绑定，不改变产品候选，也不得因此停止。

候选的干净与冻结只约束验收工作区中的独立候选副本。源项目工作区已有的暂存或未暂存变更不属于该候选时，必须原样保留，不得要求用户先处理，也不得因此停止任务。

## 二、验收工作区

项目仓库保存验收契约、固定材料、评分器和执行代码；候选绑定、运行状态、检查点与原始证据保存在当前候选使用的验收工作区，避免运行状态污染或反复使冻结候选失效。

验收工作区由正式执行配置确定，首次执行时创建，不另建 `baseline-stage` 目录：

```text
<acceptance-workspace>/
├─ execution.json
├─ state.json
├─ stage-status.json
├─ repository/
├─ binding/
├─ evidence/
└─ reports/
```

`state.json` 是 Acceptance Suite 检查点、证据复用、局部失效和基线晋升的唯一权威；`stage-status.json` 只记录本阶段的时间、轮次、当前步骤和下一动作，不复制验收结论。

只有两类情况可以将本阶段标记为 `blocked` 并停止：权威依据不足或冲突，且不同选择会改变产品定位、架构职责、任务范围或完成标准，需要用户作产品决策；实测或最小样本推算证明执行成本异常，继续运行只会浪费时间或资源。其他实现、环境、依赖、数据、工具和执行流程问题均不得作为阻塞上报，必须保持运行态，依次完成问题真实性复核、根因定位、最优修复、最小充分验证并从有效检查点继续。恢复时必须按本规则重新审计既有 `blocked` 状态；不属于上述两类的，立即改回 `running` 与对应修复阶段，保留有效证据后继续。等待用户提交是本任务禁止 Git 写操作所形成的既定交接状态，不属于阻塞。

## 三、用户提示词

### 建立首个有效内核基线

```text
目标：建立 Ownward 首个有效、可复用的内核基线。完成本阶段所需的内核验证与必要修复，直到同一份干净、冻结的候选通过固定内核基线、完整前沿观察和 Ownward 专项资格集，并由 Acceptance Suite 正式晋升为有效基线。

本阶段包括为解决真实失败而进行的内核迭代和验收执行实现修复，但只修复阻碍固定产品不变量、受保护能力或资格集成立的根因；不追求完成整个项目，不证明公开前沿，不新增或修改验收数据，不运行完整专项集、LongMemEval‑V2 或最终汇总。

本阶段的执行配置只保留 `frontier` 与 `product`，候选绑定只包含 `frontier`、`core` 与 `product`；不得配置 `community`，不得下载、读取、校验或绑定 LongMemEval‑V2 仓库与数据。社区层只在全部内部验证通过、进入最终候选验收时另行加入。

`docs/delivery/acceptance-system.md` 与 `benchmarks/acceptance/suite/` 中的契约、固定材料和执行规则是本阶段依据。验收体系的静态标准、固定材料、真值、评分口径、预算和完成边界不得修改，也不得通过降低标准使现有实现通过；预检、执行入口、适配器、状态与证据生命周期、候选绑定及其直接说明属于可修复实现，发现其偏离上述依据时必须自行修复并验证，不得因其位于 Acceptance Suite 中而停止。验收工具与产品候选分别绑定：工具实现变化更新对应工具摘要并精确失效依赖项，不要求重建或提交未改变的产品候选。每次开始、恢复或上下文压缩后，重新读取最新版本，并依据仓库、当前验收工作区、Suite `state.json` 和证据恢复事实，不依赖旧上下文转述。

当前验收工作区由正式执行配置确定。Suite `state.json` 是检查点、证据复用、局部失效和基线晋升的唯一权威；阶段进度写入同一工作区的 `stage-status.json`，不得另建平行状态体系。首次开始时原子创建该文件，此后在每个阶段开始前和结束后原子更新。至少记录：

- `status`：`running`、`awaiting_user_commit`、`blocked` 或 `complete`；
- `cycle`：当前正式候选轮次，从 `1` 开始递增；候选失败本身不得触发阻塞；
- `phase`：`preflight`、`targeted`、`core`、`frontier`、`qualification`、`repair`、`handoff` 或 `promote`；
- 候选提交、Suite `state.json` 路径和验收工作区；
- 阶段开始时间、当前步骤开始时间、最近有效进展时间和累计主动执行时间；
- 已完成事项、证据路径、失效事项与唯一下一动作。

主动执行时间只累计实际检查、执行、验证和修复时间，不计用户中断、关机或其他离线等待。只在首次开始、恢复和阶段边界核对时间，不为计时反复执行检查。

只有两类情况可以将 `stage-status.json` 标记为 `blocked` 并停止：

1. 权威依据不足或冲突，且不同选择会改变产品定位、架构职责、本阶段范围或完成标准，需要用户作产品决策；
2. 实测或最小代表性样本推算证明执行成本异常，继续运行只会浪费时间或资源。

除此之外，任何实现缺陷、验收工具错误、环境或依赖问题、数据与状态错误、配置和执行流程问题都必须自行处理：先基于事实复核问题是否成立，再定位根因、反思当前方案，按不降低验收标准且不影响其他架构与功能的最优方案修复，执行最小充分验证，并从最近有效检查点继续。不得把可自行解决的问题写成 `blocked`，不得用规则冲突代替对规则层级和任务本质的判断。外部权限或凭证不足时也必须先穷尽本地、既有和官方可用路径；只有最终转化为上述产品决策或异常耗时之一时才可停止。

恢复时必须按上述定义重新审计既有 `blocked` 状态，不得因旧状态已经写入而沿用错误结论。不属于两类真实阻塞的，原子更新为 `running` 和对应的 `repair` 或当前执行阶段，保留仍有效的检查点并直接继续。

本任务不得执行 `git add`、`git commit`、`git amend`、`git reset`、`git rebase`、`git push` 或其他改变暂存区、提交历史和远程仓库的操作。Git 只用于读取状态、差异和历史。正式验收只能绑定任务开始前已经存在或后来由用户完成提交的干净候选，不得把未提交变更伪装成正式候选。

候选的干净与冻结只约束验收工作区内的独立候选副本，不要求源项目工作区为空。任务开始前已经存在的提交可以复制为独立、干净的候选并直接验证；源项目中不属于该提交的暂存或未暂存变更必须保持原样，不得成为暂停、清理、提交或重建候选的理由。只有产品实现修复改变候选内容时，才进入等待用户提交状态；验收执行实现和无关文件变化均不改变候选身份。

按以下顺序持续执行：

1. 恢复事实并执行最低成本预检，区分源项目工作区与独立候选副本，确认候选、二进制、运行时、内部固定材料、专项所需外部智能能力和验收工作区可用；不准备社区层，也不运行正式证据层。源项目已有变更不属于候选时只记录其存在，不处理也不阻塞。
2. 在验收工作区创建或复用已经存在提交的独立、干净候选副本，按 Acceptance Suite 计划依次执行受影响的定向观察、固定内核基线、完整前沿观察和八场景资格集。已绑定且仍有效的检查点直接复用，只补失效或缺失部分。
3. 首轮全部通过后立即晋升基线，不再修改候选或继续优化。
4. 首轮失败或执行路径出现问题时，先完整汇总证据、复核问题是否成立并定位共同根因，形成一个修复批次。产品实现问题和验收执行实现问题均在本阶段自行修复；不得改变验收静态标准和固定材料，不得边发现边零碎修改、反复冻结候选或重复资格集。修复期间只运行相关单元测试、隔离预检和受影响的定向观察。
5. 修复稳定且最小充分验证通过后，按变化身份继续：仅验收执行实现发生变化时，更新工具摘要、精确失效依赖旧工具的检查点并继续，不得改变或重建未变化的产品候选；产品实现发生变化时，不执行任何提交操作，也不继续绑定未提交候选，将 `stage-status.json` 标为 `awaiting_user_commit`、`phase` 标为 `handoff`，记录修复、验证证据和提交后唯一下一动作，回复“候选修复完成，等待用户提交”并立即停止。该状态是既定交接点，不得标记或描述为阻塞。
6. 用户另行完成提交后，再次使用本提示词恢复状态；确认新提交准确包含修复且工作区满足候选绑定要求后，将其作为下一轮候选重新绑定，只运行因候选变化而失效的必要层级。该轮通过后立即晋升基线；未通过则重新执行问题复核与根因修复，不得因候选轮次本身停止。

每个正式候选周期必须遵守 Acceptance Suite 的分项成本和总墙钟边界，单轮不得超过 48 分钟。本阶段累计主动执行时间最多 2 小时；等待用户提交的时间不计入主动执行时间。任何步骤超过契约预算或累计主动执行时间达到 2 小时时，立即终止相关进程，保留全部有效检查点，将 `stage-status.json` 标为 `blocked`，说明已证实的异常成本、唯一根因和下一项最小动作后停止；不得降低标准、扩大数据、继续无证据地追加工作或以等待掩盖异常。候选未通过只产生修复证据，不自动构成阻塞。除上述异常耗时和确需用户作出的产品决策外，不得以任何其他原因停止任务。

完成条件：

- 同一份干净、冻结的候选真实通过固定内核基线、完整前沿观察和 Ownward 专项资格集；
- Acceptance Suite 已将该候选正式晋升为首个有效内核基线；
- 状态、报告、原始证据与候选绑定完整，能够中断恢复和复核；
- 没有新增或修改验收数据，没有运行完整专项集、LongMemEval‑V2 或最终汇总；
- 执行配置和候选绑定均未包含 `community`，没有获取或访问 LongMemEval‑V2 仓库与数据；
- 本任务没有执行任何暂存、提交、历史改写或推送操作；
- `stage-status.json` 已标为 `complete`。

满足后回复“首个有效内核基线建立完成”，简要说明候选、通过证据、基线晋升结果和实际主动耗时，立即停止。任何一项未满足都不得宣称完成。
```
