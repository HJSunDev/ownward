# 最终测试续跑问题收集

## 遇到问题如何处理

**每遇到一个失败，先按[四方向归因](../delivery/acceptance-system.md#最终测试失败归因)查清原因，再登记到下方对应列表；任一列表本批累计达到 10 道不同题，立即停止投放新题，保留并收齐在途结果，转入本批问题处理，不再续跑。三个列表分别计数，不按合计数触发。**

- **内核问题：** 必要信息未被可靠维护、获取或忠实交付，修复信息内核的通用短板。
- **组件问题：** 必要信息已交付，但处理流程未帮助外部智能正确使用，迭代通用的信息使用能力。
- **组件问题必须记录实际触发状态：未触发，归入触发机制问题；已触发，归入组件处理能力问题。** 以运行痕迹中的 `information_use.used` 为依据，两类共同计入组件列表的10题阈值，不另设列表。
- **需放弃的问题：** 复核完整原文后，预期答案仍缺乏合理依据；数据有冲突本身不构成弃题理由。达到阈值后集中复核并完成处置，不为命中不合理标答修改产品。
- **模型能力仍是第四个归因方向：** 当前模型已单独验证能力可用，不设累计列表；不能据此强行把任何失败塞入前三类。若出现明确反证，应记录证据并重新核实能力前提。
- 归因必须有实际交付材料、回答与判分依据；判分误判、服务失败、未完成不冒充上述缺陷，保留现场并处理。尚未定因的题不得漏掉或强行分类，先完成归因。
- 按原始题号去重；同题多次失败更新同一条，若存在两个独立根因，可分别登记并注明关联。条目只保留核心原因、证据入口和处置状态，不粘贴长日志。
- **三个列表只维护当前待处理问题，条目只保留一份；迁入持久化登记或其他权威文档后，立即从本列表删除并更新计数，不留重复条目或迁移说明。** 已触发的停跑决定不因迁出而撤销；不得用迁出来规避10题停跑阈值。本批处理完成后，按[迭代策略](kernel-v2-final-test-failure-analysis.md#后续迭代策略真题补短板固定集守能力)从实际完成位置的下一题继续。

### 组件问题：先修触发，再验效果

测试默认采用6题并发。完整验证按需触发与处理效果，通过后保存结论并移出待处理列表。

- **未触发只证明调用缺口，不能据此判断组件能力无效。** 先集中解决未触发问题，再处理已触发但执行失败或结果不合格的问题。
- 触发机制根据任务中使用信息的实际困难按需启动，提炼通用条件，提高适当场景下的触发可靠性；不按题号定制、不全量强制启动，不追求所有任务100%触发。
- **触发修复阶段只验是否实际进入组件流程。** 固定模型、档位和组件处理能力，做最小验证；观察到真实调用启动并留存证据后立即停止该次实验，不继续消耗资源生成完整结果或判分。未触发则继续优化触发机制；口头表示需要组件不算触发，主动截停不算执行失败。
- 触发验证通过仅关闭触发缺口，条目标为“已触发，效果待验”，不能记作整题解决或直接删除。随后统一验证处理效果：通过的保存结论后移出；执行失败或结果不合格的转为组件处理能力问题，继续修复。已有完整有效结果直接复用。
- 两阶段状态更新同一条记录，不重复计数；中断实验以实际调用启动痕迹为触发依据，不要求已有完整运行才生成的 `information_use.used` 结果。
