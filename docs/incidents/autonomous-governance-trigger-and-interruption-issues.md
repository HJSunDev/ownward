# 自主治理触发与主线干扰问题

> 状态：已解决；旧任务已精确迁移到一次合法恢复复核，未提前恢复产品写入
> 范围：只记录并解决自主治理运行时错误触发、抢占主线和重复复核问题；不讨论或改变 Ownward 产品功能。

## 问题表象

用户在同一任务中发送普通消息后，主 Agent 已经开始处理或已经给出正常回复，随后界面出现 Governor 复核指令，主 Agent 转去执行复核，原本的用户流程被延迟或打断。一次复核完成并返回 `continue` 后，下一次普通回复结束又出现同样的复核指令，导致正常对话和持续工作无法稳定进行。

历史记录显示：`2026-08-23 15:13:30` 主 Agent 完成正常答复，`15:13:31` 出现复核请求；该复核于 `15:17:56` 应用后，主 Agent 在 `15:19:44` 再次完成普通答复，`15:19:47` 又出现新的复核请求。上述现象已经实际发生。

## 问题的根本原因

直接原因是 Codex 的 `Stop` 只表示一轮回复结束，治理运行时却把它误当成整个开发任务的复核边界，无条件创建 `main-agent-stop` 并返回阻断指令。更深层原因是运行时没有掌握复核触发权威：`Resume(reason)` 与 `RequestReview(reason)` 接受调用者提供的任意文本，并直接把它记成 `fixed` 或 `event`，却不校验真实生命周期事件、治理事实及其唯一身份。因此普通回复可以制造复核，其他调用方也能用自由文本制造同类无依据复核；复核本身又通过 Hook 指令抢占主线，最终形成重复打断。

## 问题特征

这是**自主治理运行时的技术集成设计与实现错误**，不是用户操作错误，也不是用户需求或主 Skill 的设计结果。主 Skill 明确要求只在固定时机和真实治理事件下复核，并规定两次复核之间不得干扰正确路径；但下层运行时既让通用 `Stop` 承担了它无法可靠承担的任务完成语义，又把调用者自报的自由文本当成可信触发事实。实际代码再通过强制 Hook 交接和每轮消息注入扩大了这一错误。

## 一、用户预期的工作关系

主 Agent 是唯一持续开发者，正常接收用户消息并连续完成主线工作。Governor 是独立、只读的宏观复核支线；主线首次被明确激活、真实上下文压缩完成，或确定性看门狗记录了新的复核事件时，主 Agent 才针对该触发实例启动 Governor 一次，接收判断后继续或调整工作。

看门狗只负责记录可机械确认的事实，例如到达证据检查点却没有预期证据、经过修复后同类失败真实复发、范围发生变化或即将扩大高成本投入；是否低效、无价值或存在更优路径由 Governor 判断。复核发生在明确边界，不从正在执行的正常动作中途抢占控制权。普通消息、普通回复结束和工作包范围内的正常工作都不属于复核事件。

预期流程：

```text
用户消息 → 主 Agent 正常处理
                    │
                    ├─ 无真实复核事件 → 连续工作或正常回复
                    │
                    └─ 到达明确复核边界 → 保存当前状态
                                             ↓
                                      启动 Governor 一次
                                             ↓
                                      接收判断后继续或调整
```

## 二、已经发生的实际流程

当前项目注册了通用 `Stop` Hook。主 Agent 每次结束一轮回复都会进入该 Hook；治理实现只要发现当前没有待复核请求，就主动创建原因名为 `main-agent-stop` 的新请求，再以高优先级 Hook 指令阻止正常结束并要求主 Agent 改去启动 Governor。该指令会形成强制续跑；如果下一条真实用户消息已经到来，主 Agent 仍会优先处理这条治理指令，因此表现为正在回应用户时突然被扭去复核。

因此实际流程变成：

```text
用户消息 → 主 Agent 开始处理或完成回复
                    ↓
            普通回复触发 Stop
                    ↓
       Stop Hook 制造新的 Governor 请求
                    ↓
       Hook 指令抢占用户请求和主线控制权
                    ↓
          Governor 复核并返回结果
                    ↓
       主 Agent 汇报复核结束并再次 Stop
                    ↓
       再次制造 Governor 请求，形成循环
```

已核实的连续事实：

- `2026-08-23 15:13:30`，主 Agent 已完成“读取最近三个提交”的正常答复；`15:13:31` 随即以 `main-agent-stop` 创建 `review_74e034596373e22d93422605`。
- 该复核耗时约四分钟，最终只返回 `continue`，没有改变工作路径；`15:17:56` 应用成功。
- `15:19:44`，主 Agent按用户要求直接回答“现在可以正式继续开发”；`15:19:47` 又以同一 `main-agent-stop` 原因创建 `review_d183bf1416310969e3c1bedd`。
- 截图中出现的英文内容不是 Governor 判断，而是 Stop Hook 注入给主 Agent 的强制操作指令；它会压过用户的真实消息。

## 三、经核实的问题

以下六项分别对应错误 Stop 来源、主支线交接、普通消息隔离、验收保障、既有污染状态和触发权威六个独立修复入口。六项全部解决后，顶部记录的错误触发、主线抢占和重复复核必须在现有任务与新任务中同时消失；其余现象均为这六项的派生表现或影响，不再重复列为问题。

## 问题一：通用 `Stop` 被错误地作为复核事件源

### 发生场景与业务偏差

主 Agent 完成一次普通答复或阶段说明时，Codex 发出 `Stop`，表示这一轮输出准备结束。

预期流程：

```text
普通回复结束 → 正常结束本轮
显式完成检查点到达 → 机械校验完成证据 → 必要时复核一次
```

实际流程：

```text
普通回复结束 → Stop Hook → 创建 main-agent-stop
→ 阻止结束并要求 Governor 复核
```

### 根本原因

运行规范和实现把“本轮回复结束”错误解释成“整个开发任务可能完成”。`Stop` 不包含任务完成声明、检查点身份或新增治理事实，无法承担复核事件源；当前 `hookStop` 却在没有待复核请求时无条件调用 `RequestReview("main-agent-stop")`，并清除工作包批准、阻断退出。

### 问题性质

这是**治理触发语义及运行时实现错误**。确定性看门狗本身有价值，错误在于给通用 `Stop` 分配了它无法可靠承担的职责；不是用户操作问题，也不是 Governor 判断错误。

### 解决预期

1. 普通 `Stop` 不创建、刷新、交付或重试任何复核，不修改治理状态，也不阻止正常回复结束。
2. 首次明确激活、真实上下文压缩、具有唯一身份的治理事件和显式完成检查点仍能各自触发一次合法复核。
3. 完成保护不被削弱：只有通过 `task_complete` Governor 结论并经显式 `finish` 机械校验，任务才可标记完成。
4. 已加载旧 Hook 配置的现有任务不会因升级后调用旧 `hook stop` 命令而报错或再次阻断。

### 最优解决方案

1. 从项目 `.codex/hooks.json`、可复用 Hook 模板、安装说明、运行规范和 Doctor 必需 Hook 清单中删除 `Stop` 注册及“Stop 校验完成或生成复核”的错误语义；Doctor 还必须机械拒绝治理配置重新注册任何 `Stop`，兼容空操作只能作为旧会话仍可调用但新配置不可注册的入口存在。
2. 保留 `hook stop` 作为旧会话兼容入口，但将其实现为严格无副作用的空操作：不读取或写入状态、不返回 `decision: block`、不追加上下文、不触发 Governor。这样已经加载旧配置的任务也能立即安全结束；新任务不再注册该 Hook。
3. 删除所有依赖 `main-agent-stop` 的正常逻辑与测试。完成声明继续走已有的 `task_complete review → finish` 显式路径，`finish` 仍机械验证 Review 和全部完成证据。
4. 固定复核与事件复核统一要求具有明确来源和唯一触发实例；同一实例只能消费一次，Governor 结果、应用结果和其后的普通回复都不得形成新实例。
5. 同步修改项目运行时与 Skill 可复用资产，防止当前项目修好后又由旧模板安装回同一缺陷。

### 完成证据

- 连续多次调用兼容 `hook stop` 均返回空结果，`state.json`、工作包批准、Review 代次和事件日志逐字节不变。
- 新的项目 Hook 配置和模板均不注册 `Stop`，Doctor 不再要求它存在且会拒绝治理配置重新注册任何 `Stop`，并明确验证显式 `finish` 路径仍然失败关闭。
- 首次激活、真实压缩、真实治理事件和显式完成各自仍能触发一次合法复核，同一实例重放不增加 Review。

## 问题二：复核交接错误地抢占正常主线

### 发生场景与业务偏差

Governor 应在主线到达明确治理边界时作为只读支线被调用一次，再把结论返回主 Agent。

预期流程：

```text
真实触发到达自然边界 → 原子记录请求
→ 主 Agent 启动 Governor 并等待一次结果
→ 校验、应用 → 继续或调整主线
```

实际流程：

```text
普通回复结束 → Hook 制造请求并返回强制续跑指令
→ 指令先于用户真实消息进入主 Agent
→ 主 Agent 放弃当前用户流程，转去执行治理操作
```

### 根本原因

当前实现没有把“创建复核事件”“把事件交付给主 Agent”和“阻止产品修改”分成三个职责。Stop Hook 同时制造请求、注入高优先级操作并阻止结束，使治理支线从自然边界上的一次协作变成对当前控制流的抢占。

### 问题性质

这是**主 Agent 与 Governor 的运行时交接实现错误**。Governor 的只读职责和父子返回通道没有问题；错误在于 Hook 通过错误事件与强制续跑方式介入主线。

### 解决预期

1. 只有已经登记的合法触发实例可以启动 Governor；同一触发实例只能存在一份有效请求，没有真实事件时不存在治理交接。
2. 复核只发生在触发事件自身的自然边界，不异步插入、覆盖或截断正在处理的用户请求。
3. 主 Agent 仍是唯一执行者；Governor 只读返回判断，Hook 不替代主 Agent 决定业务动作。
4. 合法 Review 待处理时产品修改继续失败关闭，但普通沟通、只读状态检查、治理状态保存和任务正常结束保持可达。

### 最优解决方案

1. 将复核请求的**创建、交付、结果应用**分别记录：请求绑定 `review_id` 与唯一触发实例且只创建一次；交付默认只在产生该事件的自然边界发生。若该次交付被任务中断，同一治理所有者的真实 `SessionStart` 恢复边界或用户再次提交完整规范主线提示词时，只能幂等重现同一请求，不得创建新 Review；结果继续通过现有严格 Schema、摘要和 `accept-review → apply-review` 链路落盘。
2. 首次激活和压缩恢复由对应生命周期 Hook 在该边界交付；真实失败、范围漂移、证据检查点和扩大高成本投入等事件由产生该事实的命令或 PostToolUse 边界交付；显式完成检查点通过受限的结构化完成复核入口交付，`finish` 只在 `task_complete` Review 已应用后机械关单。任何事件都不得借普通 Stop 或下一条无关用户消息补发。
3. 已有合法 Review 待处理时，后续 `startup`、`resume`、`clear` 或 `compact` 只复用同一请求，不增加固定复核代次，也不把它归档替换；新治理事实先按身份去重并保留为待后续审视事实。只有权威依据或请求绑定快照真实变化、使原请求已经不可验证时，才能原子归档旧请求并创建一份当前快照替代请求，且必须记录明确失效原因。
4. `PreToolUse` 只做机械护栏：合法 Review 待处理时拒绝产品修改并返回稳定、机器可识别的原因，但不创建新 Review、不启动子 Agent，也不改写用户请求。
5. Governor 仍由主 Agent 通过 Codex 原生父子通道显式启动并等待；Hook 不在后台启动 Agent。已存在合法结果时恢复链路直接校验并继续应用，不重复启动 Governor；结果应用后原子关闭该触发实例，后续回复与工具动作不能重入。
6. 基础设施失败、待用户决策和任务交接继续使用各自已有的持久状态与恢复边界，不得借本次修复放宽失败关闭或删除治理状态。

### 完成证据

- 一次未中断的合法事件轨迹严格为“事件创建一次 → 交付一次 → Governor 返回一次 → 应用一次”；交付中断后，明确恢复只能重现同一请求并复用已经存在的合法结果，不能生成第二个 Review 或由普通消息、Stop 自动重试。
- 待处理 Review 经任意次数普通 SessionStart 或上下文生命周期恢复后仍保持相同 `review_id`、触发实例和快照；只有可证明的绑定失效才能产生一份有审计原因的替代请求。
- Governor 运行期间产品写入被拒绝；用户询问、只读调查、状态持久化和正常退出不被劫持。
- Review 应用后的普通答复和下一条用户消息不触发复核，主 Agent 从原工作包或新批准工作包继续。

## 问题三：普通消息被持续注入治理指令

### 发生场景与业务偏差

治理状态已经存在时，用户仍会在同一任务中询问状态、澄清问题、要求只读分析或临时讨论其他事项。

预期流程：

```text
普通消息 → 原样交给主 Agent → 正常回答
明确激活／合法触发／精确待处理答复 → 才附加对应治理上下文
```

实际流程：

```text
治理状态存在 → 每次 UserPromptSubmit
→ 无 Review 时注入 activeInstruction
→ 有 Review 时注入 reviewInstruction
→ 普通消息也可能被治理动作扭转
```

### 根本原因

`hookUserPrompt` 把“项目中存在活动治理状态”错误等同于“当前这条用户消息正在继续治理主线”。它没有要求本轮消息与首次激活、合法触发实例、一次性交接或待处理用户事项建立精确关系，因此把持久状态变成了每轮对话的高优先级提示源。

### 问题性质

这是**用户消息与治理主线隔离的运行时实现错误**。普通沟通与持续开发共处同一任务是正常产品使用方式，不应要求用户另开对话或记忆特殊操作。

### 解决预期

1. 没有本轮合法治理交互时，`UserPromptSubmit` 返回空结果，不向普通消息注入活动状态、Review 操作、完成状态、所有权提示或继续指令；治理为 running、Review 待处理、complete 或当前任务不是所有者，都不能仅凭持久状态把每条消息变成治理回合。
2. 首次明确激活仍能原子初始化治理并交付固定复核；治理已经存在时，同一份规范主线提示词能够明确恢复尚未完成的合法请求或原工作包。
3. 已登记的用户决策、外部输入或任务交接只能由与其身份精确对应的答复推进；无关问题可以正常回答且不改变状态。
4. Review 待处理不会因普通消息被重复交付；产品修改仍由 `PreToolUse` 失败关闭。

### 最优解决方案

1. 将 `UserPromptSubmit` 默认路径改为快速无输出；删除活动状态下每轮返回 `activeInstruction` 的行为，也不因 `review.required`、`status=complete` 或非所有者身份对每条普通消息重复返回治理文字。项目 Hook 配置同时移除普通检查阶段固定显示的 `Activating autonomous governance` 状态文案，只有真实激活、明确恢复、精确待用户事项或合法交接才产生用户可见治理反馈。
2. 首次激活只接受项目配置中完整锚定的规范主线提示词模式，并以当前 Hook 实例身份确保一次性；治理已经存在且没有待处理 Review 时，同一规范提示词表示显式恢复当前 run，并以当前 `turn_id` 创建一次结构化固定恢复触发，不创建第二个 run；已有待处理 Review 时只重现原请求。普通“继续”、状态询问或相似自然语言不得误触发治理运行或恢复交付；已完成 run 不得被该路径覆盖。
3. 合法 Review 的首次交付按问题二发生在其来源边界。状态保证它未处理前不会丢失；同一治理所有者的真实 `SessionStart` 恢复边界或明确匹配规范主线提示词的恢复请求可以幂等重现同一待处理 Review，普通用户消息不承担补发职责。
4. 待用户事项与任务交接沿用结构化身份、来源回合和单次消费校验；若当前消息不对应该事项，Hook 只提供不会改变用户意图的最小状态事实，主 Agent回答消息且不执行治理状态变更。不得用开放语义匹配自动认定用户已经授权或答复。
5. 非治理所有者任务继续由 `SessionStart` 的一次性最小事实和 `PreToolUse` 机械保持只读；其普通 `UserPromptSubmit` 同样沉默，不得每轮重复所有权提示、启动 Governor 或失效活动所有者的结果。治理已完成时普通消息也保持沉默；显式启动新目标必须走独立的新 run 边界，不能由普通消息覆盖已完成状态。

### 完成证据

- 治理状态为 running、Review 待处理、工作包已批准、complete 和当前任务非所有者五种情况下，连续普通消息均不会创建 Review、刷新代次、重复所有权／完成提示、显示治理启动反馈或强制改变当前动作；非所有者产品写入仍被机械拒绝。
- 完整激活提示只初始化一次；同一提示在未完成的已有 run 上不创建新 run：没有待处理 Review 时按当前 `turn_id` 只创建一次固定恢复 Review，已有待处理 Review 时只重现原请求；不匹配的普通消息不创建状态也不交付治理操作。
- 无关消息不能消费待用户事项或交接标识；正确身份的答复只消费一次并进入既定复核链。

## 问题四：验收缺少“不干扰正常工作”的完整业务流程证明

### 发生场景与业务偏差

此前验收分别证明 Governor 能启动、父子通道能返回、结果能校验落盘和 MCP 不冲突，却在真实任务的第一组连续普通消息中立即出现重复复核和主线抢占。

预期流程：

```text
组件自检通过 + 完整多轮业务流程通过
→ 才能判定治理体系可用
```

实际流程：

```text
组件分别连通 → 直接判定体系可用
→ 未验证普通消息、Stop、一次性触发和复核后继续
→ 集成错误进入真实任务
```

### 根本原因

验收只覆盖了“该发生的能力能够发生”，没有覆盖“不该发生时必须沉默”和“发生一次后不能重入”。组件能力被误当成了顶层业务流程成立，没有以用户真实工作关系作为最终验收对象。

### 问题性质

这是**自主治理运行时的验收设计与覆盖缺口**，不是 Governor 能力问题，也不是增加更多单元测试数量就能自动解决的问题。

### 解决预期

1. 同一套验证同时覆盖正路径、负路径、重复事件、复核后继续、现有状态迁移和真实冷启动。
2. 验收结论直接对应用户业务流程：普通工作不受干扰，合法复核恰好一次，修复后的现有任务能够继续。
3. 任何运行时、Hook 配置、模板或状态迁移变更都必须通过该回归，不能只验证自身局部模块。

### 最优解决方案

1. 建立确定性的多轮流程夹具，至少覆盖：未激活时普通消息保持沉默；首次激活恰好一次；连续普通消息与普通 Stop 全部沉默；running、complete 和非所有者状态的普通消息都不注入治理指令；真实压缩恰好一次；已有 run 上的完整规范主线提示词按当前 turn 恰好触发一次恢复且不建立新 run；具有唯一身份的事件恰好一次；同一事件重放幂等；Review 应用后的消息和 Stop 不重入；合法 Review 待处理时产品写入仍失败关闭；Review 交付中断后，普通消息不补发，同一所有者的真实 SessionStart 或规范主线提示词只恢复同一请求且不重复运行已有合法结果；待处理 Review 经 `startup|resume|clear|compact` 后保持同一身份，只有真实绑定失效才能有审计地替换；任意自由文本不能伪造 `fixed`／`event`，显式 advisory 不被普通 Hook 重试或升级。
2. 增加问题五的旧状态迁移夹具，分别覆盖“只有错误请求”和“错误结果已接受但尚未应用”，验证迁移中断后可重入、请求与结果进入审计、旧结果无法继续应用、真实工作包和证据不丢失、恢复复核只产生一次。
3. `doctor` 运行不依赖外部付费能力的全部确定性夹具，并校验项目配置、Skill 模板和运行说明采用同一触发集合；普通 `UserPromptSubmit` 不得配置误导性的固定治理状态文案。
4. 在隔离目录完成一次真实 Codex 冷启动多轮预检：普通消息、一次固定复核、一次事件复核、复核后继续和正常结束全部经过真实 Hook 与父子返回通道。预检使用最小合成状态，不运行 Ownward 产品验收或修改产品数据。
5. 将多轮流程报告、Hook 输出、状态摘要和事件日志作为可复核证据；不得以代码审查、单次脚本调用或“界面看起来正常”代替。

### 完成证据

- 上述正反路径全部通过，任一普通消息或普通 Stop 都没有治理状态变化。
- 每个合法触发实例只有一个 Review、至多一个有效 Governor 结果和一次应用；中断恢复只重现同一请求或复用既有结果，重放保持幂等。
- 冷启动预检中用户消息未被延迟、截断或替换，产品写入保护与完成机械校验仍然有效。

## 问题五：旧 Stop 产生的错误状态继续污染现有任务

### 发生场景与业务偏差

修复发生前，当前任务已经被错误 Stop 写入待处理 Review。即使新代码不再创建这种请求，持久状态仍会在下一条消息或产品动作中把它视为真实阻断。

预期流程：

```text
加载修复后的运行时 → 精确识别旧错误事件
→ 保留真实工作包、证据和进度
→ 撤销错误阻断并完成一次合法恢复复核
→ 从原检查点继续
```

实际流程：

```text
state.review.required = true
trigger = event:main-agent-stop
→ 每次 UserPromptSubmit 继续交付错误请求
→ RequestReview 已清除原工作包批准
→ 仅改代码或简单清空 required 都不能安全恢复
```

### 根本原因

`RequestReview` 不仅生成请求，还会清除当前工作包批准并改写下一动作。当前 `state.json` 已绑定错误请求 `review_d183bf1416310969e3c1bedd`；因此修复必须处理请求、批准、下一动作和审计历史的一致性，不能只删除一个布尔值，也不能清空全部治理状态。

### 问题性质

这是**错误运行时状态的兼容迁移与现有任务恢复问题**。它由问题一已经落盘的副作用造成，不是新的产品问题，也不能靠用户重新开始开发规避。

### 解决预期

1. 只识别并撤销原因严格等于 `event:main-agent-stop` 的错误请求，不影响任何合法固定复核、事件复核、用户事项或基础设施失败状态。
2. 当前活动所有者、工作包、完成条件、有效证据、失败历史和检查点完整保留。
3. 错误请求及已经形成的 Governor 结果保留为不可执行审计历史，不能再接受、应用或恢复批准。
4. 修复后的运行时只在明确恢复边界创建一次绑定新代码与当前仓库快照的合法恢复复核；通过后从原工作包继续。
5. 迁移可重入，任一步中断都不留下新旧状态混合或重复复核。

### 最优解决方案

1. 增加一次性、确定性的 `migrate-invalid-stop-review` 受限控制面命令，并把这一精确动作加入现有治理控制命令白名单，使它在错误 Review 仍为 required 时保持可达。该命令无通用“取消 Review”参数，只处理迁移身份 `invalid-main-agent-stop-v1`，在代码与配置修复完成后由修复流程显式执行；它必须在治理写锁内核对触发严格等于 `event:main-agent-stop`、请求身份和请求文件一致，不匹配即拒绝且不改变状态。它不得由 `LoadState`、`UserPromptSubmit`、`SessionStart`、`Stop` 或其他普通 Hook 懒触发，避免用户消息再次成为治理状态变更入口。
2. 将错误 `review-request.json` 原样移入 `reviews/superseded/`；若该请求已经执行 `accept-review` 但尚未 `apply-review`，还必须核对 `state.review.decision_path` 指向的结果与旧 `review_id`、触发实例和快照完全一致，将该结果保留在原 Review 历史目录并原子清除活动指针，不一致则失败关闭。为事件日志和 Review 目录中全部 `main-agent-stop` 请求及结果追加一份不可变纠正索引，记录旧 Review、触发实例、工作包和迁移身份；既有文件不改写，但这些请求与结果只能作为审计历史，不能继续应用或提供批准、完成证据。
3. 保留工作包及全部真实证据，但不凭日志猜测或静默恢复被错误请求清除的批准。迁移将工作包置于“等待恢复复核”的明确状态，并原子创建一次 `fixed:runtime-repair-recovery:<migration-id>` 请求，绑定修复后的运行时、当前仓库快照和原工作包。
4. 该恢复请求只能在配置与代码修复已经完成后，由同一治理所有者的真实 `SessionStart` 恢复边界或同一份规范主线提示词明确恢复并首次交付；交付中断时两条恢复路径都只能幂等重现同一请求，不能创建替代请求。Governor 校验工作包仍必要、有效且最优后重新批准或调整。这样既不信任错误 Stop Review，也不丢弃真实进度。
5. 用阶段化迁移标记保证“归档旧请求与可能存在的已接受结果、清除旧活动指针、纠正事件、生成新请求、保存状态”任一步中断后都可重入；同一迁移身份最多生成一个恢复 Review。迁移命令重复执行只返回既有迁移结果，不改变 Review 代次。
6. 已加载旧 Stop 注册的任务由问题一的兼容空操作保证不会再次写入；新任务加载删除 Stop 后的配置。迁移完成前产品写入继续失败关闭，但只读调查、状态保存和正常退出可用。

### 完成证据

- 当前错误请求被精确归档，所有者、工作包、条件、有效证据和检查点摘要保持不变；合法 Review 与历史事件没有被误删。
- 普通 `UserPromptSubmit`、SessionStart 和兼容 Stop 均不会启动迁移；对“只有请求”和“结果已接受但尚未应用”两种状态，显式迁移命令在旧请求／结果归档前、活动指针清除前、恢复请求生成前和状态替换前分别故障注入后均可重入，同一迁移只产生一个恢复 Review，旧结果不能再被应用。
- 恢复 Review 通过后，当前任务不再持有或信任任何 `main-agent-stop`，工作包取得与新快照匹配的批准并能从原检查点继续；真实 SessionStart 或规范主线提示词恢复中断链路时均不产生第二个 Review。
- 新建任务不会继承错误请求，旧任务的普通消息和 Stop 不再制造新污染。

## 问题六：通用复核入口允许调用者伪造触发事实

### 发生场景与业务偏差

主 Agent、Hook 或治理脚本可以调用 `resume <任意文本>` 或 `request-review --reason <任意文本>`。运行时不验证这个文本是否对应一次真实生命周期事件或已经落盘的治理事实，便分别把它记成 `fixed` 或 `event` 并创建复核。

预期流程：

```text
可信生命周期 Hook／确定性事实记录器产生结构化触发
→ 运行时校验来源、事件身份和绑定快照
→ 同一真实实例至多创建一次复核
```

实际流程：

```text
任意调用者提供 reason 字符串
→ Resume 直接标记 fixed，RequestReview 直接标记 event
→ 没有真实触发也能制造复核并清除工作包批准
```

当前事件日志已经出现 `pre-activation-preparation`、`problem-fixes-*-current-snapshot` 等多条由自由文本创建的 `fixed` 复核；它们不对应可机械核验的 SessionStart 或压缩触发实例，其中部分实际属于用户明确要求的主动审查。这证明当前运行时无法区分固定安全网、确定性事实事件和主动 advisory；并不证明这些历史审查的语义结论本身无效，但意味着即使删除 Stop，未来仍可能用另一条命令把任意请求伪装成固定或事件复核。

### 根本原因

`ReviewTrigger` 只有 `kind` 与 `reason`，没有受约束的事件类型、来源适配器、事件实例身份或事实证据。公开控制命令又直接暴露 `Resume(reason)` 和 `RequestReview(reason)`，把调用者声明误当成触发权威；`fixed` 与 `event` 因而只是标签，不是可验证事实。

### 问题性质

这是**治理触发权威与控制面 API 设计错误**。主 Agent 主动请求一次宏观建议本身可以有价值，但不能伪装成固定看门狗或确定性事件，也不能绕开同实例去重和证据约束。

### 解决预期

1. `fixed` 只能由受信任的首次激活、SessionStart／压缩恢复、完整规范主线提示词的显式恢复和受限迁移适配器创建；调用者不能用任意文本声明固定触发。
2. `event` 只能由已经在同一原子事务中形成事实身份的工作包、证据检查点、重复失败、权威变化、用户事项解决或显式完成等确定性路径创建。
3. 主 Agent 确需主动征求一次宏观建议时保留独立的 `advisory` 类型；它不冒充固定或事实事件，同一仓库与治理状态快照只能有一个活动请求。普通 Hook 不得在正常流程中重复交付或创建第二份请求；只有真实中断后的所有者恢复边界可以按问题二幂等重现同一请求。
4. 每个合法触发都能从请求反查来源、唯一实例与必要证据；自由文本只能作为说明，不能决定触发类型或身份。
5. 旧日志和已经严格校验、应用的历史结果保持不变，不因旧触发类型过宽被追溯判废；它们也不能被当成一次新的固定或事件触发重复使用。当前由错误 Stop 形成的活动阻断只按问题五精确迁移并重新确认当前工作包。

### 最优解决方案

1. 用结构化触发替代通用字符串 API：固定触发使用受限枚举、Hook 实例与会话来源；事件触发使用受限枚举、事件 ID 和证据引用。触发实例 ID 由这些规范化事实确定性生成，`reason` 仅作为不可授权的展示文本。
2. 删除正常控制面中可直接生成 `fixed` 的通用 `resume [reason]`；生命周期 Hook 只调用内部固定触发入口。将 `request-review --reason` 收敛为显式 `request-advisory-review`，或要求结构化 `kind=advisory`，不能通过参数选择 `fixed`／`event`。
3. 工作包创建、证据检查点、重复失败、权威变化和用户事项解决继续由各自拥有事实的运行时方法在同一写锁内创建事件复核，不经过公开自由文本入口；显式完成使用独立的结构化 `request-completion-review`，绑定当前权威、候选快照和完成证据摘要，不能接收自由文本事件类型。同一事实 ID 重放直接返回已有请求或已应用结果。
4. 明确激活与生命周期恢复只接受 Hook 提供并经所有权校验的结构化来源；若已有合法 Review，按问题二复用或有证据地替换，不能用不同 `reason` 静默归档它。
5. 不批量重写、重分类或失效既有事件与已应用结果；运行时升级只改变新触发的创建契约。当前活动的 `main-agent-stop` 由问题五精确归档并通过一次恢复 Review 重建当前批准，其他历史结果继续按原快照、身份和适用范围保存，不能自动冒充升级后的新触发。
6. Doctor 与多轮流程夹具验证：任意字符串不能创建 `fixed`／`event`；合法 Hook 与事实事件恰好创建一次；主动 advisory 可显式创建但不会被普通 Hook 自动交付、重试或计作固定看门狗；现有完成保护和产品写入失败关闭仍成立。

### 完成证据

- CLI 与运行时不存在“任意文本直接变成 `fixed`／`event`”的可达路径；伪造或缺少事件身份、来源、证据的结构化请求原子失败且状态不变。
- 激活、真实上下文恢复、证据检查点、重复失败、权威变化、用户事项解决和显式完成各自用真实身份恰好生成一次 Review，同一事件重放保持幂等。
- 主 Agent 显式请求 advisory 时能取得一次只读宏观判断，但连续普通消息、Stop、SessionStart 和结果应用都不会为它制造第二次请求或把它升级成看门狗事件。
- 旧日志和既有合法结果逐字节保留，升级过程不进行无关历史迁移；历史请求不会自行生成新 Review，当前错误 Stop 工作包只通过问题五绑定修复后快照的恢复 Review 重新取得批准。

## 四、统一实施顺序

1. **冻结事实并建立回归夹具**：保存当前错误请求、状态摘要和事件轨迹，先建立能够稳定复现普通消息、Stop 抢占和重复复核的隔离夹具。
2. **修正触发权威与普通消息边界**：完成问题一、问题三和问题六，使普通 Stop 与普通 UserPromptSubmit 保持沉默，关闭自由文本伪造 `fixed`／`event` 的旁路，同时保留首次激活、真实压缩、合法事实事件、显式 advisory 和完成路径。
3. **修正一次性交接**：完成问题二，把合法请求的创建、交付和应用收敛到明确自然边界，保持产品写入失败关闭但不抢占普通沟通。
4. **迁移现有错误状态**：代码、配置和迁移夹具通过后，显式执行问题五的受限控制面迁移；只归档 `main-agent-stop` 污染并生成一次合法恢复复核，保留原工作包和证据，任何普通 Hook 都不得代替该命令启动迁移。
5. **完成体系验收**：执行问题四的全部确定性夹具、Doctor 和最小真实冷启动多轮预检；确认现有任务恢复后立即停止，不开展 Ownward 产品主线工作。

六个问题必须共同关闭。仅删除 Stop、仅清除状态、仅让界面暂时不再弹出指令，或只通过单元测试，都不能判定顶部问题已经解决。

## 五、不可破坏的边界

1. Governor 始终只读，只负责宏观判断，不修改产品或治理实现。
2. 主 Agent 始终是唯一执行者；Hook 不在后台启动 Agent，也不替代用户意图。
3. 合法的首次激活、上下文压缩、确定性事件和显式完成复核必须保留，不能为消除误触发而关闭整个治理体系。
4. Review 待处理、批准失效或治理基础设施异常时，产品修改继续失败关闭；普通沟通、只读诊断、状态保存和正常退出不得被阻断。
5. 不修改产品定位、Ownward 架构、模块职责、正式能力契约、验收数据或产品功能。
6. 不删除当前任务的有效工作包、证据、检查点、所有权与历史来换取恢复；错误事件也保留为不可执行审计事实。
7. 项目运行时、Hook 配置、Doctor、Skill 模板和说明必须采用同一触发语义，不保留会重新安装旧缺陷的分叉实现。

## 六、整体完成条件

- 连续发送普通消息、读取状态和完成普通回复时，`UserPromptSubmit` 与兼容 `hook stop` 均保持沉默，不产生 Governor 复核，也不改变主 Agent 当前动作。
- 首次明确激活、一次真实上下文压缩、一个具有唯一身份的治理事件和显式完成路径分别保留正确能力；每个合法触发实例恰好复核一次，复核应用后不重入。
