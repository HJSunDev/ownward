# Codex 治理、会话恢复与 Ownward 单内核接入问题

## 文档边界

一次 Governor 启动失败及其恢复路径同时暴露了五个真实但不能混为一谈的问题：

| 问题 | 直接影响 | 所属边界 |
|---|---|---|
| Governor 错误启动产品 MCP，既有任务不能采用修复后的配置 | “own项目”无法完成复核并继续 | Codex Agent 隔离与会话恢复 |
| Governor 基础设施失败后，治理运行时没有可达出口 | 主任务被 Hook 反复推回同一失败链 | 自主治理控制面 |
| 多个主任务各自启动 stdio MCP 并打开同一资产目录 | 第二个任务因目录锁无法接入同一核心 | Ownward 产品数据面与多客户端接入 |
| 普通子 Agent 也默认继承主任务的必需产品 MCP | 开发子任务同样因目录锁启动失败，并获得不必要的数据面能力 | 子 Agent 角色隔离 |
| 治理状态没有活动主任务所有权，写锁也不能随异常进程自动释放 | 分叉恢复可能互相失效，进程崩溃可能永久阻断治理写入 | 治理状态并发与恢复 |

五者属于三条边界：问题一和问题四建立角色级数据面隔离；问题二和问题五保证治理控制面能够持续、退出和恢复；问题三让真正需要使用 Ownward 的多个客户端共享同一个权威内核。不能用共享服务掩盖错误授权，也不能用放宽治理或资产锁换取恢复。

本文是问题调查与解决设计，不替代产品需求、架构总纲或自主治理规范；方案实施并验证通过后，才把稳定结论同步到对应权威文档。

## 共同事实

1. Codex 任务“own项目”（任务 ID：`01a0294d-3776-73b1-9b39-f410cc655c51`）的历史能够完整读取，任务可以接收消息；历史目录迁移到 E 盘与本次故障没有因果关系。
2. 主任务已运行 `E:\Dev\ownward\bin\ownward.exe mcp --data-dir E:\Dev\ownward\.ownward\development`，并持有信息资产目录的独占锁。
3. 第二个进程打开同一目录时稳定返回“目录正由另一个 Ownward 进程使用”。该保护由 `internal/assetlog/directory_lock_windows.go` 中的 `LockFileEx` 实现，本身是正确的数据安全边界。
4. 故障任务中的 Governor 仍尝试初始化必需的 Ownward MCP，并在返回 MCP `initialize` 前退出；Codex 因而只看到 `connection closed: initialize response`。
5. 当前 `.codex/agents/governor.toml` 已完整定义同名 MCP transport 并设置 `enabled = false`、`required = false`，但它是在故障任务启动后形成的；修改磁盘文件不能证明既有任务已经重新加载配置。
6. 当前 Stop Hook 在治理未完成时总是返回 `decision: block`，阻止会形成新的继续提示；当 Governor 本身无法启动时，这会把失败放大为循环。
7. Ownward 已有 `mcp-http` 本机回环服务、Bearer Token 支持和 Streamable HTTP 适配测试；`TestStreamableHTTPUsesTheSameCore` 已证明该 transport 使用同一核心。多客户端方案应复用这条产品路径，而不是另造第二套内核或放宽资产锁。
8. “own项目”中普通无上下文子 Agent 也稳定因同一个 `required Ownward MCP` 启动失败，证明错误继承并非 Governor 单一角色的局部现象。
9. 治理运行时当前只有项目级 `state.json`，没有活动主任务的会话身份和所有权代次；写事务使用 `O_CREATE|O_EXCL` 创建 `.lock`，仅靠进程正常返回时删除，进程异常退出后会留下无法自动释放的锁文件。

### 官方能力边界

- Codex 自定义 Agent 可以覆盖包括 `mcp_servers` 在内的会话配置；未覆盖时才继承父任务配置，因此 Governor 的数据面隔离可以通过完整 Agent 配置实现并验证。[Codex Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- Codex 的 Stop Hook 返回 `decision: block` 时会自动创建新的继续提示，而不是结束当前任务；失败条件不变时反复返回该决定，确实会构成循环。[Codex Hooks](https://learn.chatgpt.com/docs/hooks)
- Codex Hook 会向 `SessionStart` 和 `UserPromptSubmit` 提供当前 `session_id`，而 `UserPromptSubmit` 还会提供即将发送的 `prompt`；任务恢复可以据此把 Codex 返回的分叉任务与 Hook 实际看到的会话身份做一次性、可验证的绑定，不能假定两类身份天然相同。[Codex Hooks](https://learn.chatgpt.com/docs/hooks)
- Codex 正式支持 stdio 与 Streamable HTTP 两种 MCP transport，也支持项目级配置、Bearer Token 和必需服务启动语义；单内核多客户端接入不依赖私有协议。[Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

## 问题一：Governor 数据面隔离与故障任务恢复

### 发生场景与业务偏差

主 Agent 使用 Ownward 完成产品开发，治理系统在启动、恢复或上下文压缩后触发只读 Governor 复核。

预期流程：

```text
主任务连接 Ownward → Governor 以纯只读治理环境启动
→ Governor 返回结构化结论 → 主任务登记并继续
```

实际流程：

```text
主任务已持有 Ownward 资产目录
→ Governor 继承并启动第二个 Ownward MCP
→ 第二个进程被正确的目录锁拒绝
→ Governor 在复核前启动失败
→ 既有任务继续使用启动时的旧配置，反复进入同一失败
```

问题不在 Ownward 目录锁，也不在对话历史；根因是 Governor 的产品数据面隔离没有成为启动时可验证的不变量，同时系统把“配置文件已修改”误当成“既有任务已加载新配置”。

### 解决预期

1. Governor 在任何主任务状态下都不初始化、不依赖也不继承 Ownward 产品 MCP。
2. Agent 或 MCP 配置变化后，旧任务不能被误认为已经采用新配置。
3. 故障任务的完整历史、用户意图、治理状态、工作包和有效证据均被保留，主线能够在加载新配置的任务中无损继续。
4. 恢复不依赖反复尝试旧任务，也不通过关闭资产锁或绕过 Governor 达成。

### 最优解决方案

#### 1. 把隔离写成完整、可机械验证的配置事实

- Governor 文件保留 Ownward MCP 的完整 `command`、`args`、`cwd` transport，再明确设置 `enabled = false`、`required = false`；不能依赖父配置覆盖顺序、默认值或只有开关的残缺 MCP 段。
- `doctor` 同时验证 Governor 只读属性、同名 MCP transport 完整性、禁用状态和项目 Hook 有效性。任一项不成立时，治理不能进入产品工作。
- Governor、项目 MCP 或 Hook 定义纳入运行配置身份。身份变化立即使旧冷启动结论失效，但不删除工作包和已独立成立的产品证据。

#### 2. 只用真实冷启动证明配置生效

在主任务 Ownward 已运行的条件下，以全新任务启动 Governor，确认：

- Governor 能完成复核并返回合法结果；
- 没有第二个指向同一资产目录的 Ownward 进程；
- Codex 没有 `malformed agent`、`invalid transport` 或 MCP 初始化错误。

同一任务内修改文件后的脚本直调、配置文本检查或再次尝试，均不能替代这项证明。

#### 3. 用 Codex 原生任务分叉恢复“own项目”

旧任务启动时的 Agent/MCP 配置不可被假定为热更新，因此不承诺让原任务原地变成新运行时。恢复采用 Codex 原生任务分叉：

1. 保留旧任务及原始失败证据，不删除、不覆盖历史，并确认治理状态已经安全落盘。
2. 按问题五的所有权协议冻结旧任务写入并创建待绑定的一次性交接记录；精确识别并正常停止只属于旧任务、指向目标资产目录的 MCP 进程，不结束其他 Ownward 实例。
3. 创建同目录分叉。Codex 分叉复制源任务的全部已完成历史；即使源任务仍有无法结束的活动回合，也只舍弃该回合尚未完成、尚未成立的响应，不以“等待旧任务空闲”作为恢复前提。
4. Codex 返回分叉任务身份后，恢复控制器为该目标生成短期、单次的一次性交接标识，并只向该分叉发送一条结构化继续消息。分叉首次 `SessionStart` 保持只读，不抢占所有权；随后的首次 `UserPromptSubmit` 使用 Hook 实际提供的 `session_id` 和消息中的交接标识原子完成绑定、消费标识并取得新 `owner_epoch`。交接标识与目标分叉和当前交接代次绑定、短期有效且只能消费一次；不能假定 Codex 返回的任务身份与 Hook `session_id` 是同一命名空间。旧任务随即转为退役只读，之后的消息或 Hook 不能再递增复核代次、修改工作包或重新取得产品写权限。
5. 将原治理状态、工作包和有效证据按身份重新绑定；只失效失败的 Governor 请求、未完成回合和依赖旧运行配置的结论。
6. 新任务通过冷启动预检和首次 Governor 复核后，从原工作包继续，再清理失败重试留下的纯临时残留；旧任务保留为可审计历史。

这恢复的是用户真正需要的“完整上下文与工作连续性”，不是伪造原任务已经热加载配置。原任务 ID 本身不会被宣称为原地热修复；恢复后的可用载体是包含其完整已完成历史的新分叉任务。如果未来 Codex 提供能够证明同一任务重新初始化全部 Agent、MCP 与 Hook 配置的原生能力，才可以在通过同等冷启动证据后保留原任务 ID。

### 完成证据

- 主任务持有 Ownward 时，Governor 连续多次复核均不产生第二个数据进程。
- 新任务冷启动、恢复和上下文压缩后行为一致。
- 分叉任务包含旧任务完整已完成历史，并沿用同一工作包和有效证据继续。
- 分叉任务身份与 Hook `session_id` 通过一次性交接完成唯一绑定；错误目标、错误代次、重复提交和过期标识均被拒绝，首次 `SessionStart` 不会提前抢占所有权。
- 治理所有权只属于恢复后的分叉；旧任务再次收到消息时只能说明已经迁移，不能使新任务的 Review 或批准失效。
- 原错误请求被精确失效，产品状态、信息资产和其他治理证据没有被清除。
- 结果明确区分“原任务历史被完整续接”与“原任务 ID 原地恢复”，不把分叉成功误报为旧运行时已经修复。

## 问题二：Governor 基础设施失败时治理控制面不可恢复

### 发生场景与业务偏差

Governor 可能因配置、子 Agent 启动、MCP 初始化、返回通道或结果校验等基础设施问题无法完成复核。

预期流程：

```text
Governor 基础设施失败
→ 产品修改继续关闭
→ 保存失败与工作状态
→ 自主修复治理控制面
→ 新运行环境复核通过
→ 从原检查点继续
```

实际流程：

```text
Governor 启动失败
→ Review 仍为 required
→ Stop Hook 阻止任务结束并再次要求启动 Governor
→ 用户消息或恢复再次注入同一要求
→ 相同失败无限重试，任务既不能工作也不能正常退出
```

根因是当前运行时把“产品工作必须经复核”和“对话在复核失败时也不得结束”错误地绑定在一起，并且没有记录 Governor 基础设施失败的身份、重试条件和恢复边界。

### 解决预期

1. Governor 不可用时，任何产品修改仍然失败关闭，不能伪造批准或降低治理标准。
2. 状态保存、只读诊断、治理控制面修复和正常结束始终可达。
3. 同一根因在运行条件没有变化前只失败一次，不因 Stop、用户消息、恢复或压缩而循环。
4. 技术故障由体系自主定位和修复；只有必须由用户作出的产品决策，或继续执行已经构成异常耗时与无价值消耗时，才暂停主线并找用户。
5. 修复控制面后必须在新运行环境重新获得真实 Governor 结果，旧批准不能自动恢复。

### 最优解决方案

#### 1. 在既有 Review 中增加“基础设施失败闩锁”

不新增一套平行治理状态机，也不把技术故障伪装成产品暂停。为当前 Review 保存一个结构化基础设施失败记录，至少绑定：

- `review_id`、触发实例和工作包身份；
- 归一化失败签名；
- Governor、MCP、Hook 与运行环境身份；
- 首次失败时间、最近验证事实和证据路径；
- 允许重试所需的最小状态变化。

主 Agent 看到 Governor 启动、返回或校验失败后，通过精确的治理命令登记该记录。相同 Review、失败签名和运行身份组合只尝试一次；条件未变时，SessionStart、UserPromptSubmit、PreCompact 和 Stop 只能返回已有失败事实与恢复动作，不得重新启动 Governor。

#### 2. 分离“产品失败关闭”与“任务能够结束”

- `PreToolUse` 继续拒绝所有产品写入、正式验证和其他受治理动作。
- 只读调查、状态持久化和精确的治理控制命令继续可用。
- 健康运行且仍有可执行工作时，Stop 继续按自主开发契约生成下一条有效动作，不能因为阶段结束或主 Agent 提前收尾而中断持续开发。
- 基础设施失败闩锁成立后，Stop 只能引导已经登记的诊断或控制面修复动作，不得再次启动同一 Governor；修复已经应用、必须冷启动验证时允许保存状态并正常结束。
- 用户主动打断、真实产品决策暂停和已经确认的异常资源消耗停止不被转换成自动继续提示。
- 主 Agent 声称整个任务完成却缺少有效 Governor 结论时仍必须阻止完成。允许结束只代表当前运行环境需要恢复，不代表产品获批；下一次恢复仍从同一未完成 Review 开始。

#### 3. 建立受限的自主控制面修复通道

技术故障不应因为 Governor 暂时不可用就被无条件交给用户。失败闩锁成立后，主 Agent 可以进入专用控制面修复工作包，但该通道不是任意修改 `.codex` 的授权：

- 运行时在故障发生前就必须冻结恢复允许范围、保护契约及其内容摘要；当前失败任务不能扩大自己的恢复范围。
- 允许范围只覆盖为恢复既有治理契约所需的实现、集成配置和结构性状态字段，例如修正 Governor MCP transport、Hook 实现或为失败闩锁增加 Schema 字段。
- 产品目标、权威依据、完成条件、Governor 职责与判断规则、Review 决策语义、批准条件、产品写入保护、恢复允许范围本身均为保护内容；主 Agent 不得在恢复通道中改变。
- 普通 `Write`、`Edit`、`apply_patch` 与任意 Shell 命令不能直接写入治理控制面。主 Agent 只能在隔离暂存区形成候选补丁，再通过单一的 `governance-cli repair-apply` 入口申请应用。
- `repair-apply` 使用故障前已经冻结并载入的恢复策略校验候选补丁：只允许白名单内的实现改动，验证保护内容摘要不变，拒绝清除 Review、伪造结果、修改批准、关闭治理或修改修复闸门本身；通过后才原子应用并保存完整审计差异。候选补丁不能改变正在执行的闸门或其冻结策略，因而不存在“先改守门人、再给自己放权”的循环。
- 修复前保存保护契约身份、变更基线和失败证据；修复后生成新的运行配置身份。当前失败任务不得自改修复闸门；闸门实现故障时回退到最近一个已验证版本，或由加载同一冻结契约的隔离维护任务修复。只有保护契约本身确实需要改变时，才退出自动恢复并交由用户作出对应的产品或治理决策，不能把技术修复伪装成决策阻塞。
- 修复完成后当前任务只能保存状态并结束；必须由加载新配置的任务针对冻结的保护契约运行独立 `doctor`、真实冷启动 Governor 并接受同一 Review，产品工作才可恢复。

这不是让主 Agent 自我批准，而是允许它在不可自扩张的范围内修复监督设施；监督权只有在新任务中的独立校验和 Governor 真实返回后才恢复。

#### 4. 以运行身份变化作为唯一自动重试条件

只有以下事实之一发生变化，才允许重新尝试同一 Review：

- Governor、MCP、Hook 或治理运行时身份已变化；
- 外部 Codex 运行环境的已知故障已获得可复核的恢复证据；
- 上一次失败被证明是瞬时故障，且最小探测已成功。

恢复时保留原工作包、独立有效证据和失败历史，只失效依赖旧运行身份的复核尝试。新任务成功接受 Governor 结果后，失败闩锁转为已解决审计事件，不删除历史。

### 完成证据

- 注入 Governor 启动、返回和结果校验故障，产品修改均被拒绝。
- 每种相同故障只启动一次 Governor；Stop 和后续消息不产生自动重试循环。
- 健康状态下未完成的主线仍会由 Stop 继续推进，基础设施故障修复不能削弱持续开发闭环。
- 主任务能够保存状态并正常结束，工作包和有效证据完整。
- 控制面修复不能写入产品范围，也不能自行恢复批准。
- 普通文件工具不能直接修改治理控制面；合法候选补丁只能经冻结的 `repair-apply` 闸门原子应用。
- 尝试扩大恢复范围、改写保护契约、修改修复闸门或关闭治理时被确定性拒绝。
- 新任务加载新身份后完成 Governor 复核并从原检查点继续。

## 问题三：多个主任务无法共享同一 Ownward 权威内核

### 发生场景与业务偏差

多个独立 Codex 主任务都需要访问同一个用户的 Ownward 信息体系。它们是产品客户端，不是 Governor，因此都应通过统一核心看到相同的信息身份、内容和变更结果。

预期流程：

```text
一个 Ownward 内核独占管理资产目录
→ 多个主任务作为客户端连接同一内核
→ 内核统一并发、版本和写入秩序
→ 所有任务看到同一权威状态
```

实际流程：

```text
每个 Codex 任务按 stdio MCP 配置各启动一个 Ownward 进程
→ 每个进程都尝试直接打开同一资产目录
→ 第一个成功，后续进程被目录锁拒绝
→ 客户端只看到含义不清晰的 MCP 握手失败
```

目录锁拒绝第二个资产所有者是正确行为；真正的问题是当前 stdio 部署把“客户端会话生命周期”和“权威内核生命周期”绑定在一起。它与问题一不同：Governor 根本不应连接产品数据面，而多个主任务确实需要连接产品数据面。

该能力符合“所有智能个体共享同一核心”和“不同独立会话看到相同信息”的产品方向。第一版虽不要求同时适配多种外部智能体，但不能用每个会话各自持有一套数据进程的方式反向绑死统一核心。

### 解决预期

1. 每个资产目录始终只有一个 Ownward 内核实例拥有存储与派生状态。
2. 多个主任务连接的是同一实例，不形成私有副本、旁路状态或第二套写入权威。
3. 并发读取、创建和带版本更新具有确定性结果；客户端退出不导致其他客户端失去核心。
4. 用户安装后不需要手工启动附属服务，也不需要暴露公网端口或配置外部密钥。
5. 不支持或暂不可用时返回明确、可恢复的连接错误，不能伪装成 MCP 握手异常。

### 最优解决方案

#### 1. 将现有 `mcp-http` 提升为共享接入面

由一个常驻 Ownward 内核进程打开资产目录并持有现有独占锁；它通过已经存在的本机回环 Streamable HTTP MCP 暴露同一 `mcpserver.Server` 和同一 `core.Service`。这不是新增第二条产品路径，只是把当前 stdio 的一对一 transport 换成可多客户端连接的 transport。

- 已由 Ownward 启动器管理服务生命周期的 Streamable HTTP 客户端可以直接连接该端点。
- Codex 项目配置使用轻量 `connect-or-start` stdio 连接器作为标准入口：每个任务可以独立启动连接器，但连接器只负责发现或启动唯一服务并转发 stdio 与共享端点之间的协议，绝不打开资产目录、加载模型或形成状态权威。这样服务尚未运行时，新任务也不需要用户先执行命令。
- 其他仅支持 stdio 的客户端复用同一连接器，不再各自启动数据进程。
- Governor 继续完全禁用 Ownward MCP，不是共享服务客户端。

#### 2. 把服务生命周期交给 Ownward，而不是交给某个会话

连接器与 Ownward 启动器共用确定性的 `connect-or-start` 能力：

1. 根据规范化资产目录生成唯一服务身份。
2. 先验证已登记端点的实例身份、协议版本、数据目录身份和存活状态；有效则直接连接。
3. 服务不存在时，以单独的启动互斥原子创建唯一内核；并发启动的失败方等待已成功实例就绪后连接，不能再启动第二个资产所有者。
4. 服务就绪后原子发布端点描述；异常退出或陈旧描述由下一次连接安全回收。
5. 客户端数量归零后的保活与退出由 Ownward 统一管理，不能由任一 Codex 会话直接杀死共享内核。
6. 服务升级时先停止接收新写入并完成在途提交，再由启动器切换实例；任何客户端不得自行用另一二进制抢占同一资产目录。

正式交付由 Ownward 启动器自动完成该过程；开发配置使用同一入口，避免形成只在测试中成立的特殊路径。

#### 3. 保持本机、安全和单一权威

- 端点只允许监听本机回环；默认使用每个服务实例生成的高熵 Bearer Token，令牌只保存在受当前用户权限保护的运行状态中，不进入仓库、日志或信息资产。
- 端点描述只保存连接与身份元数据，不成为第二份产品状态；信息资产和派生状态仍只由内核维护。
- 内核内部对写操作实施统一调度，保留现有期望版本检查，避免并发更新静默覆盖；读取可以并发，但只能观察已提交状态。
- 资产目录独占锁继续作为最后防线。若另一个真实数据进程尝试打开目录，仍必须失败。
- 连接握手同时校验协议、二进制、数据目录、能力配置和向量空间身份；客户端不能因协议版本相同就静默使用错误候选或错误能力代际。不兼容时明确拒绝并交由启动器执行安全升级或连接正确实例。

#### 4. 复用现有实现，补齐缺失边界

当前 `mcp-http`、回环限制、Bearer Token 和同一核心测试已经提供了正确地基；需要补齐的是 `connect-or-start` 连接器、服务发现、生命周期、并发启动、客户端配置、完整运行身份和多客户端端到端验证。无需重写 Ownward 内核，也无需放宽存储锁，更不应另建一套共享数据库或远程服务。

### 完成证据

- 两个独立主任务同时连接同一资产目录时，系统中只有一个资产持有进程。
- 一个任务创建或更新后，另一个任务通过相同稳定身份立即读取到已提交结果。
- 并发更新遵守期望版本，不发生静默覆盖、重复资产或派生状态分叉。
- 任一客户端退出、上下文压缩或重新连接，不影响其他客户端和权威内核。
- 并发冷启动、服务异常退出、陈旧端点、错误令牌和版本不匹配均给出确定、可恢复的结果。
- 服务未启动时，两个全新 Codex 任务可以同时通过标准项目配置自动汇合到唯一服务，无需用户预先运行命令。
- 候选二进制或能力身份变化时，客户端不会静默复用旧服务；安全切换不丢失已提交资产。
- stdio 连接器与直接 HTTP 客户端得到相同工具契约和结果，不形成测试专用产品路径。

## 问题四：非产品子 Agent 错误继承产品数据面

### 发生场景与业务偏差

主任务会按需启动 Governor、Explorer、Worker 或其他专门子 Agent。它们应只获得完成自身职责所需的能力。

预期流程：

```text
主任务触发明确角色 → 角色配置声明自己的 MCP 能力
→ 非产品角色不连接 Ownward → 需要产品信息的角色连接统一核心
```

实际流程：

```text
项目级 Ownward MCP 为 required
→ 未显式覆盖的子 Agent 自动继承
→ 每个子 Agent 都启动新的 stdio 数据进程
→ 被目录锁拒绝，或获得职责之外的数据面访问
```

该问题已经由“own项目”中的普通无上下文子 Agent 复现，不是对 Governor 故障的推测。根因是产品 MCP 采用“父任务默认赋予、子角色逐个退出”的授权方式，而系统没有完整的角色能力矩阵和新增角色准入检查。

### 解决预期

1. 子 Agent 的产品数据面能力由角色职责显式决定，不能因父任务拥有而自动获得。
2. Governor 和不需要用户信息的开发角色不启动 Ownward、不持有令牌，也不因目录锁失败。
3. 确实需要产品信息的角色只能连接问题三规定的统一核心，不能直接打开资产目录。
4. 新增或未登记的角色不能以继承默认值绕过能力审查。

### 最优解决方案

1. 建立唯一的子 Agent MCP 能力矩阵，把每个允许启动的项目角色标为 `disabled` 或 `shared-client`；没有显式条目的角色默认拒绝启动，而不是继承主任务产品 MCP。
2. 为 Governor、Explorer、Worker 及实际使用的其他项目角色提供完整、项目级自定义 Agent 配置。非产品角色完整声明同名 transport 并设置 `enabled = false`、`required = false`；不得只写残缺开关或依赖配置合并顺序。
3. 需要 Ownward 的专用角色只能在问题三完成后标为 `shared-client`，通过同一个 `connect-or-start` 入口连接统一内核；第一版不存在合理理由让子 Agent 再启动私有数据进程。
4. `doctor` 枚举能力矩阵、项目 Agent 文件和编排器允许的角色，验证三者一一对应；新增角色、任意内建回退或配置缺失必须在启动产品工作前失败。
5. 该规则只控制子 Agent 的工具授权，不改变主任务、外部智能体和 Ownward 内核的职责。

### 完成证据

- 主任务持有当前 stdio Ownward 时，Governor、Explorer 和 Worker 均能冷启动，且系统中没有第二个 Ownward 数据进程。
- 非产品子 Agent 的工具列表不包含 Ownward，配置错误不会静默回退到父任务 MCP。
- 需要产品信息的专用角色通过共享接入面读取与主任务相同的稳定信息身份，不产生私有状态。
- 新增未登记角色的冷启动被 `doctor` 和编排入口确定性拒绝。

## 问题五：治理状态缺少活动任务所有权与崩溃安全写锁

### 发生场景与业务偏差

持续开发会经历恢复、上下文压缩和任务分叉，旧任务与新任务可能短暂并存；任一治理命令也可能在写入过程中被强制终止。

预期流程：

```text
一个活动主任务拥有治理写权限
→ 恢复或分叉时原子交接所有权
→ 写事务由随进程死亡自动释放的系统锁保护
→ 旧任务和崩溃进程都不能阻断新任务
```

实际流程：

```text
所有任务共用项目级 state.json，但没有活动会话所有权
→ 任一 SessionStart 都能创建新复核代次并使另一任务结果失效

治理命令以 O_EXCL 创建 .lock
→ 进程异常退出时 defer 删除不会执行
→ 后续所有治理写入永久报告“被另一个 writer 锁定”
```

原子替换保护了 `state.json` 内容完整性，但不能解决谁有权推进状态，也不能让哨兵锁在进程崩溃后自动释放。根因是逻辑所有权和物理互斥都没有绑定真实运行生命周期。

### 解决预期

1. 同一治理 `run_id` 任一时刻只有一个活动主任务能够推进 Review、工作包和批准。
2. 恢复、分叉和主动迁移能够原子交接，不需要删除状态或重新开始任务。
3. 旧任务再次收到消息时不能抢回所有权、创建复核或使新任务证据失效。
4. 写入进程崩溃后锁自动释放，`state.json` 保持最近一次完整提交并可立即恢复。
5. 正常并发只产生短暂、可识别的忙状态，不被误判为永久基础设施故障。

### 最优解决方案

#### 1. 为治理运行增加活动所有权代次

- `state.json` 保存 Codex Hook 可稳定识别的活动任务身份、会话谱系和单调递增的 `owner_epoch`；所有 Hook 状态变更与治理控制命令都必须绑定当前代次，不能只依赖可能随重启变化的瞬时进程号。
- `SessionStart` 只有在会话仍属于当前任务谱系时才能刷新固定复核；非所有者只得到“任务已由另一会话继续”的只读结果，不能修改任何治理状态。正常恢复与上下文压缩保持同一所有权谱系。
- 任务分叉采用两阶段一次性交接：先冻结旧所有者并创建未绑定记录；Codex 返回分叉任务身份后，由恢复控制器生成与目标及交接代次绑定、短期有效、单次消费的交接标识并发送首条结构化继续消息。新任务首次 `SessionStart` 只读，首次 `UserPromptSubmit` 再用 Hook 实际提供的 `session_id` 消费标识、绑定会话谱系并取得新 `owner_epoch`。任务身份与 Hook 会话身份不被假定相等。交接只改变运行载体，不改变 `run_id`、工作包、完成条件或有效证据，且任一阶段失败都能回到明确的旧所有者或待恢复状态。
- 意外重复启动不能自动抢占。只有当前所有者明确交接，或通过可复核的恢复事实确认其已经不可用时，才创建新代次；竞争者由同一事务确定唯一胜者。

#### 2. 用系统持有的文件锁替代哨兵文件生命周期

- 保留统一事务入口和原子文件替换，但将 `.lock` 改为由操作系统文件句柄持有的排他锁：Windows 使用 `LockFileEx`，其他平台使用等价系统锁。进程退出时由系统自动释放；磁盘上是否保留锁文件不再代表锁是否有效。
- 所有 `state.json`、Review 请求、结果索引和事件追加都在同一事务边界内完成；读取到的版本与写入前版本不一致时重新计算，不允许丢失更新。
- 正常争用采用仅覆盖毫秒级状态事务的有界等待；超出后返回包含当前所有权和事务身份的结构化忙状态，不删除仍由活进程持有的锁，也不触发 Governor 重试循环。

#### 3. 把所有权与锁恢复纳入 `doctor`

`doctor` 必须验证所有权代次、任务身份到 Hook 会话身份的一次性交接、交接标识的单次消费与过期拒绝、防旧会话回写、进程崩溃自动释锁和原子恢复；不得通过手工删除 `.lock` 证明成功。

### 完成证据

- 两个会话同时启动时只有活动所有者能够创建 Review 或修改工作包，另一会话不能使其结果失效。
- 从故障任务分叉后，新任务原子接管，旧任务收到新消息也保持退役只读。
- 在持锁后、临时文件写入后和替换前分别强制终止进程；下一进程均能自动取得锁，并读取到旧完整状态或新完整状态，不出现半写入。
- 并发状态事务没有丢失事件、重复批准或永久残留锁，所有权与恢复历史可审计。

## 统一实施顺序

1. **先修治理控制面**：完成问题二的失败闩锁、状态驱动 Stop 语义与受限恢复通道，以及问题五的活动所有权和崩溃安全写锁，保证后续修复能够持续、结束和交接。
2. **再封闭 Agent 能力边界**：完成问题一的 Governor 隔离和问题四的角色能力矩阵，使所有治理与开发子 Agent 都不再错误继承产品数据面。
3. **恢复故障任务**：以“own项目”分叉完成所有权交接、真实冷启动和工作连续性验证，证明当前事故真正关闭。
4. **完成共享数据面**：在不改变核心能力契约的前提下，把现有 `mcp-http` 收敛为单内核多客户端接入，补齐生命周期与并发证据；随后才允许确有需要的子 Agent 角色成为共享客户端。
5. **统一回归**：同时验证角色隔离、健康主线持续推进、控制面故障恢复、任务所有权交接和产品多客户端共享，避免一个问题的修复重新引入另一个问题。

五个问题分别验收、共同结束。角色隔离通过不能把控制面恢复或共享产品内核标为完成；问题三的产品接入改造也不能成为恢复当前治理任务的前置借口。

## 不可破坏的边界

1. 不放宽、删除或绕过信息资产目录的独占保护。
2. Governor 始终只读且不连接 Ownward 产品 MCP。
3. 非产品子 Agent 默认不连接 Ownward；需要产品信息的角色必须显式授权并只连接统一核心。
4. 主 Agent 可以修复治理控制面，但不能自行制造 Governor 批准或用同一旧任务恢复产品权限。
5. 健康状态下持续开发仍会自动推进；技术故障恢复不得变成取消持续性的通用出口。
6. 治理状态仍只有一个权威和一个活动写入所有者；失败记录、端点描述和会话历史都不得成为平行任务状态。
7. 共享服务只是统一核心的接入形态，不拥有第二份信息资产，不改变内核、接入适配和能力契约的职责。
8. 不删除故障任务历史、有效工作包、独立证据或用户信息来换取恢复。
9. 开发环境与正式交付使用同一产品路径；正式用户无需手工启动附属进程、配置模型服务或暴露非本机网络端口。

## 整体完成条件

- 五个问题的真实业务链路分别通过其完成证据，没有用配置文字、单元测试或主观判断代替端到端事实。
- “own项目”的完整上下文和有效进度已在加载新配置的分叉任务中恢复并能够继续工作；原任务 ID 未被误报为已经热修复。
- Governor 基础设施故障不再造成自动重试与不可结束循环，健康状态下持续开发仍会自动推进，且产品工作仍然失败关闭。
- Governor 和非产品子 Agent 均不继承产品数据面；需要 Ownward 的角色只能通过显式能力配置连接统一核心。
- 治理所有权能够在恢复任务间原子交接，旧会话和崩溃遗留锁不能阻断或失效当前工作。
- 多个主任务能够通过唯一 Ownward 内核共享同一信息体系，资产锁和单一权威保持不变。
- 修复没有改变产品定位、信息资产边界、模块职责、正式能力契约和既有功能，也没有引入第二套产品或治理路径。

## 实施与验证结果

五个问题已按本文边界共同修复：

1. Governor、默认开发角色、Explorer 与 Worker 均使用完整的项目级 Agent 配置；产品 MCP 能力由显式矩阵决定，未登记角色不能静默继承主任务数据面。
2. Governor 基础设施失败会按运行时身份闩锁一次；产品动作继续失败关闭，但状态保存、诊断、受限控制面修复和任务退出保持可达。同一旧任务不能通过自行修复重新取得产品权限。
3. `ownward mcp` 已成为轻量 `connect-or-start` 客户端；同一数据目录只运行一个本机回环 `mcp-http` 权威核心，多个 stdio 客户端共享工具和稳定信息身份，任一客户端退出不终止核心。
