# 专项资格执行与治理失败事件真实性问题

## 文档边界

本文登记“own项目”在 Governor/MCP 死锁发生前暴露的两个独立问题。两者发生在同一任务链中，但不属于同一系统边界，也没有共同根因：问题一属于 Acceptance Suite 专项资格执行层；问题二属于主 Agent 操作与自主治理运行时的事件真实性边界。它们均不属于已登记的 Governor/MCP 死锁问题。

本文记录问题事实、根因、责任边界和解决方案；解决方案不得修改验收标准、产品能力或治理原则，只修正对应实现与错误操作。

---

## 问题一：专项资格集语义工作集中处理后超时

### 问题表象

候选 `38ca955` 执行 Ownward 专项资格集首个场景时，同一场景的五条初始信息已经分别产生语义工作，但在 240 秒阶段边界内没有产生任何语义提交，执行器因此终止整个语义阶段，资格集没有形成有效场景结果。

随后使用相同模型、推理强度和产品路径进行的单条代表性探测，在约 27 秒内完成了 `semantic_work → semantic_submit → 状态复核` 的完整闭环。这证明失败并非由单条信息无法理解、模型必然过慢或 Ownward 内核无法接受语义结果造成。

### 预期与实际流程

预期流程：

```text
取得一条可独立成立的语义工作
→ 完成该条分析
→ 立即提交并保存该条结果
→ 继续下一条
→ 全部信息进入 ready 或 uncertain 后再查询
```

实际流程：

```text
一次把五条资产交给同一个 Codex 阶段
→ 要求全部分析完毕后统一批量提交
→ 五条 work 已返回但没有中间 submit
→ 集中推理超过 240 秒
→ 整个阶段终止，已完成的局部工作不能成为有效检查点
```

### 根本原因

`benchmarks/acceptance/suite/adapters/product/verify.py` 的 `_semantic_prompt` 明确要求一次调用 `ownward_semantic_work` 取得全部资产，并在全部分析结束后调用一次 `ownward_semantic_submit_batch`；`_complete_semantics` 又把整个资产列表绑定到同一个 Codex 进程和阶段超时。

该实现把可独立完成和提交的五项工作错误地合并为一个长事务，提交时机晚于全部推理，因而同时失去了渐进提交、局部检查点和只补失败项的能力。与此同时，`_run_scenario` 在 `--resume` 遇到未完成场景时会删除整个场景目录；即使语义阶段增加逐条提交，只要这条场景级重置仍然存在，已经成立的局部检查点仍会丢失。提交 `38ca955` 修复了资格集进程控制、超时证据保留、临时目录清理与 Python 兼容性，但没有改变这两条执行路径；历史中提出的逐条 `work → submit` 修复尚未实施。

修复链路还暴露出同一执行层的证据失效粒度缺口：当前资源报告保存完整 product scope 的 `acceptance_binding`，其中包含语义适配器工具摘要。只修改语义编排也会使资源报告被判为无效，迫使候选在二进制、发布包、资源测量工具和机器条件均未变化时重新执行最长可达十分钟的资源准入。资源成本与语义编排并无这种依赖关系，这不是严谨绑定，而是把无关依赖错误耦合后造成的重复工作。

当前绑定生成器还把“被验收的产品候选提交”直接取为验收工具仓库的 `HEAD`，并要求候选二进制版本等于该 `HEAD`。Ownward 的产品代码与 Acceptance Suite 虽在同一仓库，但两者不是同一证据身份：本次只修适配器就会改变仓库 `HEAD`，现有生成器因而无法为仍是 `38ca955` 的冻结产品制品生成新 product 工具绑定，只能错误地重建产品候选并使 core、frontier 一并失效。若不先拆开候选身份与验收工具身份，方案中的“只重绑 product、复用已通过层级”在当前实现上不可执行。

逐条执行本身仍不足以保证可恢复性。当前 Codex 子进程的事件只在进程正常结束或超时返回后统一写入 `events.jsonl`；语义提交却会先持久化到候选的数据目录。若进程在“内核已经接受提交、事件与进度尚未落盘”之间退出，内核会因已有 `SemanticResult` 不再返回这条工作，而验收端又没有可复核的提交证据。仅凭终态 `status` 无法还原 `work_id` 和实际提交内容，直接跳过会制造无证据通过，直接重试又拿不到原工作。因此，场景数据状态与验收证据必须形成同一个可恢复事务边界。

### 问题性质

这是 **Acceptance Suite 专项验收执行层的编排实现问题**。

- 不是产品定位、Ownward 架构或内核能力问题。
- 不是固定数据、质量标准、资格集范围或验收体系静态设计错误。
- 不是该次执行 Agent 临时操作造成的首次失败；Agent 只是实际运行了已有适配器路径。
- 需要修正的是验收适配器如何组织可独立语义工作、何时提交结果以及如何保存局部有效进度，不能通过放宽超时或降低质量标准掩盖。

### 解决责任与方案

该问题能够由 Ownward 仓库直接解决，不需要用户或执行 Agent 临时改变操作：

1. 将专项适配器的语义阶段改为逐条闭环：每次只领取一条资产的语义工作，使用相同语义契约完成分析后立即提交并复核其进入 `ready` 或 `uncertain`，再处理下一条。
2. 为场景建立原子进度清单，绑定候选、任务、执行工具、模型配置和资源证据，保存稳定资产 ID、修订号、内核产生的 `work_id`、当前阶段、最近已验证场景数据树摘要及每条资产的终态证据；恢复时必须核对 `work_id`、当前资产修订、数据树和证据仍一致，确保逐条提交不会改变其他条目已经冻结的资产与候选上下文。每条资产使用独立、只增不改的尝试目录，进度清单只指向已经通过提交与状态复核的那次尝试，不能只凭目录存在判断有效，也不能覆盖失败原始证据。
3. 以验收工作区内的场景回滚点封闭产品状态与证据之间的崩溃窗口：首次创建尚未形成有效语义检查点时可以精确重建该场景；此后每个会改变场景数据的最小单元——单条语义提交，以及一次更新与其对应的语义提交——开始前，都从最近已验证状态生成一个带文件清单的回滚点。候选运行时没有请求在途且数据树摘要稳定后才允许生成回滚点；无法证明在线快照一致时，短暂停止候选进程完成快照，而不是冒险复制。Codex 事件流同步写入该条只增不改的尝试目录；只有提交返回、组织终态、原始事件和输出摘要全部核对通过，才把新数据树摘要与证据以落盘后的原子替换写入进度清单，再删除回滚点。恢复时，若进度、数据树与证据已经完整一致则保留新状态并只清理回滚点；否则先停止遗留进程、恢复最近回滚点，再只重做当前单元。这样即使内核已接受提交而验收进程尚未来得及落盘，也不会留下“产品已终态但没有验收证据”的半成功状态。只读查询无需快照，失败后直接重跑。
4. 将场景恢复从“未完成即整目录重置”改为按绑定、进度清单和回滚点恢复：绑定仍一致时只补未完成或提交被拒绝的条目；绑定变化或检查点损坏时才精确失效对应阶段，不能删除同候选已经通过的 core、frontier 或其他完整场景证据。
5. 单条失败只重试该条且沿用既有次数上限；异常退出保存该条已经产生的原始输出和工具事件，不用延长整体超时掩盖执行缺陷。
6. 保持固定数据、真值、模型配置、关系契约、评分口径和正式产品工具路径不变；回滚点只保护验收工作区内的隔离场景数据，不进入产品、不改变候选行为，也不成为用户运行时能力。
7. 对当前旧格式未完成场景保留原始失败证据用于审计，但因其没有任何语义终态提交，不将五条 `work` 伪装成可复用结果；只重建这个失败的 qualification 场景，不重跑已经绑定并通过的 core 与完整 frontier。
8. 增加受控的 scope 级重绑入口，使产品候选身份与验收工具身份在后续工具修复中保持独立：它必须从现有有效全局绑定取得既有冻结候选，机械验证候选提交仍存在、候选二进制与发布制品仍属于该提交，并要求当前验收工具仓库干净；随后只重新生成指定 scope 的环境、输入、工具和制品清单，将其他 scope 的绑定及清单逐字节保留。新清单与组合绑定先写入不可变的绑定代次目录并完整自检，再以一个原子活动指针切换，进程中断时仍指向上一完整代次，不能留下新旧清单混合状态。这样本次只重绑 product，无需把候选伪装成工具仓库新 `HEAD`，也无需修改或重签旧 core/frontier 报告；以后真正需要重跑某个旧 scope 时，再按其当前工具身份精确重绑该 scope。候选提交或候选制品变化仍必须走全候选重绑并使全部候选相关证据失效。不得用工作树覆盖、伪造版本输出、复制旧 product 清单或跳过当前工具哈希来绕开身份校验。
9. 将资源准入改为 product scope 内独立的资源证据绑定，只包含候选提交与二进制、发布包、生产存储报告、资源适配器、资源运行配置和机器环境等真实依赖；语义适配器、专项数据与 Codex 协议不得进入该子绑定。最终 qualification 报告仍绑定完整的新 product scope，并同时引用资源复用凭据和原资源报告摘要，因此不会削弱候选整体一致性。当前旧资源报告不得改写或直接冒充新格式：先重新校验其候选、原始证据摘要和全部真实资源依赖，校验通过后生成一份不可变复用凭据，绑定新资源子身份并引用旧报告及原始证据摘要；无法完整校验才精确失效并重测。适配器变更后重新生成 product 工具清单并通过 Suite `rebind` 只失效 qualification/full；恢复逻辑把旧失败场景与根部旧 product `binding.json` 移入只读审计位置并原子启用新绑定。禁止重建候选、重跑 core/frontier，或用语义工具变化制造无关资源重测。
10. 资格集固定包含四十条初始语义工作和两条更新后的语义工作。正式重跑前，在一次性隔离数据中以至少两条同配置、不同关系复杂度的独立语义闭环，加一次智能体查询，以及有效资源报告中的实耗事实（资源子绑定不一致时才执行一次隔离资源实测），保守推算完整资格集总墙钟；同时实测回滚点生成与恢复成本。预检不写正式检查点，也不混入候选证据。只有证明在固定三十分钟预算内留有异常处理余量才启动正式层。若推算不成立，先优化逐条执行调度、事件流落盘或快照开销，不能放宽预算、重新合并成长事务或直接开始一轮注定超时的正式运行。
11. 以故障注入夹具覆盖“提交前退出”“内核接受提交后、事件或进度落盘前退出”“进度原子替换期间退出”“更新已写入、更新后语义尚未完成”和“回滚点清理期间退出”，证明前序已终态条目及证据不变、当前单元回滚后可独立重做；同时验证绑定变化只精确失效对应阶段。以绑定测试证明“同一候选仅修改 product 适配器时保留 core/frontier、候选制品变化时全部相关层失效”，再用上述最小真实预检验证外部能力接入与预算成立。实现稳定后才重新运行受影响的专项资格层。

完成判定：故障注入后不存在“产品已终态但没有验收证据”的半成功状态，已终态条目及其证据保持不变，恢复只执行当前未完成单元；同一候选只改变语义适配器时能生成新 product 工具绑定、保留 core/frontier，并通过不可变复用凭据使用资源子绑定完全一致的既有资源报告，任一真实候选、资源依赖或旧原始证据变化则精确拒绝复用；同一绑定下完整 qualification 能从局部检查点在固定三十分钟预算内完成并形成正式报告。

### 当前状态

实现问题已经修复：专项适配器按单条语义工作形成不可变尝试和原子进度检查点，事件流实时落盘，数据变更由可恢复回滚点保护；恢复只补当前未完成单元。候选、验收工具和资源证据已经拆分为精确身份，scope 重绑采用不可变代次和原子活动指针；资源子身份完整绑定 CPU、物理内存、Python 运行时及真实测量依赖，旧资源证据只能通过完整依赖复核后的不可变凭据复用。正式资格集开始前还会以两条语义工作、一次查询和回滚实测推算完整成本，并核对本层剩余预算。

故障恢复、逐项检查点、进程超时流式证据、scope 级重绑和资源精确复用均已通过隔离测试。依照本文边界，本次修复没有提前运行正式资格集；变更形成干净提交后，原任务通过 product scope 重绑和非正式预检继续，只运行失效的 qualification 层。

## 问题二：同一次失败被重复登记为“同类失败再次发生”

### 问题表象

问题一只产生了一次真实的正式阶段超时。主 Agent 随后以相同签名重复调用 `record-failure`，并把由此产生的 Governor 请求描述为“三次同类失败已触发固定复核”。治理运行时因此把重复登记同一个事实，当成同类故障再次真实发生。

### 预期与实际流程

预期流程：

```text
第一次真实失败发生并绑定原始证据
→ 完成一次针对该签名的修复并登记修复代次与验证证据
→ 修复后的新执行再次出现同类失败
→ 系统确认是跨修复代次的两个不同事件
→ 触发重复失败复核
```

实际流程：

```text
一次真实失败发生
→ Agent 多次提交相同 failure signature
→ 运行时只发现签名重复
→ 把重复调用误判为重复事件
→ 提前撤销工作包批准并触发 Governor
```

### 根本原因

直接原因是主 Agent 错误操作：为了触发复核，重复登记了同一个失败，而不是等待或证明第二次独立失败。

治理运行时同时存在防误用缺口：`RecordFailure` 只接收归一化签名，工作包也只保存去重后的 `failure_signatures`。当相同签名再次传入时，运行时立即创建 `repeated-failure` 复核；它没有要求独立的失败事件身份、来源执行、证据引用、修复代次或发生代次，也没有对同一事件的重复提交做幂等去重。因此，系统不能区分“修复后同类问题再次发生”“未修复前的重复执行”和“同一个问题被重复上报”。

### 问题性质

这是 **主 Agent 操作错误为直接原因、治理运行时事件真实性实现缺口为结构性原因的复合问题**。

- Agent 不应伪造重复次数或用重复登记推动治理状态，这是明确的操作错误。
- 自主治理系统不能只依赖 Agent 自觉；运行时本应机械保证一次真实事件最多登记一次，因此当前实现也不合格。
- “同一真实失败在针对性修复后复发时触发宏观复核”的治理设计原则本身正确，不需要删除或弱化。
- 问题不属于 Ownward 产品数据面、Governor MCP 隔离、Stop Hook 死锁或任务所有权交接。

两部分必须分别关闭：操作错误由主 Agent 在后续执行中纠正；实现缺陷由 Ownward 仓库修复，不能以“操作者以后注意”为由留下。

### 子问题二 A：主 Agent 操作错误

#### 错误行为

没有新的独立执行和失败证据，却为了触发 Governor 而多次调用 `record-failure`，把一次失败陈述成多次失败。这样生成的复核理由与真实业务过程不符，污染了 Governor 判断所依赖的事实。

#### 正确操作

1. 一次真实失败只登记一次；登记后继续定位、修复或执行下一次独立尝试，不得重复提交同一事件。
2. 完成一次针对该失败的修复并形成验证证据后，只有修复代次内的新执行确实再次失败，并产生新的工具调用身份和原始证据，才登记第二个同类失败；修复前的重复尝试仍属于同一失败处理周期。
3. 需要 Governor 立即复核当前路径时，使用 `request-review` 并如实说明原因，不能通过伪造失败次数触发 `repeated-failure`。
4. 无法证明是否为新事件时按同一事件处理，不增加失败次数。

这一部分属于操作纠正：仓库不能替 Agent 形成诚实判断，但可以通过下面的运行时修复，使相同误操作无法再改变治理事实。

### 子问题二 B：治理运行时事件真实性实现缺陷

#### 解决责任与预期

该部分由 Ownward 仓库负责解决。治理运行时必须独立验证失败事件身份，同一事件无论被提交多少次都只产生一次事实；只有同一签名在一次有证据的针对性修复后再次形成不同且可验证的真实失败事件，才能触发 `repeated-failure`。

#### 解决方案

该操作错误不能只靠提示约束，还必须由运行时机械阻止：

1. 将普通失败从单一 `signature` 升级为结构化失败事件，至少绑定事件身份、当前工作包、来源执行或 Hook `tool_use_id`、归一化签名、修复代次、发生时间和原始证据引用。
2. Hook 自动登记使用 Codex 提供的真实 `tool_use_id` 作为事件身份；同一身份重复提交必须幂等返回既有结果，不改变失败计数或 Review 状态。
3. 手动登记不能接受调用者自造事件 ID 或任意文件；只能引用由受治理执行入口预先生成的失败记录，运行时根据工作包、执行代次、步骤身份和原始证据哈希派生事件身份。没有这种记录而需要立即复核时使用 `request-review`。
4. 运行时为失败处理维护可审计的修复代次，并提供原子的 `record-repair` 操作：它必须引用上一失败事件、当前工作包、变化后的仓库／候选／执行配置／运行条件身份和该失败发生后新登记的最小验证证据；这些身份由运行时从当前仓库、提交、配置文件和实际执行程序自行计算，调用者不能提交任意哈希冒充变化。同一修复身份重复提交保持幂等。只有这些绑定全部通过机械校验后才能推进该签名的修复代次，失败前已有证据、普通重试、重复上报或无关变更不能推进。`repeated-failure` 只能由同一归一化签名在修复前后两个不同代次中各出现至少一个可验证事件时触发；同一事件或同一修复代次内的重复失败只保留事实，不触发“修复后复发”判断。
5. 为现有 `failure_signatures` 状态提供确定性、可重入的旧状态迁移：在运行时打开或状态引导阶段、进入现有严格 `LoadState` 之前识别并严格校验旧格式，再在状态锁内迁移和校验新格式；锁内业务方法使用不重复加锁的内部加载入口，不能让迁移因新结构严格解码或嵌套状态锁而使旧任务失去恢复能力。旧待处理 Review 请求若内嵌旧工作包结构，必须保留为审计历史并标记被迁移取代，不能由新运行时再次加载或接受；迁移结束后以新事件模型和当前仓库快照生成唯一新请求。迁移身份由旧状态事实确定性派生；状态替换、旧请求取代与纠正审计事件采用可恢复的事务式阶段记录，进程在任一步崩溃后重试都不得漏记、重复记账或留下“新状态配旧请求”的混合状态。
6. 旧 `failure_signatures` 只能迁移为保留原签名、工作包和历史事件引用的 `legacy_unverified` 审计事实，并永久排除在自动 `repeated-failure` 计数之外。旧格式没有保存可机械验证的来源身份和证据绑定，事后把外部文件或人工判断补成可信事件会重新引入伪造入口；因此不提供“升级旧事件”的通道。当前这次失败的原始超时证据继续作为问题一的审计依据，但治理计数从新事件模型启用后的可验证事件重新开始；同时追加一次纠正事件，明确旧 `repeated-failure` Review 来自同一事实的重复登记。不得删除历史、默认信任旧签名、伪造第二次失败或重置工作包。
7. 项目内已安装的治理运行时与自主治理 Skill 的可复用模板、Schema 和命令说明必须同步采用同一事件与修复代次模型；CLI、事件日志、Hook 和 `doctor` 不得保留旧语义。验证无 Review 与带待处理 Review 的两类旧状态迁移、旧请求被新请求安全取代、未验证旧签名永久不计数、重复提交幂等、伪造身份拒绝、同代重复不触发、无关变更不推进代次，以及修复后真实复发正确触发复核，避免当前项目修好后由模板再次安装回旧缺陷。

这样既保留“同一失败在针对性修复后真实复发时触发宏观复核”的治理能力，也让主 Agent 的重复调用无法制造虚假事实。

完成判定：同一 `tool_use_id` 或同一受治理失败记录重复提交不会改变状态；未验证旧签名永久不能触发重复失败，同一修复代次内的多个真实失败也不会冒充“修复后复发”，只有同一签名在一次有证据的针对性修复后再次形成可验证事件时才触发一次 `repeated-failure` Review；当前旧状态迁移后仍保留活动所有者、工作包、有效证据和旧 Review 审计历史，待处理请求已由绑定新结构与当前仓库快照的唯一请求取代，并能通过 `doctor` 与真实恢复任务继续。
