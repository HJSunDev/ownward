# 存储架构

本文规定 Ownward 存储体系长期成立的方向、职责边界与第一版架构落点。具体文件格式、数据库、索引技术和压缩方式可以演进，但不得破坏本文规定的关系。

重设计的技术选择、表结构、资源预算、事务、迁移与验收由[有界内存的持久化存储与检索设计](bounded-runtime-design.md)统一规定；实现与验收状态见[改造任务](../../tasks/bounded-storage-implementation.md)，不能用设计目标替代实测结果。

## 产品判断

Ownward 的存储首先服务于产品本质，而不是服务于某一种数据库、索引或模型。它必须做到：

**让用户的信息永久、完整、可迁移，让系统对信息的理解随时可以推翻、重建和升级。**

这意味着用户拥有的是信息，而不是向量、索引、关系图或某一代模型制造出来的状态。

永久保存以用户意愿为前提。用户主动遗忘时，权威状态先阻止继续使用，再清除受控原文、派生材料与恢复副本；压实、备份、重建和世代回退均须遵循同一删除屏障，具体契约见[用户控制架构](../information-control/README.md)。

## 分层结构

| 层次     | 保存内容                                           | 生命周期                 |
| -------- | -------------------------------------------------- | ------------------------ |
| 信息资产 | 用户接受进入体系的内容、稳定身份、明确语义和来源   | 长期持有，完整可迁移     |
| 派生世代 | 向量、推导关系、推导场景、摘要、组织表示及持久化检索索引 | 可重建、可整体替换       |
| 运行状态 | 有上限的索引页缓存、热点数据、游标及任务工作区         | 随运行产生，可以直接销毁 |

模型与运行时是产品运行资产，不属于用户数据，也不应混入用户信息的备份和迁移边界。

授权决定、删除屏障及未完成清理记录属于与资产共同恢复的权威控制状态，不能归入可重建派生数据或可丢弃运行状态。

物主草稿属于同一权威基座内的独立耐久工作状态，既不是已发布资产，也不是可丢弃缓存。正文分块流式存取，修改以版本条件提交；普通资产路径不枚举草稿。发布在同一事务内完成资产更新、必要的来源原件留证、事件引用、草稿与授权移除及幂等回执。来源资料经物主修改后，当前文本标记为物主所写，单独保留一份来源原件供核对；不积累每次编辑历史。目标遗忘屏障同时遮蔽原件与绑定草稿，再由耐久清理任务回收。

## 核心结构

三个层次共同形成一个长期稳定的核心关系：**一份权威资产、一个当前有效的派生世代、若干可以随时销毁的运行结构。**

### 信息资产

信息资产是唯一权威。用户提交并被体系接受的内容应无损保存；判空、分词、大小写转换、空白处理及其他检索归一化只能作用于派生数据，不得反向改变资产。

稳定身份、明确场景、明确关系和无法安全重建且会影响信息含义的来源信息随资产长期保存。内部日志只承担安全写入和恢复职责；除非产品明确提供历史版本能力，否则实现不能把永久保存每次完整旧版本作为资产成立的前提。

纠错、现实变化及有用的历史含义保存在当前资产内容与明确语义中，不依赖旧日志存续；已明确的更正对象、说明原文定位和影响含义的时间参照同样随资产保留。定位引用只承担寻址，说明事实以原文为准。用于[信息变化核对](../information-change/README.md)的来源、直接说明集合指纹及反向索引均从当前资产重建，随材料交付的依据属于宿主工作状态，不建立第二份权威、永久回执库或资产历史。

### 派生世代

派生状态按世代管理，而不是永久追加所有历史结果：

1. 当前资产对应一个当前有效的派生世代。
2. 信息或内核变化后，在不改变资产的前提下生成新世代。
3. 新世代完整生成并通过结构与可用性校验后，原子切换为当前世代。
4. 切换失败时继续保留资产和上一个可用世代，不暴露半成品。
5. 切换成功且确认不再使用后，安全回收旧世代。

模型、组织算法和索引方式升级均遵循同一过程。用户不需要重新导入信息，也不需要理解内部模型、索引和关系结构的变化。

### 运行状态

词法、向量和图导航索引持久保存于派生世代，按信息变更增量维护；正常启动直接打开已有索引，重建只用于升级、失效或恢复。可以重建不等于每次启动都重建。

运行内存只保存有上限的缓存和任务工作区，不得包含无法从持久层恢复的唯一信息。原文、组织记录、向量矩阵、完整关系图及权威状态列表均不得以全量驻留为正常使用前提；查询、更新、备份、遗忘、迁移和重建共同遵守资源预算。

### 存储实现演进

信息资产的语义、稳定身份和权威规则属于内核；文件日志、SQLite 或其他具体存储实现只承担这些规则之下的持久化职责，不得反向定义信息资产。

替换具体存储实现时，旧实现应在新实现完成迁移及资产完整性校验前继续有效；只有新实现能够完整保持信息身份、内容和不可重建语义后，才能原子切换。迁移或切换失败时继续使用旧实现，切换稳定后才能回收旧副本。可替换性由这条完整迁移边界保证，不需要把信息资产做成可任意热插拔的通用插件。

部署迁移复用同一资产与持久状态格式，按[接入与迁移架构](../access/README.md#计划性迁移)受控交接当前权威及兼容派生结果；普通备份恢复继续执行历史快照与旧凭据失效规则。

资产变更与最小接续回执必须在同一权威事务中耐久成立，管理决定与对应回执同样保持原子性；不另建需要双写的成功状态库。旧日志格式通过同条 `assetlog` 记录实现，新存储格式通过SQLite事务实现，去重事实按需查询。压实、遗忘与迁移须保留有效回执及拒绝旧操作重放的最小依据，不复制已遗忘正文；具体边界见[断线与重复提交](../access/README.md#断线与重复提交)。

## 数据增长边界

合理的增长关系是：

```text
总存储
= 固定的模型与运行时
+ 用户当前持有的信息资产
+ 用户仍保留的私有草稿与必要来源原件
+ 当前有效的派生世代
+ 有明确上限的恢复日志
```

不能演变为：

```text
总存储
= 所有历史文本
+ 所有历史向量
+ 所有历史关系
+ 每次失败或升级遗留的旧索引
```

存储体系必须保证：

- 用户新增信息时，存储成本随有效内容近似线性增长；
- 用户反复编辑同一信息时，稳定存储不会随编辑次数持续线性膨胀；
- 物主事件呈现保留最近 30 天且至多 4096 条，已决管理记录的呈现采用相同边界；待决与安全防重放事实不随呈现过期而删除；
- 资料遗忘后，事件仅保留有界、无正文的操作事实与身份引用，不保留正文、来源或引文，也不恢复该资产的读取能力。文稿发布事件可附三类旧关联失效计数，按事件一并保留和清理，不另存关系目标清单；
- 推导关系保持稀疏且有价值，不形成无约束的全量两两关联；
- 长文本可以根据检索质量需要形成多个派生表示，但不复制为多个权威资产；
- 派生数据的单条成本可测量、可约束，并能够在内核升级后安全替换；
- 压缩只用于取得更优的质量与资源平衡，不能以损害信息质量换取表面上的体积下降。

## 架构取舍

目标不是追求最小字节数，而是在不牺牲功能完整性、信息质量和资产耐久性的前提下，让每一份长期成本都有不可替代的产品价值。

存储架构围绕“资产永久、理解可替换、当前世代唯一、旧状态可回收”建设，而不是围绕当前文件和日志做局部修补。永久追加只是可以采用的写入机制，不是必须永久保留全部历史状态的架构；向量压缩也只是可能的优化手段，不是独立目标。

## 第一版架构落点

第一版不预建未来全部存储能力，但必须建立正确且可延续的根基：

1. 用户信息内容无损保存，所有检索归一化只作用于派生数据。
2. 信息资产、派生世代和运行状态具有清晰的持久化与故障边界。
3. 派生状态能够安全重建、完整校验、原子切换并回收旧世代。
4. 内部恢复日志能够安全收敛，不因反复修改无限增长；历史版本只有在形成明确产品能力时才进入长期保留范围。
5. 接入最终 EmbeddingGemma 512 维方案后，按实际产品格式重新测量存储、内存和更新成本。
6. 只有实测证明检索质量没有不可接受损失时，才采用 `float16`、整数向量或其他压缩表示；现有表示已经达到前沿时优先保留简单可靠的方案。
7. 验证反复更新、派生失败、重建中断、模型升级、备份和空白环境恢复等完整生命周期，不以一次性批量写入代替。
8. 在同一最终候选上证明功能完整性、信息质量、资产耐久性、存储占用、内存占用和更新效率同时达到第一版完成标准。
9. 落实有界内存的存储与检索设计，解除启动及常用接口的全库物化依赖；不得以小资料库可用或磁盘体积合格代替运行资源验收。

## 明确说明与来源核对

`qualifies` 关系及可选原文定位随正文原子保存；SQLite中的原文、明确关系和反向索引在同一发布事务生效。读取使用一致快照，核对按索引访问，不扫描全库、不另存历史。旧资产日志的v3格式及其拒绝旧程序的语义在迁移中保留；对外语义见[信息变化架构](../information-change/README.md)。
