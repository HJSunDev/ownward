# 有界内存的持久化存储与检索设计

本文是存储底座重设计的技术合同；执行待办与进度见[改造任务](../../tasks/bounded-storage-implementation.md)。长期职责由[存储架构](architecture.md)规定，现状和容量证据见[原文存入、组织与派生数据](ingestion-and-derived-data.md#累计容量与启动成本评估)。设计参数和读量估算不代表已取得的产品性能成绩。

## 1. 目标与边界

用户长期积累GB级资料时，普通电脑仍能启动、查询、更新和迁移；资料总量主要增加磁盘成本，不要求正文、组织记录或检索索引全量常驻内存。缓存不足只改变读取和调度方式，不改变可查资料范围或答案依据。

本设计替换资产与派生状态的物理存储、索引执行和全量加载接口，保留原文、身份、修订、语义产物、向量计算、检索评分、授权、遗忘与迁移语义。运行时制品变更须重算模型空间身份，旧向量仅在兼容性验证成立后迁移，不能冒用旧身份。理解和判断继续由外部智能完成，不增加模型步骤，不通过减少关系、缩减取证或改变提示词降低资源成本。

当前缺陷跨越 `assetlog.Store.items`、`Lexical.documents`、`derived.Index.records/blocks/organized` 和 `ListCurrent()/AllWithEmbeddings()`；必须整体拆除其全库物化依赖。仅保存索引快照、设置Go内存参数或把数组改成内存映射不能满足目标。

## 2. 确定的技术选择

| 部分 | 实施选择 | 原因与边界 |
| --- | --- | --- |
| 持久化底座 | 单个SQLite数据库，同一服务进程管理；Go使用 `modernc.org/sqlite`，实现时锁定与项目Go版本及Windows发布平台兼容的具体版本 | 原文、控制决定和派生发布共享事务边界，避免新增跨库双写协议；不要求用户安装数据库服务。 |
| 权威与派生隔离 | 同库不同表和访问端口；派生表以世代和资产修订隔离 | 物理事务可以共用，资产权威和语义判断权限仍分开；派生删除不能删除权威表。 |
| 词法检索 | 持久化词典、倒排、文档统计；沿用当前分词和评分函数 | 不直接替换为FTS默认分词或默认排名，避免存储改造混入检索质量变化。 |
| 向量检索 | 保留原有512维 `float32`；建立分块、两级紧凑筛选索引，通过保守分数上界排除不可能入选项，再读取原向量精算 | 压缩表示只用于有正确性保证的筛选，不代替最终分数；保持原有过滤、正分数条件、Top-K及同分排序。全量原向量扫描仅用于小集合、校验或筛选失效时的精确执行。 |
| 图导航 | 持久化正反邻接、对象名称倒排及生成依赖反向索引 | 按需读取相关关系；不引入独立图数据库，不加载整张图。 |
| 内存 | 有界页缓存、共享热点缓存和预先申请的工作区 | 以字节计量，不以记录条数代替容量；不同模块和并发任务共用总预算。 |
| 本地向量运行时 | 保留EmbeddingGemma Q8及计算配置，修正嵌入专用路径的无用输出缓冲；Windows无控制台子进程保留管道和生命周期管理 | 使用同一工具链重建相互兼容的运行时制品并锁定身份；不以隔离验证程序代替正式服务，不改变模型精度、输入或向量结果。 |

SQLite提供事务、磁盘B树、分页读取和恢复；资源约束仍由Ownward负责。`cache_size` 是页缓存建议值，`mmap_size` 不代表进程内存上限，不能把设置参数当成预算执行已经成立。[SQLite缓存与映射参数](https://www.sqlite.org/pragma.html)、[Go驱动及支持平台](https://pkg.go.dev/modernc.org/sqlite)。

向量路径采用已有的“压缩近似表示筛选、原始向量确认”原理，具体分数上界适配本项目的点积计算，见[VA-file论文](https://www.vldb.org/conf/1998/p194.pdf)。不采用默认全库读原向量，也不直接改用近似Top-K：[DiskANN](https://github.com/microsoft/DiskANN)可作为另一种算法选择，但候选精算无法补回未召回资料，不能据此宣称结果等价。首个实现只维护一种筛选索引，不同时引入多个向量引擎。

## 3. 物理布局与数据模型

```text
用户数据目录/
├─ storage.json                 # 当前存储格式和活动目录；不含语义或凭据
├─ migration.json               # 仅迁移期间存在的耐久阶段与恢复依据
├─ assets/
│  ├─ .ownward.lock             # 与旧程序共用的进程锁；保留原路径
│  └─ manifest.json             # 新格式生效后保留拒绝旧程序的格式标记
├─ stores/<store-id>/
│  ├─ ownward.sqlite            # 唯一活动数据库
│  ├─ ownward.sqlite-wal        # 有界恢复日志
│  └─ ownward.sqlite-shm        # SQLite协调文件，不单独备份
└─ scratch/                     # 分批处理、迁移与排序的可清理工作文件
```

原有受主机保护的密钥与恢复材料继续使用既定保护区，不写入普通资产导出。文件目录不进入资产身份。正常运行只允许一个活动数据库；迁移中的数据库不开放业务。`assets` 中的锁与格式标记是兼容隔离入口，不是第二份资产库；迁移前其中的旧日志按第8节处理。

下表规定逻辑表组和必要索引；实现可在表组内拆表，不能改变权威归属或引入全库内存副本。

| 表组 | 主要内容与键 | 必要索引／约束 |
| --- | --- | --- |
| `assets`、`asset_payloads`、`asset_chunks` | 资产ID、当前修订、种类、时间、来源、正文摘要值与长度；正文按64 KiB字节块无损保存 | 资产ID唯一；正文按 `payload_id, chunk_no` 定位；块记录累计字节与字符位置，跨块读取保持原文顺序。 |
| `asset_contexts`、`explicit_relations` | 用户明确给出的场景与关系、定位及说明 | 资产归属索引、关系目标反向索引；与当前修订一起生效。 |
| `control_root`、授权／撤销／删除／操作回执表 | 体系身份、活动实例、控制修订、当前授权、删除屏障、接续回执及清理进度 | 按主体、目标资产、操作身份定向查找；不得启动时加载全部回执、墓碑或授权对象。 |
| `generations`、`organizations`、`organization_payloads` | 派生世代、模型空间、资产修订、组织快照、原有语义结果及处理状态 | 每个世代和资产只有一个活动组织版本；较大负载分块，保留完整语义内容。 |
| `units`、`mentions`、`links`、`link_endpoints` | 证据单元、对象提及、关系含义、方向、条件与定位 | 组织版本归属；源端、目标端和对象词项索引；定位引用当前原文，不复制完整正文。 |
| `dependencies`、`semantic_jobs` | 实际输入资产修订、使用的派生快照、有效工作身份及待处理原因 | 输入到依赖者、资产到工作索引；工作队列落盘，内存只保留正在执行的工作。 |
| `reclaim_jobs` | 已退出使用的负载／组织／索引版本、回收原因、预计字节及分批游标 | 与发布或作废决定同事务登记；按对象版本唯一、按待执行状态领取；不复制待删除正文。 |
| `lexical_documents`、`terms`、`postings` | 资产词项频率、文档长度、当前词法版本、全库文档数和总词数 | 倒排按 `term, asset_id, lexical_version` 排序；仅当前资产和词法版本参与统计与评分。 |
| `vectors` | 世代、向量空间、资产ID及修订、向量二进制 | 每份有效资产一个向量；按空间和资产ID可顺序读取；不经过JSON/Base64转换。 |
| `vector_blocks`、`vector_filter_pages`、`vector_members`、`vector_delta` | 块身份、格式版本、各维范围、两级编码与误差上界、向量身份映射、尚未归块的有效向量引用 | 筛选页与原向量分开存放；块成员唯一归属，映射绑定向量修订；同一快照内每份有效向量恰好位于一个活动块或增量区。 |

组织完整记录保留已有语义字段，查询索引只保存查找需要的键和引用。相同组织版本内的定位、条件正文按引用复用，不为正反向索引复制整份组织内容；迁移不得借此丢弃解释、条件或生成依赖。

全库统计属于持久化索引，不能每次查询读取正文计算。词项文档频率按同一读快照中的有效倒排统计；可在有界缓存中按索引修订缓存，不能使用过期频率。旧词法版本在指针切换后不参与查询，后台再回收。

## 4. 内存、并发与磁盘工作区

### 4.1 预算与计量

保留[完整产品资源阈值](../../../benchmarks/acceptance/suite/adapters/product_resource/thresholds.json)的270 MiB进程树工作内存验收边界，不在本设计中提高阈值。计量覆盖服务、本地模型及Ownward宿主连接器；外部智能体自身不计入，但不能漏算项目提供的代理进程。该指标是受支持负载下的峰值合同，不宣称操作系统能靠缓存参数强制保证RSS不越界。

以下为可调工作区的上界，不能同时满额分配；最终按整个产品的剩余预算受理任务。所有缓冲、对象复制、驱动和Go堆外开销都必须有归属。

| 项目 | 分项上界 | 执行方式 |
| --- | ---: | --- |
| SQLite页缓存总和 | 8 MiB | 常态先分配4 MiB：写连接2 MiB、两个读连接各1 MiB；有余量才扩大，连接池不自行扩张。 |
| 正文片段、元数据与有效性热点缓存 | 合计2 MiB | 共用按字节计量的缓存；键包含资产修订、组织快照及必要控制修订，不缓存整库。 |
| 检索工作区 | 合计8 MiB | 每个重查询最多4 MiB；先受理一个，只有总预算足够才受理第二个。读取批次不超过1 MiB，查找表、页号、Top-K及游标均计入，超额排序落盘。 |
| 写入、整理发布、压实与迁移工作区 | 合计4 MiB | 一个后台重工作通道；64 KiB流式读写，超出部分使用磁盘临时表。 |
| 接入解码、结果编码与传输缓冲 | 合计2 MiB | 流式传输或按页编码，排队只存请求身份和暂存位置，不保留大请求对象。 |
| 非模型进程的固定代码、驱动、连接器和Go运行时 | 初始估计24 MiB | 必须由生产装配实测替换；不含下述独立峰值余量，不能漏算连接器或堆外分配。 |

分配关系固定为：`可用非模型预算 = 270 MiB − 模型峰值预留 − 独立余量`；非模型部分取该值与48 MiB分项总上界中的较小值。独立余量至少8 MiB，不得用于常规任务分配。模型仍沿用既有模型、精度和调用配置，预留覆盖启动、短查询、既定长度分段和批量存入峰值；不能靠截短资料或降低精度满足预算。

[旧运行时测量](../../../benchmarks/vector-model-evaluation/results/embeddinggemma-runtime-optimization/llama-q8/resources.json)的模型峰值约220 MiB仅作为原始估计。修复后的完整运行时已完成单元一装配验证，模型按200 MiB预留，非模型进程合计仍取48 MiB上界，独立余量至少8 MiB；常态采用较小页缓存，重工作在预算不足时共享执行机会，并保留1 MiB控制工作区。完整检索与维护接入后复核固定开销及模型峰值，不能把各项上界直接相加当成实际分配。

受理前按所需工作区申请额度，释放后复用；SQLite缓存与Go软限制仅辅助执行。采样用于发现估计偏差，不能替代分配控制。若固定开销、模型和一个最小查询连同余量仍放不下，首个装配验证即判定不达标，在迁移前解决依赖或装配开销；不通过反复杀模型、丢任务或偷偷提高验收阈值处理。并发连接器的固定开销同样占额度，不能以无限新建进程绕过共享预算。

**实施前实测（2026-09-16）：超限根因已定位，隔离修复成立。** 原最小装配的短批量峰值为272.32／271.59 MiB；补测较长合法查询后，原向量运行时所在进程树达到666.98 MiB。原因是现用llama.cpp的EmbeddingGemma计算图不产生词预测结果，输出分配器却仍按“词表大小×输入输出位置数”分配并清零词预测缓冲。仅消除Windows控制台开销不足以解决这一问题。[原装配证据](../../../benchmarks/acceptance/suite/adapters/product_resource/bounded-assembly-precheck-20260916.json)。

修复限定于EmbeddingGemma嵌入模式：不分配该无用缓冲，其他模型及模式不变。下表使用相同编译器、同一C接口验证程序、原GGML计算后端，以及相同SQLite、连接器和5 MiB实际持有工作区；唯一变量为上述分配条件。

| 隔离对照 | 进程树峰值 | 结果一致性 |
| --- | ---: | --- |
| 原分配逻辑 | 664.78 MiB | 与正式运行时输出一致 |
| 修正分配逻辑 | 204.97 MiB | 短／长查询、中英文资料及批量共6组、39个512维向量逐字节一致；数据库保真、回滚、快照、检查点和完整性校验通过 |

上述小样只证明隔离修复成立，C接口验证程序没有进入正式版。[隔离材料](../../../benchmarks/acceptance/suite/adapters/product_resource/bounded-assembly-recovery-20260916.json)。单元一随后统一重建完整运行时并更新制品和空间身份；6组、39个向量与修复前逐字节一致。实际存取代码经stdio、连接器、HTTP及SQLite贯通，在4线程、无额外Go内存限制的条件下，服务、模型及连接器合计峰值217.46 MiB，保留52.54 MiB余量。[装配证据](../../../benchmarks/acceptance/suite/adapters/product_resource/bounded-unit-one-20260916.json)。这是已实现存取范围的验收，完整检索、并发维护和迁移交付仍按后续执行单元验证。

向量块目录、紧凑编码、查询结果缓存和过滤集合同样落盘或计入共享预算；不得另加随资料量增长的常驻码表、全量压缩向量或资产ID集合。并发超出执行槽时排队，排队时间计入用户等待，不能用串行化掩盖延迟。

### 4.2 达到预算时的行为

- 撤销、遗忘屏障及恢复控制优先取得控制工作区和下一个短写事务；普通前台请求优先于可推迟的整理。检查点和已触发背压的归块属于必要维护，必须获得执行机会，不能被持续查询永久挤占；具体调度见第7节。
- 排队不占数据库读事务，不保留整段正文或候选全集；取消请求后释放工作区、游标和临时文件。
- 高频词的候选、图遍历的待访问集合和已访问集合超出内存时进入磁盘临时表。不能直接截断后宣称查询完成。
- 单条长原文与大批量导入使用流式暂存，不能为了省内存把一份资产拆成多个用户资产；宿主连接器、服务端及出站响应共同遵循第4.3节，不能只优化最后的数据库写入。
- 未能受理的操作返回明确的资源或存储错误，不报告保存成功；已经持久接受的操作按原身份接续。资源约束不能通过改写、截断原文或丢弃待处理工作实现。

`temp_store=FILE`，临时目录归服务管理，磁盘余量在接受大操作前检查。`mmap_size=0` 作为首个实现配置，避免把全库映射误当作无内存成本；不得关闭系统缓存或防护。操作系统可回收文件缓存与进程RSS分别观察，整体机器可用内存下降和换页同样属于成本，不能移到系统缓存后不计。

### 4.3 从接入到交付的流式路径

现有MCP SDK的HTTP路径先执行 `io.ReadAll`，stdio路径先解码完整 `json.RawMessage`；当前 `CreateInput.Content string` 和包含完整正文的返回对象也会物化内容。仅将存储接口改成读取器不能解决入口与出口的峰值。保留外部工具名称、JSON字段和正文含义，新增项目内部的有界编解码适配，覆盖以下路径：

| 路径 | 确定的改造 |
| --- | --- |
| 宿主stdio → Ownward连接器 | 在SDK读取之前，以64 KiB缓冲将JSON负载落入受保护暂存区，流式解析RPC信封；SDK只收到不超过64 KiB的内部参数投影。大字符串及列表通过本次调用的只读引用交给工具适配器，不先构造完整字符串或切片。 |
| 连接器 → 本地／远程HTTP服务 | 出站 `RoundTripper` 将内部投影还原为原协议的JSON字节流；服务端在认证HTTP中间件之后、SDK处理器之前执行相同的落盘与投影。不得把本机文件路径或内部引用通过网络交给远端。 |
| MCP工具 → 产品端口 | 使用SDK低层 `Server.AddTool` 注册原公开Schema，处理器对暂存参数做等价的流式校验；不再使用会整包反序列化的泛型大负载处理器。产品端口传递可重复读取的 `ContentSource` 和按项游标；创建、更新、批量、语义提交及读取结果均不得在后续重新拼成整份对象。 |
| 产品结果 → 服务端 → 连接器 → 宿主 | 结果使用只读快照材料及流式JSON模板，SDK处理小信封，出站适配展开正文；HTTP响应进入连接器时也先落盘再进入SDK。原有 `structuredContent` 和文本形式若均需交付，分次流式编码，不能在内存保存两份正文。 |

适配器包在SDK的 `IOTransport` 读写流、HTTP处理器和客户端 `RoundTripper` 外侧，不分叉SDK或重写会话协议。内部引用由适配器生成，绑定连接、认证主体、RPC调用和字段位置，并与真实外部字段分离；外部提交的同名标记不能取得引用。工具处理器必须验证原始参数，而不是仅验证投影；适配器拒绝重复关键字段、无效转义及超出既有Schema的输入。只实现Ownward既有协议和工具结构所需的编解码；初始化、取消、通知和会话语义继续复用SDK。HTTP仍沿用当前JSON响应模式，接续材料过期须明确失败，不能假装返回完整结果。

操作身份与摘要依据原参数的逻辑内容，不包含临时路径或引用令牌。`mutationDigest` 的既有规范化含义保持不变：字段排序可在磁盘完成，字符串转义、数值规范化和数组顺序须与原规则等价；小输入逐项对照现有函数。断线重试重新产生临时引用仍映射同一操作。出站恢复原字段与字节含义，不能通过改工具参数让调用方承担分块工作。

暂存分配计入全局磁盘额度，认证后才允许形成可访问材料；字段顺序未知时先暂存，再按已识别工具与授权校验，校验完成前不执行产品动作。取消、超时、断线和崩溃后回收无主暂存；耐久接受后需要接续的材料绑定操作身份保留。输出先形成可读取材料并关闭数据库快照，再做最终授权核对并开始网络交付，不持读事务等待慢客户端。暂存材料携带来源与控制依赖，纳入遗忘清理；撤销后未开始交付的材料不得输出，已交付部分沿用现有控制边界。大负载额外暂存和再次读取须计入完整耗时及峰值磁盘占用，不能只报告内存降低。

直接落点为 `cmd/ownward/shared_mcp.go`、`host_connector.go`、`connector_operation.go`、`internal/adapter/mcpserver` 和 `internal/contract`。首个装配验证覆盖stdio、HTTP和两者串接，检查中文转义跨块、大字符串、批量、重复请求、取消及响应输出；任何一个位置仍整包缓冲，都不能通过端到端内存验收。

## 5. 读写与检索执行

内部接口收敛为五类：`ReadAssetMeta(id, revision)`、`OpenContent(id, revision)`、`ReadRanges(id, revision, ranges)`、`ScanAssets(cursor, pageBudget)`、`ClaimSemanticJobs(limit)`；读取器和游标均携带快照／版本约束并显式关闭。写入接收元数据、内容读取器和操作身份，检索返回候选身份、分数及依据引用，不在中间结果复制完整 `Information.Content`。替换 `ListCurrent()/All()` 的所有生产调用，不保留隐式收集全库的兼容包装。

普通接口不物化全部资产或正文；词法访问匹配倒排，图导航访问相关邻接，向量检索按下文读取筛选索引与必要原向量。向量筛选索引的遍历仍可能随向量数增长，不能称为常数成本。导出、迁移、校验和重建使用稳定顺序游标，每页同时受条数与字节预算限制。待处理工作直接查询持久队列，不通过枚举所有资产重新发现任务。

### 5.1 原文写入、更新与组织发布

1. 校验调用权限，将原文和明确语义流式写入不可见暂存记录，计算字节摘要与词法表示；分块写入可接续，尚未成为用户资产。暂存只由原操作和当前获授权主体访问。
2. 在短事务中重查权限、删除屏障和预期修订，发布资产当前指针、明确关系、词法版本、必要失效标记、语义工作及原操作回执，并为退出使用的旧版本登记回收任务。事务耐久提交后才返回保存成功。分块暂存与发布指针共同实现原子可见，不暴露半篇正文。
3. 词法倒排可以提前分批写入，但查询必须连接当前资产和当前词法版本；发布前不可见。全库文档数及总词数在发布事务更新，词项频率以有效版本为准。
4. 外部智能领取既有语义工作，继续按原流程组织；材料按资产身份读取，不扫描全库寻找待处理工作，不持有数据库事务等待模型。
5. 组织结果先形成不可见版本并建立单元、关系、依赖和向量。发布事务核验原工作、目标修订、全部输入及组织快照，原子切换活动组织、关系及向量，并登记向量增量区和旧组织的回收任务；迟到结果拒绝并回收其暂存，重复提交沿用回执。向量从发布时即可查，不能等待后台归块才生效。

新库在建表及启用WAL前设置 `page_size=16384`、`auto_vacuum=INCREMENTAL`，随后采用 `journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON`、`automatic_index=OFF`、`wal_autocheckpoint=0`；检查点及空间归还由第7节的调度执行，避免默认自动检查点与预算控制并行。所有连接明确设置相关参数，查询所需索引随格式固定，避免隐式建立大临时索引。外键约束不使用会一次清除全图或整篇大正文的级联操作，清理由受控批次完成。事务结果不确定时关闭该写连接、重新读取操作回执后决定接续，不盲目重复提交。[SQLite耐久提交与WAL](https://www.sqlite.org/wal.html)。

### 5.2 词法查询

沿用 `lexicalTerms/tokenize`、中文单字与双字处理、词项权重、常见词过滤、文档长度归一化、精确ID加分、上下文过滤和同分排序。ID、明确场景及明确关系仍进入原有检索表示。

查询词及权重写入该读连接的临时表，通过与有效倒排的连接查询取得按资产ID及词项有序的单个游标，逐个资产计算完整得分，只保留Top-K；不用当前“所有候选→得分大map”的执行方式，也不为每个词占用一个连接。排序和过大K使用磁盘临时表，返回预算维持原工具契约。先确定候选身份和得分，才读取交付需要的正文；查询结束清理该连接的临时状态。

### 5.3 向量查询

#### 索引结构

原向量及归一化、点积实现沿用当前代码。每块最多1,024条向量，以实际归一化后的 `float32` 值计算各维范围，等分为256个区间，编码为8位区间号，拆成两个独立的4位平面；第一级每条256字节，第二级再256字节。块头保存范围和包围球：以本块向量均值为中心，半径覆盖全部成员；成员保存身份及两级区间中点重建误差的保守上界。常量维度单独标记，最大值进入最后区间，范围和误差向外舍入，异常数值不得进入索引。

第一级定位较宽区间，第二级收紧区间；两级都只是筛选工具，最后仍使用原向量计算原分数。编码直接由向量计算，不训练新模型、不调用外部AI、不改变已有向量空间。块及编码页以有序键保存于SQLite，代码页不夹带原向量或整份组织记录；原向量按成员映射定位。

#### 查询与完成判定

1. 按原逻辑得到查询向量及有效检索范围。范围过滤只来自既有上下文、世代与控制合同，不以关键词、时间新旧或热点程度删减向量搜索范围。
2. 对少量增量向量直接精算；遍历块目录，优先处理可能得分较高的块以建立Top-K门槛。门槛未形成时，可先精算当前块中重建分数较高的少量有效向量；门槛始终来自实际已算分数，不能使用离线参照的答案。排序只影响执行顺序，所有未被严格排除的块最终都要处理；目录和排序队列不得全量驻留。
3. 块的分数上界低于当前门槛时跳过整块；否则读取第一级筛选页。单条向量仍可能入选时，再读取对应第二级页，最后才读取原向量精算。原向量读取按页合并、去重；访问稠密时在该块改用顺序精算，避免逐条随机读取。
4. 未取得K个有效正分数结果时，门槛为0；取得后使用其中第K名的精算分数。只有有效范围内的精算结果能提高门槛。同分候选按原资产ID顺序竞争；上界等于门槛时不得丢弃。无效、已删除或范围外记录不能成为剪枝依据。
5. 所有块及增量向量均已处理或被可靠上界排除后，才返回完整结果。候选看起来稳定、已找到K条、超出预计读量或到达时间预算，都不是精确完成的依据。

上界的实现合同：查询为 `q`，编码重建值为 `c`，保存的误差 `r ≥ ‖x−c‖₂`，则实数点积满足 `q·x ≤ q·c + ‖q‖₂r`；块包围球使用相同不等式。两级取各有效上界的最小值。实际实现须再计入上界计算的向外舍入和当前 `float32` 点积误差，不能直接将实数公式当成机器计算保证。对正常范围的浮点乘加，可采用保守项 `γ₂d · ‖q‖₂ · max‖x‖₂`，其中 `γₘ = mu/(1−mu)`、`u = 2⁻²⁴`、`d = 512`；还须覆盖所选SIMD路径的舍入及下溢行为。无法建立可靠界时直接精算。误差判定须与编码、归一化及计分版本一起固化并验证。

这保证压缩筛选不会以舍弃可能入选的资料换速度。高维分布或近同分资料可能使筛选很弱，此时执行更多精算；**保证结果正确不等于保证任何规模、任何查询都在固定毫秒内完成。** 不以“不漏结果”为由接受普遍超时，也不以性能不达标为由静默切换近似结果。

#### 增量、更新与维护

- 新向量先进入持久增量区，与组织发布同事务生效；查询合并活动块与增量区。同空间增量累计至256条或空闲整理时，后台分批归块；服务内所有可查询空间的增量合计达到1,024条，触发组织发布背压，先完成一批归块。小块可与同空间相邻小块合并，始终只重写最多1,024条，避免长期小写入形成海量空疏块。原文保存与既有资料查询保持可用，发布排队须计入组织耗时。
- 不可变块在同一快照内保持成员与范围一致；新块分批构建、验证后，短事务切换成员归属并移除对应增量项。更新先使旧向量失效，新向量进入增量区；不得将超出旧范围的新值直接写进旧块。查询不会漏查、重复计分或使用失效成员提高门槛。
- 删除成员不必同步收紧范围，较宽上界只多做工作；失效占比达到四分之一时局部重打包，空块回收。构建只处理受影响块，在4 MiB后台预算内分批完成；不因一次写入重建全库，也不复制原向量作为第二份长期存储。持续写入下用发布背压防止增量和废弃块无界堆积。
- 索引格式、计分或向量空间变更走世代构建与原子切换；普通崩溃恢复复用已提交的块和增量状态。筛选记录损坏时隔离受影响块，以校验完整的原向量精算并安排修复；原向量损坏则明确失败，不返回伪完整结果。

#### 读盘与存储成本

读量按实际页面计算：`D = 页大小 × 实际读取页面次数`；覆盖两级编码、原向量、块头、身份、范围过滤、B树内页、溢出页和增量区，同页重复读取也计入。估算净负载可写为 `256N·p₄ + 256N·p₈ + 2048N·pᵥ`，其中三个比例分别是对应数据的页面触及比例，不能用候选条数比例替代。少量候选分散在许多页面时，第二级仍可能接近全读。

实际估算还需加入数据库页布局、重复读取及元数据成本。耗时同时计入读字节、随机I/O次数、筛选计算、精算、范围校验、查询向量生成与排队，不能用磁盘带宽或候选减少率冒充完整耗时。

| 向量数量 | 原向量全扫描负载 | 新索引第一级负载 | 两级筛选编码新增磁盘体积 |
| --- | ---: | ---: | ---: |
| 10万条 | 204.8 MB | 25.6 MB | 51.2 MB |
| 100万条 | 2.048 GB | 256 MB | 512 MB |

以上为512维净编码，采用十进制，不包含身份、误差、块头和SQLite开销；第一级是原负载的八分之一，**不能据此宣称查询快八倍**。全部筛选编码净增原向量体积的25%，占原文比例取决于资产粒度；以已测每份约10 kB原文的结构估算，净增约5%，不是所有用户的固定比例。重建期只允许一个正在替换的块副本，世代升级与迁移另行核算峰值，不长期保留历次索引。

原向量少到其完整读取成本低于筛选开销时，直接精算是同一执行器的成本选择；阈值由垂直切片同负载比较确定，且不超过单查询工作区。大量近同分、筛选不通过或数据损坏引发的精算必须分别统计，不能以小库成绩代替GB规模可用性。

有限的[离线机制检查](../../../benchmarks/acceptance/suite/adapters/product_resource/bounded-filter-design-evidence.json)复用了4,734条真实向量，用1个缓存查询和12个文档向量留一探针检查动态Top-10：13次均与同一实验计分参照一致，平均精算25.6条；理想16 KiB页面布局下读量平均约为原向量全扫描的27.3%。这支持进入生产切片验证，不构成产品质量或耗时成绩：实验采用双精度计分，页面未含SQLite开销，探针也不是代表性用户查询集；不得直接外推百万规模的筛选率。

### 5.4 图导航、依据读取与有效性

按资产、单元或对象键读取名称倒排及相邻边，分页执行原导航顺序、深度和预算。图遍历仅维护当前任务所需集合，超预算时落磁盘；不删除条件或跳过原来允许访问的关系。

命中后按原文位置读取必要块，恢复跨块完整片段；原位置匹配、前后文和Unicode字符偏移规则不变。单条大资料内部的取证、分词与排序也必须分批，不可读取整篇后再宣称按需读取。原有段落选择需要文档内统计时，采用流式统计与评分两遍读取，在磁盘暂存段落边界和过大候选；保留原段落划分、权重、上下文补全和去重含义。

每次工具执行使用有限生命周期的一致读快照；返回身份、内容和关系来自同一有效版本，不能混用前后修订。快照在模型调用之前关闭。跨调用游标绑定世代、主体与必要修订，简单列表使用键集定位，图遍历的必要接续状态保存在有期限的磁盘工作记录中；状态变化或过期时明确要求接续或重新取证，不维持长事务等待智能体，不把无限游标状态堆进内存。

## 6. 授权、遗忘与失效安全

权限判断继续归权威层；入队、实际执行、提交和最终交付均按既有合同核验。最终交付使用最新权威控制状态，并在既有控制临界区与撤销操作排序，不能只检查任务开始时的读快照。持久化索引只是候选入口，不能凭索引命中绕过当前授权、资产状态、端点快照及生成依赖检查。

原文变更、组织替换或删除屏障提交时，同时推进持久化有效性修订并登记直接受影响项。大范围依赖失效可分批处理，但发布屏障后不得存在仍能交付受污染派生内容的窗口：未在当前修订下验证的记录，交付前沿实际生成依赖核验；环和高扇出使用有界工作区及磁盘已访问集合。有效性缓存按修订失效，不能等待后台标记走完全图才停止使用。

遗忘先耐久记录停止使用屏障，再按既有[清理合同](../information-control/README.md#清理覆盖与防复活)清理原文、派生、索引、暂存、WAL及受控副本。SQLite删除行或 `secure_delete` 不能单独证明完成：还需结束相关旧快照、检查点并清理日志，必要时生成不含目标的新数据库、校验切换并移除受控旧库；全过程服从预算。不能承诺清除系统外部备份或底层介质残留，沿用既有产品承诺。

旧操作回执、删除身份和不可丢失的控制状态保存在索引表中，按原有效期和重放规则收敛；不为了内存上限删除安全依据。迁移回退、派生世代回退和普通备份恢复仍分别执行既有规则，不能恢复旧凭据或复活删除屏障之后的内容。

| 正常启动 | 读取存储指针、数据库头、活动世代及最小控制状态，打开固定数量连接；不枚举全部资产，不加载全部向量，不对全库哈希或执行全库完整性扫描。 |
| 非正常退出 | 由SQLite恢复已提交事务；读取未完成操作、语义及回收队列索引接续。先恢复授权与删除屏障，再开放接口；不重新调用AI恢复仍有效的组织结果。 |
| 物理索引升级／修复 | 从已有原文和语义产物分批构建新索引版本；存储布局变化不使语义结果自动失效。向量筛选页失效时只从受影响原向量重建；索引损坏如实限制受影响能力，不能返回无依据的“无结果”。 |
| 派生能力升级 | 独立构建和验证候选世代，提交时再次检查资产、输入及控制状态，原子切换活动指针；回收旧世代前等待引用释放并执行删除屏障。 |
| 备份与恢复 | 使用一致快照流式导出权威资产及允许携带的控制状态，默认资产备份不混入派生或活动秘密；兼容部署迁移按原合同额外携带派生结果。 |

### 7.1 版本回收与磁盘收敛

回收按持久化版本身份执行，覆盖日常修订、组织替换、作废暂存和世代切换；不依赖全库扫描或进程内待办。首批暂存与所属操作／构建身份同事务登记，重启按未完成操作索引判定接续或作废。发布新版本与登记旧版本回收任务原子成立，失败构建通过其操作身份登记回收。回收完成后删除队列项，只保留既有合同要求的控制状态与回执，不积累永久清理历史。

| 对象 | 可回收条件与处理 |
| --- | --- |
| 旧正文负载及明确语义 | 已不被当前资产或尚可接续的已接受操作使用。按负载、修订与所有权索引检查实际引用，再删除正文块及仅属于该修订的记录；共享负载仍有有效引用时保留。 |
| 旧组织及检索表示 | 旧组织不再有效后，按组织版本分批删除单元、对象、关系、倒排和向量；仍共享的块按第5.3节处理。尚被使用的依赖引用保留身份、修订和失效事实，引用关联这类元数据而非待删负载；最后一个必要引用消失后回收对应元数据。不能因删掉正文而把旧依赖误认成有效，也不能为这些元数据永久保留旧正文。 |
| 作废暂存及旧世代 | 先耐久记录操作作废或世代退役，禁止再次发布，再按所有权分批回收；仍有效的接续材料保留。读快照结束后其旧页面才可由检查点释放，跨工具调用不保留数据库读事务。 |

领取、引用核验、删除该批记录及推进游标在同一短写事务内完成，按依赖顺序删除子记录后删除负载；中断重做同一批不得误删当前版本。普通读取由SQLite快照隔离保护，无需为每个读者另建持久租约；结果暂存完成后释放快照。已经作废的旧版本不得重新挂为当前版本；重建以新的版本身份发布。遗忘屏障优先于任何接续，普通回收不能代替第6节要求的受控副本清除。

**积压与吞吐共同受控。** 维护使用既有4 MiB后台工作区，单批删除负载最多1 MiB，页写放大同时服从WAL预算。退役字节在发布事务内记账；普通回收积压达到64 MiB时，下一次会增加积压的普通替换先等待回收。单个大对象或已预留空间的整世代切换可一次超过此阈值，后续替换须先降回阈值以内；这是暂态调度阈值，不限制用户资料大小。撤销与遗忘不受该背压阻塞。回收持续失败时保留现场并明确报错，不能继续无限积累或丢掉新旧任一份有效资料。

**空间复用与归还是两步。** 删除后的空闲页先供后续写入复用，常态保留最多8 MiB复用余量；超出余量时，维护通道执行有界的 `incremental_vacuum(64)`，每批最多归还64个空闲页（16 KiB页下为1 MiB），连同页面搬移、WAL和检查点计入成本。磁盘余量不足以覆盖已接受工作和必要维护时，暂停新的非必要空间预留，优先回收，空闲页可全部归还；不能在每次保存后重写全库。增量收缩不整理页内碎片，也不证明遗忘完成，验收需分别核对有效数据、待回收数据、空闲页和实际文件体积。[SQLite空间回收机制](https://www.sqlite.org/pragma.html#pragma_auto_vacuum)

同一份资料反复更新时，稳定磁盘成本由当前有效数据、必要控制元数据和受控暂态空间决定，不随编辑次数持续增长；后台回收及空间归还不调用AI、不改变有效检索内容，代价是受预算控制的磁盘I/O与极端积压时的写入等待。

### 7.2 调度与WAL收敛

单写连接只执行短事务，不持有写事务等待模型、网络或读查询。撤销授权、停止使用和遗忘屏障优先取得下一个写事务；普通写入受背压时，控制提交仍可使用保留的工作区与日志空间。大范围控制对象先分批暂存，最后以短事务发布屏障，物理清理另行接续；控制生效不能等待全量清理。

| WAL状态 | 执行动作 |
| --- | --- |
| 达到8 MiB | 请求 `PASSIVE` 检查点，只复制当前可安全合并的页面；不在控制写队列中执行等待所有读者退出的检查点。 |
| 达到24 MiB | 暂停普通增长写入和可推迟的整理，停止受理新的普通读事务（含短查询）；排队者不占事务，现有读者排空后执行检查点及日志重置。控制事务继续受理，保留至32 MiB的空间供其使用，不能被普通任务消耗。 |
| 控制提交需要的空间超出保留量 | 取消持有旧快照的相关长读，确认SQLite查询已中断、游标与事务已释放，再完成检查点；不持有控制写锁等待读者。取消如实返回，不交付部分成功或自动循环重跑。实际磁盘耗尽且无法耐久提交时明确失败，不能假称撤销或遗忘已生效。 |

24／32 MiB是调度阈值，不是SQLite保证的文件硬上限。大对象以不超过1 MiB负载的事务分批暂存，发布事务不包含整篇正文；控制事务同样限制大小。实施须测得并计入单个事务的索引页写放大，在受理前预留，避免开始后越过保留空间。不能删除活动WAL，也不能只暂停写入却继续放入新读者，使检查点永久无法收敛。

必要维护通过入场调度获得进展：存在日志收敛、增量归块或版本回收背压时，每轮已有前台工作释放资源后，先允许一个有界维护批次，再补充普通执行槽；控制提交仍优先。有待回收记录或超过复用余量的空闲页但尚未背压时，也在写队列轮转中插入有界维护批次，不能只等全系统空闲。每批释放事务和工作区，避免持续前台请求饿死维护或后台独占前台；日志空间不足时先检查点，再执行产生新日志的回收或归块。普通长查询不因周期性检查点反复重启；仅在控制保留量耗尽等必须释放旧快照的条件下取消。

长备份采用可接续页复制，数据持续变化时使用既有受控冻结完成一致快照；不无限固定旧读事务。故障恢复中发现校验失败明确报错或进入受控修复，不能忽略错误打开旧库。

## 8. 存储格式迁移

这次改变物理格式，不改变信息或语义能力。现有准备资料的原文、AI组织结果和兼容向量可迁移复用；需要更新的是物理快照及其身份，不能继续让旧格式收据代表新格式，也不能要求无变化的材料重新调用AI。

### 8.1 唯一写入口与旧程序隔离

所有新存储实例及迁移、回退工具先独占原路径 `assets/.ownward.lock`，并持有到全部存储连接关闭；沿用Windows `LockFileEx`／Unix `flock` 的同一文件锁，不新增一个旧程序不认识的锁代替它。持锁期间不能移动或删除该锁文件及其目录，SQLite文件锁不代替这层新旧版本互斥。

旧程序的 `assetlog.ensureManifest` 只接受已知格式且不读取 `storage.json`。因此迁移必须在原 `assets/manifest.json` 耐久写入专用拒绝格式 `ownward.asset-log/retired-v1`，随后才构建、切换新库。旧程序运行时会先因同一目录锁被拒绝；服务停止或崩溃后会因未知格式被拒绝。清理旧正文后仍永久保留此无正文标记与锁路径，不能删空目录让旧程序自动初始化新库。全新SQLite资料库也建立相同隔离入口。

`migration.json` 只保存迁移身份、源／目标相对位置与格式、原清单、阶段、检查点及校验依据，不复制用户正文或凭据。文件更新使用同目录临时文件、文件同步及平台耐久替换；Windows沿用带 `MOVEFILE_WRITE_THROUGH` 的替换，Unix替换后同步父目录。原清单和迁移意图必须先落稳，再写拒绝标记；阶段不明、身份不符或校验失败时停止开放业务，不能猜测应打开哪份库。

### 8.2 执行与中断恢复

1. 停止旧实例，校验源、空间与版本，取得共用目录锁。耐久保存迁移意图及原清单，再耐久写入拒绝标记；标记完成前不开始目标构建。若此阶段中断且旧程序后来写过源，下次持锁后重新识别源，不复用旧检查点。
2. 用专用流式迁移器读取已隔离的源，将最后有效记录的归并放入目标SQLite；不得调用全库物化的旧 `Open()/All()`。检查点绑定迁移身份、源身份及位置，原文、明确语义、控制屏障、必要回执、有效组织结果及兼容向量全部保留。
3. 分批构建物理索引并核对身份、修订、正文摘要、控制决定、依赖、向量覆盖及检索合同；不调用AI。目标库保存同一迁移身份及初始为假的 `activated` 标记，完成同步、检查点与关闭后，耐久登记目标已校验。
4. 耐久替换 `storage.json` 指向目标，在业务写门关闭下完成启动与最小读取检查。通过后，先在目标数据库事务中将 `activated` 单向改为真，再开放任何业务变更，包括权限变更；此后只允许向前恢复，即使尚未发生第一笔用户写入也不直接回退旧库。
5. 在 `activated=false` 且源完整时允许取消迁移：先耐久登记回退决定，再恢复旧存储指针，最后恢复原清单并同步，才允许旧入口重新写入。回退一经决定不再接续同一目标；中断后只完成回退，旧入口已开放后发生的新写入仍归源权威。
6. 目标激活后按清单清除旧资产日志、被新库接替的旧控制／派生副本和迁移暂存，保留隔离标记与锁。清理可接续，完成前不报告迁移全部结束；遗忘覆盖尚未清除的受控源副本。清理完成后删除迁移过程文件，活动库及隔离标记保留必要的格式与身份依据。

| 中断位置 | 唯一恢复方向 |
| --- | --- |
| 拒绝标记写入前 | 旧库仍为权威；重新持锁并核对源后再隔离，目标尚不可用。 |
| 已隔离，构建或校验未完成 | 旧程序继续被拒绝；新版接续同一源的构建，或先耐久决定回退再恢复旧入口。 |
| 指针已切换，目标未激活 | 业务写门保持关闭；完成目标检查，或按固定顺序回退，不能仅凭指针存在就接受写入。 |
| 目标已激活 | 只从目标接续；拒绝恢复旧清单，目标不可用时明确进入恢复处理，不回退陈旧数据。 |
| 已决定回退，尚未收尾 | 只恢复源入口并废弃目标；不因目标文件看似完整而重新切过去。 |

这些文件与数据库不组成跨介质原子事务，安全性来自上述持锁、耐久顺序和单向决定。恢复须交叉核对迁移身份、指针与目标激活标记；矛盾或无法确定时失败关闭。缺少指针但存在隔离标记或目标库时，不得初始化为空库。

迁移是一次格式升级维护，不是每次启动流程。空间不足时在切换前停止并保留源，不通过删除唯一原文腾空间；源与目标及工作文件的峰值磁盘空间必须提前估算。

## 9. 实现落点与顺序

| 落点 | 必须完成的变化 |
| --- | --- |
| `contract`／`authorityport` | 将内核需要的全量列表改为定向元数据、正文范围读取、受快照约束的游标；显式关闭资源。批处理接口不得隐含全库切片。 |
| `authoritysubstrate`／新SQLite存储实现 | 保留唯一权威、授权与控制提交边界；资产、操作回执和相关控制决定按各自合同在事务内成立。旧 `assetlog` 仅用于受控旧格式读取和迁移。 |
| `derived`／`retrieval` | 从全库对象持有者改成持久化索引的读写与执行器；实现向量两级筛选、保守上界、精算及增量合并，保留原评分、关系语义、候选预算和过滤。 |
| `core` | 将查询、组织工作领取、失效、遗忘、世代构建、快照和维护改为定向或流式执行；发布与回收登记同事务，落实积压背压及空间归还，保留有效性检查。 |
| 接入／装配／生命周期 | 共享预算、固定连接池、受控并发、流式大负载、取消释放和启动状态；取消成功装配对全库重建的依赖。 |
| 备份、迁移与测试材料适配 | 识别存储格式；复用未变化的语义材料，迁移生成新的物理快照身份；实现共用旧目录锁、拒绝格式标记和中断状态机，旧二进制不得误用新快照。 |

### 9.1 可行性验证与实现验收的边界

前置验证只消除可能推翻关键机制或技术路线的不确定性，以足以决定实施或修改方案的最小隔离切片取得证据，不计入正式执行单元。它不提前完成整套实现或穷尽功能与故障场景，也不证明产品已经通过验收；已成立且依赖未变的证据直接复用。具体验证项、结果及接续状态统一维护在[改造任务](../../tasks/bounded-storage-implementation.md)。

第4.1节的隔离修复不能替代正式运行时集成与资源核验；正式构建、完整接入行为、并发控制、WAL收敛及迁移恢复随对应执行单元实现并验证，第10节的验收义务不减少。验证代码不自动进入正式产品。

向量验证复用已准备的真实材料，对照正式计分的精确扫描；前置阶段仅完成决定路线所需的最小落盘核验，完整过滤、近同分、重复向量、边界值及增删改覆盖随检索单元完成。以真实页读取与计算成本推算更大规模，不能靠复制相同向量推断选择性，不能用编码体积代替完整查询成本。若证据否定筛选收益或既定成本边界，先修正该机制，不迁移完整资料后再以默认全扫描掩盖失败；无需重做语义组织或展开多引擎竞赛。

## 10. 验收与完成条件

| 维度 | 必须取得的证据 |
| --- | --- |
| 信息与检索质量 | 同一原文、语义产物和向量下，资产逐字节一致；词法、向量、图与依据选择的候选、排序、过滤和预算等价。向量验证全部成员被覆盖、所有上界不低估、原分数与同分顺序不变；容差不能用于放过误剪枝或Top-K变化，不新增模型请求。 |
| 内存有界 | 记录服务、模型、连接器的RSS、私有提交、峰值、缓存和工作区；覆盖冷启动、长输入／输出、批量嵌入与检索并存，保持独立余量。扩充资料只增加磁盘数据，运行缓存和容纳的任务工作区不随N扩大；更新、图高扇出、重建、迁移也必须成立。 |
| 查询与启动 | 保留现有适用负载下的[内核阈值](../../../benchmarks/acceptance/v5/thresholds.json)和[完整产品阈值](../../../benchmarks/acceptance/suite/adapters/product_resource/thresholds.json)，不靠冷／热缓存混用证明达标。统计向量两级通过率、实际页读取、精算率及退回顺序读取的比例，不能用启动变快抵消查询变慢。 |
| 写入与磁盘成本 | 同题同材料比较原文耐久写入、组织发布及后台归块的完整耗时；没有新增AI调用、前台全库重建或等待索引才可查。固定当前资料量反复修订、组织替换及构建失败，验证回收中断可接续、有效数据不误删、待回收字节受控，清理后文件体积不随次数持续增长；分别核算编码、碎片、空闲页、WAL及临时副本，继续满足既有派生体积约束。 |
| 控制与耐久 | 提交前后中断、响应丢失重试、并发修订、权限撤回、遗忘、迟到语义结果及WAL恢复；验证长读＋持续写入＋撤销，以及回收与发布交错。迁移在每个耐久边界中断并用实际旧版本尝试打开：锁、拒绝标记及回退顺序必须阻止双写；目标激活后任何失败均不得恢复陈旧源。 |
| 用户体验 | 启动不等待全库整理；正常保存保真、检索覆盖不缩水；后台工作不会耗尽前台预算；错误与未完成状态真实，用户不用管理冷热资料或缓存。 |

容量评估同时列累计原文字节、资产数量、长度分布、词项／关系／依赖数量，不能用“一页文档”代替长期总量，也不能只测短合成文本。先复用已有小规模真实产物测量单位成本与分配上界，对500 MB、1 GB、10 GB推算；仅在推算存在会改变设计选择的非线性疑点时做最小补测，不逐档实跑巨量资料。

现有毫秒阈值属于其冻结负载，不能直接宣称覆盖任意GB规模；新增规模必须同时报告推算的冷、热查询成本及不确定性，不能只宣布内存下降。若不能兼顾已有质量、受控内存与可接受查询成本，设计不得冒充已落地，需在对应执行机制上收敛后再迁移正式资料。

验证优先使用固定组织材料下的确定性等价检查，避免重做100／500题语义准备。通过受影响功能验证后，再按当前有效名单和既定判分条件完成固定14题与24题的端到端回归；既有失败与已移除题按当前登记处理，不把架构迁移扩成信息使用层的无限优化。完成迁移、必要回归和资源验收后停止，不自动续跑最终500题。
