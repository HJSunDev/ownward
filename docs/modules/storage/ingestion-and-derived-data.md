# 原文存入、组织与派生数据

## 维护规则

1. 本文必须与正式代码的实际行为一致；实验候选和设计设想不得写成已实现能力。
2. 内核代码变更或功能方案调整时，必须即时核对并在同次变更中同步更新相关内容；受影响的历史测量不得继续代表新实现。
3. 仅保留流程、职责、产物、成本及必要依据，删除过程记录、重复说明和无关信息。

**核心定位：信息组织与存储策略。** 在完整保留已接收原文的前提下，统筹持久化的信息类型与派生表示、生成与更新时间、组织结构与存储粒度，以及派生数据的体积增长。这些决策共同影响信息覆盖、检索准确性、依据完整性及查询时的计算与推理工作量，是系统质量、响应效率和长期维护成本的核心决定因素之一。

本文说明原文进入内核后如何成为可检索、可关联的信息，不包含用户提问后的取证作答。长期约束见[存储架构](architecture.md)，语义职责见[语义理解架构](../semantics/README.md)。实现核对基线：`158f73de243d09168c514fa927fc89ec7548a4bc`，2026-09-16。

**新存储格式的实现边界：** SQLite存取底座及保存→组织→检索→取证路径已实现。原文按64 KiB分块保存；组织结果、版本依赖、词法倒排、原向量及筛选块、图单元与关系均持久化于数据库，查询按需读取，不在启动时物化全库。组织发布校验输入版本并原子切换，新增向量立即可查，归块不改变原分数和排序；图导航保留明确关系优先及发布顺序，分页和重启沿用该顺序。已接受的语义结果不会因本地向量待恢复而重新派发AI工作；理解与判断仍由外部AI完成。现有用户资料尚未迁移，以下流程及保存关系仍描述当前启用的日志存储；维护、恢复与迁移完成后再整体替换。执行状态及验证依据见[改造待办](../../tasks/bounded-storage-implementation.md#单元二持久化检索与语义组织)。

## 处理流程

**原文是权威资产，语义组织只生成可替换的派生信息，不改写原文。保存成功与组织完成是两个状态；组织失败不撤销已保存的原文。**

| 环节 | 执行方 | 实际工作 | 产出 |
| --- | --- | --- | --- |
| 保存原文 | 内核代码 | 原样保存提交的正文，登记身份、版本及来源，更新词法索引。 | 权威资产及可按词检索的入口。 |
| 准备组织材料 | 内核与宿主代码 | 内核选取候选关联资料，固定输入版本并登记待处理工作；宿主按输入预算分组、调度。 | 供外部AI阅读的原文、候选资料及组织任务。 |
| 语义组织 | 外部AI | 阅读资料，提取检索信息、证据单元与对象，判断有依据的关系和适用条件。 | 结构化组织结果；没有可靠依据时允许不生成关系。 |
| 校验与发布 | 内核代码及本地向量模型 | 校验身份、版本、引用位置与结构；补齐向量，持久化组织结果并更新检索、图导航结构。 | 可用于检索和关联取证的派生状态。结构校验不等于证明AI判断必然正确。 |
| 失败恢复（按需） | 宿主、外部AI与内核 | 保留已成功的来源，对失败来源修正格式、定位或重新组织，再执行相同校验。 | 合格结果，或保留明确的未完成状态；不靠删减原文或放宽校验交付。 |

语义判断由外部AI完成，内核负责保存、约束和使用这些判断。排队及纠错会增加等待，但不构成独立的信息产物。

## 生成的信息及用途

处理单位是一次写入的一份资产，不是固定的一轮对话。五轮对话合并写入时，共用一份原文资产及其摘要、主题、线索和组织结果；分成五份写入时，则分别生成。批量调用可以同时处理多份资产，但输出仍逐份对应。

原文保存在数据目录的 `assets/information.jsonl`；派生记录保存在 `state/organization.binlog`，通过资产ID及版本绑定原文，其中 `analysis` 保存组织信息，向量与管理字段随同一记录保存。词法、向量检索和图导航结构从这些记录构建到运行内存，不是分别复制一套原文。

```text
磁盘（关闭服务或关机后保留）
├─ 原文资产A：完整正文、身份、版本、来源
└─ A的派生记录：绑定A的身份和版本
   ├─ 摘要、主题、检索线索
   ├─ 图数据：证据单元、对象定位、关系及条件
   ├─ 向量
   └─ 依赖与处理凭据

运行内存（服务启动时构建，进程退出后释放）
├─ 词法索引：根据原文找资料
├─ 向量检索结构：根据语义相似度找资料
└─ 图导航索引：沿已保存的关系找相关内容
```

**正常重启会恢复检索结构，不会丢失已保存的信息。** 启动时，代码读取磁盘上的当前资产和有效派生记录：重新对原文建立词法索引，将已保存的向量载入检索结构，并根据已保存的图数据重建导航索引。这一过程不调用外部AI，也不重新计算仍有效且与当前向量配置一致的向量；只承担本地读盘和索引构建成本，耗时与内存占用随资料规模变化。原文或向量配置变化导致的派生失效，属于另行更新，不是每次重启必做的语义组织。

| 信息 | 内容与用途 | 生成方式及保存位置 |
| --- | --- | --- |
| 摘要、主题、检索线索 | 当前正式测试所用轻量宿主由AI为每份资产选择一个代表性原文片段作为摘要，生成最多4个主题标签，并选择最多8个原文片段作为检索线索；摘要和线索正文由代码按AI选择摘取，不自由改写。 | 保存为 `analysis.summary/topics/cues`，随派生记录绑定原文资产及版本。内核接口本身也支持其他宿主提交文本形式的语义结果。 |
| 推导场景（接口支持，当前测试路径未生成） | 可记录影响含义或适用性的场景键、值、置信度及原文依据。当前轻量宿主的输出格式不包含此字段；100题4,734份资料中均未生成，不能计作已有实际产物。 | 内核接收后可保存为 `analysis.inferred_contexts`，随派生记录绑定资产及版本；不同于写入方明确提供的 `contexts`，也不同于关系中的适用条件。 |
| 证据单元、对象及定位 | 标出独立事项、对象及角色，保留对应原文和必要上下文，支持精确取证，并为图中的节点提供原文依据。 | 外部AI选择，代码转换并校验定位；持久化于派生状态。 |
| 图关系及适用条件（图的边） | 连接资料、证据单元或对象，表达同一对象、包含、支持、冲突、推导等关系；保存方向、具体含义及适用条件的原文依据。例如“支付模块 → 属于 → 星河项目”。 | 外部AI判断，内核校验后保存为派生记录中的 `analysis.organization.links`，同时更新内存中的图导航索引。 |
| 向量 | 支持语义相似检索。 | 本地向量模型生成，持久化于派生状态；当前每份资产保存一个512维 `float32` 向量，占2,048字节。 |
| 词法索引 | 建立词项到原文的映射，支持关键词检索。 | 内核从权威资产构建，保存在运行内存中。 |
| 向量检索结构 | 组织各资产的向量，供查询向量比较并召回语义相近的资料。 | 内核从持久化向量构建，保存在运行内存中。 |
| 图导航索引 | 按图的节点组织正向、反向连接，支持沿关系查找其他节点及其原文依据。 | 内核从已保存的图关系构建，保存在运行内存中，可在重启后重建；不再次调用AI生成关系。 |
| 版本、依赖及处理凭据 | 识别组织结果的输入版本，支持失效检查、恢复和重复提交处理。 | 代码生成，持久化于派生状态。 |

**图数据以派生数据形式持久保存，图导航索引负责在内存中高效使用这些数据。** 资料、证据单元及对象构成可连接的节点，关系是连接节点的边；AI提出关系，内核校验并保存后更新图导航索引。图中的推导关系不替代原文事实。

当前正文不超过320个UTF-8字节时可直接生成向量；更长的正文保留完整内容，待语义结果返回后，将摘要、主题、线索等检索表示分块向量化，再聚合为一个资产向量。中间分块向量不逐份长期保存。

## 耗时来源

主要耗时是外部AI阅读与输出组织结果，其次包括本地向量计算、校验和索引维护；整批导入还可能叠加关联资料重复阅读、共享资源排队及纠错。

| 单文档实测 | 完整组织就绪 | 其中外部AI请求耗时 | 外部AI请求数 |
| --- | ---: | ---: | ---: |
| 1,193字符，新资料库 | 42秒 | 约36秒 | 1次 |
| 10,479字符，新资料库 | 117秒 | 约113秒 | 1次 |

2026-09-15，版本 `a3df3f3`，千问3.8 Flash／medium，各测一次；不是稳定均值，不含PDF解析或OCR。完整体验与保存确认口径见[信息沉淀实测](../../delivery/first-version-delivery-definition.md#信息沉淀)。多来源批量导入的分钟级等待不能全部归为有效推理，也不能直接代表单文档体验。

## 实测存储成本

2026-09-16按原文正文的UTF-8字节及产品数据文件实际长度统计；kB、MB采用十进制单位。派生数据为 `state/organization.binlog`，产品总量为完整 `ownward-data` 目录，包含原文、派生记录及管理信息，排除测试日志、请求响应、备份副本和共享模型文件；不包含运行内存占用。

| 样本 | 原文正文 | 派生数据 | 产品数据总量 | 总量／原文 |
| --- | ---: | ---: | ---: | ---: |
| 一页内容，1,193字符 | 3.08 kB | 15.42 kB | 20.10 kB | 6.52倍 |
| 长文档，10,479字符 | 27.04 kB | 17.59 kB | 46.77 kB | 1.73倍 |
| 100题准备资料，4,734份来源 | 49.85 MB | 86.46 MB | 139.08 MB | 2.79倍 |

前两项使用上述单用户实测产物。100题按[固定名单](../../../benchmarks/longmemeval_s/selections/stratified-100-v1.json)统计，含[第387题背景修订](../../tasks/benchmark-material-revisions.md)；在配置的评测环境根目录中，`runs/stratified-100-q387-background-v1-20260916/identity.json` 的 `materials` 固定各准备收据和产品文件身份。仅统计准备快照一次，不叠加答题时的工作副本。

100题派生数据的构成如下，合计约为原文的1.73倍：

| 构成 | 体积 |
| --- | ---: |
| 证据单元、对象、关系及原文定位 | 44.90 MB |
| 向量 | 9.70 MB |
| 摘要、检索线索和主题 | 6.49 MB |
| 当前记录的版本、依赖、处理凭据及格式开销 | 15.25 MB |
| 尚未压实的旧状态记录 | 10.13 MB |

组织信息是最大部分：原文定位保存摘录及消歧前后文，可在多个单元和关系中重复出现；这部分文本合计约35.49 MB，已包含在44.90 MB内。短文本更容易受固定向量和结构字段开销影响，不能将某个样本的放大比例当成所有数据的固定比例。

维护操作可压实旧记录，派生世代切换后回收旧世代；普通写入不会每次自动压实。上述统计仅说明批量导入后的磁盘成本，不代表运行内存成本，也不能证明每类派生信息都具有与其成本相称的独立收益。

## 累计容量与启动成本评估

评估对象是长期累计资料总量，不是单次写入量。2026-09-16使用本文基线的正式内核代码测量本地加载与索引重建，不调用外部AI；较大容量根据已有测量推算。

| 累计原文体积 | 重启加载与重建时间 | 启动后内核进程内存 | 依据 |
| --- | ---: | ---: | --- |
| 约10 MB | 1.2—1.6秒 | 103—108 MiB | 实测 |
| 约50 MB | 6.2—7.4秒 | 439 MiB | 实测 |
| 约105 MB | 12.9—14.0秒 | 907—934 MiB | 扩展样本实测 |
| 约210 MB | 36—39秒 | 约1.8 GiB | 扩展样本实测 |
| 约500 MB | 约1—1.5分钟 | 约4—4.5 GiB | 同等资料结构推算 |
| 约1 GB | 约2—3分钟 | 约8—9 GiB | 同等资料结构推算 |
| 约10 GB | 普通电脑可能先遇到内存不足，无法保证启动时间 | 数十GiB量级 | 同等资料结构推算 |

实测使用i7-10710U、16 GB内存，每档两个新进程依次测量，限制两个CPU执行线程，未清空系统文件缓存。材料来自已完成组织的100题资料，平均每份原文约10 kB；超过4,734份的扩展样本复用原文和关系结构，不代表同等数量的独立真实文档。推算假设平均文档长度、词汇及关系密度相近，实际成本还受这些因素影响；内存不足时可能显著偏离推算。

内存列包含原文、组织记录、索引及运行时开销，不包含本地向量模型进程；是启动后的进程物理内存快照，不是索引净体积或长期稳定占用的承诺。原文MB、GB采用十进制，内存MiB、GiB采用二进制。

**判断：这是基础性架构设计缺陷，违反长期信息存储产品必须控制运行资源的基本要求，应作为核心可用性的阻塞问题处理。** 当前实现要求原文和组织记录全量驻留、索引全量重建，缺少有效约束全库内存占用的机制，使用户正常积累资料就会持续推高内存需求与启动成本，最终可能挤占其他应用资源或无法正常启动。约50 MB原文已带来约439 MiB启动内存占用，500 MB原文按现有结构推算即需数GiB，尚未计入本地模型；这已暴露基础设计问题，不能作为一般性能优化后置。产品必须能在明确、可控的运行资源预算内使用长期累积的GB级资料，不能要求用户随资料增长持续扩充内存，也不能靠限制正常资料积累掩盖这一缺陷。
