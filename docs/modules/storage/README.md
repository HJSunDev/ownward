# 信息存储与增长控制

本文说明 Ownward 当前如何保存一条信息、各类派生数据与长期信息资产的关系、实际存储成本，以及第一版完成前必须解决的增长问题。

长期方向与第一版架构边界见[《存储架构》](architecture.md)。

针对全库驻内存与启动重建缺陷，实施合同见[《有界内存的持久化存储与检索设计》](bounded-runtime-design.md)。正式装配已接入SQLite，四个改造单元均已关闭；状态与验收边界见[改造任务](../../tasks/bounded-storage-implementation.md)。

正式实现的处理流程、产物及真实资料体积见[《原文存入、组织与派生数据》](ingestion-and-derived-data.md)；本文保留存储原则、历史基线与增长控制边界。

## 存储原则

> 信息资产随用户内容线性增长；派生数据具有明确、受控的单条成本，不因更新和失效状态无限堆积，并且任何派生数据都可以安全清理和重建。

长期信息资产是唯一权威。向量、关系、语义分析和索引只为组织与检索服务，不得替代资产，也不得成为恢复资产的必要条件。

## 一条信息的存储结构

| 内容 | 磁盘持久化 | 与初始文本的关系 |
|---|---|---|
| 长期信息资产 | 是 | 原样保存提交的正文、稳定 ID、明确场景和明确关系，是唯一权威；判空与检索归一化不改写正文。 |
| 语义派生状态 | 是 | 保存摘要、主题、线索、推导场景、推导关系、向量，以及不复制权威正文的紧凑工作引用和提交回执；可由长期信息资产重新生成。 |
| 词法索引 | 是 | 保存词项到原文的倒排关系及统计，按需查询，不在启动时全库重建。 |
| 向量索引 | 是 | 保存原向量、增量区和保守筛选块，按预算分批读取并精确计分。 |
| 关系图索引 | 是 | 保存节点、边、定位及正反向索引，按关联范围读取。 |
| 向量模型 | 是，固定一份 | 整个产品共享，不随信息数量增长。 |

原文资产与派生信息统一持久化于SQLite，按资产身份及修订关联：

```text
长期信息资产
└─ 原始内容与不可丢失的明确语义

派生状态
├─ 向量
├─ 摘要、主题和线索
├─ 推导场景
├─ 推导关系
├─ 紧凑语义工作引用与提交回执
└─ 词法倒排、向量筛选及图导航索引
```

运行内存只保留有界缓存和工作区；索引落盘的新增磁盘成本单独核算，不能继续沿用旧日志体积描述当前实现。

## 历史体积基线

以下数据是历史候选 `78a5198` 在同机十万条、384 维、短合成文本条件下的旧基线，不代表当前实现的存储格式或体积：

| 项目 | 体积 |
|---|---:|
| 长期信息资产 | 26.77 MiB |
| 派生状态 | 176.77 MiB |
| 完整存储占用 | 210.03 MiB |

最终选定的 EmbeddingGemma 使用 512 维 `float32` 向量，每条固定占用 2048 字节，十万条向量约为 195.3 MiB，比旧 384 维基线增加约 48.8 MiB。曾按旧格式估算的十万条完整存储 `253～259 MiB` 已因存储格式演进失效，不能描述当前实现，也不能作为完成证据。

历史V1存储候选曾在版本化内部视图中，以同一组代表资产对比v3等价写入：产品总存储为旧格式的`7.09%`，派生存储为`1.43%`，反复更新后的权威恢复日志为压实前的`41.80%`。这些数据说明当时的紧凑引用、回执和日志收敛机制，不代表SQLite的当前成本。

对于很短的信息，固定长度向量和派生元数据可能使完整存储达到原始文本的数倍；文本越长，向量的固定成本占比越低，整体放大比例也越低。EmbeddingGemma 模型与运行时约 358.5 MiB，是一次性固定成本，不随信息条数增加。

## 当前增长风险

- 资产、组织及索引通过SQLite事务发布；旧修订、失效组织、WAL及空闲页由持久维护队列分批回收，不依赖重新加载全库。
- 旧资产日志与v2—v5派生记录经流式转换、保真校验和耐久切换迁入新库；保留原锁与永久拒绝标记，防止新旧程序双写。
- Q8 压缩的是模型权重，当前向量仍按 `float32` 保存；不能把模型量化误认为索引已经量化。
- 持久化索引显著增加磁盘占用；当前完整资源与容量数据见[现状说明](ingestion-and-derived-data.md#累计容量与启动成本评估)，不能用内存降低或旧格式成绩代替磁盘与查询成本验收。

## 第一版完成前

1. 持续验证原文保真，确保写入、更新、恢复及派生重建不改变用户提交的正文。
2. 接入最终 512 维向量方案后，按实际产品格式重新测量不同信息规模和更新频率下的磁盘与内存占用。
3. 在同一最终候选上验证大规模反复更新、v3 迁移、派生失败、世代重建中断、备份与空白恢复，证明日志收敛不会损害当前权威资产、原子切换和精确恢复。
4. 只有在检索质量没有不可接受损失且最终资源证据确有需要时，才采用 `float16`、整数向量或其他额外压缩表示；不得把可选压缩冒充当前缺失能力。
5. 使用最终模型、维度、关系和更新负载重新通过同类存储前沿验收，不能沿用旧 384 维基线或定向内部视图代替最终结论。
