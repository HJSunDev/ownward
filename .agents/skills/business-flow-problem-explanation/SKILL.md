# 业务流程化问题说明

描述问题时，既保留必要的代码级和系统级事实，也必须把它们准确映射到最顶层的相关业务流程，使读者能够看清问题如何发生、为何不符合预期以及修复后应达到什么状态。

问题说明必须回答：

1. **发生场景**：谁在什么条件下，为了什么目标执行什么操作。
2. **预期流程**：正常情况下，业务应当怎样从开始走到结果。
3. **实际流程**：问题发生后，流程实际走向哪里，在哪个节点偏离预期，造成什么可观察结果。
4. **原因映射**：底层代码、数据、状态或协议缺陷怎样逐层影响系统行为，最终形成顶层业务问题。
5. **目标状态**：修复后业务流程应恢复成什么样；需要说明结果边界，但不把未经确认的实现方案冒充目标。

所有业务描述必须由仓库事实、运行证据或明确需求支持。不能为了便于理解而虚构场景、夸大影响或省略关键技术事实；无法确认的内容必须标明是推断或未知。业务映射用于帮助理解，不能代替根因、证据和必要的技术细节。

按问题复杂度合并表达，避免为了套格式重复同一信息；顶层只上升到与该问题直接相关的业务关系，不泛化为无关的产品愿景。
